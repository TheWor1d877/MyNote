## 背景：HTTP 里的 ETag 是什么

ETag（Entity Tag）是 HTTP 协议里用于缓存验证的一个响应头。服务器给某个资源（网页、图片、API 返回的数据）生成一个唯一标识符，通常是内容哈希或版本号。

流程：

1. 浏览器第一次请求资源，服务器返回内容，并带上：
   ```
   ETag: "abc123"
   ```
2. 浏览器把内容和这个 ETag 一起缓存。
3. 下次请求同一资源时，浏览器带上：
   ```
   If-None-Match: "abc123"
   ```
4. 服务器比对：
   - 没变 → 返回 `304 Not Modified`，不传内容，浏览器用缓存。
   - 变了 → 返回 `200 OK` 和新内容，以及新 ETag。

关键性质：

- **内容决定**：内容相同则 ETag 相同，内容不同则 ETag 几乎必然不同。
- **获取成本低**：可以用 HEAD 或条件请求拿到 ETag，不需要下载文件 body。


## 问题：一张放不进 etcd 的清单

一个数据集有几十万个块（chunk），需要一张表记录“第 i 块存在哪里”：

```
块编号 → 存储位置
0      → s3://bucket/part-0000
1      → s3://bucket/part-0001
...
500000 → s3://bucket/part-5000
```

这张表太大，放不进 etcd（上限 1.5MB），所以放到对象存储上，并切成若干**分片文件**，每片不超过 10 万条：

```
index-000.json   块 0~99999
index-001.json   块 100000~199999
index-002.json   块 200000~299999
index-003.json   块 300000~399999
index-004.json   块 400000~499999
```

数据集更新时，可能只改动少数几个块。比如只改了块 350000 的位置，它落在 `index-003.json` 里。

理想情况：只重新读取 `index-003.json`，另外 4 个分片不动。

**要解决的问题就是：怎么知道另外 4 个分片没变？**

## 角色定义

| 角色 | 是谁 | 知道什么 | 不知道什么 |
|---|---|---|---|
| 写入方 | 写数据的计算任务 / worker | 自己写了哪些块 | 分片怎么切、块落在哪个分片 |
| 分片构建任务 | 生成分片的离线作业 | 自己改了哪些分片 | — |
| 清单管理方 | 在线服务，读分片、在内存里维护“块 → 位置”映射 | 内存里的旧映射 | 构建任务什么时候改了哪些分片 |
| 对象存储 | S3 / OSS | 无 | 无，纯被动存储 |

关键：**对象存储不通知任何人。** 所有感知变化的行为，都由读侧主动发起。


## 为什么写入侧和读取侧是分离的

- **写入侧（构建任务）**：一次性、大批量、离线。一次更新可能产生几十万新块，跑几十分钟到几小时。可能是 Spark 作业、离线 pipeline、定时任务。
- **读取侧（清单管理方）**：在线、常驻。要随时响应“第 350000 块在哪”，需要低延迟，内存里必须一直有映射，不能因为构建任务跑几小时就停摆。

两者生命周期、资源需求、运行节奏完全不同。硬塞进一个进程，要么在线服务被离线任务拖死，要么离线任务受在线服务限制跑不动。

这是**两条路线共同的前提**，不是 ETag 路线独有的。


## 路线一：ETag 轮询

#### 适用前提

- 写入侧和读取侧分离。
- 没有统一的提交协议，构建任务改完分片不通知任何人。
- 业务能接受最终一致（读侧晚一点看到新版本）。

#### 流程

初始加载：

1. 清单管理方下载所有分片，解析出“块 → 位置”映射，放进内存。
2. 记下每个分片的 ETag。

数据集更新：

3. 写入方写新块到对象存储。
4. 构建任务重新生成受影响的分片，上传到对象存储。
5. 构建任务结束，**不通知任何人**。

读侧刷新：

6. 清单管理方**定期**（比如每 N 秒）对每个分片发 HEAD，拿当前 ETag。
7. 和记下的旧 ETag 逐个比：
   - 一样 → 跳过。
   - 不一样 → 下载这个分片，解析，更新内存映射。
8. 用新 ETag 替换旧 ETag。

#### 这一路线解决什么、不解决什么

解决：

- 避免每次刷新都全量下载所有分片，省 IO。

不解决：

- **跨分片原子性**：一次更新涉及多个分片时，读侧可能刷新到一半新、一半旧。
- **块已写、索引未更新的一致性问题**：构建任务没写完时，读侧看到旧索引，新块已存在但无人指向。
- **查询低延迟**：定期轮询本身有可见性延迟；如果改成查询时比对，延迟更高。



## 路线二：快照 + 原子提交

#### 适用前提

- 能引入一个原子提交点（事务日志 / manifest / 快照指针）。
- 写入路径统一，或者至少构建任务能控制提交动作。

#### 对象存储里放什么

1. **块文件**：数据本体。
2. **分片文件**：索引，记录“块 → 位置”。每个分片一个对象，**文件名带版本或唯一 ID**。
3. **提交标记**：一个很小的对象，记录“当前有效版本指向哪些分片”。

#### 流程

初始加载：

1. 清单管理方读提交标记（一次请求，文件很小）。
2. 按标记指向的分片列表，逐个下载分片，解析出映射，放进内存。
3. 记下当前提交标记的版本。

数据集更新：

4. **写新块**：写入方把新块写到新位置，不覆盖旧块。
5. **写新分片**：构建任务生成新分片（新文件名），上传到对象存储。此时对读侧不可见，因为提交标记还没指向它们。
6. **原子提交**：所有新分片上传完成后，构建任务原子地发布新提交标记，指向这批新分片。
7. **读侧刷新**：清单管理方**定时读提交标记**（或被通知后读）。标记没变，继续用旧映射；标记变了，按新标记指向的分片列表重新加载。

清理：

8. 记录每个旧版本被替换的时间，等超过一个“最大读侧刷新间隔”，确认没有读侧还在用旧快照，再删除旧块和旧分片。

#### 重新加载”到底做了什么

对比新旧分片列表：

- 新出现的分片 → 下载并解析。
- 消失的分片 → 从内存映射里删掉对应条目。
- 两次都有的分片 → 直接复用内存里已有的映射。

**注意：这是以分片文件为单位整块替换内存映射，不是逐条更新。** 前提是分片文件名带版本、不复用旧名，否则列表对比识别不出变化。

#### 这一路线解决什么

- **跨分片原子性**：提交标记一次性切换，读侧要么看到完整旧版本，要么看到完整新版本。
- **块/索引不一致窗口**：新快照发布的前提是新块和新分片都已写完，读侧不会看到指向不存在块的索引。
- **可见性延迟**：仍然存在（提交后到读侧下一次轮询之间），但读侧看到的是完整旧版本，不是矛盾状态。



## 两条路线的关系

**互斥，不是叠加。**

| | ETag 轮询 | 快照 + 原子提交 |
|---|---|---|
| 谁知道变了 | 没人知道，靠轮询猜 | 提交标记精确记录 |
| 跨分片原子性 | 没有 | 有 |
| 块/索引不一致窗口 | 有 | 消除 |
| 查询延迟 | 靠后台刷新缓解 | 读内存快照，快 |
| 还需要 ETag 吗 | 需要 | **不需要** |

选择依据：

- 只求省 IO、能接受最终一致 → ETag 轮询。
- 要求一致性、原子生效、低延迟查询 → 快照 + 原子提交，删掉 ETag。



ETag 只解决“省 IO”，不解决“保正确”。快照 + 原子提交解决“保正确”，此时 ETag 没有职责，应当删除。两条路线二选一，不要混用。
