#面试-Go语言-复习  解释 Go 泛型的实现方式（GC shape stenciling）：为什么泛型没有对所有类型做完全的单态化？接口装箱又会对热路径性能造成哪些影响？

C++ 模板的做法是完全单态化——`vector<int>`和 `vector<float>` 编译出两份完全独立的机器码，运行最快，但代码膨胀严重

Go的选择是： GC Shape Stenciling
不是按照具体类型分组，而是按照GC形状来分组
当两个类型的底层类型相同或者都是指针的情况下，他们才属于同一个Shape Group
比如 int 和 type MyInt int 共享一个 shape，所有指针——`*time.Time`、`*bytes.Buffer`、`*uint64`——不管指向什么，全都归到同一个 shape 组
优点： 防止代码膨胀，减少编译时间与二进制体积

编译器为每隔Shape生成一份实例化代码，同时传入一个字典作为隐藏的第一个参数，这个字典存储了所有的运行时元数据，如`runtime._type`
泛型函数内部所有需要“知道具体类型”的地方，不是靠编译期硬编码，而是通过字典去查




接口装箱 = 把裸值包装成 interface 那“类型指针 + 数据指针”的表示
需要多用一块堆内存，内存分配要占用时间，而且堆内存是垃圾回收（GC）管的，你分配得越多，GC 越忙，越拖慢整个程序。
可能本来一次操作不需要分配内存，现在每次都在分配。分配多了，GC 就得频繁跑，程序总时间自然就上去了。
泛型用在编译期类型确定的场景，热路径上不要传接口进去。
