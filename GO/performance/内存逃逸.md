## Go编译器自动决定变量位置
#面试-Go语言-复习 解释逃逸分析，以及哪些常见写法会让变量逃逸到堆上？

在 C/C++ 中，你要自己写 malloc() 把变量放堆上，写 free() 释放它。
但在 Go 中，你只管写 x := 10 或 s := &Student{}，Go 编译器会自动判断：这个变量该放栈还是堆？这个判断过程，就叫 逃逸分析（Escape Analysis）。

“逃逸” = 本该在栈上的变量，“逃”到了堆上。

## 什么情况下会发生内存逃逸
| 场景                      | 为什么逃逸？                                                          |
| ----------------------- | --------------------------------------------------------------- |
| 1. 返回局部变量的指针            | 函数结束后，栈帧销毁，但外面还要用这个变量 → 必须放堆                                    |
| 2. 把变量传给接口（interface{}） | 接口要能装任何类型，必须在堆上统一管理,interface 存的是指向数据的指针，编译器无法确定数据的生命周期，所以保守扔堆上 |
| 3. 在闭包里用到局部变量           | 闭包可能在函数结束后才执行，变量必须活着 → 放堆                                       |
| 4. 变量太大（比如大数组）          | 栈空间小，放不下 → 自动挪到堆                                                |
## 内联与内存逃逸的关系
内联和逃逸分析是互相影响的，而且方向是双向的。

#### 内联让逃逸分析更准
 一个变量如果在函数 A 里创建、被传到函数 B，编译器在分析 A 的时候，不知道 B 拿它干了什么——因为 B 是个独立的编译单元（或者说独立的函数体）。
所以保守起见，只要变量被传给了别的函数，编译器倾向于认为它逃逸了。
```go
func B(p *int) {
    // 只是读一下，没存起来
    _ = *p
}

func A() {
    x := 1
    B(&x)  // B 没内联时，x 大概率逃逸
}
```

#### 逃逸分析反过来影响内联
内联本身是有成本的：函数体展开会让代码变大，代码膨胀会伤害 CPU 的指令缓存，可能得不偿失。
所以编译器对内联有个“预算”，不是想内联就内联。
那什么情况下更愿意内联？当内联能带来明确收益的时候。 其中一个收益就是：内联之后能消除堆分配。
如果一个函数被内联后，能让原本逃逸的变量留在栈上，省掉一次堆分配和后续 GC 压力，那这次内联就是值的，即使代码变大一点也划算。

## 示例
```go
package main

import (
	"fmt"
)

func getValue() *int {
	x := 114
	return &x
}
func main() {
	p := getValue()
	fmt.Println(*p)
}
```
- 运行
`go build gcflag="m" main.go`
可以看到:
./main.go:8:2: moved to heap: x

- 原因：
Go 不允许你返回指向栈变量的指针并让它失效,它要保证：
   “只要你能访问一个变量，它就一定是有效的。”

## 使用pprof观察堆分配
```go
package main

import (
	"fmt"
	"log"
	"net/http"
	_ "net/http/pprof" // 导入即注册 /debug/pprof 路由
)

func main() {
	// 分配大数组（会逃逸到堆）
	p := [100000000]int{}
	fmt.Println("Allocated 800MB array. Visit http://localhost:6060/debug/pprof/heap")

	// 启动 pprof HTTP 服务器（独立 goroutine）
	go func() {
		log.Println(http.ListenAndServe("localhost:6060", nil))
	}()

	// 阻塞主 goroutine，防止程序退出
	select {}
}
```

```bash
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap
```
