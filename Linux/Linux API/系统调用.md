系统调用不是"一次函数调用"，而是一次特权级的完整穿越，而且真正的开销大头不在指令本身，在 CPU 微架构层面的连带损失。

一次空系统调用大概在200ns左右
而一次普通函数调用一般在5ns左右

开销可以分成显式的与隐式的：
## 显式开销
上下文开销是最重要的开销
1. 用户态程序把系统调用号与参数放进寄存器，然后触发一条陷入指令
2. CPU 先把当前的状态寄存器压栈
3. 执行内核函数：内核要先校验参数，然后在执行
4. 返回值放进 rax，然后恢复第二步保存的所有寄存器，切回用户栈

## 隐式开销
流水线冲刷：现代 CPU 靠乱序执行和分支预测跑满吞吐。系统调用是一个不可预测的跳转，内核代码的地址根本不在用户态的分支预测器历史里，所以预测必然失败，流水线要冲刷重来。切回来之后还要重新预热。这部分大概 100-200 纳秒，在高频场景下能占总开销的 30%。

缓存污染。 内核代码和内核数据结构被拉进 L1/L2/L3，会把用户态的热数据挤出去。系统调用返回后，你原本缓存好的业务数据没了，得重新从内存拉。

 Spectre 缓解措施带来的成本：Meltdown 和 Spectre 漏洞出来之后，内核引入了 KPTI（内核页表隔离）。
 以前内核空间和用户空间映射在同一份页表里，切特权级不需要切 CR3，这是 Linux 一个很重要的设计优化。KPTI 之后不行了，为了防侧信道攻击，用户态页表里不能映射内核，所以每次进出内核都要切页表、刷 TLB。

## 高并发网关场景下的决策
一个网关处理一个请求，至少要 accept、read、write、close，3-5 次系统调用。
网关的连接数多，epoll_wait 一次返回一批事件，应用要逐个 read，每个 read 都是一次完整的四步往返。事件密集的时候就是短时间内密集陷入内核。

#### 优化方向
一是批量，这是最直接的。 N 次操作合并成 1 次，四步往返只走一遍。比如 readv/writev 一次读写多个 buffer，日志先在用户态缓冲区攒一批再 write。glibc 的 printf 就是这个思路——不是每次调 write，攒满了才下去一次。

二是 vDSO。 有些系统调用内核其实不需要做任何特权操作，比如 gettimeofday、clock_gettime。内核把这些函数的实现直接映射到用户态地址空间，调用时根本不陷入内核，省掉第一、二、四步，开销从 300 纳秒降到 20 纳秒。网关里如果每秒取几十万次时间戳做超时判断、打 metrics，这个优化是白捡的。

三是 io_uring。 用用户态和内核共享的环形缓冲区，应用把几百个请求填进队列，一次提交，内核批量处理，应用直接从共享内存收割结果。这是把"批量"做到极致。
