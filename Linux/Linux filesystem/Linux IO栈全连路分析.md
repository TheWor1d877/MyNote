## read()
一次普通的read(),需要在内核中经历七层：

```text
┌─────────────────────────────────────────────────────────┐
│ 应用层（Application）                                     │
│   read(fd, buf, count)                                  │
├─────────────────────────────────────────────────────────┤
│ VFS 层（Virtual File System）                             │
│   经 fd 表找到 struct file → inode → address_space        │
│   路由到具体文件系统，统一 read 语义                        │
├─────────────────────────────────────────────────────────┤
│ Page Cache 层（命中则在此短路）                             │
│   在 address_space 里查 page 是否已缓存                    │
│   ✓ 命中：直接 copy_to_user，跳到返回，不碰下面四层          │
│   ✗ 未命中：分配 page，发起读，进入下面四层（同步阻塞）       │
├─────────────────────────────────────────────────────────┤
│ 文件系统层（File System: ext4/xfs/btrfs）                  │
│   文件 offset → 逻辑块号映射（extent/间接块）               │
│   触发 readahead 预读，构造 bio                            │
├─────────────────────────────────────────────────────────┤
│ 通用块层（Generic Block Layer）                           │
│   bio 合并、排序，blk-mq 多队列分发，生成 request            │
├─────────────────────────────────────────────────────────┤
│ 设备驱动层（Device Driver: NVMe/SATA/SCSI）               │
│   逻辑块号 → 硬件命令，提交到设备队列                        │
├─────────────────────────────────────────────────────────┤
│ 物理层（Physical Device: SSD/HDD/NVMe）                   │
│   闪存读 / 磁盘寻道读，DMA 把数据写入 page cache 页          │
├─────────────────────────────────────────────────────────┤
│ 回到内核收尾（I/O 完成中断 → 唤醒进程）                      │
│   copy_to_user：page cache → 用户 buf，read 返回字节数      │
└─────────────────────────────────────────────────────────┘
```
`struct_file`: 代表一次打开。每次open都会创建一个struct_file。同一文件被两个进程打开，就会有两个struct_file,它存储的是这次会话的打开状态以及指向inode的指针
`struct inode`: 代表文件元数据，大小、权限、所有者、时间戳，以及数据在磁盘上在哪些位置（extent 或块指针，同一个文件不管 open 多少次，内存里就一份 inode。
`address_space`: 挂在 inode 上（inode->i_mapping）。它是 page cache 的管理中枢：内部用一棵树（xarray）按文件偏移索引所有缓存过的页

`bio`: 块 I/O 的基本描述单元。它不搬数据，只描述"要读哪些页、从哪个逻辑块开始、多长、方向
bio 是文件系统视角的"I/O 描述"，request 是块层视角的"要真正下发给设备的一个请求单元"
`blk-mq`:现代CPU给 每个CPU核心都配了一个软件队列，硬件侧也有多个硬件队列
request从软件队列映射到硬件队列下发，这样多核并发读写时不用抢同一把锁

## write()

一次普通的 write()，在内核中也需要经历七层：
```txt

  用户态
┌──────────────────────────────────────────────────────────────┐
│  write(fd, buf, count)                                       │
└───────────────────────────────┬──────────────────────────────┘
                                │ 系统调用，用户态→内核态
  内核态                        ▼
┌──────────────────────────────────────────────────────────────┐
│ VFS 层，检查权限                                               │
│  fd ──► fd 表 ──► struct file ──► inode ──► address_space     │
│  （一次打开）      （一次打开）    （每个文件）  （每个文件的页缓存）  │
│  路由到具体文件系统                                             │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 文件系统层 + Page Cache                                        │
│  ① 若文件变大：分配块（extent）、更新 inode、元数据进 journal   │
│  ② 分配/找到 page cache 页，CPU 拷贝 buf → page cache          │
│  ③ 标记脏页（dirty page）                                      │
│  ──► write 返回用户态，数据还在内存，未落盘                     │
└───────────────────────────────┬──────────────────────────────┘
                                │
════════════════════════════════╪═══════════════════════════════
                                │   分界：以下为异步回写段，
                                │    write() 已返回，由 flusher 触发
════════════════════════════════╪═══════════════════════════════
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ flusher 回写线程（脏页超阈值 / 到期 / fsync / 内存压力触发）     │
│  调用文件系统 writepages                                       │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 文件系统层                                                     │
│  脏页文件偏移 → 逻辑块号（LBA）；构造 bio                       │
│  bio = 块 I/O 描述单元（哪些页、写到哪段盘、多长、方向=写）       │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 通用块层                                                      │
│  bio 合并 → request；I/O 调度器排序；blk-mq 多队列分发          │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 设备驱动（NVMe/SATA/SCSI）                                    │
│  LBA → 硬件写命令，提交到设备队列                               │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 物理设备（SSD/HDD）                                            │
│  page cache ──DMA──► 设备（不占 CPU，方向：内存→设备）          │
│  SSD 闪存编程 / HDD 寻道写入                                    │
│  完成后发中断 → 脏页变干净页                                    │
└──────────────────────────────────────────────────────────────┘
```

每一层存在的问题：

| 层级 | 典型瓶颈 | 症状 |
|------|---------|------|
| 应用层 | 序列化/反序列化开销、小 I/O 频繁系统调用 | CPU 高、syscall 多 |
| VFS 层 | 路径查找（path lookup）、权限检查 | 元数据操作慢 |
| 文件系统层 | inode 分配、日志提交（journal commit）、extent 分裂 | 元数据 I/O 高 |
| Page Cache | Dirty Page 积压、回写阻塞 | 内存抖动、writeback 延迟 |
| 通用块层 | I/O 调度器排队、请求合并失败 | await 高、队列深度大 |
| 设备驱动层 | 硬件队列满、中断亲和性差 | 队列拥堵、CPU 软中断高 |
| 物理层 | SSD GC、HDD 寻道、带宽饱和 | util 100%、吞吐上不去 |
## PageCache的读缓存与写缓存
- 读缓存：
Read 进来，先拿文件偏移去 address_space 里查这页在不在。在，就直接 copy_to_user 拷给用户返回，全程不碰磁盘。不在，就在 page cache 分配一页，发起真实 I/O 从磁盘读，DMA 把数据填进这页，再拷给用户。
读缓存通产还带有预读，内核发现现你在顺序读，会提前把后面几页也读进来。
所以读缓存的价值不只是"避免重复读"，还有"提前读"，降低后续 read 的延迟。

- 写缓存：
 write 进来，不是直接落盘，而是分配或找到对应的 page cache 页，把用户数据拷进去，然后把这页标记为脏页（dirty page）。标脏之后 write 就返回了，数据还在内存，脏页由内核回写机制处理。
 触发条件：
 1. 脏页占比超过阈值触发后台回写
 2. 脏页存在超过一定时间（到期回写）
 3. 显式 fsync/sync
 4. 内存压力下回收

注意： write 返回成功不等于数据落盘。page cache 是易失的，机器掉电脏页就丢。要保证持久化必须显式 fsync，它会强制把该文件的脏页刷到设备并等完成。
