#面试-计算机基础-复习  什么是 page cache？它如何影响训练数据读取、模型加载和日志写入性能？
## 介绍
page cache 说白了就是内核拿空闲内存当磁盘的缓存，是Linux软件层面的，不是硬件
读文件，数据先拷进 page cache，下次再读同一块就直接从内存拿，不落盘。你写文件，也是先写进 page cache，标记成 dirty page，后台 flusher 线程再慢慢回写磁盘。所以 write() 返回成功，不代表数据已经落盘，只代表写进内存了

## 训练数据读取
对于顺序读取是有好处的，增加吞吐
但是随机采样，多路并发的一个情况下，Cache命中率不会高
而且多一次拷贝
所以训练框架会走 O_DIRECT 绕过 page cache，直接 DMA 到用户态缓冲区，省掉那次拷贝。

## 模型加载
模型文件基本是只读、大块顺序读，page cache 特别合适。
第一次加载慢，之后如果内存够，权重常驻 cache，再加载就快。
但是模型占用内存大，如果出现内存争抢发生缺页中断（page cache 是全局共享、会被回收的）
又使用mmap拿到指向PageCache的指针，page cache 映射物理页的方式，可能会发生性能抖动

你以为模型在内存里，其实内核随时可能把它回收掉。

## 日志写入
走的是 buffered write，写进 page cache 就返回，所以写日志本身很快。

但 dirty page 攒到阈值会触发回写，这时候如果磁盘跟不上，write 会被拖慢。更麻烦的是，大量日志会把 page cache 挤占，导致吗模型权重被挤出去
所以要做限流


## Buffered IO与Drict IO选择
#面试-计算机基础-复习  解释 buffered I/O 与 direct I/O 的区别，以及 O_DIRECT 在数据库和分布式存储中的取舍。

Buffered I/O，也就是默认的 read/write
你调 read(fd, buf, n)，内核不是直接把磁盘数据塞进你的 buf。它先看 page cache 里有没有这块数据。有，就直接从 page cache 拷到你的 buf；没有，就先把磁盘数据读进 page cache，再从 page cache 拷到你的 buf。

多拷贝一次，但是好处是使用PageCache预读了，可以缓存复用
缓存可以跨进程共享

O_DIRECT，就是打开文件时加个 flag，告诉内核：别走 page cache
你调 read(fd, buf, n)，内核直接让 DMA 把磁盘数据搬到你的 buf 里。磁盘→用户缓冲区，一步到位，省掉中间那次拷贝。写也一样，直接从用户缓冲区 DMA 到磁盘，不经过 page cache。
代价： 没有预读，并且有对齐要求
因为 O_DIRECT 绕过了 page cache，数据是 DMA 引擎在磁盘和你的内存之间直接搬。DMA 是硬件干的活，硬件是按块操作的——磁盘的块大小传统是 512 字节，现在常见 4K。


所以选择很直接：访问模式随机、数据量大、内存又紧张、而且你能自己管对齐和缓存策略，比如数据库、训练框架读大文件，用 O_DIRECT。访问模式不确定、要复用、要简单，就走 buffered I/O。

#### 数据库，分布式存储层面
数据库为什么倾向 O_DIRECT？因为数据库自己就有一套 buffer pool。
如果再走 page cache，等于同一份数据缓了两遍，内存白白浪费。
更关键的是刷盘时机不可控。数据库对持久化顺序有严格要求
自己实现逻辑更好

但也不是全盘 O_DIRECT。比如有些数据库的 WAL 写入走 buffered + fsync，因为日志是顺序追加、量小、需要低延迟，fsync 能精确控制持久化点。


分布式存储这边逻辑类似。对象存储、Ceph 这类系统数据量大、访问模式自己最清楚，通常绕过 page cache，自己做缓存层——本地 SSD 当二级缓存、自己管淘汰策略（LRU/LFU、本地 SSD 二级缓存、冷热分层）。这么做一是避免 page cache 被大流量顺序写冲垮，把有用的数据挤出去；

二是回收和回写节奏自己可控，不会被内核的 flusher 拖出性能抖动。
