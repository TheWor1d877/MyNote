## 令牌与令牌桶
想象一个桶：
桶里装着令牌（token），每个令牌代表发送 1 个字节（或 1 个包）的权限
桶有一个容量上限（burst）
系统以固定速率往桶里注入令牌（rate）
数据包要发送，必须从桶里取走对应数量的令牌
桶里令牌够 → 包发出去；不够 → 包排队等待，或直接丢弃

关键： 长期平均速率由注入速率决定，短期突发由桶容量决定。


## 核心参数
1. rate（令牌注入速率）
每秒往桶里放多少令牌。这是长期平均带宽。
比如 rate 1mbit，就是每秒注入 1Mbit 对应的令牌量。

2. burst（桶容量）
桶最多能存多少令牌。它决定能允许多大的突发。
burst 太小：突发流量会被限得很死，甚至正常的小突发也过不去，吞吐上不去
burst 太大：允许很大的突发，限速不够平滑
burst 通常按字节表示。一个经验规则是：burst 至少要能容纳一个 RTT 内的流量，否则 TCP 会因为限速导致吞吐暴跌。

3. latency（延迟，tbf 特有）
tbf 里还有一个 latency 参数，表示一个包最多能在队列里等多久。超过就丢弃。它和 burst 有换算关系：
burst = rate × latency
所以 latency 和 burst 通常指定一个即可，另一个自动推导。


## 典型行为
#### tbf(整形)
令牌不够时，包排队等待，等令牌攒够再发。这会延迟包，但尽量不丢。
超速 → 排队 → 等令牌 → 延迟发送
适合需要平滑发送的场景。

#### policing(监管)
令牌不够时，包直接丢弃（或标记）。不排队，不延迟，但会丢包。
超速 → 直接丢
适合入口限速、防止滥用。

#### 算法实现：惰性计算
不用真的起个定时器每秒往桶里加令牌（那样有定时器开销、还不精确）。而是惰性计算——记录"上次取令牌的时间"和"当前还剩多少令牌",每次请求来时用时间差算出这期间该攒多少令牌，补上再扣。

## htb
htb（Hierarchical Token Bucket）是分层的令牌桶，每个 class 都有自己的令牌桶
```text
root htb (rate 100mbit)
├── class A: rate 40mbit, ceil 100mbit
└── class B: rate 70mbit, ceil 100mbit
```
每个 class 有一个 rate 令牌桶和一个 ceil 令牌桶
发一个包，要同时从两个桶取令牌
父 class 的带宽是子 class 的总和约束

就是classA上限40,classB上限70,总和上限要看ceil是100

## `golang.org/x/time/rate`
```go
limiter := rate.NewLimiter(rate.Limit(100), 200)

// 在网关里
if !limiter.Allow() {
    // 返回 429
}
// 或者带 context 阻塞等待
err := limiter.Wait(ctx)
```
Allow() 是非阻塞的，拿不到令牌立刻返回 false；Wait(ctx) 是阻塞的，会等到有令牌或者 ctx 被取消——这个 ctx 很重要,否则慢请求会一直挂着

Alllow用于保护后端不会崩溃的场景
Wait用于外部API限速

## 网关场景下面的限流策略
全局限流：保护整个服务，防雪崩。一个进程一个 limiter。

按维度限流：按用户、按 API key、按 IP、按模型。每个维度一个独立的 limiter,存在 map 里（要注意 map 的并发安全和清理，不然 key 无限增长会内存泄漏）。

保护GPU利用率: 与其让 1000 个请求挤进去互相拖慢、显存 OOM,不如限流把并发压在合理水位，每个请求都能稳定返回
