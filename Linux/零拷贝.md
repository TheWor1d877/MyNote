## 传统IO缺点
通过网络发送一个文件:
DMA先将数据从磁盘读入内核缓冲区（Page Cache）
CPU将数据从内核缓冲区放到用户空间缓冲区（read系统调用）
CPU 将数据从用户空间缓冲区拷贝到内核的 Socket 缓冲区 (write() 系统调用)。
DMA 引擎将数据从Socket 缓冲区拷贝到网络接口卡 (NIC)。

这样就需要四次拷贝数据，但是2,3次完全是多余的
这两次 CPU 拷贝不仅浪费了 CPU 资源，还占用了内存带宽，并且引发了两次昂贵的上下文切换（用户态 <-> 内核态）。

## 零拷贝
#面试-计算机基础-复习  什么是零拷贝？列举 Linux 中常见的零拷贝技术，并说明各自适用场景。

零拷贝的目标就是解决传统读写数据在内核态和用户态之间来回搬的次数，通过绕过用户空间，让数据直接在内核空间内部完成流转。
#### mmap
核心思想映射，直接将文件映射到进程用户态下面的内存中，省略读写到用户态的步骤（步骤2），直接将数据从内核缓冲区到socket缓冲区

mmap相对于read没有拷贝，拿到的是指向内核空间page Cache的指针，修改完成之后，内核之后再帮你刷回磁盘。
     
read 是拷贝，不是映射。用户态拿到的是一份数据的复制品，不是"指向内核数据的指针"。

注意： 文件不管怎么操作都是内核态下面的概念，从来没有真正搬运到用户态下面

#### sendfile
使用sendFIle系统调用完成零拷贝，专门用于文件描述符到 socket的数据传输。
   
```text
[Disk] --> [Kernel Buffer (Page Cache)] ------------> [NIC]
                             |                         ^
                             | (描述信息传递，无数据拷贝)
                             v
                      [Socket Buffer]
```


应用程序调用 sendfile(in_fd, out_fd, ...)。
内核通过 DMA 将文件数据读入 Page Cache（如果尚未缓存）。
内核将 Page Cache 中文件描述符直接传递给 Socket 缓冲区。
DMA 引擎根据文件描述符直接从 Page Cache 读取数据并发送到 NIC

sendfile全程都在内核态，用户拿不到指向文件的指针，所以不能修改
#### io_uring
#面试-计算机基础-复习  什么是 io_uring？它相比 epoll + 传统 AIO 有哪些优势？适合哪些 AI Infra 场景？
一个接口，来统一文件，Socket，管道等各种IO
整个 I/O 提交和完成都做成异步环形队列，适合高并发网络服务
用户态使用mmap与内核 态共享这些队列
大部分IO不需要系统调用就能直接提交与得到结果
![[Attachments/Pasted image 20261009153318.jpg]]


io_uring是完成通知模式，直接将读写请求丢进队列，做完后内核将结果放到完成队列，而不是epoll那种就绪通知模式
而且 io_uring 不像 epoll 只管 socket，它文件和网络 I/O 统一了，一套接口全搞定
对于短连接高并发还是epoll更强，数量多但是每个io都很小的，io_uring更适合

与AIO相比，io_uring能走Direct IO与buffered IO都支持，AIO缓存 I/O 用不了
而且对网络 socket 有支持

AI Infra场景下：
最直接的场景是推理服务的数据加载与KV Cache的换入换出
对于推理阶段的小的随机IO，io_uring相比与SPDK，GDS更适合
而预训练和微调阶段是大块顺序传输，GDS 也就是 GPUDirect Storage 优势更明显

Go runtime 目前没有原生 io_uring 支持，需要走 cgo 或者第三方库。

###### 面试题目
- O_DIRECT 的三重对齐（缓冲区地址、长度、偏移）为什么必须满足？overlayfs 上 O_DIRECT 报 EINVAL 的根因是什么？

O_DIRECT 不走页缓存，数据直接在用户内存和块设备之间传输。块设备的物理操作单位是逻辑块，通常 4K。DMA 传输要求内存地址按块大小对齐，传输长度必须是块大小整数倍，文件偏移也必须落在块边界上。三个条件任意一个不满足，内核在 `iomap_dio_rw` 里校验不通过，直接返回 `EINVAL`。

overlayfs 是联合文件系统，写操作会触发 copy-up，把文件从 lower 层复制到 upper 层。但 overlayfs 本身不直接对应块设备，它下面还有 ext4 或 xfs。O_DIRECT 要求底层文件系统支持直接 I/O 语义，overlayfs 的 copy-up 路径和文件语义无法保证这一点，所以内核拒绝。

验证时把写目录挂载到宿主机的真实文件系统上，用 `df -T` 确认文件系统类型。


- 4MiB 大块经 HTTP 抓取时，瓶颈为什么在网络带宽上？io_uring 省下的 syscall 对吞吐的预期为什么是中性的？

4MiB 大块抓取时，单次传输数据量大，主要耗时在网络传输。假设带宽 1Gbps，理论上限约 125MB/s，4MiB 一个文件，每秒最多处理三十多个。此时本地磁盘写入速度不是限制因素。

io_uring 减少的是系统调用次数和上下文切换开销。但大块场景下，网络传输时间远大于系统调用时间，省掉几次 syscall 对整体吞吐影响很小。所以预期是 syscall 数下降，但吞吐和基线持平。这说明瓶颈在网络带宽，不在本地 I/O 路径。

- 小文件高 IOPS 臂才用得上 io_uring，两边都要报。v4 的持续预取让小文件请求更密集，你怎么设计“启动路径 vs 持续预取路径”的对照，证明收益来自 io_uring 还是来自请求分布变化？fio 测出的裸盘上限和你的实现差多少？

要证明收益来自 io_uring 而不是请求分布变化，需要控制变量：

- 固定同一批文件、同样的大小分布、同样的并发度、同样的请求顺序。
- 跑三组：Go buffered、C++ buffered、C++ O_DIRECT + io_uring。
- 再做一组固定回放队列：把请求到达的时间点钉死，分别用 buffered 和 io_uring 跑。

如果固定回放队列下，io_uring 的 IOPS 更高、P99 延迟更低、syscall 更少，就能确认收益来自 io_uring 本身。

**fio 裸盘上限的对比方法：**

用 fio 测同盘、同块大小、同队列深度、同 O_DIRECT 模式下的性能上限。

- 实现接近 fio：本地 I/O 路径已经接近物理极限，瓶颈在网络或调度。
- 实现远低于 fio：本地路径还有优化空间，或者瓶颈在网络、序列化、单线程处理。
- 实现超过 fio：测量口径有问题，可能走了页缓存、没有真正 O_DIRECT，或者 fio 参数不一致。


## Go语言中的应用
Go 的 http.FileServer 在底层就尝试使用 sendfile 来高效地提供静态文件服务。

- 如果响应需要被中间件修改（例如加 gzip 压缩头、鉴权头），那么 sendfile 的优化路径就会被绕过，退化为普通的 read/write。
- 主动控制：在某些极端场景下，你可能需要通过 `syscall.Sendfile` 来手动调用，以获得最大的控制


#### 关键条件
源：必须是 `*os.File`，并且以 只读模式 (`os.O_RDONLY`) 打开。
目标：必须是 未被包装的 `*net.TCPConn`。如果你使用的是 `http.ResponseWriter`，它内部已经被多层封装（chunked, gzip, headers等），无法触发零拷贝。
```go
package main

import (
    "net"
    "os"
)

func handleConn(conn net.Conn) {
    // 1. 打开文件 (必须是 os.O_RDONLY)
    file, err := os.Open("/path/to/large_file.bin")
    if err != nil {
        return
    }
    defer file.Close()

    // 2. 断言 conn 为 *net.TCPConn
    if tcpConn, ok := conn.(*net.TCPConn); ok {
        // 3. 调用 WriteTo
        // 在 Linux 上，这会自动尝试 syscall.Sendfile
        _, err = file.WriteTo(tcpConn)
        if err != nil {
            // 处理错误
        }
    }
}
```
