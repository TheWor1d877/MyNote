普通 RPC 的痛点（一元 RPC）
想象你要上传一个 10GB 的电影文件：
```protobuf
// 普通 Put 请求（一元 RPC）
message PutRequest {
  string key = 1;
  bytes value = 2; // ← 10GB 数据一次性塞进来！
}
```
内存爆炸：客户端/服务端都要加载 10GB 到内存
网络超时：传输可能花 1 小时，中间断网就全失败
无法重传：第 99% 时失败，必须重传整个 10GB


## 常见问题
Q：如何实现大文件断点续传？
A：
客户端记录已上传的 chunk_index
重连后先询问服务端“已收到哪些块”
只重传缺失的块（通过 chunk_index 定位）

Q：为什么不用 TCP 自带的可靠性？
A：TCP 只保证单次连接可靠，但：
连接可能中断（需要应用层重传）
无法验证文件整体完整性（需要 CRC32
