对象存储之所以没有目录树，是因为在 PB 级数据面前，传统的 inode 树状结构会导致严重的元数据热点
对象存储将 Bucket 作为唯一的逻辑隔离边界，内部全部是扁平的 Key-Value。为了在数百个节点中快速定位，系统必须依赖确定性哈希路由。

在目前主流的大规模对象存储元数据实践中，基于LSM-Tree的键值存储（KV Store），尤其是RocksDB，是应用最广泛的技术内核，尽管它通常被封装在更上层的分布式数据库中，而非直接被应用调用。提供了极高的写入性能和良好的可扩展性，非常适合存储和更新海量的、扁平化的键值对元数据
- 但是LSM-Tree存在问题：
低效的目录操作：执行一个目录重命名操作（如将 images/ 改为 pics/），在LSM-Tree中可能需要扫描并修改海量的Key，开销巨大。
冗余的前缀比较：在进行范围查询（如列出 images/ 目录下所有对象）时，系统需要在每个Key上重复比较相同的前缀“images/”，造成了性能损耗。

实战中，我们必须在 K8s 节点层引入本地元数据缓存（如 JuiceFS 或 Alluxio），把对象存储的元数据拉取转化为本地内存的 O(1) 查找。

## MiniIO与Ceph
MiniIO：MinIO 使用 SipHash 算法对对象路径和集群 Deployment ID 进行哈希取模，直接映射到纠删码组（Erasure Set）。它没有独立的元数据节点，元数据（xl.meta，基于 MessagePack 序列化）直接内联在数据盘上。这种设计彻底消灭了元数据服务器的单点瓶颈，换取了极致的线性扩展能力。

Ceph RGW 的妥协：Ceph 的 Bucket Index 是一个存储在 RADOS 对象中的 Key-Value Map（底层是 OMAP）。当 Bucket 内对象达到百万级时，单对象索引会成为写入瓶颈，因此 Ceph 引入了索引分片（Sharding）。在 AI 训练场景中，如果你用 Ceph 存数据集，必须配置合理的 Bucket 索引分片数，否则数据灌入时网关会直接被打挂

MIniIO是集中式元数据系统，Ceph是分布式元数据系统
