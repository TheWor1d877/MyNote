文件、对象、块，这三种存储架构就像是三种不同形态的“容器”，它们底层的物理逻辑完全不同。
## 分布式文件存储
文件存储提供目录树结构，支持标着POSIX接口，算法工程师不需要改代码，就能把本地训练脚本无缝迁移到分布式集群上。但“文件”这个概念，在分布式世界里，其实是被硬生生“撕碎”的。

POSIX接口在分布式系统中不容易被实现，在分布式系统中往往实现的是**阉割部分 POSIX 语义**，只保留必需的子集，以此换取百倍的性能提升。

#### 大文件流式访问
文件存储的终极优势在于“顺序读写”。大模型训练的数据加载器（DataLoader）通常是按顺序批量读取数据的。文件存储可以将一个大文件切成几百 MB 的“块（Block）”，分散到多台机器上，GPU 节点可以**并发地从多台机器拉取数据**，从而把单机磁盘 I/O 变成集群网络带宽。

#### GFS
Google 的 GFS（Google File System）是分布式文件系统的祖师爷。它的核心设计极其简单粗暴：
- **Master（单点大脑）**：只负责管理元数据（文件名、目录结构、文件与 Block 的映射）。为了快，元数据全在内存里。
- **ChunkServer（苦力）**：负责真正存储数据块。
- **Client（智能客户端）**：Client 先问 Master 这个文件在哪，Master 返回 ChunkServer 的列表。然后 Client **直接**跟 ChunkServer 通信读写数据。
GFS 的设计初衷是“顺序读写海量大文件”，这完美契合了早期 AI 训练（如图像分类）的需求。
但是GFS是单点的主从架构，不适合海量小文件，这样会导致元数据查询成为瓶颈
所以，**GFS 架构在现代 AI Infra 中已经被淘汰，但其“元数据与数据分离”的思想被保留了下来。**

#### HDFS
HDFS 几乎是 GFS 的开源复刻版，核心交互机制如下：
- **NameNode（大脑）**：管理文件系统命名空间和元数据。
- **DataNode（苦力）**：实际存储数据块（默认 128MB 一个块）。
- **心跳与块汇报（保命机制）**：DataNode 每隔 3 秒向 NameNode 发一次心跳（证明我还活着）；每隔 6 小时汇报一次自己存了哪些块。如果 NameNode 10 分钟没收到心跳，就认为 DataNode 死了，立刻触发副本重建。

但是，HDFS仍然存在海量小文件的问题
HDFS不支持并发写入，设计初衷是为了“一次写入，多次读取“，但是现代 AI 训练需要频繁更新 Checkpoint，HDFS 根本扛不住高频的随机写。

现代ai并行文件系统采用分布式元数据架构，针对NVMe SSD与RDMA网络做了IO栈优化
#### checkpoint
Checkpoint 就是**把内存中当前的“元数据快照”持久化地保存到磁盘上**的一个过程。
以 **HDFS** 为例（GFS原理类似），这个过程通常由 **Secondary NameNode（辅助名称节点）** 触发：
1. **滚动日志**：NameNode 正在写一个日志文件（EditLog），Secondary NameNode 通知它“别写了，换个新日志”。
2. **拉取数据**：Secondary NameNode 把 NameNode 内存中的当前目录树（FsImage）和刚才那个旧的日志（EditLog）拉到自己机器上
3. **合并（核心）**：Secondary NameNode 把旧的 FsImage 和 EditLog **在内存中合并**（重放日志），生成一份**全新的、最新的 FsImage**。
4. **回传**：把这份新的 FsImage（即 Checkpoint 文件）传回给 NameNode。

元数据服务器当断电重启的时候需要用元数据镜像与操作日志拼凑出来的

## 分布式对象存储（S3/MinIO/Ceph RGW）
对象存储中，没有目录树的概念，查找起来更加快捷，并且支持百亿级别的文件数量，且性能不会随着文件数量的增加而下降。
采用扁平化KV模型与RESTful API

这种 存储结构将算与存彻底分离，完全独立扩容

#### KV模型
每个对象由三部分组成：
- **Key（唯一键）**：比如 `dataset/2023/img001.jpg`（注意，这只是一个字符串，不是真实的物理路径）。
- **Value（数据本体）**：真实的二进制数据。
- **Metadata（元数据）**：自定义的标签（比如 `author: zhangsan`, `type: cat`）。  
    底层存储时，对象被扁平化地散列到不同的物理节点上。
    
#### RESTful API
对象存储不使用`open()`,`read()`等单机POSIX接口，直接走HTTP/HTTPS协议，这意味着它天生就是为了跨网络、跨数据中心、甚至跨云而生的。

#### Amazon S3
在S3中数据是不可变的，改数据只能重新PUT一个完整的对象上去

这种设计让底层的分布式存储变得极其简单，因为不需要复杂的分布式锁，也不需要处理“读改写（Read-Modify-Write）”的并发冲突
这种只读属性完美匹配AI训练“一次写入，多次读取”的模式

S3不适合频繁写入小文件

对象存储的使用需要在设计之初就采用，文件存储的代码不能强加与对象存储之上

对象存储的地位：
1. 数据湖底座：所有的原始语料、清洗后的数据集，全部存入 S3/MinIO。它是数据的“终极归宿”，成本极低（配合 EC 纠删码），容量无限
2. 1. **训练数据源**：现代 AI 框架（如 WebDataset）已经可以直接从 S3 流式读取数据进行训练，彻底消灭了“把数据从 S3 拷贝到本地 NFS 再训练”的低效环节。

#### MiniIO 与 Ceph RGW
MinIO 是用 Go 语言写的，极其轻量，没有沉重的历史包袱。它深度利用了现代硬件：全面拥抱 NVMe SSD，利用 SIMD 指令集加速纠删码（EC）计算，原生支持 RDMA。
- **Go（MinIO）**：直接编译成**静态二进制文件**，不依赖外部运行时。它启动极快（毫秒级），内存占用极小（几十MB）。Go的协程（Goroutine）极其轻量，可以轻松创建成千上万个并发任务来同时处理海量S3请求，而不会像Java线程那样压垮操作系统。
- NVMe SSD走的是**PCIe总线**，延迟是微秒级（0.02ms），带宽可达 7GB/s。
- 纠删码（Erasure Coding，如Reed-Solomon）是MinIO代替3副本的省钱手段。存12个数据块，允许坏4个盘不丢数据。但纠删码的本质是**大量的矩阵乘法（Galois Field 伽罗瓦域运算）**。如果纯用Go的循环去算，CPU会被吃满，导致数据写入速度被**CPU拖慢**，而不是被SSD拖慢。MinIO内部的EC库（`klauspost/reedsolomon`）**手写了汇编代码**，调用CPU的 **AVX2 / AVX-512 SIMD指令**。这意味着**一条CPU指令同时算16个字节的异或/乘法**

## 分布式块存储
块存储是最底层的存储，不关心是什么文件，只认识固定的块大小，通常是4kb

操作系统（Linux）拿到一块块存储后，会把它当成一块**真实的本地物理硬盘（如 `/dev/sdb`）**。你可以在上面随便格式化（ext4/xfs），建文件系统，甚至装一个数据库

块存储没有文件系统的目录树开销，也没有对象存储的 HTTP 协议开销。它的 I/O 路径极短，延迟极低。

在k8s中给Pod挂载PVC的时候，底层使用的就是块存储，为ai容器提供一种持久化与动态供给的本地磁盘幻觉

#### Ceph RBD
**它把一块虚拟的硬盘，硬生生地“切碎”成了无数个 4MB 的 Object（对象），然后扔给了底层的 RADOS 集群去存。**  
当你的 AI Pod 往 `/dev/sdb` 写入 4KB 数据时，Ceph 的客户端（内核模块或用户态库）会立刻把它打包成一个 RADOS 请求，通过网络发给底层的 OSD 节点。

如果 vLLM 网关需要挂载一个共享的数据库来存会话状态，或者需要一块高性能的 Scratch Disk（临时盘）来跑编译任务，Ceph RBD 是绝佳选择

Ceph RBD支持快照与克隆

#### CRUSH算法
核心功能： **给定一个数据块，快速算出它到底存在哪几台物理硬盘/服务器上。**

当 AI Pod 要读写某个数据块时，客户端**不需要问任何人**，只需要在本地用 CRUSH 算法算一下：“根据这个块的 ID，结合当前的集群拓扑，它应该在 Node A、Node B 和 Node C 上。” 然后直接发网络请求！

解决的问题: 消除HDFS的NameNode 单点故障与性能瓶颈

核心能力：
- **故障域隔离**：你可以告诉 CRUSH 算法：“这 3 个副本，绝对不能放在同一个机架（Rack）上，甚至不能放在同一个机房里！” 这样哪怕整个机架断电，AI 训练也不会丢数据。
- **异构硬件调度**：你可以告诉 CRUSH：“高频访问的 AI 模型权重，只允许分布在 NVMe SSD 节点上；冷数据允许分布在 HDD 节点上。” 这就实现了纯算法层面的智能调度！

输入输出：
输入是分为两部分： 数据ID与当前集群的拓补图
输出是N个具体硬盘的IP地址/设备路径

动态扩容：
加硬盘时只迁移少量数据（约1/N）
本质：新增硬盘不引发"数据大逃难"。

## 存储方式的选择
- **海量训练语料**：用 **对象存储（S3/MinIO）**，便宜、无限扩展。
- **高并发训练数据加载**：用 **并行文件存储（Lustre/WekaIO）**，提供 POSIX 接口和极致的吞吐。
- **K8s 容器根目录、数据库、临时计算盘**：用 **块存储（Ceph RBD/EBS）**，提供低延迟和持久化
块存储是 AI Infra 的“地基”，它负责让 K8s 容器跑得稳、起得快；但它绝不是 AI 训练数据的“主战场”
