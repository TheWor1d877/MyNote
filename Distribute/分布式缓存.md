## 底层数据结构
Redis 的核心竞争力不在于它支持 5 种数据类型，而在于它根据数据量和大小，在底层动态切换数据结构。这本质上是一种空间与时间的运行时权衡（Space-Time Tradeoff）。
在数据量小时，Redis 极度偏爱压缩列表（ziplist）。它的核心思想是放弃指针，换取连续内存。连续内存对 CPU Cache 极其友好，但代价是插入/删除可能引发连锁更新（O(n)）。
为了解决 ziplist 的连锁更新问题，Redis 7.0 引入了 listpack（列表包） 全面替代 ziplist。listpack 允许每个节点独立存储长度信息，彻底消除了连锁更新。当数据量超过阈值（如 Hash 元素 > 512），底层才会退化为 hashtable 或 skiplist（跳表）+ hashtable。、

在ai场景下，我们更偏向于适用更激进的内存池化与块状分配

## 高可用架构
Sentinel（哨兵模式）的痛点：
架构本质：一主多从 + 外部监控集群。哨兵通过 Raft 算法变种选举 Leader，在主节点客观下线（ODOWN）时，自动将复制偏移量（offset）最大的从节点提升为新主。
物理妥协：哨兵模式无法解决单机内存瓶颈和写入并发上限。无论你的从节点有多少个，写请求永远只能打到唯一的 Master 上。此外，主从异步复制在故障转移（Failover）瞬间，存在不可避的数据丢失风险。在 AI 高并发网关场景下，单点 Master 会成为绝对的流量漏斗。

Redis Cluster的破局方法:
架构采用无中心节点的P2P架构，通过Hash将数据打散到多个Master上面
- 智能路由：客户端不需要知道拓扑，连任意节点即可。如果请求的 Key 不在当前节点，节点会返回 MOVED 或 ASK 重定向。这本质上是一种客户端侧的负载均衡。
- 脑裂与多数派写入：在网络分区（脑裂）场景下，Redis Cluster 遵循少数派节点拒绝写入原则，保证数据不会在多个分区被同时修改。

在ai 训练中，我们必须将不同的Request ID或者Session ID路由到不同的GPU实例上面去，实现真正的水平拓展

KV Cache在节点之间的迁移成本极高，必须做到拓扑感知（Topology-Aware），尽量让同一个 Session 的请求落在同一个 GPU 上，避免跨节点的 KV Cache 传输。


## 缓存三大经典问题
业务系统中，缓存穿透，集击穿，雪崩是为了保护MySQL，但是在AI Infra中这些问题的本质是保护昂贵的GPU算力与慢速的底层存储
#### 缓存穿透
查询一个根本不存在的数据
解法： 使用布隆过滤器或者缓存空值

如果 DataLoader 频繁请求不存在的 Shard 文件，会导致元数据服务器（MDS）被瞬间打挂。我们在分布式存储网关层，同样会使用分布式布隆过滤器来拦截无效请求，保护底层的 Lustre/WekaIO 集群。

#### 缓存击穿
这个热点 Key 突然过期了（比如 TTL 到时间了），此时成千上万的并发请求同时发现缓存未命中，于是全部直接打到数据库，DB 瞬间被压垮。

解决办法： 热点感知，对于高频访问的缓存Key，直接将这些内容进行缓存锁定（PIN），禁止被淘汰，或者在网关层做请求合并（多个请求同时请求统一资源的时候，就会使用一个请求去取得这份资源）

#### 缓存雪崩
大量 Key 同时过期，或 Redis 宕机

在分布式训练中，如果所有 Worker 在同一时刻发起 Checkpoint 写入，或者同时从远端拉取数据集，会导致存储网络带宽瞬间打满（类似雪崩）。解法是错峰调度（Jitter）：在 K8s 调度层或训练框架层，为 Checkpoint 和数据预取任务引入随机延迟或分批执行，平滑 I/O 曲线。
