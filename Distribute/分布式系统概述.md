扩展性（Scale-out）：
	以前我们想让电脑跑快点，就换更好的 CPU、加更大的内存，这叫“垂直扩展”（Scale-up）。但现在大模型太猛了，单台电脑就算把主板压弯了也装不下。所以我们只能“水平扩展”（Scale-out），也就是把任务拆成几万份，分给一万台电脑一起算。
容错性（Fault Tolerance）：
	一台电脑可能用十年不坏，但一万台电脑，可能每天都会有几台坏掉（比如断电、风扇坏了、硬盘烧了）。
透明性（Transparency）：
	写算法的科学家只关心“我的模型聪不聪明”，他们不想管“数据从哪个硬盘读的”、“哪台机器在算”

## CAP理论
#面试-分布式系统-复习  解释 CAP 定理的准确含义，以及为什么它常被误解为“三选二”。
C： 线性一致性，同一时间在不同节点上面能看到的是同一份数据
A： 可用性，每个非故障节点收到的请求必须得到非错误相应，必须要给出回应
P： 分区容忍性，指的是网络分区发生时系统还能继续运行

P是可以不要的选项，他是现实约束，所以真实情况是C与A只能二选一

CP 强一致 + 容错 
Kubernetes 的 etcd 就是这种。集群的调度状态绝对不能错，哪怕网络断了，宁可让系统暂停（不可用），也不能让两个节点同时指挥一个 Pod。

AP 高可用 +  容错
 想象一下，GPU 一秒钟烧几万块钱，如果因为网络稍微卡了一下，数据加载器就报错罢工，GPU 停转了，这损失谁担得起？所以，就算数据稍微旧一点、或者读重了，也绝不让 GPU 停下来等数据。

<span style="color:rgb(221, 85, 85)">状态管理（如 K8s 调度）必须是 CP 的，而数据流（如训练数据读取、推理请求）必须是 AP 的。</span>
#### “etcd 是 CP 系统，那它分区时少数派节点完全不能用，这算不算设计缺陷？”
少数派完全不能用恰好是CP实现的方式
etcd 是 Kubernetes 的元数据存储，存的是集群的期望状态：有哪些节点、哪些 Pod、哪些配置、哪个节点是 leader。这类数据的特征是量不大、但绝对不能读到过期的值。
所以etcd 的设计目标从一开始就是强一致，不是高可用优先。

etcd 用 Raft，写操作必须获得多数派节点确认才算提交。假设 3 个节点，quorum 是 2。网络分区把集群切成 2 和 1，多数派那 2 个节点能选主、能提交写、能正常服务。少数派那 1 个节点知道自己不在多数派里，它没法确认自己持有的数据是不是最新的，也没法确认自己如果接受写会不会和多数派冲突。这时候它只有两个选择：要么继续接受读写，返回可能过期的数据，这就违背了 C；要么拒绝服务，等重新连上多数派再恢复。etcd 选了后者。

## BASE理论
BASE 就是 AP 的“工程落地版”。既然我们选了 AP，承认了数据不可能时刻完美一致，那我们就定个规矩：
- 基本可用：核心功能必须活着。双十一抢购，就算购物车暂时打不开，但“下单”和“支付”这两个核心按钮必须能点。
- 软状态：允许数据在中间状态停留一会儿。北京的数据更新了，上海晚个 0.1 秒再更新，没关系。
- 最终一致性：只要网络不再断开，过一段时间，北京和上海的数据最终一定会变成一样的。

## PACELC
CAP 只在“网络分区发生”这个前提下讨论 C 和 A 的取舍，但系统绝大多数时间是没有分区的，那段时间里同样有一个绕不开的取舍：一致性和延迟。
当P发生的时候从A与C之间选择，不发生的时候从L与C中选择
L是延迟，C是一致性

你写一份数据，要让多个副本都确认写入成功才算完成，这就要等副本之间的网络往返。副本越多、跨的可用区越远，这个往返就越久，写延迟就越高。想降低延迟，就得放松一致性，比如只等多数派确认就返回，或者异步复制、写完主副本就返回。这就是 L 和 C 的取舍
