Docker 依赖 dockerd 守护进程（单点故障、安全风险）
Podman 无 daemon，每个命令独立执行，更符合 Linux 进程模型

docker的架构图：
```
用户终端
   │
   ▼
docker CLI（命令行工具）
   │
   ▼（通过 Unix socket /var/run/docker.sock）
dockerd（守护进程，root 权限）
   │
   ▼
containerd → runc → 实际容器进程
```
所有的进程均为dockerd的子进程

podman的进程架构
```
用户终端
   │
   ▼
podman CLI
   │
   ▼（直接调用）
runc / crun（OCI 运行时）
   │
   ▼
实际容器进程（你的 shell 的子进程）
```

## 验证podman无守护进程
- 启动一个容器
`podman run -d --name demo nginx`
- 查看 demo 容器的主进程 PID
`podman inspect demo --format '{{.State.Pid}}'`
- 查看进程树(假设pid是12345)
`pstree -p | grep -A5 -B5 12345`

进程关系图：
```txt
nginx worker (27894+) 
  ↑
nginx master (27852)
  ↑
conmon (27832)                ← Podman 的容器监控器
  ↑
systemd --user (2046)         ← **你的用户级 systemd 实例**
  ↑
systemd (1)                   ← 系统 init 进程（PID 1）
```
Podman 确实没有传统意义上的守护进程（daemon）。它使用一个名为 conmon（Container Monitor）的轻量辅助进程来管理单个容器的日志和生命周期，但 conmon 是按容器实例创建的，随容器启停，不存在全局常驻的中央服务进程。这与 Docker 的 dockerd 守护进程有本质区别——后者是单点、常驻、root 权限的中心化组件
