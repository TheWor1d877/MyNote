一张 GPU 如果只跑一个小模型，大部分显存和算力都在空转。把卡切细一点、排紧一点，就能让同一张卡同时承载更多推理副本。
## 虚拟化技术： vCUDA/HAMI的显存与算力切分
HAMi 是目前云原生场景里比较成熟的 GPU 虚拟化方案，属于 CNCF 孵化项目

HAMI在Time-Slicing与MPS的更高层上面解决调度与隔离问题
MIG 是硬件级隔离，每个实例有独立 SM、显存通道、错误域，隔离更强；
HAMi/vCUDA 是软件级隔离，通过 libvgpu.so 拦截 CUDA API，粒度更细，但隔离强度弱于 MIG；


工作流程分成四层：
```text
Pod声明资源 -> HAMI Webhook 改写资源调度路径 -> HAMI Scheduler 选择节点与GPU切片 -> HAMi-Core / vCUDA 在容器内拦截 CUDA API，强制执行显存和算力限制
```
HAMi-Core（即 libvgpu.so）本身并不修改 GPU 驱动或应用程序，它通过 Linux 的动态链接机制，抢在真正的 CUDA 库之前加载，从而在应用程序和 GPU 之间插入一个拦截层。
libvgpu.so 加载后，它需要让应用程序对 CUDA 函数的调用重定向到自己的实现上。这依赖于对 dlsym 函数的劫持。



限制资源：

| 资源  | 声明方式                         | 作用            |
| --- | ---------------------------- | ------------- |
| 显存  | `nvidia.com/gpumem`（MiB）或百分比 | 限制容器最多能分配多少显存 |
| 算力  | `nvidia.com/gpucores`（%）     | 限制 GPU 计算时间占比 |
#### MIG,Time-Slicing,MPS,HAMi四者区分

| 技术               | 所在层面                      | 一句话本质                                                        |
| :--------------- | :------------------------ | :----------------------------------------------------------- |
| **MIG**          | **硬件层**（GPU 芯片内）          | 把一块物理 GPU 在**硬件上切成**最多 7 个独立小 GPU，每个有自己独立的显存和计算核心            |
| **Time-Slicing** | **驱动/虚拟化层**               | **时间片轮转**，多个进程轮流使用同一块 GPU，同一时刻只有一个在跑                         |
| **MPS**          | **运行时层**（CUDA API 层）      | 让多个进程的 CUDA kernel **并行**跑在同一块 GPU 上，共享 CUDA Context，减少切换开销  |
| **HAMi**         | **调度与隔离层**（Kubernetes 之上） | 通过 **CUDA API 劫持**在软件层面实现显存/算力的**配额限制**，让 Pod 以为自己独占了一部分 GPU |
MIG走空间路线，在硬件层面上面将GPU切分开，隔离最强，但是切分粒度固定

Time-Slicing 走“时间”路线：所有任务共享全部显存，但轮流用计算核心。隔离性最弱，一个任务把显存吃光，其他全挂

MPS 是 Time-Slicing 的“优化版”：它不满足于“轮流”，而是让多个进程的 kernel 真正并行执行，提升利用率、减少切换开销 -4-19。但它同样没有硬隔离，一个进程崩溃可能影响其他进程

HAMi 的定位：它不直接和 MIG/MPS 抢底层，而是站在 Kubernetes 的视角做“管理”


## 超密部署：单卡多副本
部署思路
1. 先测清单副本资源消耗
   用 nvidia-smi、dcgm-exporter 或 pytorch 显存监控，看每个副本实际占多少显存、平均算力利用率多少。
2. 确定单卡可承载副本数
   比如一张 80GB A100 上，一个 7B FP16 推理副本占 14GB 显存、平均算力 20%，那理论上可以放 4~5 个副本。
3. 用 HAMi 限制每个副本
   给每个 Pod 设置显存和算力上限，避免某个副本突然吃满显存。
4. 配合推理引擎的并发能力
   vLLM、SGLang 这类引擎本身支持连续批处理。单副本内部也能同时处理多个请求，不需要靠副本数量硬堆并发。
5. 设置 QoS 策略
   在线推理适合用 fixed share 或 burst share；离线批处理可以用 best effort，资源紧张时


两条提升并发的路径：
- 多开副本
- 单副本内连续批处理（更优）

vLLM/SGLang 的核心技术叫 Continuous Batching（连续批处理）。它的关键点是：
- 传统推理：一个请求生成完整回复才处理下一个，GPU 大量时间在等。
- 连续批处理：请求 A 生成到第 3 个 token 时，请求 B 可以立刻插进来一起算；某个请求生成完了，它占的位置马上让给新请求。

结果是单副本就能把 GPU 算力吃满，同时服务几十上百个并发请求。这时候你再开多个副本，反而会：
- 每个副本各占一份显存（如 14GB），显存不够分
- 副本之间抢算力，互相干扰
- 调度、上下文切换开销增加

多副本是为了单个副本吃不满算力与显存的时候，填充用的


示例：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-embedding
spec:
  replicas: 5
  template:
    spec:
      containers:
      - name: embedding
        image: embedding-service:latest
        resources:
          limits:
            nvidia.com/gpu: 1
            nvidia.com/gpumem: 8000
            nvidia.com/gpucores: 20
```
