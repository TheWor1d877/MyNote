## KV Cache的显存占用
单条请求的占用
设模型参数为：
```text
L = 层数
H = 注意力头数
D_h= 每头维度
n = 序列长度（prompt + 已生成 Token）
b = 数据类型字节数（FP16=2, INT8=1, FP8=1）
每层每 Token 需要缓存 K 和 V 两个矩阵，每个矩阵大小为 H * D_h
KV Cache 大小 = 2 × L × n × H × D_h x b
```
Llama-3-70B中单条请求占用空间约21.5GB

Batch 的影响
KV Cache 是按请求独立分配的，batch size 翻倍，KV Cache 总占用也翻倍。这也是为什么高并发下显存压力远大于单请求场景

## KV Cache 量化： INT8/FP8压缩
KV Cache 的值分布相对集中，对精度要求不如权重敏感。将 FP16 降到 INT8 或 FP8，显存直接减半，精度损失通常可以忽略

#### 实现
- Per-Token量化： 对每个Token的KV向量独立计算缩放因子，比全局量化精度更高
KV Cache 的值分布很不均匀。有的 token 向量数值普遍偏大，有的普遍偏小。如果用一个全局缩放因子，小数值的 token 会被压到极低精度甚至归零；大数值的 token 又会把整体动态范围撑得太大，导致所有 token 都损失精度。
Per-Token 量化让每个 token 自己决定自己的缩放尺度。一个数值小的 token，用自己的缩放因子，也能映射到 INT8 的合适区间里，精度损失就小得多

- KV Cache专用量化
KV Cache 是推理时动态生成的。每来一个新 token，就要生成它的 K 和 V，立刻量化写入缓存。你没办法提前知道下一个 token 的数值范围。
KV Cache 量化必须在推理路径上面在线完成，需要低延迟的量化与反量化Kernel：量化（写入时）+ 反量化（注意力计算前）

注意额外开销：
如果单独写一个kernel用来量化/反量化，这里面的数搬运开销可能
比省下的显存收益高
正确的做法：把反量化逻辑直接写进注意力 kernel 内部。注意力 kernel 从显存读 INT8 数据，在片上寄存器或 shared memory 里就地转换成计算精度，直接参与 QK^T 和 PV 矩阵乘。数据只搬一次，转换几乎零额外开销

- 混合精度： K 用 FP16、V 用 FP8，因为V 的分布更均匀、没有明显离群点，更适合量化；K 的分布有离群点、更不均匀，需要更精细的量化处理（per-channel、更高精度或 FP8 的动态范围）来保精度。

## 分层缓存架构
当显存装不下全部 KV Cache 时，可以把"暂时用不到"的部分搬到更便宜的存储层级：

```
┌──────────────────────────────────────────┐
│  GPU HBM（最快，容量最小）                  │
│  存放：当前活跃 batch 的 KV Cache          │
├──────────────────────────────────────────┤
│  CPU DRAM（较慢，容量大）                   │
│  存放：当前请求的历史 KV，等待下一轮 decode  │
├──────────────────────────────────────────┤
│  NVMe SSD（最慢，容量极大）                 │
│  存放：长时间不活跃的会话 KV，支持跨会话复用  │
└──────────────────────────────────────────┘
```
关键设计：
- 预取（Prefetch）：在 GPU 计算当前 Token 时，异步从 CPU/SSD 拉取下一轮需要的 KV，掩盖传输延迟
- LRU 淘汰：最近最少使用的会话优先卸载到下一级
- 跨会话复用：对于系统 prompt 或长文档前缀，KV Cache 可以持久化到 SSD，新请求直接加载，避免重复计算
- 配合 PagedAttention 的分页机制，以 block 为单位换入换出，避免整条请求迁移

延迟权衡：
- HBM CPU DRAM 带宽约 20~30 GB/s（PCIe 4.0 x16）
- 换出 1 GB KV Cache 约需 30~50 ms
- 如果频繁换入换出，延迟会显著上升


## KV Cache卸载
- vLLM 的 swap_space
vLLM 启动时可通过 --swap-space 参数分配 CPU 内存作为交换区。当 GPU 显存不足时，自动将部分请求的 KV Cache 换出到 CPU，等该请求调度回来时再换入。
```bash
python -m vllm.entrypoints.api_server \
    --model meta-llama/Llama-3-70B-Instruct \
    --swap-space 16  # 分配 16GB CPU 内存作为交换区
```
