## vLLM：通用部署的事实标准
vLLM 目前是大模型推理部署里生态最成熟、使用最广的框架。

它的核心底座是 **PagedAttention**，把 KV Cache 切成固定大小的块，按需分配、动态回收，显存利用率可以稳定在 90% 以上。 配合连续批处理，GPU 利用率通常能拉到 80%~100%，高并发下吞吐量表现很稳。

2026 年的 vLLM 已经补齐了很多能力：

- 原生支持 **FP8/INT8 KV Cache 量化**；
- 集成 **EAGLE 系列投机解码**；
- 支持 **Prefix Caching / RadixAttention**，多轮对话和前缀复用效果明显；
- 支持 **分离式 Prefill-Decode**；
- 兼容 OpenAI API，支持多 LoRA、流式输出、张量并行、流水线并行。

vLLM 最大的优势是“模型适配快”。新模型出来后，vLLM 通常一两周内就能支持。 如果你希望快速上线、少踩坑、模型种类多，vLLM 是最省心的选择。

短板也有：它在 NVIDIA GPU 上很强，但单序列延迟和极致吞吐通常不如 TensorRT-LLM；结构化输出能力虽然有，但不如 SGLang 原生。

## TensorRT-LLM：NVIDIA 硬件上的性能上限

TensorRT-LLM 是 NVIDIA 官方推理框架，主打算子级深度优化。

它会在部署前把模型编译成专用推理引擎，做算子融合、内存布局优化、FP8/INT8 量化、In-flight Batching 等处理。H100/A100/B200 上，它的吞吐和延迟通常处于第一梯队。

2026 年 TensorRT-LLM 的几个关键变化：

- 已支持类似 PagedAttention 的分页 KV Cache；
- FP8 混合精度推理更成熟；
- 对 Blackwell 架构做了深度适配；
- 投机解码、Skip Softmax、多模态推理能力陆续补齐。

它的强项很明确：**固定模型 + NVIDIA 硬件 + 追求极致性能**时，TensorRT-LLM 往往能再压出 1.5~2 倍收益。

但代价也不小。引擎编译耗时长，模型改动后要重新编译；只支持 NVIDIA GPU；调试门槛比 vLLM 高不少。 如果你的业务模型经常换、团队 CUDA 经验有限，TensorRT-LLM 的维护成本会比较高。

## SGLang：Agent 和结构化输出的首选

SGLang 的定位和其他两个不太一样。它不只是一个推理引擎，更像是一个面向生成任务的运行时。

它有两个杀手锏。

**第一，RadixAttention 前缀缓存。**  
多轮对话、Agent 工具调用、RAG 工作流里，system prompt、工具描述、知识库前缀经常高度重复。SGLang 会把相同前缀的 KV Cache 复用起来，缓存命中率能提升 3~5 倍，多轮对话吞吐显著高于通用框架。

**第二，原生结构化生成。**  
SGLang 支持 JSON Schema、正则表达式、EBNF 等约束解码，生成过程中直接限制 token 空间，保证输出格式合规。 实测 JSON 合规率可以达到 99% 以上，速度损失通常在 10% 以内。 这对 Agent 的 Function Calling、工具调用、数据抽取非常关键。

另外，SGLang 的 Python DSL 写复杂工作流很顺手，比如“先检索、再调用工具、最后整理成 JSON”，几行代码就能串起来。

不足在于：它对纯通用 API 服务的生态成熟度还略低于 vLLM；超长正则约束可能引发状态机膨胀；小模型上额外编译开销不一定划算。

## 选型建议

| 场景 | 首选 | 理由 |
|---|---|---|
| 通用高并发 API 服务 | **vLLM** | 模型支持广、部署简单、生态成熟 |
| NVIDIA 硬件 + 固定模型 + 极致延迟/吞吐 | **TensorRT-LLM** | 算子级优化最强，H100/A100/B200 收益明显 |
| Agent、多轮对话、工具调用 | **SGLang** | RadixAttention + 结构化生成优势突出 |
| 长上下文 + 前缀复用 | **SGLang / vLLM** | SGLang 缓存更强，vLLM 通用性更好 |
| 快速验证、多模型切换 | **vLLM** | 新模型适配最快，OpenAI API 兼容 |
| 国产化/异构 GPU | **vLLM / LMDeploy** | TensorRT-LLM 只支持 NVIDIA |
