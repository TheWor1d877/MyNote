分布式推理系统在生产环境中面临三大类故障：
- GPU硬件故障
- 网路故障
- 节点故障

## 故障检测： GPU 掉卡、网络分区、节点宕机
GPU 掉卡：GPU 从 PCIe 总线上"消失"，nvidia-smi 无法识别该设备，但节点操作系统仍正常运行。
网络分区（Network Partition）：分布式系统中部分节点间网络连通性中断，导致通信组分裂为多个孤立子集。
XID 错误码：NVIDIA 驱动向内核日志打印的错误报告，用于标识 GPU 硬件、驱动或应用层的故障类型


## 弹性容错
Elastic Training 思想在推理场景的迁移，故障节点的自动剔除与任务迁移

#### 训练场景下面的弹性容错
训练场景的弹性容错已有成熟方案（TorchElastic、AWS SageMaker HyperPod、阿里云 AIMaster），但推理场景有以下本质差异：

| 维度 | 训练场景 | 推理场景 |
|-----|---------|---------|
| 故障容忍度 | 可接受分钟级中断（从 Checkpoint 恢复） | 要求秒级恢复，SLA 违约即损失 |
| 状态依赖 | 模型参数 + 优化器状态，可从共享存储加载 | KV Cache 驻留显存，丢失需重算 |
| 并行策略 | DP/TP/PP 固定，弹性调整需重分片 | TP 组固定，仅 DP 副本可弹性伸缩 |
| 恢复目标 | 收敛精度不受影响 | 请求不丢失、延迟不抖动 |

#### 推理场景下面的弹性容错架构
检测到节点发生故障，自动执行以下流程：
1. 故障广播：故障节点的 Elastic Agent 通过 Rendezvous 后端标记当前 run_id 为无效，通知所有存活节点。
2. 进程组重建：存活节点进入等待状态，重新协商 World Size，排除故障节点。NCCL 通信组自动重建，TP 组保持不变，仅 DP 副本数减少。
3. 流量切换：负载均衡器（如 Envoy、Nginx）检测到故障 Pod 的 Readiness Probe 失败，自动将流量路由到健康副本。

k8s管理的是单个Pod（Deployment）的生命周期，但是无法管理整个进程组的生命周期
进程组中的Pod挂掉后，需要全部重启，不然之间的通信会乱掉

之后开始任务迁移与状态恢复过程:
- Pod 自动重建：Training Operator 或 Deployment 控制器检测到 Pod 失败后，自动拉起新 Pod 替换故障节点。新 Pod 需保留相同的 Rank ID、端口范围和主机亲和性。
- KV Cache 迁移：在 PD 分离架构中，Decode 节点故障时，其负责的 KV Cache 可通过 RDMA 快速迁移到备用节点。腾讯云 FlexKV 的异步流水线设计可将缓存读写操作与 GPU 计算完全重叠，隐藏数据搬运延迟。
- 请求重试与幂等性：推理失败时设计自动重试机制（指数退避、最多 3 次），配合请求 ID 实现幂等性，防止雪崩效应。

###### 工程建议：
- TP 组不可弹性：TP 组内 GPU 必须通过 NVLink/NVSwitch 互联，弹性调整会导致通信拓扑破坏，因此 TP 规模应固定。
- DP 副本弹性：DP 副本间无通信依赖，可自由增减，适合应对流量波动和故障恢复。
- Rendezvous 后端高可用：etcd 或 Kubernetes API Server 必须部署为多副本集群，避免单点故障导致弹性机制失效。

## KV Cache检查点机制
KV Cache 检查点：将推理过程中生成的 KV Cache 持久化到非易失存储（DRAM/SSD/分布式存储），在节点故障或请求中断后快速恢复，避免重算。

行业已形成"以存换算"的共识，构建"GPU HBM → CPU DRAM → 本地 NVMe SSD → 分布式存储"等多级缓存体系

| 存储层级 | 介质 | 容量 | 访问延迟 | 适用场景 |
|---------|------|------|---------|---------|
| L0: GPU HBM | HBM3/HBM3e | 80~141 GB/GPU | <1μs | 活跃推理的 KV Cache |
| L1: CPU DRAM | DDR5 | 512 GB~2 TB/节点 | 100~300 ns | 短期闲置、可能快速复用的状态 |
| L2: 本地 NVMe SSD | PCIe 4.0/5.0 SSD | 4~30 TB/节点 | 10~100 μs | 冷数据、长上下文会话 |
| L3: 分布式存储 | RDMA + SSD 池 | PB 级 | 100~500 μs | 跨节点共享、全局复用 |
