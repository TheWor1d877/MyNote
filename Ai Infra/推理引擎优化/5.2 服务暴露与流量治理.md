将模型变成稳定的线上服务,还需要网关,健康检查,发布,路由这几关
推理流量和普通 HTTP 请求差别很大：请求长度不确定、响应是流式的、GPU 负载又不均匀。所以通用的微服务治理方案直接拿来用，往往会踩坑。
## 网关层面设计: 
推理服务最常见的交互方式是流式输出。用户发一个 prompt，服务端按 token 逐段返回。
网关层面如果按照短请求处理,会遇到问题:
- 连接超时会被提前切断
- 响应缓冲导致首字延迟变高
- 重试机制把同一个 prompt 重复发给后端，造成重复扣费；
- 长连接占用过多，网关自身成为瓶颈。

关键配置:

| 配置项 | 推荐做法 |
|---|---|
| 超时 | 流式响应建议把 read timeout 调到 60s 以上，或针对 `/v1/chat/completions` 等路径单独配置 |
| 缓冲 | 关闭响应缓冲，避免网关攒够完整响应才转发 |
| 重试 | 对 POST 流式接口禁用自动重试，防止重复生成 |
| 连接复用 | 启用 HTTP/2 或 HTTP/1.1 keep-alive，减少与后端 Pod 的建连开销 |
| 限流 | 按用户、API Key 或租户做并发和 QPS 限制 |
| 日志 | 记录 prompt 长度、生成 token 数、首字延迟，方便后续排查 |

## 健康检查: Readiness Probe拓展
k8s 默认的 readiness probe 通常只检查端口是否通。这对推理服务远远不够。端口通了，可能模型还没加载；模型加载了，也可能 KV Cache 已经爆满，再接新请求只会排队超时。

更合理的做法是把探针接到推理引擎的内部状态上。以 vLLM 为例，可以检查 /health 或 /metrics：
```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
```
这样当某个 Pod 排队过长时，会自动从 Service 后端摘除，流量不会再打过去。liveness probe 则保持简单，只判断进程是否还活着，避免因为临时负载高就频繁重启。

## 灰度发布
推理服务的发布风险比普通 Web 服务更高：模型权重变了、推理引擎版本变了、量化方式变了，都可能直接影响延迟和准确率。
#### 滚动更新
k8s的Deployment默认就是滚动更新,省资源,适合日常小版本迭代
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```
maxUnavailable: 0 保证更新期间容量不下降，maxSurge: 1 允许临时多起一个 Pod 做替换。配合 readiness probe，新 Pod 模型加载完成后才会接入流量。

问题: 回滚慢,更新期间新旧版本同时存在,可能对API或者输出格式有破坏性变更,需要额外兼容

#### 蓝绿部署
维护两套完整环境，流量通过 Service selector 一键切换。
```yaml
# Service 指向绿色环境
selector:
  app: llm-inference
  track: green
```
切换快,回滚快,适合可用性极高的场景,但是资源翻倍,成本高

#### 金丝雀发布
先放 1%~5% 流量给新版本，观察 TTFT、TPOT、错误率、GPU 显存占用等指标，确认没问题再逐步放量。
这个策略需要网关或服务网格支持按权重分流。Argo Rollouts、Istio、ALB 权重路由都可以实现。推理场景下，金丝雀发布尤其重要，因为模型效果变化很难通过单元测试完全覆盖。

## 智能路由与队列深度感知
传统负载均衡按轮询或最少连接数分发请求，这对推理服务效果不好。两个请求的 prompt 长度可能差十倍，输出 token 数也完全不确定。轮询看起来均匀，实际落到 GPU 上的负载可能天差地别。
智能路由会根据若干个关键指标来,把新请求发给当前最空闲的副本
vllm:num_requests_waiting：排队等待的请求数；
vllm:num_requests_running：正在 GPU 上处理的请求数；
vllm:gpu_cache_usage_perc：KV Cache 使用率；
vllm:num_requests_swapped：被换出到 CPU 的请求数。

比如阿里云 ALB 扩展版已经支持基于这些指标的负载感知路由，ASM 也提供了 InferencePool 来做类似事情。

##  Service Mesh 开销评估：Sidecar 对 P99 延迟的影响
Service Mesh 能提供 mTLS、灰度路由、重试、熔断、指标采集等能力，但代价是每条请求都要多经过一层或多层代理

| 模式 | P99 延迟增加 | 资源开销 |
|---|---|---|
| 无 Mesh | 基准 | 无额外开销 |
| Sidecar（iptables + Envoy） | +1.5ms ~ 3ms，高并发下更高 | 每 Pod 约 0.2~0.5 vCPU，50~200MB 内存 |
| Sidecar + eBPF sockmap | +0.5ms ~ 1ms | CPU 开销降低，内存变化不大 |
| Ambient L4（ztunnel） | +0.1ms ~ 0.3ms | 节点级共享，开销显著降低 |
| Ambient L4+L7 | 略高于纯 L4 | 按 Namespace 按需部署 Waypoint |
