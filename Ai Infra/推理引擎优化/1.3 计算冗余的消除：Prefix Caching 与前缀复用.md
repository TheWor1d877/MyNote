## 重复计算的浪费
大模型推理的实际业务场景中，大量请求共享相同的前缀 Token。最典型的三类场景如下：
   多轮对话：每一轮新请求都携带完整的对话历史，前几轮的 Prompt + Response 完全重复。
   固定 System Prompt：企业级应用中，每个请求都会附带数百甚至上千 Token 的角色设定、行为约束、格式要求等系统提示词。
   RAG（检索增强生成）：检索到的知识库文档作为上下文注入 Prompt，同一份文档可能被多个用户请求复用。

这些重复的前缀Token不需要计算一遍KVCache
如果一个 1000 Token 的 System Prompt 被 100 个请求共享，GPU 就要重复执行 100 次完全相同的 Prefill 计算。

## 解决办法： 基于 Token ID 序列的哈希匹配、Radix Tree 数据结构、LRU 淘汰策略
#### 基于 Token ID 序列的哈希匹配
每个 Block 在生成时，系统会根据该 Block 内所有 Token 的 ID 序列计算一个哈希值（Hash）。这个哈希值作为该 Block 的"指纹"，存储在 Block Table 中。当新请求到来时，系统逐 Block 比对其 Token 序列的哈希值与缓存中已有 Block 的哈希值。如果匹配成功，说明该 Block 的 KV Cache 已经计算过，可以直接复用，无需重新执行 Prefill 计算。

#### Radix Tree 
本质是一个存储KV Cache的字典树

为了高效管理海量的前缀，vLLM 使用 Radix Tree 来组织缓存的 KV Cache。Radix Tree 是一种多叉树结构，每个节点代表一个前缀，从根节点到某个节点的路径就对应一个完整的 Token 序列。

```text
Root
  │
[你 是 一 个 助 手]
  │
[，]
  │
  ├── [帮 我 写 代 码]      ← 原请求
  │
  └── [今 天 天 气 怎 么 样] ← 新请求
```

#### LRU（Least Recently Used）淘汰策略
显存池容量有限，当缓存填满时，系统需要决定淘汰哪些 Block。vLLM 采用 LRU 策略，即优先淘汰最久未被访问的 Block。这种策略基于"局部性原理"：最近被复用的前缀，在未来被再次复用的概率更高。
名词解释：
Radix Tree：一种压缩的前缀树，常用于字符串匹配和路由表查找。在这里用于组织 KV Cache Block，支持高效的前缀匹配和共享。
LRU：一种经典的缓存淘汰算法，维护一个访问顺序链表，最近访问的元素移到链表头部，淘汰时从尾部移除最久未访问的元素。


## 零开销优化: vLLM V1 版本如何通过数据结构简化，实现缓存未命中时的性能无损
早期版本的 Prefix Caching 存在一个隐患：当缓存未命中（Cache Miss）时，系统需要回退到传统的 Prefill 计算流程，这个切换过程本身会带来额外的开销（如哈希计算、树遍历、状态切换等），导致"用了缓存反而更慢"的尴尬情况。

哈希计算和树遍历是"前置检查"，必须先做完，才知道要不要算 Prefill。

#### 优化方法
- 哈希计算与 Prefill 计算并行
```text
请求到达
  ↓
┌─────────────────┐    ┌─────────────────┐
│  CPU 侧          │    │  GPU 侧          │
│  算哈希           │    │  直接开始 Prefill │
│  遍历 Radix Tree  │    │  计算             │
│  查缓存           │    │                  │
└─────────────────┘    └─────────────────┘
        ↓                      ↓
   如果命中：               如果未命中：
   通知 GPU 停止           Prefill 已经算了一部分
   复用已有 Block          继续算完即可
```

- Block Table 原地复用
以前：
命中：从 Radix Tree 拿到已有 Block，拼成 KV Cache
未命中：新分配 Block，算完 KV Cache，再挂到 Radix Tree 上
这两种路径的数据结构，状态管理，指针操作都不同，切换的时候需要状态转换，这就产生了开销

V1的做法：
无论命中与否，请求最终都通过 Block Table 访问 KV Cache。
```text
请求的 Block Table：
  ┌─────────────────────────────┐
  │ 逻辑 Block 0 → 物理 Block 7  │
  │ 逻辑 Block 1 → 物理 Block 3  │
  │ 逻辑 Block 2 → 物理 Block 12 │
  └─────────────────────────────┘
```

命中：Block Table 直接指向 Radix Tree 里已有的物理 Block
未命中：Block Table 指向新分配的物理 Block

- Radix Tree 轻量级遍历
哈希匹配过程仅在 CPU 侧进行，且 Radix Tree 的节点指针存储在连续内存中，遍历效率极高（纳秒级），对整体推理延迟的影响可以忽略不计
