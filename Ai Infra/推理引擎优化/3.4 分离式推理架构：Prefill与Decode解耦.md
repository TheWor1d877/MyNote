Prefill 阶段：处理用户输入的 Prompt，一次性计算所有输入 Token 的 KV Cache。此阶段计算密集，因为需要处理大量 Token 的并行 Attention 计算。

Decode 阶段：逐个生成输出 Token。此阶段内存密集，因为每次迭代只需计算 1 个 Token，但需要读取整个 KV Cache。

Prefill 需要大量算力来并行计算，而 Decode 需要高带宽来读取 KV Cache。将两者混在同一个批次中会导致资源争抢：Prefill 会占用大量算力，拖慢 Decode 的迭代速度；Decode 会占用显存带宽，限制 Prefill 的计算吞吐。

算力再强，如果数据喂不上来，也得闲着。带宽再大，如果算力不够，数据读进来也算不完。
二者相互占据着对方缺少的资源

```text
┌──────────────────────────────────────────────┐
│                  GPU 芯片                    │
│                                              │
│   ┌──────────────┐      ┌──────────────┐     │
│   │   计算核心    │      │  显存控制器    │     │
│   │ (SM/Tensor)  │─────→│ (Memory Ctrl)│─────→ HBM
│   └──────────────┘      └──────────────┘     │
│          ↑                    ↑              │
│          └────────────────────┘              │
│              所有数据都要经过这里               │
│                                              │
└──────────────────────────────────────────────┘

```

## 架构设计：Prefill 池 + Decode 池 + KV Cache 传输
Prefill 节点池
- 负责处理 Prompt，构建 KV Cache；
- 适合用高算力 GPU，张量并行可以开得更大；
- 调度时会优先复用前缀缓存，避免重复计算长上下文。

Decode 节点池
- 负责逐 Token 生成；
- 适合用大显存、高带宽 GPU；
- 更关注 TPOT、TBT 和连续批处理效率。

KV Cache 跨节点传输
Prefill 完成后，需要把 KV Cache 送到 Decode 节点。常见传输方式有：
- RDMA / GPUDirect RDMA：跨节点显存直传，延迟通常在毫秒级；
- NVLink：同机多卡之间迁移，延迟极低，几乎可以忽略；
KV Cache传输开销必须小于他带来的收益



## Chunked Prefill
Chunked Prefill 是 vLLM 为缓解长 Prompt 推理阻塞而引入的调度机制。传统做法中，一个很长的 Prompt 在 Prefill 阶段会一次性占用大量算力和显存带宽，导致同一批次里的 Decode 请求长时间得不到执行，从而拉高 Decode 延迟。Chunked Prefill 把长 Prompt 的 Prefill 计算拆分成多个小 Chunk，每个 Chunk 不再单独霸占整个批次，而是与 Decode 请求混合组成一个 batch 一起执行。这样既避免了单个长 Prefill 阻塞整个批次，又让 Decode 请求能够持续获得调度机会，延迟不会受到太大影响。

以每次切成 512 Token 的 Chunk 为例，模型每次只处理 512 个 Token 的 Prefill，单步算力需求变得可控，不会因为超长 Prompt 一次性涌入而挤占全部资源。与此同时，剩余的算力和显存带宽可以分给 Decode 请求，使已经在生成阶段的请求仍能稳定推进。因此，Chunked Prefill 的核心价值在于：通过“长 Prefill 分块 + 与 Decode 混批执行”，在吞吐和延迟之间取得更好的平衡，尤其适合长 Prompt 与在线 Decode 请求并存的推理场景。

## 开源项目：

| 项目        | 核心思路                                                                 | 适用场景              |
| --------- | -------------------------------------------------------------------- | ----------------- |
| Mooncake  | 以 KV Cache 为中心的分布式架构，Prefill/Decode 池 + 分布式 KV Cache 池，支持 RDMA 和分层缓存 | 大规模集群、长上下文、多轮对话复用 |
| Splitwise | 同机内解耦，Prefill 和 Decode 放在同一节点不同 GPU 上，通过 NVLink 迁移 KV Cache          | 中小规模部署，改造成本低      |
| DistServe | 跨节点解耦，Prefill 和 Decode 可独立设置并行策略，重点优化 Goodput                        | 中长上下文、高并发 Serving |
| FlowKV    | 优化 KV Cache 块级传输和负载感知调度，降低跨节点迁移延迟                                    | 异构 GPU、负载波动明显场景   |
   
Mooncake 的特别之处在于，它把 Prefill/Decode 解耦和 KV Cache 存储层绑在一起。KV Cache 不再只挂在某个 GPU 上，而是可以被集群共享、复用和淘汰。
Splitwise 更轻量，适合先在同一台 8 卡节点里试水 PD 分离。它的优势是部署简单，但扩展性受限于单机资源。
DistServe 则更强调跨节点调度和并行策略独立配置，比如 Prefill 用 TP=4，Decode 用 TP=1，从而分别优化算力和带宽。
