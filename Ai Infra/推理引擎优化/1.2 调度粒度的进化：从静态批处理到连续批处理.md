核心问题：GPU 算力如何被高效利用。传统推理框架的批处理机制存在严重的"木桶效应"，导致 GPU 在大量时间内处于空转状态。vLLM 通过迭代级调度（Iteration-level Scheduling）彻底重构了请求的生命周期管理

## 静态批处理到连续批处理
传统框架采用静态批处理，即一个批次（Batch）中的所有请求必须同时进入、同时完成。这意味着批次中所有请求的处理时间由最长的那个请求决定。

假设一个 Batch 包含 4 个请求，其中 3 个是短请求（各生成 10 个 Token），1 个是长请求（生成 200 个 Token）。GPU 在执行前 10 次迭代时，4 个请求都在参与计算，利用率较高。但从第 11 次迭代开始，3 个短请求已经完成，它们的槽位被空置，GPU 只能为剩下的 1 个长请求服务。此时 GPU 的并行计算能力被严重浪费，实际利用率跌至 25%。
如何更好的利用并行计算能力是关键
```text
静态批处理时间线示意（Batch Size = 4）：

迭代次数  | 请求A(10tok) | 请求B(10tok) | 请求C(10tok) | 请求D(200tok)
---------|-------------|-------------|-------------|-------------
  1-10   |   ██████     |   ██████     |   ██████     |   ██████      ← 满载
  11-200 |   [空闲]     |   [空闲]     |   [空闲]     |   ██████      ← 75%算力浪费
```

#### 迭代级调度：Iteration-level Scheduling
vLLM 将调度粒度从"批次级"细化到"迭代级"。每次迭代（即每生成一个 Token）后，调度器都会重新评估所有请求的状态：已完成的请求立即移除并释放显存，新到达的请求可以动态插入当前批次。
###### 实现原理
动态插入：每次迭代结束之后，调度器都会检查显存池中又没有足够的空闲Block，如果有就会从队列中取出新的请求加入批次
动态移除： 当某个请求生成到 EOS（结束符）或达到最大长度时，立即从批次中剔除，其占用的 Block 归还给空闲池。
公平性保障：通过 FCFS（先来先服务）或优先级队列，避免长请求永远占据资源。

```text
迭代级调度时间线示意（Batch Size = 4）：

迭代次数  | 槽位1 | 槽位2 | 槽位3 | 槽位4
---------|------|------|------|------
  1-10   |  A   |  B   |  C   |  D   ← 初始批次
  11-15  |  E   |  B   |  C   |  D   ← A完成，E插入
  16-20  |  E   |  F   |  C   |  D   ← B完成，F插入
  21-200 |  E   |  F   |  G   |  D   ← C完成，G插入
```

## Prefill/Decode阶段解耦
Prefill 阶段：处理用户输入的 Prompt，一次性计算所有输入 Token 的 KV Cache。此阶段计算密集，因为需要处理大量 Token 的并行 Attention 计算。

Decode 阶段：逐个生成输出 Token。此阶段内存密集，因为每次迭代只需计算 1 个 Token，但需要读取整个 KV Cache。

Prefill 需要大量算力来并行计算，而 Decode 需要高带宽来读取 KV Cache。将两者混在同一个批次中会导致资源争抢：Prefill 会占用大量算力，拖慢 Decode 的迭代速度；Decode 会占用显存带宽，限制 Prefill 的计算吞吐。

```text
┌─────────────────────────────────────┐
│              GPU 芯片                │
│  ┌───────────┐    ┌───────────┐    │
│  │ 计算核心   │───→│ 显存控制器 │───→ HBM
│  │ (SM/Tensor)│    │ (Memory   │    │
│  └───────────┘    │ Controller)│    │
│        ↑          └───────────┘    │
│        │                ↑          │
│        └────────────────┘          │
│         所有数据都要经过这里          │
└─────────────────────────────────────┘
```
算力再强，如果数据喂不上来，也得闲着。带宽再大，如果算力不够，数据读进来也算不完。
二者相互占据着对方缺少的资源

Chunked Prefill 的平衡艺术：vLLM 引入了 Chunked Prefill 机制，将长 Prompt 的 Prefill 计算拆分为多个小 Chunk（块），每个 Chunk 与 Decode 请求混合执行。这样既避免了单个长 Prefill 阻塞整个批次，又保证了 Decode 请求的延迟不受太大影响。
切成 512 的 Chunk：每次只进来 512 Token 的 Prefill，算力需求可控，Decode 还能分到一部分算力和带宽

参数调优：chunked-prefill-size 控制每个 Chunk 的 Token 数量。设置过小会增加 Prefill 的总耗时（因为多次启动 Kernel 的开销），设置过大则会影响 Decode 的延迟。通常建议设置为 512~1024。

## 吞吐量与延迟
增大批次大小可以提升吞吐量（单位时间处理的 Token 数），但会增加每个请求的延迟（因为批次越大，每次迭代的计算时间越长）。

在生产环境中，建议通过压测工具（如 locust 或 k6）模拟真实负载，绘制"吞吐量-延迟"曲线，找到满足 SLA（服务等级协议）延迟上限的最大吞吐量点。
