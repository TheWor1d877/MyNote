torch.compile 只优化“张量计算图”，不优化 DataLoader 的 I/O、Python 数据加载、CPU 预处理和 CPU→GPU 传输
所以如果训练瓶颈在数据侧，torch.compile 基本救不回来。

## 图捕获边界： 只捕获张量操作，不捕获DataLoader
DataLoader的完整链路：
```text
Sampler 生成索引
→ Worker 进程读磁盘
→ Dataset.__getitem__ 解码/增强
→ collate_fn 组装 batch
→ pin_memory 拷贝到页锁定内存
→ .to(device) H2D 传输
→ 模型前向/反向
```
torch.compile 的编译入口是 TorchDynamo。它会拦截 Python 字节码，把连续的 PyTorch 张量操作捕获成 FX Graph。
torch.compile 通常只作用在最后一段，也就是模型前向、反向以及部分 loss 计算。前面的磁盘读取、解码、增强、collate、pin_memory、H2D 传输都不在 FX Graph 里。

## 为什么数据加载瓶颈不会被 torch.compile 优化掉
- DataLoader 不在图中
DataLoader 是 Python 进程、队列、文件系统 I/O，不属于 FX Graph。torch.compile 不会把 Dataset.__getitem__ 编译成 GPU kernel。

- CPU 侧瓶颈无法被 GPU 编译器消除
如果瓶颈是磁盘读慢、JPEG 解码慢、增强太重、collate 太复杂，那么即使模型前向再快，GPU 仍然会等数据。

- H2D 传输不在图优化范围内
.to(device)、pin_memory、CUDA Stream 调度属于运行时数据搬运。torch.compile 不会自动把 CPU→GPU 传输隐藏掉。

- 编译模式也救不了 I/O
mode="reduce-overhead" 主要借助 CUDA Graphs 减少 kernel 启动开销；mode="max-autotune" 主要优化 kernel 参数。 它们都不能替代 DataLoader 预取、pin_memory 或 GPU 端解码。
