## 对象存储不适合作为直接训练数据源
对象存储的特点: 无限容量，极低单价，可靠性强
- 协议层面
但是对象存储基于HTTP/REST API，每个对象读写都是一次完整的HTTP请求
不适合ai训练中的海量小文件场景，每次读取一个样本都要发起一次 HTTP 请求，协议开销远大于数据本身

- 元数据操作的灾难
对象存储采用扁平kv村年初元数据，没有真正的目录结构
遍历操作需要逐页扫描，性能与文件数量呈线性关系

- 随机读的惩罚

- 解决办法
冷热分离架构： 对象存储只用在冷数据底座，热数据高性能并行文件系统(Ceph,Lutre)或者缓存加速层(JuiceFS,Alluxio)

## JuiceFS与Alluxio 的设计
#面试-分布式系统-复习  什么是 JuiceFS、Alluxio、CubeFS 这类分布式文件系统？它们的核心抽象和缓存策略是什么？
#### JuiceFS
JuiceFS：元数据与数据分离，缓存的是 Block(数据，不是元数据)
架构上面是元数据引擎 + 对象存储的形式

文件存储形式： Chunk + Slice + Block
Chunk（64MB，仅逻辑概念），Slice（用于处理覆盖写/追加写），Block 是对象存储里真实存在的对象，磁盘缓存与分布式共享的基本单位

缓存形式: 内核PageCache + 客户端内存Buffer + 本地磁盘Block Cache + 分布式缓存组来存储数据
元数据不缓存，而是存在外面存储引擎中

#### Alluxio
Alluxio 新一代 DORA 架构去掉了集中式 Master。元数据和数据都落在 Worker 节点上

客户端通过一致性哈希定位文件对应的 Worker，直接与该 Worker 通信，无需经过中央节点。

Alluxio中文件内容被切成固定大小的 Page，缓存在 Worker 的本地存储里

缓存层次：Worker的PageStore用来缓存Page
而元数据是L1,L2两级缓存：L1存储在内存缓存中，L2存储在RocksDB中

## 元数据缓存与数据块缓存

| 维度    | 元数据缓存                      | 数据块缓存                    |
| ----- | -------------------------- | ------------------------ |
| 缓存对象  | 文件名、权限、目录结构、Chunk/Slice 映射 | 实际文件内容（4MB Block 或 Page） |
| 访问特征  | 小数据、高频访问、延迟敏感              | 大数据、带宽敏感、可预取             |
| 存储介质  | 内存为主，RocksDB 为辅            | 本地 NVMe SSD              |
| 淘汰策略  | TTL + LRU                  | LRU / LFU                |
| 一致性要求 | 强（目录操作需实时可见）               | 弱（训练数据通常只读）              |

## 缓存一致性在分布式训练中的妥协
分布式缓存的核心矛盾：性能与一致性不可兼得。CAP 定理告诉我们，在分区容错性（P）必选的前提下，一致性（C）和可用性（A）只能二选一。

#### JuiceFS的一致性模型
- 元数据缓存：
一个客户端修改并关闭文件后，其他客户端重新打开时能看到最新修改 => C
1 秒的内核元数据缓存 TTL，FUSE 会把一部分元数据缓存在内核里，平衡性能与一致性，但内核元数据缓存没有主动失效机制，只能等待过期。
- 本地数据缓存
一旦数据下载到本地缓存盘，一致性就依赖于缓存盘的可靠性。如果磁盘数据被篡改，客户端会读到错误数据。可通过 --verify-cache-checksum 策略校验缓存完整性
- 对象存储层
采用追加式写入方式，文件的任何修改都会生成新的Block，原有的Block保持不变，因此读取的时候，天然会得到最新数据。
失效的旧 Block 由回收站或碎片合并（Compaction）机制异步清理。

#### Alluxio的一致性模型
Alluxio 将底层存储系统（UFS，如 S3、HDFS）作为唯一可信数据源（Source of Truth），自身作为无状态加速层：
- Write-through：写入时立即持久化到 UFS，确保完全一致性，但写性能较低
- Write-back（Beta）：批量异步刷新到 UFS，写性能高，但存在数据丢失风险
- TTL 刷新：用户可配置缓存生存时间，短 TTL 保证强一致性，长 TTL 最大化只读场景性能


## 分布式训练中的妥协方案
在 AI 训练场景中，缓存一致性的处理往往做出以下妥协：
- 训练数据视为只读：绝大多数训练数据集在训练期间不会修改，因此可以激进地设置长 TTL 甚至永久缓存，完全避开一致性问题。这是最常见的"逃避式"解决方案。
- Checkpoint 接受短暂不一致：模型权重保存（Checkpoint）通常采用 write-through 策略确保不丢失，但多节点并发保存时可能产生短暂的不一致窗口。实践中通过保存后校验或原子重命名来兜底。
- 多节点缓存不同步：在分布式训练中，每个训练节点独立维护本地缓存，节点间不主动同步缓存内容。这导致节点 A 缓存的数据，节点 B 需要重新从远端拉取——牺牲了缓存共享的效率，换取了架构的简单性。JuiceFS 企业版的"分布式缓存组"是这一问题的进阶解法，但社区版不支持。
- 最终一致性兜底：对于非关键路径（如日志、中间结果），接受秒级甚至分钟级的最终一致性，通过 TTL 过期或定期全量刷新来保证" eventual correctness"。
