## DataLoader核心架构
DataLoader是一个生产者-消费者流水DataLoader是一个异步解耦的“生产者-消费者”系统，主进程是消费者，专注模型计算，多个Worker进程是生产者，负责从磁盘读取、解码、增强和打包数据
启动方式：
Linux：默认使用fork(),子进程采用写时复制策略，共享父进程内存，启动快
但是WIndows采用spawn(),所以同样的代码跨平台肯能会出问题
#### `_BaseDataLoaderIter._next_data() `的完整流程
```text
__next__()
  → _next_data()
    → _next_index()        # next(self._sampler_iter)
    → _dataset_fetcher.fetch(index)  # [dataset[i] for i in index] + collate_fn
    → pin_memory (可选)
    → 返回 batch
```

`_dataset_fetcher.fetch() `内部会先按 index 列表调用 `dataset[i]`，得到一组样本，再交给 collate_fn 组装成 batch。

多进程路径 `_MultiProcessingDataLoaderIter` 逻辑类似，只是 fetch 和 collate 发生在 worker 子进程里，结果通过队列送回主进程。

## Worker 进程的内存模型
num_workers 控制的是数据加载子进程数量

| 设置 | 行为 | 影响 |
|---|---|---|
| `0` | 主进程同步加载 | 简单、省内存，但 GPU 容易等数据 |
| `>0` | 每个 worker 是独立进程 | 可并行读盘、解码、增强 |
| `persistent_workers=True` | epoch 间不销毁 worker | 减少进程创建开销，但要注意内存泄漏 |

当设置 num_workers=8 时，PyTorch 会 fork 出 8 个子进程。每个子进程会获得一份 Dataset 对象的副本（通过 pickle 序列化传递）。
可能出现的问题: Dataset内存爆炸，数据加载需要懒惰化，不要在`__init__`中加载全部数据


## 多进程队列的序列化开销与共享内存优化
Worker加载数据之后，需要将数据传递回主进程

- 路径一：共享内存（Shared Memory）—— 默认首选
当数据较小时（默认小于 1MB），worker 会将数据写入 /dev/shm（共享内存）
主进程直接从共享内存读取，零拷贝、零序列化，效率最高
PyTorch 会自动管理共享内存的生命周期，无需手动调用 share_memory()

- 路径二：队列（Queue）—— 降级方案
当数据较大或共享内存不足时，会回退到 Queue
Queue 底层基于 Unix socket 或 Windows pipe，涉及 pickle 序列化 + 多次内存拷贝
对于大 batch 或复杂嵌套对象（如自定义类实例），序列化成本会显著上升，反而抵消并行收益

共享内存可能会耗尽！
/dev/shm是tmpfs文件系统，默认大小通常是物理内存的一半。在 Docker 容器中，默认共享内存仅 64MB。
如果Pytorch的Multiprocessing无法完美回收每个共享内存，可能会导致碎片化或者轻微泄漏

## prefetch_factor 的物理意义与内存膨胀风险
prefetch_factor 控制每个 worker 提前加载多少个 batch 到缓冲区。总预取 batch 数 = num_workers × prefetch_factor

假设一个 batch 加载耗时 50ms，GPU 计算耗时 30ms。如果 prefetch_factor=1，worker 加载完一个 batch 后就 idle 等待主进程取走；如果 prefetch_factor=2，worker 会继续加载下一个 batch，当主进程取走第一个 batch 时，第二个已经就绪——GPU 几乎不会等待数据。

但是会造成内存膨胀，训练到一半被系统 SIGKILL

调优原则：
从 prefetch_factor=2 开始尝试
如果 GPU 利用率低且内存充足，适当增大
如果内存紧张或出现 OOM，优先降低 prefetch_factor，其次降低 num_workers

## `collate_fn`: batch的组装逻辑
collate_fn 接收的是一个 batch 的样本列表
```python
[
  (img0, label0),
  (img1, label1),
  ...
]
```
默认的`default_collate`会将他们堆成`(images,lables)`

可能需要自定义：变长序列，目标检测，多模态输入等。

性能上要注意：如果 collate_fn 里做了大量 Python 层拼接、拷贝或 padding，worker CPU 
开销会上升，可能反过来拖慢数据供给。

## 配置


```python
train_loader = DataLoader(
    train_dataset,
    batch_size=batch_size,
    shuffle=True,
    num_workers=1,              # 从 1 开始，逐步增加
    pin_memory=True,            # GPU 训练必开
    persistent_workers=False,   # 先关，稳定后再开
    prefetch_factor=1,          # 非常关键，从 1 开始
    drop_last=True,
)
```
