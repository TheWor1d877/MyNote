GPU 的计算速度远快于数据准备速度
一次训练迭代：
读取磁盘 → 解码 → 预处理 → 传输到GPU → 前向传播 → 反向传播

如果串行执行，GPU会有大量空闲等待时间——等待CPU从磁盘读取，等待解码，数据拷贝等等内容

预取（Prefetching）的核心思想
在 GPU 计算当前 batch 的同时，CPU 后台线程已经开始准备下一个 batch 的数据。通过流水线并行，将数据准备与 GPU 计算重叠执行，隐藏 I/O 延迟。

```
时间轴：
GPU:   [计算 batch_0] [计算 batch_1] [计算 batch_2] ...
CPU:   [准备 batch_1] [准备 batch_2] [准备 batch_3] ...
       └──── 重叠执行 ────┘
```

## 预取算法
#### 顺序访问模式
场景：ImageNet 顺序训练、流式读取 WebDataset
数据访问地址递增，下一个batch的物理位置可以预测
策略：固定步长预取（Stride Prefetching），提前 N 个 batch 发起读取请求

#### 随机访问模式
典型场景：强化学习 replay buffer、需要 shuffle 的训练、CorgiPile 等局部 shuffle 策略。
数据访问地址离散分布，无法预测下一个 batch 的位置
关联预取（Correlation Prefetching）：基于历史访问记录建立地址关联表，预测可能访问的下一个地址
重要性感知预取（Importance-Informed Prefetching）：如 ImPACT 系统，根据样本重要性分数决定预取优先级，减少不重要数据的无效预取
但是准确率低下，可能大量数据都用不到

#### 混合访问模式
典型场景：多数据集混合训练、课程学习（Curriculum Learning）、持续学习中的 replay 策略。
部分数据顺序访问（如主数据集），部分数据随机访问（如 replay buffer）

分层预取：顺序数据用大步长预取，随机数据用小窗口缓存
自适应预取（Adaptive Prefetching）：根据运行时状态动态调整预取策略，如 MindSpore 的 Dataset AutoTune 持续检测瓶颈位置并调整并行度和预取窗口
GPU Warp 感知预取（WASP）：在 GPU 层面监控 warp 执行进度，为进度较慢的 warp 提前预取数据，实现 16.8% 的加速


## 预取线程与计算线程的调度隔离
预取的核心是异步——预取线程在后台工作，不能阻塞计算线程。但异步带来了调度冲突的风险
二者不能共享CPU核心，否则会导致上下文切换开销，以及缓存行污染

必须要线程亲和性：将预取线程跟计算线程绑定道不同的CPU黑奴，实现物理隔离
```python
import os
import threading

# 计算线程绑定到 CPU 0-7（高性能核心）
os.sched_setaffinity(0, set(range(8)))

# 预取线程绑定到 CPU 8-15（能效核心或独立 NUMA 节点）
prefetch_thread = threading.Thread(target=prefetch_worker)
prefetch_thread.start()
os.sched_setaffinity(prefetch_thread.ident, set(range(8, 16)))
```

## 三流并行：三流水线架构
据预取流（Prefetch Stream）：负责从磁盘/网络读取数据
计算流（Compute Stream）：负责前向/反向传播
通信流（Comm Stream）：负责梯度同步（all-reduce）

三者通过 CUDA Event 实现精准依赖，GPU 同时执行三个任务，利用率可从 60% 提升至 90%+。

## 缓存淘汰
| 策略 | 原理 | 适用场景 | 缺陷 |
|------|------|----------|------|
| LRU（最近最少使用） | 淘汰最久未被访问的数据 | 顺序/局部性强的访问 | "缓存污染"：一次性大批量读取会冲掉热点数据 |
| LFU（最不经常使用） | 淘汰访问频率最低的数据 | 长期稳定的热点访问 | 历史高频数据滞留，新热点难以进入 |
| W-TinyLFU | 滑动窗口频率统计 + admission window | 混合负载、突发热点 | 实现复杂，需要维护频率计数器 |
| ARC（自适应替换缓存） | 动态平衡 LRU 和 LFU，维护 ghost 链表 | 访问模式频繁变化 | 内存开销大，需要维护四个链表 |
| 重要性感知淘汰 | 根据样本重要性分数决定淘汰优先级 | 强化学习、课程学习 | 需要额外的重要性评分机制 |

内存水位控制
预取缓存不能无限增长，需要设置高水位（High Watermark）和低水位（Low Watermark）：
高水位（如 80%）：当缓存使用量超过此阈值时，停止预取，等待消费线程消耗数据
低水位（如 50%）：当缓存使用量低于此阈值时，恢复预取，填充缓存
紧急水位（如 95%）：触发强制淘汰，快速释放空间
