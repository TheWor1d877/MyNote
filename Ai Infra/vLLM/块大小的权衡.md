block_size的大小如何权衡，从四个方面考虑：
“前缀命中粒度”、“内部碎片”、“hash 计算成本”、“调度器组批边界”
#### 前缀命中粒度
prefix cache 按整块哈希复用，block_size 就是最小命中单位。
16 改 32 后，前缀长度是 16 倍数但不是 32 倍数的请求，变成无法命中，命中集合变了——这是语义变化，不是快慢。

#### 内部碎片
最后一块填不满的部分就是内部碎片，期望浪费约 block_size/2 个 token 槽位。16→32 是每请求平均多浪费约 8 个 token，纯内存利用率问题。

#### hash 计算成本
块数 ≈ 总 token / block_size，块大小减半块数翻倍，哈希次数和块表条目跟着翻倍。这部分是 CPU 管理路径开销，改大只是变快，不改语义。

#### 调度器组批边界
调度按 block 分配 KV、按块判断请求能不能进批，block_size 决定显存账本的精度。改大后账本变粗，会出现"剩点显存但不够一块"的浪费，某些请求能否进批的判定结果会变——语义相关。

#### 更改块大小之后的变化
行为变：前缀命中集合、组批结果、碎片分布与随之的抢占决策。
只是变慢/变快：哈希与块表查找开销、块表内存占用。

## block_size大小
vLLM 的 block size 是一个可配置参数，默认值在不同时期有变化：早期常用 16，后续有提案将默认值调整为 64，以降低每 block 的管理开销并匹配部分 attention backend 的偏好。
