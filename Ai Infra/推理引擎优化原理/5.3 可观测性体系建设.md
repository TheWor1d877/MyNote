推理服务上线之后出现问题,需要将所有层搜串联起来看
## 监控指标: DCGM Exporter 采集 GPU 底层数据
DCGM（Data Center GPU Manager）是 NVIDIA 提供的 GPU 管理和监控框架，DCGM Exporter 则负责把这些数据转换成 Prometheus 格式的指标暴露出来

在 K8s 集群里，通常以 DaemonSet 方式部署到每个 GPU 节点，监听 9400 端口。 推荐通过 NVIDIA GPU Operator 统一管理，避免手动维护版本兼容性。

| 指标名 | 含义 | 关注点 |
|---|---|---|
| `DCGM_FI_DEV_GPU_UTIL` | GPU 计算利用率（%） | 长期空闲说明资源浪费，持续满载需关注排队 |
| `DCGM_FI_DEV_FB_USED` | 显存使用量（MiB） | 趋势上升可能泄漏，接近上限会触发 OOM |
| `DCGM_FI_DEV_GPU_TEMP` | GPU 温度（℃） | 超过 85℃ 可能降频，超过 95℃ 可能关机 |
| `DCGM_FI_DEV_POWER_USAGE` | 功耗（W） | 接近功耗上限时会触发 throttling |
| `DCGM_FI_DEV_XID_ERRORS` | 最近 XID 错误码 | 非零值说明硬件或驱动异常 |
| `DCGM_FI_PROF_SM_ACTIVE` | SM 活跃率 | 低值 + 高 GPU util = 启动/同步开销大 |
| `DCGM_FI_PROF_DRAM_ACTIVE` | 显存带宽活跃率 | 低值 + 高 SM active = 计算受限；高值 + 低 SM active = 显存带宽受限 |

## 业务指标：vLLM 内置 metrics 端点
LLM 在 /metrics 端点暴露了丰富的 Prometheus 指标，启动时通过 --metrics-port 指定监听端口即可。 这些指标按作用可以分成三类：

调度状态指标
vllm:num_requests_running：当前在 GPU 上运行的请求数；
vllm:num_requests_waiting：排队等待的请求数；
vllm:num_requests_swapped：被换出到 CPU 的请求数（V1 引擎已弃用）；
vllm:gpu_cache_usage_perc：GPU KV Cache 使用率，1.0 表示 100%。

延迟指标
vllm:time_to_first_token_seconds（TTFT）：首 Token 延迟，包含排队 + Prefill；
vllm:time_per_output_token_seconds（TPOT）：Token 间延迟，反映 Decode 速度；
vllm:e2e_request_latency_seconds：端到端请求延迟；
vllm:request_queue_time_seconds：纯排队耗时；
vllm:request_prefill_time_seconds / vllm:request_decode_time_seconds：

Prefill/Decode 阶段耗时。
吞吐与缓存指标
vllm:prompt_tokens_total / vllm:generation_tokens_total：累计输入/输出 Token 数；
vllm:num_preemptions_total：抢占次数，频繁抢占说明显存紧张；
vllm:gpu_prefix_cache_hits / vllm:gpu_prefix_cache_queries：前缀缓存命中情况（V1 引擎）。


Grafana 里建议建三个面板：硬件层（DCGM）、引擎层（vLLM 调度 + 延迟）、业务层（QPS、Token 吞吐、错误率）。三层放在一起看，定位问题会快很多。


## 全链路追踪：P99 延迟飙升时的定位方法
指标告诉你"慢了"，追踪告诉你"慢在哪"。
vLLM 从 0.6.x 开始支持 OpenTelemetry tracing，可以按请求生成完整的调用链。 一条请求的 Span 树通常长这样：
```text
llm_request (入口 Span)
  ├─ wait（排队等待）
  ├─ prefill（处理 prompt，生成第一个 token）
  ├─ kv_transfer（多卡/多节点 KV 传输）
  └─ decode（逐 token 生成）
      └─ [迭代 N 次...]
```

采集粒度可以配置：
Level 0：只有入口 Span，开销最小；
Level 1：额外产生 wait、prefill、decode、kv_transfer 阶段子 Span，日常推荐；
Level 2：再按调度迭代逐次记录 Span Event，采集 token 级明细，排查问题时临时开启。

##  自定义指标与 KEDA 联动：秒级弹性伸缩
KEDA（Kubernetes Event-driven Autoscaler）是一个基于 Kubernetes 的事件驱动自动扩缩器。它的核心作用是根据外部事件源（如消息队列长度、数据库指标等）的负载情况，自动调整 Kubernetes 中工作负载的副本数量，甚至能够将副本数缩减到零
Kubernetes 原生的 HPA（Horizontal Pod Autoscaler）主要依赖 CPU、内存等资源指标来扩缩容。但在很多场景下，应用的压力并非来自资源消耗，而是来自待处理的事件数量。例如：
- 消息队列里堆积了多少条未处理的消息
- 数据库中有多少条待执行的查询
- 监控系统中某个业务指标是否超标
这些情况下，即使 CPU 使用率不高，应用也可能需要扩容来加快事件处理速度。KEDA 就是用来填补这个空白的。

- 方案一: Prometheus Adapter + KEDA
Prometheus 采集 vLLM 指标 → Prometheus Adapter 暴露为 Custom Metrics API → KEDA 读取并驱动 HPA
```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-scaler
spec:
  scaleTargetRef:
    name: vllm-inference
  minReplicaCount: 2
  maxReplicaCount: 10
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus:9090
      metricName: vllm_num_requests_waiting
      threshold: "20"
      query: |
        sum(vllm:num_requests_waiting) by (deployment)
```

- 方案二: KEDA External Scaler 直连
写一个 External Scaler，直接连 vLLM Pod 的 /metrics 端点读取指标，通过 gRPC 协议上报给 KEDA。好处是链路更短，延迟更低，可以压到亚秒级。
