## 资源配额：Requests/Limits 的严格匹配
CPU 和内存可以设置 requests 小于 limits，让 Pod 在空闲时“借用”更多资源。GPU 不行。
Kubernetes 把 GPU 当作扩展资源，它无法像 CPU 那样做时间片节流，也无法像内存那样通过 cgroup 精确限制显存使用。所以 GPU 资源只允许在 limits 里声明，并且 requests 必须等于 limits/
对于在线推理服务，建议把 CPU 和内存的 requests 也设成等于 limits，让 Pod 拿到 Guaranteed QoS 等级。这样在节点资源紧张时，它会被最后驱逐。
如果用了 HAMi 这类虚拟化方案，显存和算力的细粒度限制由 HAMi 在容器内通过 vCUDA 拦截执行，K8s 层面的` nvidia.com/gpu: 1` 仍然遵循上述规则。

## 故障隔离：ECC、Xid 与 GPU 自动隔离
GPU 硬件故障在生产环境并不罕见。显存位翻转、NVLink 链路异常、过热降频、驱动崩溃，都可能导致推理结果出错或服务中断。
NVIDIA GPU 驱动会通过 NVRM 事件机制把错误码写入 /var/log/messages 或 /var/log/syslog，这些错误码叫 XID。 常见的有：
- XID 31/43/48：显存 ECC 错误；
- XID 79：GPU 掉卡，通常需要更换硬件；
- XID 32/64：驱动或固件异常。
ECC 错误分两类：单比特错误可以自动纠正，双比特错误不可纠正，会直接触发 Xid 报错。
生产集群里，靠人工盯日志不现实。主流做法是用 Node Problem Detector（NPD） 监控节点日志，检测到 Xid 错误后上报为 Kubernetes Event 或 Node Condition，再由 Device Plugin 把异常 GPU 标记为不可调度。

## 共享内存： /dev/shm默认64MB
对于AI推理场景远远不够
常见场景：
- Pytorch DataLoader使用多进程加载数据，进程之间通过共享内存传递Batch数据
- NCCL多卡通信在多卡推理或者训练的好时候需要优先使用共享内存做低延迟传输
- 大模型推理引擎在多进程部署的过程中需要使用共享内存

解决方案很简单，用 emptyDir 卷覆盖 /dev/shm：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-inference
spec:
  template:
    spec:
      containers:
      - name: inference
        image: llm-service:latest
        volumeMounts:
        - name: dshm
          mountPath: /dev/shm
      volumes:
      - name: dshm
        emptyDir:
          medium: Memory
          sizeLimit: 2Gi
```

sizeLimit的大小调整：

| 场景 | 推荐大小 |
|---|---|
| 普通推理服务 | 256MB ~ 1GB |
| 多进程 DataLoader | 1GB ~ 2GB |
| 多卡 NCCL 通信 | 2GB ~ 4GB |
| 32B+ 大模型多卡推理 | 4GB+ |

emptyDir 的内存从 Pod 申请的 memory 里扣除，不会额外增加节点内存使用。
如果写入量超过 sizeLimit，Pod 会被 OOM 驱逐
