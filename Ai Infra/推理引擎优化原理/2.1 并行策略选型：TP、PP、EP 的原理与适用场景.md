当模型参数规模突破单张 GPU 的显存上限时（如 Llama-3-70B 需要约 140GB FP16 显存，而 A100 单卡仅 80GB），分布式推理成为唯一选择
但多卡协同并非简单地"把模型拆开"——不同的切分方式会带来截然不同的通信开销和硬件利用率。本节将从数学原理出发，剖析三种主流并行策略的本质差异。

## 分布式采样
DistributedSampler 的作用是把完整数据集的索引按 rank 切分，保证每个 rank 只读到不重叠的子集。
```python
indices = list(range(len(dataset)))
if shuffle:
    random.shuffle(indices)
indices = indices[rank:len(indices):world_size]
```

set_epoch(epoch) 必须调用。如果不设置，每个 epoch 的 shuffle 结果相同，数据顺序不会变化。
drop_last 控制尾部处理。数据集大小不能被 world_size 整除时，多余数据要么丢弃，要么补齐，保证各 rank 数据量一致。
shuffle 参数在 DataLoader 中必须设为 False。因为 shuffle 已经由 DistributedSampler 完成，DataLoader 再 shuffle 会破坏分片逻辑。
自定义采样器。如果数据存在类别不平衡，可以继承 DistributedSampler 实现类别平衡采样，但要保持分布式分割逻辑不变。

## TP: 张量并行
矩阵切分的数学原理、All-Reduce 通信模式、适合层内并行的场景
矩阵乘法可以拆分到多个设备上面进行并行计算，然后通过简单的加法进行合并

#### 列并行
如果我们将 W 按列切分为 n 份：`W = [W₁, W₂, ..., Wₙ]`，同时 X 保持不变
```text
Y = XW = X[W₁, W₂, ..., Wₙ] = [XW₁, XW₂, ..., XWₙ]
```
最后将所有的Y拼接起来形成最终结果

但问题在于，Transformer 中并非所有运算都能如此"完美切分"。以自注意力机制中的 QKV 投影为例，Q、K、V 三个矩阵需要同时计算，且后续的 Attention 打分涉及 Q 和 K 的点积。如果 Q 和 K 被切分到不同 GPU 上，点积就无法直接进行
#### 行并行
如果 W 按行切分为 n 份：`W = [W₁ᵀ, W₂ᵀ, ..., Wₙᵀ]ᵀ`，那么 Y = XW 可以写成
```text
Y = XW₁ + XW₂ + ... + XWₙ
```
每个 GPU 计算 Yᵢ = XWᵢ，最后将所有 Yᵢ 相加得到最终结果。注意这里是"求和"而非"拼接"，这与列并行形成互补。

## PP: 流水线并行
PP在层间切分模型，将连续的Transformer层分配给不同的GPU
数据流像一个流水线：输入从 GPU0 进入，经过 8 层计算后传递给 GPU1，再经过 8 层后传递给 GPU2，依此类推，最终从 GPU3 输出GPU0 负责层 0-7，GPU1 负责层 8-15，GPU2 负责层 16-23，GPU3 负责层 24-31。

问题： Bubble
```text
朴素流水线调度示意（PP=4，4 个 Micro-batch）：

时间步 →
GPU0: [F0][F1][F2][F3][  ][  ][  ][  ]  ← F=Forward
GPU1: [  ][F0][F1][F2][F3][  ][  ][  ]
GPU2: [  ][  ][F0][F1][F2][F3][  ][  ]
GPU3: [  ][  ][  ][F0][F1][F2][F3][  ]
GPU0: [  ][  ][  ][  ][B3][B2][B1][B0]  ← B=Backward（训练时）
GPU1: [  ][  ][  ][  ][  ][B3][B2][B1]
GPU2: [  ][  ][  ][  ][  ][  ][B3][B2]
GPU3: [  ][  ][  ][  ][  ][  ][  ][B3]

空闲气泡占比 = (3+3) / (8+8) = 37.5%
```
在推理场景中，虽然没有 Backward 阶段，但启动阶段的空闲依然存在。如果 PP=8，启动气泡将占据 87.5% 的时间——这显然不可接受

需要使用1F1B策略消除气泡

## EP: 专家并行
将FFN层替换成多个专家，每个专家是一个独立的FFN子网络
对于每个Token，通过路由器动态选择（路由器计算专家权重）Top-K个专家进行处理，最后加权输出

在EP中不同的专家分配到不同的GPU上面
每张 GPU 只存储并计算 1 个专家

#### 通信方式
Dispatch（分发）：每个 GPU 将自己持有的 Token 按照目标专家所在的 GPU 进行分组，然后发送给对应 GPU。
Expert 计算：每个 GPU 对收到的 Token 执行其负责的专家计算。
Combine（合并）：计算结果按照原始 Token 顺序发回给持有该 Token 的 GPU。

这个过程涉及到所有GPU向GPU传递信息，即All-to-All通信

#### 缺点
MoE 的致命弱点是负载不均衡——如果路由器将大量 Token 路由到少数几个专家，这些专家所在的 GPU 将成为瓶颈，其他 GPU 则处于空闲状态

解决方案：
Auxiliary Loss（辅助损失）：在训练时加入负载均衡损失，鼓励路由器均匀分配 Token 到各专家。
Expert Capacity（专家容量）：为每个专家设置处理 Token 的上限，超出容量的 Token 被丢弃或路由到次优专家。
Dropless 路由：DeepSeek-V3 提出的无丢弃路由策略，通过动态调整路由权重保证所有 Token 都被处理

## 总结： DP,TP,PP,EP之间的关系
DP 切数据，每张卡存完整模型
TP 切层内矩阵，每张卡存部分参数
PP 切层 每张卡存储部分层
EP 切FFN 每张卡存储部分专家

这四种并行策略是 正交的，可以同时用
DP 维度：数据批次被切成多份。
TP 维度：每一层的参数矩阵被切成多份。
PP 维度：模型的层被切成多段。
EP 维度：MoE 的专家被切成多组。

```
总 GPU 数 = DP_size × TP_size × PP_size × EP_size
```

选择顺序：先看单卡放不放得下 → 放不下用 PP+TP → 是 MoE 加 EP → 有余力加 DP通信代价：TP > EP > DP > PP，所以 TP/EP 尽量放节点内，PP/DP 可跨节点
