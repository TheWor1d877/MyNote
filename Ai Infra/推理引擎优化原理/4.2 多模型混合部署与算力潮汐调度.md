多个模型挤在同一张卡上，谁先算、谁让路、谁该被限制？这块就是混部和潮汐调度要解决的。
## 混部干扰隔离:显存带宽争抢与QoS保障
多模型共享GPU的时候，最大的干扰是显存带宽，一般不是算力
GPU 算力可以分时复用，但 HBM 带宽是共享物理通道
带宽不够则会让所有任务一起变慢

常见的QoS分级思路：

| 等级         | 任务类型           | 保障方式             |
| ---------- | -------------- | ---------------- |
| Guaranteed | 在线推理、Agent 主链路 | 独占显存配额，算力保底，不被抢占 |
| Burstable  | 低优先级推理、批处理     | 可借用空闲算力，资源紧张时被限速 |
| BestEffort | 离线训练、评测、数据清洗   | 只能使用剩余资源，随时可能被驱逐 |

对延迟敏感的任务设置更高优先级
用算力配额限制低优先级任务的 GPU 时间占比

如果集群里有 MIG，还可以把在线推理放到独立 MIG 实例上，离线任务放到另一个实例，物理层面减少干扰。

## 潮汐算力调度
GPU 集群的负载通常有明显潮汐：白天在线推理请求多，夜间空闲。离线任务如果也单独占卡，白天卡闲置、晚上又不够用，整体利用率会很低。

K8s 里可以用 PriorityClass + 抢占 来做这件事。
```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: online-inference
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: offline-batch
value: 100000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
```
在线推理中的Pod使用更高优先级，离线任务采用低优先级
可以配合Volcano Kueue这类批处理调度器

实用策略：
离线任务只申请requests，不设置过高的limits,尽量使用空闲资源
在线任务一旦需要扩容就会将低优先级别的任务逐步腾退

## 干扰检测与动态降权
静态配额能解决大部分问题，但有些干扰是动态出现的。比如某个离线任务突然启动大 batch 推理，或者某个实验脚本疯狂申请显存，都会影响同卡上的在线服务。

可以用 DCGM-Exporter + Prometheus + Grafana 做实时监控

当检测到某个 Pod 出现以下行为时，可以判定为“噪声邻居”：
- 显存带宽长期接近上限；
- GPU 利用率持续过高，挤压同卡其他任务；
- 频繁触发 CUDA OOM；
- 导致同节点在线推理 TPOT 明显升高。

处置方式可以分层：
- 限速：通过 cgroups 或 HAMi 降低其算力配额；
- 降权：把它标记为低优先级，资源紧张时优先驱逐；
- 迁移：调度器把它重新排到负载较低的节点；
- 驱逐：严重干扰时直接杀掉 Pod，保护在线 SLA。
