## FlashAttention原理
改变数据的搬运方式，不改变Attention的数学公式
标准 Attention 实现会将 `N` * `N` 的注意力矩阵完整写入 HBM，导致显存复杂度为 
O(n^2)
显存相对于SRAM来说速度很慢
FlashAttention 通过三个关键技术避免这一瓶颈：
#### 分块计算
不让中间结果落地到HBM上面，而是都在SRAM中完成

传统Attention：
```text
第1步：从 HBM 读 Q、K → 算 S = QK^T → 把 S 写回 HBM
第2步：从 HBM 读 S → 算 P = softmax(S) → 把 P 写回 HBM
第3步：从 HBM 读 P、V → 算 O = PV → 把 O 写回 HBM
```
瓶颈在于`S`与`P`的反复读写，时间复杂度O(n^2)

FlashAttention的做法：
将`QKV`都切开：
```text
Q: [Q₁, Q₂, Q₃, ..., Q_{T_r}]
K: [K₁, K₂, K₃, ..., K_{T_c}]
V: [V₁, V₂, V₃, ..., V_{T_c}]
```

```Cpp
for i in Q_blocks:                        // 外层循环：每次处理一个 Q 块（大小 B）
    m, l, O = -inf, 0, 0                  // m=已见分数最大值, l=指数和, O=输出累加器
    for j in KV_blocks:                   // 内层循环：遍历所有 K/V 块
        S = Q_i · K_j^T                   // 算当前 Q 块与这个 K 块的分数矩阵（B×B，只在快速缓存里）
        mNew = max(m, rowmax(S))          // 把本块行最大值并入全局最大值，得到新的全局最大值
        alpha = exp(m - mNew)             // 旧累积量基于旧最大值 m，现在换成 mNew，要乘这个修正因子
        P = exp(S - mNew)                 // 本块分数减新最大值后取指数，得到本块的 softmax 分子
        l = alpha * l + rowsum(P)         // 更新归一化分母：旧的先修正，再加上本块的指数和
        O = alpha * O + P · V_j           // 更新输出：旧的先修正，再加上本块 P 对 V 的加权和
        m = mNew                          // 最大值更新为本轮的新值，供下一块用
    O = O / l                             // 所有 K/V 块遍历完，l 是完整分母，统一归一化
    write O to HBM                        // 只把最终结果写回慢速显存
```
###### 优点：
- 从 HBM 只读取 `Q`、`K`、`V`（一次），只写入最终结果 `O`（一次）。
- 中间的 `S`（分数矩阵）和 `P`（指数化分数矩阵）只在 SRAM 里以小块形式产生和用完，从不写回 HBM。
- 因此 HBM 的读写量大幅下降，瓶颈从内存带宽转回计算本身。

###### 时间复杂度：
- 前向的时间复杂度为 O(N² · d / √M)，其中 `N` 是序列长度，`d` 是头维度，`M` 是 SRAM 容量（以元素个数计）。
- 直观理解：把块大小取到 `√M`，使每块 `S`/`P` 能塞进 SRAM，这样 HBM 访问次数被压到最低；总计算量仍是 O(N²·d)，但慢速内存的搬运量降到 O(N²·d / √M) 量级。
- 当 SRAM 足够大（`M` 随硬件增大）时，这个因子变小，实际加速越明显；这也是为什么分块大小 `B` 通常取和 `√M` 同量级的值。

#### 在线Softmax
分块计算的时候，每个块只能看到部分Key
为了保证最后的Softmax结果正确,使用在线Softmax
```text
对每个块 j，计算局部最大值 m_j 和局部指数和 l_j：
  m_j = max(S_j)          // 当前块的行最大值
  l_j = sum(exp(S_j - m_j))  // 当前块的归一化分母

全局 Softmax 通过递推更新：
  m_new = max(m_old, m_j)
  l_new = l_old · exp(m_old - m_new) + l_j · exp(m_j - m_new)
  O_new = (l_old · O_old · exp(m_old - m_new) + P_j · V_j · exp(m_j - m_new)) / l_new
```
这样只需一次前向遍历，无需存储完整的 `n`×`n` 矩阵

#### 重计算
反向传播计算梯度时，需要用到前向里的指数化分数矩阵 `P`（即 `exp(S - mNew)`，`N`×`N` 大小）。FlashAttention 选择不在前向时把这个矩阵存下来，而是在反向时用 `Q`、`K` 和保存的少量统计量（`m`、`l`、`O`）重新算一遍 `P`。因为重算发生在访问极快的 SRAM 里，多算一遍的代价远小于把 `N`×`N` 矩阵写进再读出慢速 HBM 的代价。这就是用额外计算换内存带宽的典型做法。

## CUDA  Graph
#### 问题
一次 `model.forward()` 在 GPU 上需要上千个kernel依次启动
对于每个kernel的启动流程：
1. Python 层调用 → 2. C++ 前端 → 3. CUDA Runtime（`cudaLaunchKernel`）→ 4. GPU 驱动提交命令

单个kernel可能启动只需要几微秒但是启动就需要10~50微秒
CPU 准备一个 kernel 的时间，比 GPU 执行它还长

#### CUDA Graph介绍
把"一串 kernel 的启动动作"录下来做成一张图，之后整张图一次提交，不再逐个 kernel 走 CPU 调度。
整张图走一遍CPU-GPU交互，GPU 按图里的依赖自己跑，不需要CPU调度
launch 开销从"每个 kernel 付一次"变成"整张图付一次"

#### 工作原理
Capture（录制）阶段：用真实数据正常跑一次计算，但把这次跑在某个 stream 上的所有 GPU 操作（kernel launch、memcpy、依赖关系）记录下来，存成一张图。这次跑是真的在算，图是副产品。
Replay（重放）阶段：之后不再逐个 launch，而是 `cudaGraphLaunch` 一次，把整张图提交给 GPU。GPU 按图里记录的顺序和依赖关系自己执行，CPU 不再参与每个 kernel 的调度。

先Capture一次，然后反复replay

#### 限制
图必须是静态的
CUDA Graph 录下来的是固定形状、固定地址的操作序列。这意味着：
- 输入 tensor 的 shape 必须固定。shape 一变，图就对不上，得重新 capture。
- kernel 参数里的地址要固定。通常配合预分配固定大小的显存池使用。

## vLLM使用CUDA Graph解决动态长度问题
vLLM自回归解码阶段(decode)正好是普通执行方式最致命的短板： CPU启动开销

每生成一个 token，模型里所有层、所有算子都要被触发一遍。一个大模型 decode 一步，可能涉及几百上千个 kernel 启动
decode 是反复执行、形状相对稳定、kernel 数量极多且每个都很小的场景

CUDA Graph 录制时，会把输入 tensor 的地址、shape、内存布局全部固化为图的静态参数。
replay 时只是往这些固定地址里填新数据，图的结构本身不能变
但是vLLM的decode是动态的： Batch size变化，单个seq的KVCache长度在变化，PagedAttention 的 `block_table` 在变

## vLLM解决办法
#### 图池 + Batch Size 分桶 + Padding：解决 Batch size变化
不追求一张图适配所有的batch，而是预先构建一个离散的图池

vLLM 预先定义一组候选 batch size 档位，在启动时为每个档位各 capture 一张完整的 decode 前向图，存进图池
运行时按实际 batch size 找最接近的档位去 replay。
一个batch中空缺的地方用padding token填充
padding算是对算力的浪费，但这个浪费换来的是每一步 CPU launch 从“几百次”降到“一次 replay

这个列表不是均匀的：小 batch（1、2、4）覆盖得密，因为小 batch 时 CPU launch 开销占比最高，需要精细匹配；大 batch 时 GPU 计算占比上升，档位稀疏一点影响不大。

###### 运行时具体逻辑：
实际 batch size 为 `B`：
1. 找档位：在图池列表里找最小的 ≥ `B` 的档位，用那张图 replay。
2. Padding 对齐：把 `B` 个真实请求的输入张量拷到图输入槽位的前 `B` 行，剩下的槽位用 padding token 填充。这些 padding token 的 `slot_mapping` 指向 dummy block，attention 结果会被忽略，不参与实际输出。
3. 超出图池上限（比如 `B > max_capture_size`）：回退到普通 eager 执行。正确性不受影响，只是失去图加速，每一步的 CPU launch 开销重新出现

#### Block Table 作为图的可变输入：解决 `block_table` 在变或者 seq 长度在变的一种方法(可变输入)
把 `block_table` 和 `slot_mapping` 声明为图的“可变输入缓冲区

图录制时不固化 `block_table` 的具体值，而是给它留一个固定地址的输入槽位。

每次 replay 前，CPU执行：
1. 将`block_table`内容更新： 把当前 decode step 最新的逻辑 block → 物理 block 映射写进那个固定槽位
2. 重新计算 `slot_mapping`：`slot_mapping` 建立“第 `i` 个 query token 需要访问物理地址 `addr` 处的 KV”的映射。图的结构（kernel 序列、grid 维度）完全不变，但图依赖的数据每步可以刷新。

启发： 我们对于CUDA Graph中可以将所有参数都从原来写死的标量/指针，改成固定地址的buffer内容，kernel还是从原来的位置读取，但是每步读到的内容可以 通过memcpy刷新

###### `slot_mapping`与`block_table`的区别
`slot_mapping` 是“写”的地址，服务于当前正在生成的 token的KV向量；`block_table`是“读”的索引，服务于 attention 去翻阅整段历史 KV
每个请求都会维护自己的`slot_mapping`与`block_table`
decode 的 attention 需要读取历史，而 `slot_mapping` 只覆盖了当前这一步，所以需要`block_table`

`slot_mapping`本身通常就是利用 `block_table`计算出来的一个“快捷方式”

###### Full CUDA Graph
Full CUDA Graph 把“图结构”和“图输入数据”彻底解耦了。 Block table 的内容属于“输入数据”，不属于“图结构”。录制时只录“去这个槽位读数据”这个动作，不录“数据具体是什么”。


#### Piecewise CUDA Graph：解决单个seq的KVCache长度在变化的一种方法(不进图)
实际 serving 中不只有“纯 decode batch”。Chunked prefill + decode 混合时，attention 部分的动态性更强：prefill 的 query 长度、decode 的 KV 长度、`block_table` 的变动同时存在，整图 capture 的约束很难满足

做法 ： 在`attention`算子处将计算图切开，只capture，不依赖动态`block_table`的部分

```text
Full Graph 录制范围：
  [QKV 投影] → [attention（读 block table）] → [输出投影] → [FFN/MoE] → 下一层

Piecewise Graph 录制范围：
  [attention 算子]  ← 留在图外，eager 执行
  [QKV 投影]        ← capture 进子图
  [输出投影 + FFN/MoE] ← capture 进子图
```
eager: 动态计算，不走预制的图

具体来说，依赖 `block_table` 的 attention 算子（包括 `slot_mapping` 计算、`block_table` 查找、`QKV` 加载、`Q·Kᵀ`、`SoftMax`、`A·V`）全部留在图外走 eager

而`QKV` 投影、输出投影、FFN/MoE 这些“输入张量形状固定、与 `block_table` 内容无关”的密集计算被分段 capture 成 CUDA Graph

###### vLLM的混合策略
vLLM V1 默认的 `FULL_AND_PIECEWISE` 模式下，两条路径互补使用：

| 场景                                             | 走哪条路径                                           |
| ---------------------------------------------- | ----------------------------------------------- |
| 纯 decode batch                             | Full CUDA Graph（整图，`block_table` 作可变输入）       |
| 混合 batch（prefill+decode / chunked prefill） | Piecewise CUDA Graph（attention eager，其余分段图） |

#### 图池的“上限”管理与回退策略
图池不是无限大的。每个 capture 的图都要占用显存,capture 本身也有启动时间成本。

 vLLM 不会盲目 capture 几百张图，而是用有限的档位覆盖主要场景，超出范围的 batch 直接回退 eager

回退场景：
- Batch size 超出图池最大档位
- Attention backend 的 `block_table` 格式变化：如量化模式的改变，物理布局直接变化了
- Speculative decoding 的 `num_spec_tokens` 变化：导致 decode query length 改变，图结构不匹配。
