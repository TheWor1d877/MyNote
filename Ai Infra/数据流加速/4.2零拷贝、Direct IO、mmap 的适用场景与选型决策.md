如何减少数据本身的搬运
## 传统IO的特点：
4次拷贝 + 4次上下文切换:
磁盘 通过DMA 进入内核Page Cache 通过CPU 进入用户缓冲区
用户缓冲区 通过CPU进入 Socket缓冲区 通过DMA 进入网卡进行发送

read 与Write 进入/退出内核态都需要切换上下文
在高并发场景下，这些"搬运工作"可能占用超过 30% 的 CPU 资源，而 CPU 真正该做的是业务逻辑计算

## mmap
原理：内存映射文件
让内核 Page Cache 和用户空间共享同一块物理内存，消除内核用户的 CPU 拷贝
减少从内核Page Cache到用户缓冲区的拷贝

```text
磁盘 → [DMA] → 内核 Page Cache ←[mmap 映射]→ 用户虚拟地址
用户虚拟地址 → [CPU] → Socket 缓冲区 → [DMA] → 网卡
```

mmap 触发的是缺页异常（Page Fault）机制——首次访问映射地址时，内核才真正从磁盘加载数据到 Page Cache。 这意味着 mmap 是懒加载的，不会一次性把整个文件读入内存。

典型用途：
多个进程共享同一文件内容（共享内存式读写）
大文件随机访问、数据库的 Buffer Pool 实现
加载动态库、可执行文件
## Direct IO
打开文件时带 O_DIRECT 标志，读写时数据不经过内核页缓存，直接在用户缓冲区和磁盘之间走 DMA
彻底绕过 Page Cache，用户缓冲区直接和磁盘/网卡通过 DMA 通信
核心思想：彻底绕过 Page Cache，用户缓冲区直接和磁盘/网卡通过 DMA 通信。

```text
磁盘 → [DMA] → 用户缓冲区（直接，不经过 Page Cache）
```

- 用户缓冲区必须内存对齐
- 一个read/write对应一个IO请求，不做写合并
- 应用程序需要自己管理缓存

典型用途：
数据库（MySQL InnoDB、Oracle 等）自己管理缓存，不想让 OS 再缓存一遍
对缓存一致性要求高、或数据量巨大不适合走 page cache 的场景
## Zero-Copy
 一个设计目标/技术统称，不是某个具体 API。目标是让数据在传输过程中尽量少拷贝、少经过 CPU。
 最经典的场景：把文件发送到网络（比如 Web 服务器发静态文件）。

零拷贝方式（sendfile()）：
```text
磁盘 → 页缓存 → 网卡
       (DMA)   (DMA，配合 SG-DMA)
```
数据根本不进用户空间，2 次拷贝且都由 DMA 完成，CPU 不参与搬运。

## 对比
| 维度 | mmap | Direct I/O | 零拷贝（sendfile+SG-DMA） |
|------|------|-----------|------------------------|
| Page Cache | 依赖 | 绕过 | 依赖 |
| CPU 拷贝次数 | 1 次 | 0 次 | 0 次 |
| 上下文切换 | 4 次 | 2 次 | 2 次 |
| 内存对齐要求 | 否 | 是（512B/4KB） | 否 |
| 数据可修改 | 是 | 是 | 否（内核空间流转） |
| 适用文件大小 | 大文件更优 | 大文件更优 | 大文件更优 |
| 典型应用 | 数据库、消息队列索引 | 数据库、分布式存储 | Nginx、Kafka 数据文件 |
