**算力账**：prefill 的注意力计算量随上下文长度近似平方增长。一条 4000 token 的请求，注意力交互次数在千万量级；一条 400 token 的请求，在十万量级，差两个数量级。decode 每步只算一个新 token，但注意力要对整个 context 做，单步 O(n)，累计到生成 m 个 token 是 O(n·m)。

**存储账**：KV Cache 是线性的，每 token 一份固定大小的 K/V 向量，跟上下文多长无关。BF16 下 Qwen3-8B 每 token 约 144 KiB，一条 2K token 的请求占约 288 MB。单位是 MB 级。注意 KV Cache 大小取决于 KV 头数 × 层数，不跟总参数量挂钩——Qwen3-30B-A3B 的每 token KV 反而比 8B 小。

**缓存账**：缓存的块留着不淘汰，占的是本可以服务新请求的显存和带宽。这是机会成本，不直接体现在账单上，但真实存在。

## 错配的结构：收入线性，成本超线性
固定 token 单价下，收入 = 单价 × token 数，线性。

但是成本： 
算力成本随上下文长度超线性增长，prefill 是平方项，decode 累计也是超线性；
显存成本线性增长，但显存是有限资源，占用就要付出相应的机会成本；
缓存保留成本不在账单上，但占用的容量本可以接新请求。

## 用户视角与企业视角
用户天然希望缓存尽量不淘汰——缓存留着，下次命中就不用重算，API 费用更低
固定单价下，长上下文“单位算力更便宜”。每 token 单价不变，但长上下文实际消耗的算力更多，用户觉得自己赚了。


缓存对企业是库存成本，留着占显存、占带宽，影响单位时间能服务的请求数。企业的诉求也是合理的。
收入线性增长，电力和 GPU 时间超线性增长。长请求毛利率被压缩，极端情况下“花 10 倍电力只挣一倍的钱”，长请求在补贴短请求，超过阈值可能亏本

## 企业不能限制长请求
第一，长上下文是真实需求。RAG、长文档分析、多轮对话，这些场景用户就是要长上下文，限制长度等于拒绝市场。

第二，加价如果拍脑袋，会扭曲调度。如果只是简单按长度线性加价，长请求可能被过度抑制，而实际成本是平方的，线性加价仍然低估了超长请求的真实成本。

所以解法不是“限制”或“简单加价”，是让价格和调度反映真实成本结构。
