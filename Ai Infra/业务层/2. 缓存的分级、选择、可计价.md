用户想要“别删我的缓存”，企业想要“别占我的资源”，这个矛盾怎么在业务上解，而不是靠引擎层一刀切。

“所有缓存都留着”和“所有缓存都不留”都是错的。
前者让企业成本失控，缓存占着显存和带宽，本可以服务新请求的容量被锁死。后者让用户命中率归零，重算成本转嫁回 GPU，TTFT 恶化，吞吐下降——企业其实也亏，只是亏在另一个地方。

## 缓存场景
不是所有缓存都值得留。 缓存价值高度依赖场景，不同场景下的缓存利用率不同
batch 处理场景的缓存命中率能到 92%，因为所有请求共享完全相同的 system prompt；
RAG 最低，约 45%，因为每次检索的文档片段不同。

缓存策略必须区分场景，全局一套 LRU 对所有 workload 都不公平。 高复用前缀和一次性前缀不能混在同一个池子里

## 三层缓存：按照职责划分层级
显存层：放正在被引用的块，以及命中概率最高的热前缀。这一层没得省，attention 要直接消费 KV，放在别处就得搬回来，延迟不可接受。

CPU 内存层：放刚被释放但短期内可能复用的块。vLLM 的分层 offloading 设计里，所有 KV 数据都经过 host memory 中转，host 层是一个真正的 LRU/ARC 缓存，不是临时暂存区。命中时直接从 host 加载，成本比显存低一个数量级，延迟在可接受范围内。关键设计是：从 GPU 到 host 的复制是快速的 PCIe 传输，host 复制完成后 GPU 显存立刻释放，后续的存储写入、网络传输、RDMA 都不再占用显存

磁盘/远端层：放冷但有长期复用价值的前缀。比如隔天还会回来的长会话，或者多个实例共享的 system prompt。文件系统层用内容寻址命名，相同 token 序列映射到同一个 key，多个 vLLM 实例共享同一个存储挂载点时自动共享 KV 数据，不需要额外配置。

卸载不是免费。 从显存搬到内存、从内存搬到磁盘，都有带宽和延迟成本。所以下沉要有门槛。不是所有被淘汰的块都值得往下沉。

## 淘汰策略：按照复用模式分队列
UniCache 的四个队列（针对 LLM serving 场景的 prefix cache 淘汰）：
Evict-First Queue：放低复用潜力的块，包括单轮无模板任务的 prefill 块、单轮任务的所有 decode 块。按位置偏移排序，从偏移最大的开始驱逐，尽量保住早期前缀 token。
Session-Reuse Queue (Agentic)：放 agentic 多轮会话的块。agentic 步骤通常在秒级返回，复用间隔短，用拟合的历史轮次间隔 CDF 算淘汰优先级。
Session-Reuse Queue (Chat)：放 chat 多轮会话的块。chat 的轮次间隔分布跟 agentic 不同，所以分开管理，同样是基于间隔 CDF 算优先级
Structural-Reuse Queue：放单轮但有结构化 prompt 的任务（如工具调用、代码生成）的块。这类任务复用价值主要取决于 prompt 中的位置，按位置偏移归一化打分，偏移越大越先淘汰。



## 计费上缓存成本显性化
云厂商已经在做这件事，模式可以直接参照：
显式缓存创建按标准输入价的 125% 左右计费，命中时只收 10% 左右；
隐式缓存由系统自动决定留不留，命中收 20% 左右，但不保证命中率。

缓存从“白送的福利”变成有创建成本、有保留成本、有命中收益的 SKU
企业通过定价结构控制毛利，而不是靠拒绝缓存。用户如果觉得缓存费太贵，可以选隐式模式，接受命中率的不确定性。选择权给用户，成本透明化。
