# GPU 单卡实测报告与总结

## 一段话总述

我租了一张 A100-SXM4-40G，自己写了一套测量装置，实测 vLLM 0.33 跑 Qwen2.5-7B-Instruct 的并发性能。输入固定 512 token，输出强制 128 token，并发从 1 扫到 32，每档双跑。吞吐从 79 涨到 1477 tok/s，接近线性，测试范围内没有饱和。我另外设计了三个对照实验：把 KV 池压到 1/37 触发抢占、连发 200 条观察长时漂移、换 AWQ 量化版同并发对比。数据用客户端逐请求记录和服务端 Prometheus 两套独立通道对账，差不到 0.1 tok/s。全部代码、原始数据和交互报告在 GitHub 仓库 TheWor1d877/vLLM-on-GPU-test，报告挂在 GitHub Pages。

## 实验设计与执行

环境锁版本：驱动 595.84，CUDA 13.0，torch 2.14.0，vLLM 0.33.0，模型权重四个 safetensors 文件逐个算 sha256 写进配置。租卡机按小时计费，所以装置在本地 4060 上用 0.5B 小模型提前彩排，租卡后只执行一条命令，全程零手敲。

负载口径有三个设计点，都是为了让数据可比。输入用固定种子的随机 token id 序列，不走文本编码，保证每条输入恰好 512 token。请求带 ignore_eos 和 max_tokens=128，强制每条输出 128 token，否则模型提前停止，输出长短不齐，ITL 在档位之间没法比。并发用 asyncio 信号量控制，40 条请求全部提交，信号量放行多少就并发多少。

采集分三层。客户端记逐请求的 TTFT、ITL 序列、输出 token 数、总耗时、起止时间戳。服务端起 Prometheus 每秒抓 vLLM 的 /metrics，实验结束用 query_range 导出时间序列，排队时间分位数和抢占次数从直方图与计数器重建。卡级用 nvidia-smi dmon 每秒记利用率、显存、SM 频率、功耗。三层全部自动落盘，人不参与记录。

三个现象实验各有明确目的。现象 A 用 --num-gpu-blocks-override 640 把 KV 池压到 10240 token，只够 16 条 640 token 序列，32 并发必然触发抢占，用来量 KV 池不足的代价。vLLM 0.33 启动时校验池子至少装得下一条 max_model_len 序列，所以同时带 --max-model-len 8192，请求只有 640 token，口径不受影响。现象 B 在默认服务上并发 16 连发 200 条，看长时运行有没有漂移。现象 C 换 AWQ 权重重启服务，同并发档对比，并从启动日志确认量化内核走的是 Marlin 还是回退慢路径。

验收写进执行驱动：每段跑完立即校验每条请求的输出恰好 128 token，不符当场终止。最终 760 条请求全部通过，0 失败 0 截断。

## 数字背后的机制

吞吐未饱和的原因在负载与池容量的比例。32 并发乘 640 token 是 20480 token，KV 池有 381008 token，占用不到 6%，调度器不需要排队等块。decode 阶段是访存受限：每生成一个 token 要把权重读一遍，batch 增大时一次读权重服务更多请求，吞吐近线性上涨。单并发实测 79 tok/s，对照 A100 的 HBM 带宽 1.55 TB/s 除以权重 15.3 GB 的理论值约 100 tok/s，量级吻合，差值来自 prefill 摊销与采样开销。

AWQ 快 49% 同样来自访存。4-bit 权重把每步 decode 的权重读取量压到约 1/4，Marlin 内核负责高效反量化。没有快 4 倍的原因：KV cache 的读取量不变，注意力计算不变，prefill 是计算受限不吃权重压缩的收益，反量化本身有开销。KV 池从 38 万扩到 55 万 token，因为权重省下的显存划给了池子。

抢占的机制是换出加重算。池子不够时调度器把部分请求的 KV 块释放，请求重新排队，恢复时重新 prefill。现象 A 里 TTFT P50 从 33 ms 涨到 2747 ms，涨的就是排队加重复 prefill 的时间。吞吐还有 789 tok/s，因为池子仍够 16 条序列同时 decode，batch 收益还在，代价集中在延迟尾部。

GPU 利用率量的是 SM 忙碌时间占比，不是单位时间做多少功。并发 1 到 16 利用率都是 100%，吞吐照样从 79 涨到 1017，因为每个忙碌周期处理的 batch 更大。并发 32 利用率降到 75%，吞吐反而最高，访存等待增多但每步产出更多。只看利用率会误判系统还有余量或者已经饱和。

## 追问预案

面试官大概率会问「32 并发没饱和，真正的天花板在哪」。我的回答：这次负载太轻，KV 占用 2.8%，瓶颈没暴露。找拐点要加并发到 128、256，或者把输入输出拉长到接近池容量，让排队和抢占自然出现。经济并发点的定义是达到峰值吞吐 90% 的最小并发，这次测试范围内吞吐一直涨，所以经济并发点只能给下界 32，给不出确切值。报告里如实写了未饱和，没有编一个拐点。

追问「AWQ 为什么不是快 4 倍」，按上面的机制答：权重读取压到 1/4，但 KV 读取、注意力计算、prefill 都不受益，反量化有开销，49% 是这些项叠加后的实测值。再追问「KV 池为什么变大」，答 gpu-memory-utilization 0.9 的预算固定，权重占用减半以上，余量划给 KV 池。

追问「抢占具体做了什么，vLLM 怎么处理」，答 V1 引擎默认重算策略：释放被抢占请求的 KV 块，请求回等待队列，恢复时重新 prefill，不做 KV 换出到主机内存。证据是现象 A 的 TTFT 尾部升高而吞吐没有崩，重复 prefill 吃的是延迟。追问「为什么吞吐掉得不算多」，答有效 batch 仍有 16 条序列，decode 的访存摊销还在。

追问「利用率 100% 为什么吞吐还能涨」，答利用率是时间占比不是效率，batch 增大让每个忙碌周期产出更多 token。这个问题可以顺势讲 decode 访存受限的本质。

追问「为什么用随机 token id 不用真实文本」，答控制变量：文本经 tokenizer 后长度不可控，token id 能保证输入恰好 512；固定种子保证双跑输入逐字节一致。追问「为什么强制输出 128」，答输出长度不齐时 ITL 和吞吐在档位之间没有可比性，ignore_eos 加 max_tokens 把输出钉死。追问「这样测出来的结论对真实业务成立吗」，答这是受控基准，量的是装置与调度的性质，真实负载的长度分布会改变饱和点，但访存受限、抢占代价、量化收益这些机制结论可迁移。

追问「排队时间怎么测的」，答客户端测不到排队，请求发出到首 token 的时间里排队和 prefill 混在一起。我用服务端直方图 vllm:request_queue_time_seconds 按档位时间窗取桶增量，按 histogram_quantile 同款算法重建 P50/P99。这里踩过分辨率的坑，见下一节。

追问「怎么保证数据可信」，答四件事：版本锁加权重 hash，环境可复现；每档双跑，最大差 1.5%；客户端与服务端两套独立测量对账，差 ≤0.1 tok/s；输出完整性硬断言写进执行驱动，760 条全部恰好 128 token。

追问「如果重跑一次你会改什么」，答加并发档到 128 以上找真实拐点，输入输出加长让 KV 池压力接近真实业务，现象 B 拉长到 10 分钟以上并多轮重复确认漂移是否稳定。这次 B 的漂移 6.9%，频率功耗无节流，排除了功耗墙，但漂移根因没有隔离，我不会在面试里给它编一个解释。

## 踩坑与定位过程

这部分是最能体现动手能力的素材，四个坑都是测量装置的问题，不是 vLLM 的问题。

token 计数漏计。第一版客户端按流式 chunk 的 text 字段数 token，主档和服务端对账差 0.25%，现象 A 差到 41%。我先怀疑 vLLM 抢占丢 token，做了一组自洽性检查：客户端 ITL 序列长度和输出计数内部一致，说明不是记录丢失而是计数口径错。读 vLLM 0.33 源码确认流式 chunk 的 token id 列表在 token_ids 字段，且要请求带 return_token_ids=True 才返回；text 是增量 detokenize 结果，抢占重算时会出现空 text 的 chunk，按 text 计数就漏了。修复后在现象 A 同样条件下跑探针，40 条请求全部精确 128 token。这个坑的讲法重点：双通道对账发现差异，先验证装置再怀疑被测系统，用源码和探针定位。

直方图分辨率不足。排队时间默认桶从 50 ms 起，主档排队都在 1 ms 以内，全落进首桶，重建出来的 P50/P99 各档位一模一样。我在配置里加了 0.001 到 0.04 s 的细桶，主档 0.5/0.99 ms 和现象 A 的 400/2969 ms 才分开。讲法重点：重建分位数的精度受桶边界限制，指标看着有值不等于有分辨率。

计数器跨重启清零。现象 A/C 各自重启服务，Prometheus 计数器随进程清零。第一版窗口增量取窗口后第一个样本做终点，读到的是下一台服务的零值，抢占次数显示为 0。改成取窗口内最大值，累计曲线跨重启加偏移。讲法重点：时间窗口的边界条件要对着采集链路想一遍，服务生命周期和采集窗口不对齐就会取错值。

冒烟覆盖不全。冒烟配置关闭了现象 A，也没查输出完整性，两个缺陷都漏到正式跑才暴露，浪费了一次租卡机时。修复后的冒烟规则：正式跑会走的分支一条不关，数量可以缩；数据不变量写成硬断言，冒烟和正式跑共用；冒不起的路径做最小探针。这个坑的讲法重点：冒烟的验收对象是数据正确，不是流程跑通。
