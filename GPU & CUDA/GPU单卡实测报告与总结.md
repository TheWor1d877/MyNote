# 单卡 4090 上 vLLM 并发天花板实测

## 0. 一句话目标

用一次真卡租用，测出：**这张 4090 跑这个模型，并发加到多少就开始“白忙活”；白忙活的标志是什么；哪些现象只有真卡能暴露。**

---

## 1. 用什么卡

**租：RTX 4090 24GB。**

不租 A100：显存太大，KV 池不容易耗尽，瓶颈拐点出不来。  
不租 3090：同 24GB，但算力弱一些，更容易先撞算力而不是撞显存/KV。  
你本地 4060 8GB：只用来调脚本、验证启动参数，不出验收数据。

---

## 2. 租卡前在 4060 上必须做完的事

- benchmark 脚本跑通，能输出逐请求 JSON：每条请求的 TTFT、输出 token 数、总耗时、排队时间。
- vLLM 启动命令确认不报错，量化版能加载即可，不要求性能。
- README 模板写好，顶部留空填：卡型号、驱动、CUDA、vLLM 版本、模型名、量化方式。
- 准备一条 `nvidia-smi dmon -s pucvmet` 记录命令。
- 准备两个固定随机种子的请求生成配置：输入 512 tokens，输出 128 tokens。

---

## 3. 租到 4090 后的执行顺序

### 第一步：锁版本 + 显存基线，15 分钟，必须做

记录并写进 README 顶部：

- 卡型号
- 驱动版本
- CUDA 版本
- vLLM 版本
- 模型名和模型 hash
- 量化方式，没有就写 FP16

然后做两件事：

1. 启动 vLLM 加载模型，**不发请求**，记录：
   - `nvidia-smi` 显存占用
   - vLLM 日志里的 KV cache 大小
2. 单独跑一个空 PyTorch 进程，记录：
   - `torch.cuda.memory_allocated()`
   - `nvidia-smi` 显存占用
   - 两者差值就是 CUDA context + 驱动开销，**实测，不许估**

这两个数是后面显存账对账的底。

---

### 第二步：并发扫描，核心数据，60–90 分钟，必须做

档位：**1、2、4、8、16、32**。

每档 **40 条请求**。  
输入输出固定：**输入 512 tokens，输出 128 tokens**，固定随机种子。

每档记录：

- TTFT：P50、P99
- ITL：P50、P99
- 吞吐：tokens/s
- **排队时间**
- **KV 块占用百分比**
- **是否出现抢占，抢占次数**
- GPU 利用率
- 显存占用
- SM 频率

关键做法：

**每档跑两次，间隔 20 秒。**

- 两次吞吐差超过 15%：第一次标记“预热跑”，丢弃，用第二次。
- 第二次更低，且 SM 频率下降：记录为功耗墙候选。
- 不要加档重跑，一次租卡没有重跑机会。

---

### 第三步：显存账对账，10 分钟，必须做

用第二步的峰值 `torch.cuda.max_memory_allocated`，和 vLLM 报告的 KV 块占用对照纸面值。

差额按顺序归因：

1. 权重：纸面算
2. 激活：纸面估 + 余量
3. CUDA context：第一步实测
4. 碎片：剩余全归这里

记录：

- 权重占比
- 激活占比
- CUDA context 占比
- 碎片占比

**如果碎片占比超过 15%，记下来，这是可讲点。**

---

### 第四步：时间去向表，必须做

四段拆：

1. 排队
2. Prefill
3. Decode
4. 采样与调度开销

拆分方法：

- 排队：直接用请求级排队时间。
- Prefill：关闭 chunked prefill，用 TTFT 减排队时间近似。
- Decode：总耗时减 TTFT。
- 采样与调度：总耗时减排队、减 prefill、减 decode 的残差。

每个并发档给占比，并写随并发变化。

重点看：

- 低并发时 prefill 占比高不高
- 高并发时排队占比是否飙升
- decode 占比是否先稳后降

---

### 第五步：主动触发现象，时间够就做，差异化弹药

#### 现象 A：OOM 落在 KV 池

做法：

- 32 并发档
- `--max-model-len` 调到模型支持上限
- `--gpu-memory-utilization` 调到 0.95
- 输出长度上限翻倍到 256

记录：

- 是否 OOM
- 报错信息里是否提到 KV cache
- OOM 瞬间 `nvidia-smi` 显存数值
- 权重显存有没有涨

目标画面：**OOM 了，但显存没满。**

#### 现象 B：功耗墙导致长跑吞吐下滑

做法：

- 并发 16
- 跑 200 条请求，约 3–5 分钟
- 全程 `nvidia-smi dmon -s pucvmet`

记录：

- 第 1 分钟吞吐
- 第 5 分钟吞吐
- SM 频率变化
- 功耗变化

判断：吞吐下降超过 10%，且 SM 频率下降超过 5%，才算功耗墙。

如果卡散热太好没触发，报告写“未观测到功耗墙”，这也是有效结论。

#### 现象 C：量化 kernel 回退，可选

如果跑 AWQ/GPTQ 4-bit：

- 看 vLLM 启动日志用的是 Marlin 还是 fallback
- 出现 `falling back` 或慢路径关键词就记录
- 没出现就写“该量化配置未触发回退”

不要为了这个放弃主实验。

## 5. 测量有效性记录

规则：

- 同档两次吞吐差超过 15%：丢第一次，用第二次。
- 第二次更低且 SM 频率下降：写功耗墙结论。
- 不改参数加档重跑，因为只有一次租卡。
- 为观测改掉的开关逐条登记，比如关闭 chunked prefill、设置 `enforce_eager`。
- 每条数字标来源：**实测 / 文档 / 论文**。

## 7. 回来后的反直觉讲法模板

“我租了一张 4090 跑 vLLM，本来想验证并发越高吞吐越高。结果并发到 8 还在涨，到 16 只涨了一点，到 32 几乎不动。拆时间发现，32 并发时 TTFT 的 P99 里排队时间占了大头，prefill 本身没慢多少。GPU 利用率显示很高，但它是在忙着跑已经在跑的请求，新来的全在等 KV 块。后来我故意推到 OOM，报错说 KV 池不够，但 `nvidia-smi` 显示显存还没满。这两个数文档不会告诉我，只有真卡跑出来才知道。这张卡在这个模型上的经济并发点大概在 8 到 12 之间，超过就是给 GPU 制造‘我很忙’的假象。”

讲法顺序：

1. 先说哪个数字是亲手测的。
2. 再说一个只有真卡才暴露的现象。
3. 最后说这张表怎么支撑 P2 的预热与扩容判断。

## 8. 不要做的事

- 不要租 A100。
- 不要用 4060 出验收数据。
- 不要一次测两组输入输出分布，先拿一组干净数据。
- 不要等 OOM 自然出现，要主动触发。
- 不要用“加档重跑”处理波动。
- 不要写没有实测表支撑的数字进简历。
