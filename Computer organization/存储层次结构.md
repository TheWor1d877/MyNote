#面试-计算机基础-复习 础什么是存储层次结构？寄存器、L1/L2/L3 Cache、主存、NVMe SSD、网络存储的延迟量级大致是多少？
计算机中CPU与存储之间有几个数量级的速度差距，为了平滑过渡计算机做了一套分层缓存体系，越往上面的层越贵越快

寄存器：时钟周期级别
L1Cache是1ns左右
L2Cache是几纳秒
L3Cache是20ns左右
主存80ns左右
MVMe SSD 微秒级别，100微秒左右
网络分情况，如果用RDMA 10微秒左右，如果走普通TCP的话可能要到毫秒级别了

基本上从L1缓存到主存再到硬盘，每一级差不多就是100倍的差距

我们要做的就是让数据尽量待在 HBM 或本地 NVMe，别每次都回远端拉

#面试-计算机基础-复习 解释 Cache Line 的概念，以及为什么 false sharing 会严重伤害多线程程序性能
 CPU 和主存之间搬数据的最小单位，不是按字节搬，而是一整行一整行地搬，常见是 64 字节
这么做是因为空间局部性——你用了这个变量，大概率马上会用到旁边那几个

false sharing： 两个完全无关线程有两个变量ab，ab恰好在同一Cache Line上面，无论谁修改变量，对方的Cache Line直接失效，这样造成结果就是本来没有共享数据的两个线程开始竞争了

问题： 缓存命中率暴跌
解法： 缓存行对齐，不够放下直接从下一行开始

拓展1:
MESI是多核CPU缓存一致性的协议
M已修改，本核缓存中数据是脏的，与内存不一致，只有本核心持有，其他核心如果读需要我先写回内存
E：独占，数据与内存一致，且只有本核持有，可以随时升级为M
S： 数据与内存一致，可能有多个核同时持有。本核只能读，写需要先请求独占权
I： 本核缓存行无效，不能使用，需要重新从内存或其他缓存获取。

拓展2: Go语言验证false sharing
```go
type BadMetrics struct {
	A int64
	B int64
}

type GoodMetrics struct {
	A int64
	_ [56]byte // 8 + 56 = 64，刚好隔开
	B int64
}
```

拓展3: 常见false shraring场景
分片计数器，使用数组作为计数器，`counts[0] `和 `counts[1]`逻辑上互不干扰,但是往往在同一Cache Line中，且被不同的线程持有

锁的竞争，持有锁的线程写锁住的Value的时候，锁本身就会变成modified，其他线程争抢锁的时候发现锁所在的Cache LIne 失效，重新等待线程写回在读取，锁的获取路径就变慢了。

总结就是同一Cache Line上最好放不会被多个线程共享的资源
