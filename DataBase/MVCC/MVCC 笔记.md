## MVCC 是什么
**MVCC = Multi-Version Concurrency Control = 多版本并发控制**
> 核心目标：**读不阻塞写，写不阻塞读**  
> 核心手段：一条数据在数据库里同时存在**多个版本**，不同事务看到不同版本



## MVCC 是怎么做到的
#### 三个核心组件（以 MySQL InnoDB 为例）

| 组件 | 作用 |
|----|----|
| **隐藏字段** | 每行数据后面附带隐藏列 |
| **Undo Log** | 存旧版本数据，形成版本链 |
| **Read View** | 判断某个版本对当前事务是否可见 |

#### 关键隐藏字段
- `DB_TRX_ID`：最后修改这一行的事务 ID
- `DB_ROLL_PTR`：指向 Undo Log 中上一个版本
一条数据 → 多个版本 → 通过指针形成**版本链**

##  可见性判断
Read View 里主要记录：
- 当前未提交的事务 ID 集合
- 低水位 / 高水位

**判断逻辑（简化版）**
> 沿着版本链，找到第一个满足条件的版本：  
> 修改它的事务 **在 Read View 生成时已提交**

效果：
- 读已提交：**每次查询**生成新 Read View
- 可重复读：**事务第一次查询**生成 Read View，一直复用

## 不同隔离级别的行为

| 隔离级别 | 是否使用 MVCC | 行为                     |
| ---- | --------- | ---------------------- |
| 读未提交 | ❌         | 直接读最新数据（脏读）            |
| 读已提交 | ✅         | 同一事务内，两次查询可能不同         |
| 可重复读 | ✅         | 同一事务内，查询结果一致（MySQL 默认） |
| 串行化  | ❌         | 加锁，完全串行                |
|      |           |                        |

#### 常见使用场景
1. **高并发读多写少系统**  
   → MVCC 天然友好
2. **报表 + 实时交易混合**  
   → 长事务读报表，不影响短事务写入
3. **避免不必要的锁**  
   → 能用 MVCC 就不要 `select for update`

## 常见误区 

| 误区            | 正确理解                    |
| ------------- | ----------------------- |
| MVCC 解决所有并发问题 | ❌ 写–写冲突仍需锁              |
| MVCC 存了完整多份数据 | ❌ Undo Log 会被清理         |
| MVCC = 可重复读   | ❌ 是不同隔离级别对 MVCC 的不同使用方式 |
