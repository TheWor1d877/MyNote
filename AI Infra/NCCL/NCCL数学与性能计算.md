## 总公式
$$
\text{estimated time} \approx \text{latency} + \frac{\text{bytes}}{\text{effective bandwidth}}
$$

| 符号 | 现实世界含义 |
| --- | --- |
| latency | 就算消息很小，你也逃不掉的固定启动与逐步推进延迟 |
| bytes | 真正需要搬运的 payload 大小 |
| effective bandwidth | 考虑完拓扑、channels、协议与算法结构后，真正有用的带宽 |

## busBW：原始带宽
$$
\text{busBw} = \text{nChannels} \times bw
$$
- `bw`：单个 channel 预计能跑到的带宽；
- `nChannels`：NCCL 打开的channel数；
- `busBw`：NCCL 认为整台系统在这个候选方案下，能往 fabric 上打出的总原始带宽。

## ring all-reduce的有效带宽
对于 ring 路径，模型会再乘上一个“有用工作 / 总步骤”的比例。

在 all-reduce 中，NCCL 会用：

$$
\text{nsteps} = 2 \times (nRanks - 1)
$$

然后用大致如下的比例：

$$
\frac{nRanks}{nsteps}
$$

## tree all-reduce的延迟
在 `src/graph/tuning.cc` 中，tree all-reduce 的延迟表达式长这样：

$$
2 \times \left((nRanks/nNodes - 1) \times intraLat + \log_2(nNodes) \times interLat\right)
$$


- `intraLat`：节点内延迟，也就是同机内 GPU 之间或本地汇聚的代价；
- `interLat`：跨节点延迟，也就是网间/节点间通信代价；
- `nRanks/nNodes - 1`：本节点里还需要吸收多少个本地伙伴；
- `log2(nNodes)`：跨节点树高，大概就是树要爬几层；
- 前面的 `2`：all-reduce 不是单向动作，要“上去一次，再下来一次”。

## simple、LL、LL128区别
在 NCCL 中，一个 FIFO slot 并不是一块预先刻好格子的静态内存，而是一段由 Protocol 决定“内部字节如何解释”的线性缓冲区


| | **Simple** | **LL** | **LL128** |
|---|---|---|---|
| **Slot 内有效数据占比** | 接近 100% | 约 50% | 约 95% |
| **Flag 位置** | **不在 slot 数据区内部**；靠 fence 后更新连接级指针 | **与数据交错**：每 4B 数据配 4B flag | **集中在一个 128B 行末尾**：前 120B 数据，最后 8B flag |
| **写入同步方式** | 先写数据 → memory fence → 再更新 flag/指针 | **8B 原子写**：数据与 flag 作为整体落地 | **128B 原子写**：整行落地后，最后一个 word 的 flag 才生效 |
| **Slot 的“视觉形态”** | 一条几乎纯数据的连续区间 | 一串 “D-F-D-F-D-F…” 的小格子 | 一串 “120B Data + 8B Flag” 的行 |


```
Simple slot（数据区）:
┌──────────────────────────────────────────────────────────────┐
│                        Payload Data                          │
│                   （几乎全部是有效数据）                         │
└──────────────────────────────────────────────────────────────┘
   Flag 不嵌在这里面；数据写完后，通过 fence + 连接级更新来通知对方


LL slot:
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ D 4B │ F 4B │ D 4B │ F 4B │ D 4B │ F 4B │ D 4B │ F 4B │ ...
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
  每 8B 是一个原子单元（4B 数据 + 4B flag）
  写的时候，数据和 flag 在同一次 8B 原子操作中落地


LL128 slot:
┌──────────────────────────────────────────────┬──────────┐
│                 120B Data                    │ 8B Flag  │
├──────────────────────────────────────────────┼──────────┤
│                 120B Data                    │ 8B Flag  │
├──────────────────────────────────────────────┼──────────┤
│                 120B Data                    │ 8B Flag  │
└──────────────────────────────────────────────┴──────────┘
  每 128B 是一个原子行；flag 是该行的最后一个 word（word 15）
  整行 128B 原子落地后，末尾 flag 才能被安全读到
```



#### Simple
在 Simple 协议中，这个“flag”并非嵌入在数据块里，而是一个独立的、**连接级别的进度指针**（`connStepPtr`）。它记录着这条连接上“生产”和“消费”的进度。
- **发送方（生产者）**：在将数据写入 FIFO slot 并确保写入对系统可见（通过 **system-scope memory fence**）后，会**原子地更新**这个指针，将其推进到新的值。这表示“我已经把数据准备好了，你可以来取了”。
- **接收方（消费者）**：它的 GPU 线程会**在一个循环中持续地“轮询”**（读取）这个指针的值。一旦发现指针的值达到了它期望的进度，就意味着对应的数据块已经完整地落在 FIFO 中，可以安全读取了。

###### 详细步骤
1. **写入数据**：发送方的 GPU kernel 将 payload 写入本地 Channel 的 FIFO slot 中。此时数据已经在 GPU 的写缓存或 L2 缓存中，但对其他设备（如对端 GPU 或网卡）**尚不可见**。
2. **System-scope Memory Fence**：这是关键的一步。因为 GPU 的写入操作出于性能考虑，可能会在**写合并缓冲区（Write-Combining Buffer）或 L2 缓存**中停留，不会立即“刷”到对全局可见的内存中。`system-scope memory fence` 指令强制要求：**在 fence 之前的所有写操作，必须在 fence 完成之前，变成对整个系统（所有 GPU、CPU、NIC）可见的状态**。这确保了后续更新的指针值是可信的——只要指针更新了，它指向的数据就一定是完整可读的。
3. **更新连接指针（“只改 flag”）**：发送方在 fence 之后，会**原子地**更新共享内存中的 `connStepPtr`。例如，代码中可以看到类似 `STORE(connStepPtr, step);` 的操作。**这不是一个主动的“通知”消息**，它只是把一个共享内存地址的值改掉了。
4. **接收方轮询（Polling）**：接收方的 GPU 线程（或 CPU proxy 线程）会**在一个 `while` 循环中持续读取**这个指针的值。它反复检查指针的当前值是否已经达到了自己期望的进度。接收方必须等发送方写完一个完整的 Slot（即一个 Step）并更新共享进度指针后，才会开始拉取数据。代码示例如下：
```c
    while (connStepCache < step + StepPerSlice) {
        __builtin_amdgcn_s_sleep(1); // 短暂休眠
        connStepCache = atomicAdd_system((unsigned long long *)connStepPtr, 0); // 轮询读取
    }
```
5. **读取数据**：一旦接收方通过轮询发现指针的值符合预期，它就知道了对应的 FIFO slot 中数据已经就绪，于是安全地从该 slot 中读取 payload。

#### LL

LL 把同步粒度缩到了最小：**4B 数据配 4B flag**，两者打包成一个 8B 单元，用 **8B 原子写**（在某些实现里描述为 16B 原子存储）一次性落地。

```
LL 的一个基本单元:
┌────────────┬────────────┐
│  Data 4B   │  Flag 4B   │
└────────────┴────────────┘
     ↑              ↑
   payload      epoch/标志

写入时，CPU/GPU 不是“先写数据、再写 flag”，
而是把 Data 和 Flag 拼成一个 8B 值，用一次原子写发出去。
```

接收方**直接轮询那个 4B flag**，看到 flag 匹配就说明对应的 4B 数据已经到达。**不需要额外的 fence 或连接级通知**。
代价是**一半的 slot 空间被 flag 占了**，有效带宽只有 50% 左右；
好处是延迟极低，适合 KB 级小消息。


#### LL128

LL128 把同步单元从 LL 的 8B 放大到 **128B 的一整行**。每一行的布局是：
**前 15 个 64-bit word（120B）全部是 payload，第 16 个 word（最后 8B）是 flag**。

```
一个 128B 行（16 × uint64）：

word 0   word 1   word 2   ...   word 14   word 15
┌────────┬────────┬────────┬─────┬─────────┬──────────┐
│ 8B 数据│ 8B 数据│ 8B 数据│ ... │ 8B 数据 │ 8B Flag  │
└────────┴────────┴────────┴─────┴─────────┴──────────┘
  ←──────────── 120B Payload ────────────→  ← 同步信号 →

关键写入顺序：先写 word 0..14 的数据，最后写 word 15 的 flag。
依赖 NVLink 的 128B 原子写：整行落地后，末尾 flag 才可信。
```

接收方检查一行是否就绪时，只需要看**该行最后一个 word 的 flag**。因为硬件保证 128B 行是原子落地的，flag 出现就意味着整行的 120B 数据已经完整。**flag 开销从 LL 的 50% 降到约 5%**，同时保留了 flag-based 的低延迟特性；代价是要求数据在内存中 **128B 连续对齐**，并且依赖 NVLink 的原子写能力。
