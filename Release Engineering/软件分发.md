## 软件分发的三条通道
| 通道 | 拿到的是什么 | 受众 | 你需要付出的维护 |
| --- | --- | --- | --- |
| 源码 | git 仓库 / Go module | 想读代码、想 import、想自己编译的人 | push 就完成；要可被 import 才需额外改造 |
| 容器注册表 | 镜像 | 想在 k8s 上跑起来的人（不需要装任何开发环境） | 一套构建 + 推送的自动化 |
| Release 附件 | 单个可执行文件 | 只想在自己电脑上敲命令的人 | 可选，工具能代劳 |

## go get介绍与使用条件
Go内置的依赖管理系统，当Go需要 引入外部库的时候，需要使用go get或者go mod tidy来同步

但是需要三个条件：
1. module 路径必须是能解析成网址的形式
` example.com/user/repo/core` 这种带点的斜杠路径，Go 才知道去哪个域名取。其余路径只能当作内部/保留形式

2. 那个仓库上有以 v 开头的 SemVer tag。 Go 的版本号直接读 git tag，没有 tag 就没有版本可取。

3. 子目录里的 module，tag 必须带目录前缀。 

只有当你希望"别人在自己的 Go 程序里复用 core 这个库"时，才需要做这件事；这是可选能力，不是发布的前提。

## 镜像通道
发布流程里的动作序列是：tag 出现 → CI 构建 4 个镜像 → 推到公网可匿名拉的注册表 → manifest 里的地址指向那个不可变 tag

之后别人只要 kubectl apply -k 一套目录，不需要 Go、不需要 Dockerfile、不需要问你"这个镜像去哪下"。

注册表的选择：GitHub 自带的容器注册表（ghcr.io）和仓库绑在一起、免费额度大、私有仓库权限沿用 GitHub 权限，是单人项目默认答案。

## Release 附件与 go releaser
GitHub 的 Release 页面 = 一个 git tag + 一段人写的说明 + 若干可下载文件。
构建页面的方法：
1. 手动做：tag 之后在网页上建 Release、把编译好的文件拖上去
2. 工具化做：goreleaser 这类配置文件，一条命令交叉编译多平台（darwin/linux × amd64/arm64）、生成校验和文件、按 commit 记录生成变更说明、推 Release。

检查文件是否值得放进Release：
- 交付物里有给人本地敲的 CLI → 值得，因为别人没有你的编译环境，三个平台的文件加一份 checksums.txt 是基本礼貌。
- 交付物是跑在 k8s 里的服务 → 二进制附件几乎无用，没人会直接跑 controller manager，他们要的是镜像。
