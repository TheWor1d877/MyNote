commit 一次内容快照
branch 一个会往前移动的指针，指向"当前这条线最新的那个 commit
tag 一个钉死不动的名字，指向某一个具体 commit
remote 另一份仓库副本 + 你 push 的目标

## tag的作用
三个用途：
标记发布点，让"这个软件的第 4 版"有一个可寻址的名字。git checkout v1.4.0 就把工作树还原成那一版，一模一样，可复现。

给 CI 的触发条件：CI 系统（GitHub Actions）允许"只有出现新 tag 时才执行发布流程"。这样"打 tag"这个动作本身就等于"我宣布这是正式版"，构建、发布、通知全部自动跟着发生。

让别人精确取回某版本：Go 的依赖、Docker 镜像 tag、包管理器，绝大多数都读 git tag 来决定"我拉哪个版本"。

tag一旦发布，最好不要修改，如果有问题打补丁是最优解

#### 版本号规则：SemVer
格式 主.次.补丁（MAJOR.MINOR.PATCH），每一位由变更性质决定，而不是由工作量或时间决定

| 位 | 什么时候 +1 | 使用者升级后 |
| --- | --- | --- |
| 主 X.y.z | 破坏性变更：不改他的代码/配置就跑不起来 | 必须动手改 |
| 次 x.Y.z | 新增功能，向后兼容 | 什么都不用改，白拿新功能 |
| 补丁 x.y.Z | 只修 bug | 什么都不用改 |
算不算破坏性的标准： 升级后使用者的东西会不会坏，比如公共接口的改变

v0.x.y 是豁免区：SemVer 明确说 0 开头表示"公开接口未稳定，随时可破坏"。所以 v0 阶段你加功能也可能把主版本之外的东西改掉，不必有心理负担；真正的承诺从 v1.0.0 开始。

## commit → push → tag 的正确顺序
```text
1. 工作树干净（改动全部 commit，或明确 stash/移到别的分支）
2. commit 到本地 main，测试本地能过
3. push origin main          ← 提交先进公共历史
4. 等 CI 绿（编译过 + 单测过）
5. 在那个 commit 上打附注 tag
6. push origin <tag>         ← tag 单独一次 push，不会跟着 --tags 一起乱推
7. CI 被 tag 事件触发 → 构建镜像/二进制 → 发布
```

为什么 tag 必须在 push 之后：tag 指向的 commit 得先存在于公共历史里。如果你在一个只有你本机有的 commit 上打 tag 并只推 tag，别人拉到的仓库里那个 commit 不存在，checkout 直接失败。

为什么 tag 要单独 push：git push --tags 会把你本地所有历史遗留 tag 一起推上去，包括你早就废弃的那些。规矩是每次只推当前这一个
