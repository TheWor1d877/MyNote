16. 一次请求跨网关、推理引擎、缓存层、存储后端，trace 怎么串起来？span 该按什么边界切？
   【要点】上下文传播走 W3C `traceparent` 头，span 携带 trace id、span id、parent id；Dapper（Sigelman et al., Google 2010）的四个概念 trace id、span、annotation、dapperlog 是这套模型的原型，其中 dapperlog 讲的是「日志里带上 trace id，让外部工具能反查」，这条在工程上最常漏。切分规矩：一个 span 对应一个可归因的阶段（排队、prefill、decode、缓存查询、回源、H2D 拷贝），按阶段切、不按进程切。代码面：Go 从 `ctx` 取，vLLM 侧有 `--otlp-traces-endpoint` 与 `--collect-detailed-traces`。

17. 头采样与尾采样怎么选？各自丢掉了什么？
   【要点】SDK 侧的采样器是 `AlwaysOn`、`AlwaysOff`、`TraceIdRatioBased`、`ParentBased`（环境变量值形如 `parentbased_traceidratio`），便宜，但要在错误发生之前决定留谁，慢请求和错误请求基本抽不到。Collector 侧的 `tailsamplingprocessor`（配置键 `tail_sampling`，策略有 latency、status_code、probabilistic、stringattribute、and）在网关层收齐整条 trace 再判，能留住慢与错，代价是全量先收上来，Collector 的内存与网络按倍数涨。跨语言统一的 rules-based sampler 至今没有定论（UNVERIFIED；Java contrib 里有 `RuleBasedRoutingSampler`，1.57.0-alpha）。收尾要给数：采样率 × 每 trace span 数 × 日均请求量 = exporter 带宽与后端存储量（15 章的算法）。

18. 指标基数怎么控制？GPU 多租户的标签体系怎么设计，两套标签冲突是怎么回事？
   【要点】与本章 21 题的分工：那题答定义，这题答配置与命名。基数是所有 label 取值的笛卡尔积；request id、pod 名、token 数这类无界值一律不进 label。官方口径能给的是 Prometheus 存储文档里「压缩后平均每个 sample 1–2 字节」（磁盘侧），每 series 的内存开销没有官方数字，社区常引的 1–3 KiB 属二手说法，答题时按「记不准、量级如此」处理。GPU 侧：dcgm-exporter 默认指标 `DCGM_FI_DEV_GPU_UTIL`、`DCGM_FI_DEV_FB_USED`、`DCGM_FI_DEV_FB_FREE`，Pod 维度靠 kubelet pod-resources 映射（`--kubernetes`），标签名可能是 `pod` 也可能是 `exported_pod`，取决于 relabel 配置。同一个集群里两套名字并存时，查询会静默返回空，这是「指标没数据」类误报的一个来源。

19. 多窗口多燃烧率的 SLO 告警怎么写？为什么「错误率超过 1% 就告警」不够？
   【要点】Google SRE Workbook 第 4 节的配方：14.4× 燃烧率配 1h 与 5m 双窗口（1 小时用掉 2% 预算）page；6× 配 6h 与 30m（6 小时用掉 5%）page；3× 配 1d 与 2h（1 天用掉 10%）开 ticket；1× 配 3d 与 6h（按 30 天预算刚好烧光）开 ticket；短窗口取长窗口的约 1/12，两窗同时满足才触发，用来滤掉瞬时抖动。单阈值的问题在于它按绝对错误率判：高流量服务 1% 是事故，低流量服务 1% 是几次请求的抖动，同一个阈值对两者都失真。工具现状：sloth v0.16.0（2026-04-04）、pyrra v0.10.1（2026-06-25）。

20. 推理服务的 SLI 选哪几个？错误预算怎么反过来约束发布节奏？
   【要点】选用户能感知的：TTFT（`vllm:time_to_first_token_seconds`）、逐 token 间隔（`vllm:inter_token_latency_seconds`、`vllm:request_time_per_output_token_seconds`）、端到端（`vllm:e2e_request_latency_seconds`）、成功率（`vllm:request_success_total`）、准入拒绝（`vllm:admission_rejections_total`）。路由级指标另有一组：`vllm:kv_cache_usage_perc`（它替换了旧的 `gpu_cache_usage_perc`，旧名现在查不到）、`vllm:prefix_cache_queries`、`vllm:prefix_cache_hits`、`vllm:num_requests_running`、`vllm:time_in_queue_requests`、`vllm:request_queue_time_seconds`。错误预算的作用是流程约束：剩余预算低于设定值时只放行修复类变更，特性发布排队。这条要能说出谁有权豁免、豁免记在哪，否则它只是口号。

24. eBPF 零插桩现在能做到哪一步，边界在哪？
   【要点】OpenTelemetry eBPF Instrumentation（OBI，仓库 `open-telemetry/opentelemetry-ebpf-instrumentation`，前身是 Grafana Beyla，2025 年捐给 OTel）在 2026-10-30 发布 v1.0.0，是首个稳定核心版本，Go 侧 API 与部分信号仍在 beta。它能解析 OpenAI/Anthropic/Gemini/Qwen 的协议并把 LLM 调用还原成 trace，阿里云把它接进 CloudMonitor 2.0（组件 ack-onepilot）。「OBI 是阿里自研产品」属误传，它是上游项目。Cilium 侧目前只有网络观测加 OTel adapter，所谓 Observability for AI 的官方产品页没检索到（UNVERIFIED）。三条边界：拿不到业务语义（租户 id、prompt 模板名要自己补），需要匹配的内核版本与 CAP_BPF 权限，探针自身开销必须实测（20 章 27 题的测法）。

25. OTel 的信号面与 SDK 侧参数：哪几路已经稳定，队列参数为什么算故障域？
   【要点】traces/metrics/logs 为 stable，profiles 是第四路信号：2026-03 公布 public alpha，Collector 从 v0.148.0 起支持（pprof receiver 与 Elastic 捐赠的 eBPF profiler）；OTLP 默认端口 gRPC 4317、HTTP 4318，规范对前三路 stable、对 profiles 仍标 development。SDK 批量导出参数要一口气报出：`OTEL_BSP_MAX_QUEUE_SIZE`、`OTEL_BSP_SCHEDULE_DELAY`、`OTEL_BSP_MAX_EXPORT_BATCH_SIZE`、`OTEL_BSP_EXPORT_TIMEOUT`。语义约定当前版本 v1.44.0（2026-08-04），GenAI 与 MCP 的约定从 v1.42.0 拆到独立仓库 `semantic-conventions-genai`，状态仍是 Development。答题落点：队列上限与导出超时共同决定「观测链路自己变成故障源」的边界，说得出这四个变量比说「我们接了 OTel」有信息量。

26. token 级成本可观测在 2026 年标准化到哪一步了？
   【要点】引擎侧已经是现成计数器：`vllm:prompt_tokens_total`、`vllm:generation_tokens_total`，SGLang 侧 `--enable-metrics`（默认关）后有 `sglang:prompt_tokens_total`、`sglang:generation_tokens_total`、`sglang:time_to_first_token_seconds`。标准化发生在 `gen_ai.*` 语义约定：属性名 `gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens`（从 prompt/completion 改名而来）、`gen_ai.request.model`、`gen_ai.provider.name`，状态 Development，尚未稳定；对应的 GenAI 指标名还没查到稳定版本（UNVERIFIED，仓库 docs/gen-ai/gen-ai-metrics.md 存在但文档站抓取失败）。他自己的版本：每卡每小时产出与每百万 token 成本（06 章 27 题、13 章的账），这套比等标准发布更快，答题时先给自算口径再说标准。
