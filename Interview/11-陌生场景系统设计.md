# 陌生场景系统设计

**答题格式固定三段**：① 基线设计（目标函数 → 分层 → 关键取舍）；② 约束叠加三连（下面表格里的四类，逐条说哪些决策翻转）；③ 一句话自贬——这个设计第一个崩掉的地方在哪。第三段几乎没人写，写出来就是加分项。

**禁用条款**：本章每题都不许引用 TrainCache / KVRouter 的既有结论。允许复用你的方法，但不允许复用答案。

## 约束叠加模板

| 叠加的约束 | 通常翻转哪些决策 |
|---|---|
| 规模 ×100 | 集中式元数据 → 分片或哈希；同步调用 → 异步与批处理；全内存索引 → 分层索引；本地缓存 → 一致性哈希环 |
| 一个字节都不能丢 | 写路径必须落盘确认；缓存从"可丢"降级为"必须可重建"；副本或纠删码；幂等与重传 |
| 预算砍到 1/10 | 冗余降、命中率依赖升、可用性显式降级、离线预热替代在线扩容 |
| 跨地域 / 跨可用区 | 强一致变贵、就近读、复制延迟进 SLO、写冲突要选边 |
| 只读缓存变可写 | 失效协议、版本号、写穿还是写回、并发写序 |

## T1 · 必须脱口而出

1. ★ 设计一个日均 500 亿次小对象读的对象存储访问层。三连：规模 ×100 / 一个字节都不能丢 / 预算砍到 1/10。

【要点】目标函数先说：每 GB/s 成本，或每请求成本（小对象场景下后者先成为瓶颈）。分层：客户端缓存 → 边缘/本地缓存 → 元数据 → 后端；键规范化与命中率依赖是核心取舍。翻转：×100 时集中式元数据必换成分片或哈希环；“不能丢”把缓存从可丢组件降级为必须可重建；预算 1/10 只能靠提命中率，并显式声明可用性降到哪一档。自贬：先崩的是小对象 GET 的请求费或元数据 QPS，带宽排在后面。
2. ★ 设计一个只支持"追加写 + 消费组"的日志系统：分区、复制、顺序保证三件事各自的代价。三连：分区数从 12 到 10 万 / 消费端要求精确一次 / 单条消息从 1KB 变成 5MB。

【要点】目标 = 追加写吞吐与消费端可容忍延迟。必讲：分区内有序、跨分区无序，这一点决定了下面的全部取舍；复制用 ISR 还是异步，决定 fsync 能否被隐藏。翻转：分区从 12 到 10 万时瓶颈从数据面转到 controller 的元数据管理与副本调度；精确一次要幂等 producer + 事务，或消费端去重，代价是吞吐与乱序处理；单条 5MB 时大 value 不该进日志本体，改引用 + 对象存储，代价是崩溃一致性。自贬：先崩的是 fsync 批量与页缓存抖动。
3. ★ 设计一个多租户推理平台：SLO 分级、抢占、超卖、账单四件事怎么互相牵制。三连：新增一个"不许被抢占"的付费等级 / 租户数 ×50 / GPU 供给突然少 30%。

【要点】目标 = 单位成本下的 SLO 达成率；利用率只是手段。取舍：超卖换成本、预留换确定性，两者要写成同一个式子（每等级的最低冗余）。翻转：新增“不许被抢占”等级就得划预留池，供给立刻变紧；租户 ×50 时公平调度从手工配额变成 per-tenant 令牌桶，账单必须自动化；供给少 30% 时要**事先写死谁先被砍**，不能临场决定。自贬：第一个崩的是账单——共享缓存与批处理让成本摊不回租户头上。
4. ★ 设计 Kubernetes 上的 gang 调度器：为什么 all-or-nothing 与既有调度器模型冲突。三连：任务数 ×100 / 要求支持部分回滚 / 队列里 70% 是大任务。

【要点】冲突根源：既有调度器是“单 Pod 独立决策、失败回队列”，gang 要求“一组要么全起要么全不调”，跨节点的原子性必须靠外部记账。翻转：任务 ×100 时预留空转成本变成主要矛盾，需要回填与分层队列；支持部分回滚就要有抢占 + 检查点语义；70% 是大任务时小任务会被饿死。自贬：先崩的是“已预留但等不齐”的那批卡怎么计费。
5. ★ 网关下游有三个服务，其中两个已经变慢：设计你的限流、超时、降级与熔断策略。三连：慢的那个服务承载 60% 的收入 / 上游无法感知你的降级 / 流量突然涨 5 倍。

【要点】目标 = 保住整体可用；单个调用可以失败。手段四层：超时收敛、舱壁隔离（每依赖独立连接与并发预算）、熔断、降级返回旧值或部分结果。翻转：慢服务承载 60% 收入时不能直接熔断，要做功能级降级（保入口、砍非核心字段）；上游感知不到降级就必须显式加标记头并在 SLA 里声明；流量 ×5 时策略从“保功能”切到“保核心”。自贬：降级路径本身没被测过，这是最常见的第二个故障来源。
6. ★ 设计一个全球部署的配置分发系统（亿级客户端拉取、变更要求分钟级生效）。三连：生效时间收紧到 5 秒 / 服务端不可用时客户端必须用最后一次已知配置 / 单个配置项从 1KB 变 1MB。

【要点】目标 = 生效时间 P99 + 控制面不可用时客户端的可用性。结构：版本化配置 + 推拉混合 + 就近只读副本 + 客户端本地持久化。翻转：5 秒生效就得从拉改成推或长轮询，扇出成本与连接数一起爆；“不可用时用最后已知配置”要求客户端落盘且启动不阻塞，代价是必须显式承认陈旧窗口；单配置 1MB 时要增量 diff 与命名空间拆分。自贬：先崩的是配置风暴——大量客户端同时收到变更打穿出口带宽。
7. ★ 设计一个训练数据湖的元数据服务：目录树、版本、血缘、权限。三连：文件数从千万到百亿 / 要求"某次训练用了哪些字节"可精确回放 / 元数据服务本身不允许成为单点。

【要点】目标 = 目录操作延迟 + 可精确回放。结构：命名空间分片 + 不可变版本 + 血缘追加日志。翻转：百亿文件时目录树热点与列举分页是主矛盾，深度递归必须禁止；“精确回放用了哪些字节”把设计推向内容寻址与不可变快照，代价是 GC 与元数据写放大；不允许单点意味着共识层写放大，热分片要读写分离。自贬：先崩的是血缘写入成本——每次读都记一行，元数据流量会追平数据流量。
8. ★ 设计一个以 Raft 为共识层的强一致 KV，要求读性能接近单机。三连：跨机房部署 RTT 30ms / 90% 的读可容忍陈旧 / 单个 value 从 1KB 变成 10MB。

【要点】目标 = 线性一致读的吞吐；写吞吐另算。手段排序：LeaseRead（最便宜，依赖时钟与租约）→ ReadIndex（不写日志但要确认领导权）→ 走 Raft 日志。翻转：RTT 30ms 把提交延迟下限钉死，只能靠跨区只读副本；90% 读可陈旧要拆成两套 API，代价是接口复杂度与用户误解；value 从 1KB 到 10MB 时不能进 log，改外挂 blob + 引用，代价是崩溃一致性。自贬：先崩的是租约续期在跨区抖动下造成读写同时不可用。
9. ★ 设计一个大规模构建/推理制品缓存（键由输入算出，命中则跳过计算）。三连：键空间 ×100 / 客户要求缓存里的数据 24 小时内物理删除 / 命中率跌破 40% 时整件系统的目标怎么改。

【要点】目标 = 跳过计算省下的总时间；命中率只是手段。结构：输入规范化后哈希成键 + 分层缓存 + singleflight 防并发重算。翻转：键空间 ×100 时内存索引放不下，改概率型结构 + 远端索引，代价是假阳造成误命中，属于正确性问题，不能按性能问题处理；24 小时物理删除与内容寻址多副本冲突，删除扇出与可证明删除成为新成本；跌破 40% 命中时目标函数要换成“回源成本 vs 重算成本 vs 存储成本”。自贬：键算错把不同结果映射到同一键，这属于事故。
10. ★ 设计一个能扛住单可用区故障的多区域推理服务。三连：只允许 30% 的流量跨区 / 切换必须自动 / 数据库不允许双写。

【要点】目标 = 切换时间 + 常态成本，两者直接对冲：多活贵但切换快，主备便宜但切换慢。翻转：只允许 30% 跨区流量 → 必须流量本地化且各 AZ 容量对等预留，成本立刻上去；切换要自动 → 与脑裂防护、人工闸门冲突，必须定义“什么条件才允许自动”；数据库不允许双写 → 只剩异步复制，切换必然丢数据，**RPO 要写进 SLO，写明能接受丢多少数据**。自贬：先崩的是“切过去之后剩下的 AZ 装不下全量”这个容量假设。

## T2 · 应当会答

11. ★ 上面每题的"自贬段"专项练习：挑你答得最好的两题，写出第一个崩掉的组件和它崩之前会先出现哪个指标异常。
12. 设计一个内部平台的成本归因系统：怎么把 GPU、缓存、带宽摊到每个任务和租户头上，误差能接受到什么程度？
13. ★ 设计一个大规模日志采集与检索：为什么"全量索引"在成本上撑不住，你砍掉哪一部分换搜索能力？
14. 设计一个 CDN 型边缘缓存的回源协议：抖动、回源风暴、缓存键规范化三处最容易出事的取舍。
15. ★ 设计一个分布式锁服务：租约、fencing token、时钟漂移各兜住哪种失败？什么场景下你应该拒绝提供锁，改用共识协议？
16. 设计一个推理请求的排队与公平调度：FIFO、最短作业优先、按租户配额、按 SLO 等级四种策略的公平性定义分别是什么？
17. ★ 设计一个 checkpoint 存储：写入端要高吞吐、保留端要省钱、恢复端要秒级。三目标冲突时你怎么排序，排序依据来自哪里？
18. 设计一个对象存储的冷热自动分层：判定冷的依据是什么？误判的代价往哪边偏？
19. ★ 给一个已有的单地域服务加"合规要求数据不出省"，架构最少要改哪几处？为什么这类需求通常先排除跨区缓存？
20. 设计一个大规模容器镜像与模型权重的分发系统：P2P、预拉取、按需加载三档各自的失败模式。
21. ★ 设计一个"只给你 3 周"的系统：列出你会主动放弃的四类非功能需求，并写出放弃它们各自的失效条件。
22. 设计一个内部推理 API 的限流与计费系统：怎么防止一个调用方用超长上下文把服务压垮？token 级限流与请求级限流的差别在哪。

28. 什么时候该在系统设计里主动引入你已经实现过的机制（比如你的预取窗口、准入策略）？引入的边界条件是什么，怎么避免变成"背项目"？
