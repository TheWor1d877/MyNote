## C. S1 mini-Raft：论证题（1–7）

> 定位是回答“P1 为什么用 etcd、不自研 Raft”，不是把 Raft 做成能上线的库。3 周止损，对拍报告写完就停。

1. ★【取舍】P1 为什么最终用 etcd、不自研 Raft？给三条工程理由，再给一个“自研也可能赢”的反例场景（什么条件下值得自研）。如果面试官说“你就是不会写 Raft 才用 etcd”，你怎么用 3 周内跑通的选举、复制、快照、崩溃恢复反驳？
2. ★【正确性】`votedFor` 不落盘如何在一次分区恢复后造成同任期双投？leader 为什么不能直接提交前任任期的日志？挑一个写出时序，标清 term、日志索引、投票方向。快照里的 `lastIncludedIndex` 和 `lastIncludedTerm` 各解决什么，漏了后者会在哪一步坏？
3. ★【上难度】故障注入你实际做了哪几类（`kill -9`、多数派/少数派/不对称分区、时钟跳变）？已提交数据零丢失的判据是什么？哪一类故障下你的实现表现最差？如果只允许保留一类故障做回归，你保留哪类？
4. ★【对标】【复现】和 etcd 的对拍怎么做？同一串操作逐项比较什么（返回值、日志顺序、恢复后的数据）？举一个“行为不一致”的例子，并解释是你的 bug 还是设计选择。P1 README 里那句“结论见附录”的结论到底是什么？
5. ★【白板】Pre-Vote 防的是什么具体故障？joint consensus 为什么不能一步切？两者你都没实现，但要能讲清“如果实现，第一步改哪里”。ReadIndex 与 Lease 对时钟的依赖差在哪？
6. ★【天花板】⏳ Raft 提交延迟的理论下界是什么（leader→多数派→leader 一个 RTT + fsync）？主节点故障的无主窗口下界是什么（选举超时 [T,2T) + 投票 RTT + 日志追平）？你的实现离这两个下界各有多远？如果没测，面试时怎么诚实说“我知道下界但没量”？
7. ★【复盘】【止损】3 周止损日到了，你砍了什么、保留了什么？丢包扫描、无主窗口分布、etcd 五差异笔记，你做了哪个、没做怎么交代？如果重来，你会先写对拍 harness 还是先写 Raft 主体？为什么？

## D. S3 eBPF 观测：四件归因（8–13）

> MVP 不是单个探针：块 I/O 延迟直方图、major fault、预读命中/浪费归因、和 P1 指标对齐，四件围绕同一轮 benchmark，缺一件不算完成。

8. ★【工程】block I/O 延迟直方图为什么用 tracepoint（`block_rq_issue` + `block_rq_complete`）按 request 指针配对，再在 per-CPU map 里按 log2 bucket 聚合？ringbuf 方案在高 IOPS 下会怎样？issue 了但永远没 complete 的请求怎么清理，request 指针被内核复用怎么防错配？
9. ★【归因】为什么 preheat 命中 page cache 时没有 block I/O 事件？readahead 产生的 major fault 为什么可能不记在消费者进程名下——这个归因陷阱怎么用实验验证？为什么它本身就是上等弹药，而不只是一个实现细节？
10. ★【交付】【复现】四件 MVP 怎么围绕同一轮 benchmark 组织？inotify 文件事件、dataloader 打点、内核块 I/O、major fault 怎么对到同一条时间线？映射表长什么样？如果四件里只做成两件，你怎么判断自己算不算完成？
11. ★【数字】⏳ 同一轮 benchmark 下，用户态观测（inotify/dataloader）和内核观测（块 I/O + major fault）的停顿差多少？预读到底帮忙还是帮倒忙？「预取命中率归因图」怎么标清瓶颈落在页缓存还是块设备？如果两个口径不一致，你先信哪个？
12. ★【天花板】⏳ eBPF 探针自身的开销怎么量（每 I/O 多少 ns、对 P99 的影响）？你能测到的最小延迟是多少？per-CPU map 与 ringbuf 在“低开销”和“不丢事件”之间怎么取舍？用 `/proc/diskstats` 采样兜底时，采样周期会漏掉什么、口径差多少？
13. ★【降级】CO-RE 解决了什么问题？为什么优先 tracepoint、少用 kprobe（ctx 字段跨版本更稳）？eBPF 挂不上时怎么降级到 `/proc/diskstats`，并诚实标注两个口径的差异？内核版本、权限、容器环境三道门槛你各踩过哪个？

## E. S4 bitcask：WAL / merge / 恢复（14–21）

> 只做 WAL、merge、崩溃恢复。CAS、refcount、P2P 是 P1 的，不碰。核心对比是 P1 重扫描 vs S4 WAL replay。

14. ★【对标】【证据题】⏳ P1 用重扫描做 crash recovery（重启约分钟级），S4 用 WAL replay（目标秒级）——你实测的启动恢复时间对比表数字是多少？为什么 WAL 没上 P1 主路径？README 里那个 X 具体是什么（工程复杂度、merge 崩溃窗口、维护成本），不能写“没时间”。
15. ★【正确性】merge 的 manifest 原子切换：rename 数据 → rename hint → 写 manifest，崩溃落在每一步分别怎么恢复？为什么 manifest 必须先写临时文件再 rename？旧文件什么时候才能删？记录头时间戳为什么用 8 字节，4 字节秒级时间戳的 2038 问题具体怎么爆？
16. ★【取舍】fsync 三档（逐条刷盘 / group commit / 只靠 OS）的吞吐、延迟、丢数据风险表。group commit 协调者崩溃时边界行为是什么？P1 缓存块为什么不逐块 fsync，S4 为什么不能照搬这个假设？
17. ★【数字】⏳ 10M key 的索引内存/数据量比实测多少？key 平均长度 × 数量 × Go map 开销，这条账怎么算？全内存索引什么时候放不下，bitcask 什么时候输给 LSM？你有没有画出“索引内存/数据量”的比值曲线？
18. ★【数字】⏳ merge 前后读放大多少倍（读一份有效数据平均要从磁盘读多少份）？写放大怎么算？merge 期间写延迟抖动的丑数字敢报吗？如果 merge 把 P99 写延迟抬高 10 倍，你怎么向用户解释这是可接受的？
19. ★【上难度】【复现】⏳ fuzz 崩溃矩阵两个维度：崩溃时机（写 WAL 中途、写 tombstone 中途、merge 写新文件、rename 之间、manifest 写入中途）× 崩溃方式（`kill -9`、`/proc/sysrq-trigger` 模拟断电）。每一格跑几次？重启后全量校验什么？矩阵全绿之前你允许自己进 benchmark 吗？
20. ★【对标】数据量超过内存后，bitcask 为什么输给 LSM？对比 SSTable、稀疏索引、分层 compaction 的读写放大。LevelDB 的 MANIFEST 和你的 manifest 长得几乎一样——你读到什么程度，能白板讲清“哪些是巧合、哪些是同一个约束推出来的”？
21. ★【天花板】⏳ 单写者 append 的吞吐上界是不是 1/fsync 延迟？group commit 能把上界抬到多少？读路径“索引命中后一次 pread”的理论下限是一次 I/O，你的实测离它多远？全内存索引的内存下界怎么算，你的实现比下界多了多少开销？
