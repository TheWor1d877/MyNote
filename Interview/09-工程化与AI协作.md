# 工程化、协作与 AI 研发（分级版）

按重要性分三档：T1 必须能脱稿讲满 3–5 分钟；T2 能讲清 90 秒；T3 为扩展与速查。★ 仅表示原题库标记，已不完全等同 T1。

## T1 · 必须脱口而出

1. ★ 解释代码评审的核心关注点，哪些问题应该在评审中拦住，哪些应该留给测试。
2. ★ 什么是测试金字塔？单元测试、集成测试、端到端测试在 AI Infra 中如何分配。
3. ★ 什么是表驱动测试？Go 中如何用它覆盖调度器或网关的边界条件。
4. 解释 CI/CD 流水线的关键阶段，以及如何为 GPU 相关代码设计 CI。
5. 什么是 feature flag？如何在推理网关中安全地灰度新路由策略。
6. 解释设计文档的结构：背景、目标、非目标、方案、取舍、风险、迁移。
7. 解释故障复盘的文化与结构，如何区分根因与触发条件。
8. ★ 什么是开源贡献路径？如何从 good first issue 走到核心模块 patch。
9. AI 生成代码占比上升后，代码评审的关注点应该如何变化？哪些缺陷类型会被系统性放大，哪些评审习惯反而更要保留？
10. ★ 如果让你把“我做了一个训练数据预取层”讲成面试项目，你会如何组织背景、瓶颈、方案、数据、取舍与反思？
11. ★ 如果让你为一个 20 人 Infra 团队设计"人 + agent"的研发流水线，你会如何划分权限、评审、CI、度量与事故责任？

## T2 · 应当会答

12. 解释 mock 与 fake 的区别，在测试 K8s 控制器时如何选择。
13. 什么是 flaky test？在分布式系统测试中如何治理。
14. 解释竞态检测与压力测试在 CI 中的位置。
15. 测试金字塔在没有常驻 GPU 的 CI 里会怎么变形？哪几层会被迫上移或下移，代价转移到了哪里？
16. 什么是制品仓库？容器镜像与模型文件分别如何做版本管理。
17. 解释语义化版本与 API 兼容性，在 Operator 与 CRD 演进中如何落地。
18. 什么是 RFC 流程？开源 Infra 项目中 RFC 如何推动架构演进。
19. 什么是 on-call？AI Infra 值班时最常遇到的告警类型有哪些。
20. 解释 runbook 的价值，如何为推理服务与训练任务编写可执行手册。
21. ★ 解释如何定位一个开源项目的 issue，并提交可被接受的 PR。
22. 解释 DCO sign-off 的含义与 Signed-off-by 的作用，以及一个规范的开源 PR 从分支提交、DCO 签名、CI 通过到 review 礼仪的完整工程流程。
23. ★ 一份高质量的 issue 应该包含哪些要素？为什么精确复现步骤、已排查项与环境信息是其中的关键。
24. 如何为 AI 辅助研发划出"可信边界"：哪些 Infra 模块允许 agent 直接改、哪些必须人工签核？请给出可执行的分级规则，而不是原则口号。
25. 当测试与实现可能由同一个模型生成时，如何避免"自证正确"？独立 oracle、变异测试与人工抽检分别该放在哪一层？
26. 如何度量 AI 辅助研发的真实收益？为什么 PR 数、代码行数是坏指标，应该看哪几条工程指标？
27. 多个 agent 并行修改同一个仓库，如何避免接口与抽象漂移？所有权、契约与合并顺序应该怎么设计？

## T3 · 扩展与速查

28. 把 agent 接进 CI（自动修 flaky、自动升级依赖、自动补回归用例），收益与风险各在哪？熔断条件应该怎么设？
29. 代码、日志与训练数据送进外部模型时的合规边界：脱敏、留存与供应商审计分别怎么落地？
30. 多 agent 的共享状态放在哪里：黑板、消息队列还是 CRDT？各自在并发与失败下的表现有何不同？
31. Agent 的工具调用带副作用时，如何做到"效果上的 exactly-once"？幂等键、去重窗口与补偿动作怎么配合？
32. 多机 agent 沙箱如何选型：容器、gVisor、Kata、Firecracker 在隔离强度、冷启动与部署密度上的取舍是什么？
33. 如何观测一个多 agent 系统：trace 的 span 粒度、token 与工具成本归因、失败归因，和推理网关的观测有什么不同？
34. 多个 agent 给出冲突结论时如何裁决？投票、仲裁 agent 与人工升级分别在什么条件下可信？
35. flaky test "重跑通过"为什么是技术债而非解决了问题？辩论一下：容忍 1% 的 flaky 率换取发布速度，这笔账在 AI Infra 项目里应该怎么算。
36. 被遗忘的 feature flag 会让路由矩阵爆炸：估算 10 个残存 flag、每个 3 个状态的组合空间有多大，并辩论 flag 该不该有强制到期日。
37. RFC 流程过慢会把创新闷死，过快又会让架构失控：设计一条"什么样的改动必须走 RFC"的分界线，并说明它如何保护小改动快速前进。
