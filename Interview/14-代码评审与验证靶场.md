# 代码评审与验证靶场（带实物材料）

这一章的形态和全书其他章节不同：**每道题都必须对着材料作答**，口述框架在这里不算答案。目标是练"给你一段你不完全信任的代码/数据，你能否定位错误层次 → 构造最小复现 → 给出能捕获它的断言 → 判断影响半径"。

每道题后面的【要点】是自判用的答案骨架，先答完再看，别看一半就往下翻。

## 材料 A ｜ Go 并发预取器（题 1–3 共用）

```go
type Prefetcher struct {
	mu       sync.Mutex
	pending  map[string]bool
	sem      chan struct{}
	wg       sync.WaitGroup
	budgetMB int64
	used     int64
	window   int
}

func NewPrefetcher(concurrency int, budgetMB int64, window int) *Prefetcher {
	return &Prefetcher{
		pending:  make(map[string]bool),
		sem:      make(chan struct{}, concurrency),
		budgetMB: budgetMB,
		window:   window,
	}
}

// budgetLeft 剩余可预取字节。budgetMB 在本项目其他位置一律按 1024*1024 解释。
func (p *Prefetcher) budgetLeft() int64 {
	return p.budgetMB*1000*1000 - p.used
}

// PrefetchRange 从 cursor 开始预取 window 个块。
func (p *Prefetcher) PrefetchRange(blocks []string, cursor int) {
	for i := cursor; i <= cursor+p.window; i++ {
		if i >= len(blocks) {
			break
		}
		key := blocks[i]
		if p.pending[key] {
			continue
		}
		p.wg.Add(1)
		go func() {
			defer p.wg.Done()
			p.sem <- struct{}{}
			defer func() { <-p.sem }()

			p.mu.Lock()
			p.pending[key] = true
			p.used += chunkBytes
			p.mu.Unlock()

			p.fetch(key)
		}()
	}
}
```

**题 1 ★** 这段里有三个缺陷。找出来，每个说明：触发条件是什么、在什么负载下才会暴露、严重度排序。

【要点】① `p.pending[key]` 的读在锁外、写在锁内——map 的并发读写是硬失败（`fatal error: concurrent map read and map write`），不是概率性数据错乱，所以它会在压测里直接打死进程；② 单位换算：`budgetMB` 全项目按 1024×1024 解释，这里按 1000×1000，预算越大超发越多（1 GiB 预算错 4.6%），属于"小额测试永远发现不了"的那类；③ 边界：`i <= cursor+p.window` 实际取 window+1 个块，`window=0`（关闭预取的对照组）时仍会多取一个——**这条最致命，因为它污染的是你的 baseline**，所谓"无预取"对照组里其实有预取。排序按 ③ → ① → ②：③ 让实验结论错、① 让进程死、② 让成本账虚。

**题 2 ★** 为这三个缺陷各设计一个能必现捕获的测试，写出断言而不是步骤。哪个缺陷用单测捕获不了、必须靠别的机制？

【要点】① 用 `-race` + 两个 goroutine 同时 `PrefetchRange` 重叠区间；② `NewPrefetcher(4, 1024, 2)` 后断言 `budgetLeft() == 1024*1024*1024`，写死期望常量而不是同样用 1000 算——**断言里复用被测代码的换算式等于没测**；③ `blocks` 长度 1、`cursor=0`、`window=0`，断言 fetch 调用次数恰为 1（用计数 fake）。② 属于"单测能抓但没人会写这种单测"，真正兜住它的是②的另一种机制：预算口径只允许存在一处定义（常量或单一函数），散落的换算式靠评审 + lint 拦。

**题 3** 除三个缺陷外，指出这段代码里你会在评审中提出、但不属于"错"的两处。

【要点】`pending` 只增不减 → 无上限增长，长跑必成内存问题（属于缺生命周期而不是 bug）；`p.fetch(key)` 的返回值/错误被丢弃 → 失败静默，需要指标或重试兜底。附加可提：`sem` 在 `wg.Add` 之后才获取，等待许可的 goroutine 仍占内存，高并发下 goroutine 数不受 `concurrency` 约束。

## 材料 B ｜ 一段 PR diff（题 4–5 共用）

背景：显存 block 池，`Alloc` 从 `freeList` 取块、`Acquire` 增引用、`Release` 减引用，in-flight 请求持有块期间不允许复用。

```diff
 func (p *BlockPool) Release(blockID int) {
-	p.mu.Lock()
-	defer p.mu.Unlock()
-	if p.refCount[blockID] > 0 {
-		return
-	}
-	p.freeList = append(p.freeList, blockID)
+	p.refCount[blockID]--
+	if p.refCount[blockID] == 0 {
+		p.freeList = append(p.freeList, blockID)
+	}
+}
+
+func (p *BlockPool) ReleaseAll(ids []int) {
+	for _, id := range ids {
+		defer p.Release(id)
+	}
 }
```

**题 4 ★** 这个 PR 要合之前必须拦下哪几处？给出每处的错误后果，并说明它会在生产的哪个症状里首次现身。

【要点】① 去掉了 `p.mu`，`refCount` map 与 `freeList` 切片的并发读写直接进硬失败或数据错乱；② 语义从"引用为 0 才回收"改成"每次 Release 递减"，但旧代码里 `Release` 被设计成**幂等**（重复调用不回收），调用方据此在错误路径上也调它——改成递减后重复 Release 会把计数减成负数，`== 0` 永不再成立，块永久泄漏（症状：池子可用块数单调下降到 0，然后新请求全部排队）；③ 没有下界保护，且同一块可能被两次 `append` 进 `freeList` → 两个请求分到同一块（症状：输出串扰，A 用户看到 B 用户的 token，这是正确性事故不是性能事故）；④ `ReleaseAll` 里 `defer` 在循环内 → 全部推迟到函数返回才执行，且每个 defer 都是一次调用，锁与计数在长循环末尾集中释放，语义和写法意图都不对。

**题 5** 如果作者只允许你提一条 review 意见，你提哪条？为什么？

【要点】提 ②/③ 那条组合（引用计数语义变更 + 无下界保护）。理由：① 会被 `-race` 和 CI 抓到、④ 是可维护性问题，而语义变更是**只有读过调用方才知道的破坏**——review 的价值在于覆盖机器覆盖不到的部分。这也正是评审关注点在 AI 生成代码时代的位移：格式、空检查、锁这类机器能拦的，人力应该省下来查契约。

## 材料 C ｜ 一份测试用例集（题 6–7 共用）

```go
func TestPrefetchWindow(t *testing.T) {
	cases := []struct {
		name    string
		blocks  int
		cursor  int
		window  int
		wantGet int
	}{
		{"小窗口", 100, 10, 2, 3},
		{"标准窗口", 100, 10, 8, 9},
		{"大窗口", 100, 10, 32, 33},
		{"尾部截断", 10, 7, 4, 3},
		{"起点即终点", 10, 9, 0, 1},
		{"空数据集", 0, 0, 4, 0},
	}
	for _, c := range cases {
		t.Run(c.name, func(t *testing.T) {
			p := NewPrefetcher(4, 1024, c.window)
			blocks := makeBlocks(c.blocks)
			p.PrefetchRange(blocks, c.cursor)
			p.wg.Wait()
			if got := p.fetchCount(); got != c.wantGet {
				t.Fatalf("got %d want %d", got, c.wantGet)
			}
		})
	}
}
```

**题 6 ★** 这份用例覆盖了六个场景，`go test` 全绿。它漏掉了哪四类？其中哪一类会让材料 A 的边界缺陷长期存活？

【要点】① 断言的期望值（3、9、33）本身是按 `window+1` 写的——**用例把缺陷固化成了规格**，这就是"起点即终点 window=0 期望 1"看着合理的原因，材料 A 的 ③ 靠这类用例永远抓不到；② 无并发用例（同区间多 goroutine、重叠 cursor 前进）；③ 无预算用尽与 `budgetLeft` 交互的用例（预算为 0 时还预取吗）；④ 无重复调用/幂等用例（同一 cursor 调两次应不重复 fetch，依赖 `pending`）。另可提：`cursor` 越界（cursor > len）与负数没有用例。核心结论一句话：**覆盖率 100% 不等于捕获率高**。

**题 7** 重写这份用例的断言方式，使它能在缺陷被引入的第一时间失败，而不是跟着缺陷一起改期望值。

【要点】把"数了几个块"改成**规格来源与实现分离**：期望值由测试内独立实现的规格函数给出（如 `wantGet = min(window+1, len-cursor)` 用参考实现而非被测代码），或对 `window=0` 显式钉字面量并写注释说明这是"关闭预取"的对照配置；再补一条性质测试（同一 dataset、window 从 0 到 64 扫描，断言 fetch 字节数随 window 单调且 `window=0` 时增量为 0）。这就是独立 oracle：测试的正确性不能来自被测代码自己。

5,direct,0.000,0.985,1219.9,2,cold,1970000000

**题 8 ★** 817× 加速、CV < 0.5%、每行都有数字。这个结论能不能成立？列出致命缺陷与各自补救动作。

【要点】① `arm` 与 `cache_warm` 完全混淆——direct 恒冷、pre 恒暖，读者无法区分"机制有效"与"缓存本来就有数据"，必须同态对比（冷 vs 冷、暖 vs 暖）；② 顺序偏差：同一 epoch 内 direct 先跑、pre 后跑，节点页缓存、tc 状态、其他租户负载都在漂移，需要随机化或交替运行（ABBA）；③ 样本量：每格 1–2 次就报小数点后三位，CV 小可能只是同一次运行的自相似，需要多轮 + bootstrap CI；④ `hit_rate` 与 `stall_ratio` 的因果方向没证明，缺"关掉预取但保留缓存热度"的第三臂。可成立的部分只有"量级差很大"，不能写成机制归因。

**题 9** 只允许你加一个实验臂，加哪个？为什么它的信息量最高？

【要点】加 **"pre 但缓存预热到同等热度"或"direct 但跑在已暖的缓存上"** 这一臂（warm-direct）。信息量最高的原因：它单独把"缓存状态"这个混杂因子从"预取机制"里剥出来，一眼看出 817× 里有多少属于机制、多少属于现场。凡是两臂差异可能来自环境而非设计时，第三个臂的作用都是**把环境和机制解耦**。

## 材料 E ｜ 变异测试靶（题 10–11 共用）

```go
// ShouldPrefetch 判断第 i 个块是否值得预取：在窗口内、未缓存、且预算充足。
func (c *Cache) ShouldPrefetch(i, cursor, window int, cached map[int]bool) bool {
	if i < cursor || i > cursor+window {
		return false
	}
	if cached[i] {
		return false
	}
	if c.remaining <= 0 {
		return false
	}
	return true
}
```
现有单测：窗口内命中 true、已缓存 false、窗口外 false、空 map true 共 12 个用例，全绿。

**题 10 ★** 写出三个能让现有 12 个用例全部存活的变异体。

【要点】① `i > cursor+window` → `i >= cursor+window`（边界 off-by-one，除非有用例恰好在 cursor+window+1 才暴露）；② `i < cursor` → `i <= cursor`（cursor 自身那块不再预取，测试若都从 cursor+1 观察则存活）；③ `c.remaining <= 0` → `c.remaining < 0`（remaining 恰为 0 时多预取一块，需要一条预算=0 的用例）；④ 删除 `cached[i]` 分支里的 `return false`（若用例只检查返回 false 的集合而不检查重复 fetch 次数则存活）。这四条里 ①② 属于"窗口边界相邻值"，③ 属于"阈值等号"，是变异测试最容易暴露的两类。

**题 11** 把上面这套做法变成你能长期执行的纪律：给你的项目定一条变异测试门禁，写清在哪一层跑、跑哪些算子、什么信号就停。

【要点】结构：范围（只对核心判定函数跑，不对全仓）、算子（边界 ±1、比较符方向、常量取反、删除 early return）、判据（存活体数量 > 0 就要补用例）、停机（单函数变异集跑完即停，不追全量覆盖率，因为变异测试的边际收益在前几个算子最高）。这题的考点是把方法论落成可执行的一次性动作，而不是说出名词。

## 其余题目（无材料，练的是纪律与判据）

**题 12 ★** 拿到一段 AI 生成的实现，你的前十个动作是什么？给出顺序和每步要排除的缺陷类别。

【要点】先跑起来看什么都能不做（能不能编、有没有单测），再定契约（它假设的输入边界/并发模型/错误语义是什么，这决定后面算不算 bug），再看单位与边界、再看并发与生命周期、最后看性能。核心是**先钉契约再挑刺**：跳过契约直接读代码，会把"实现不符合你没说的要求"误判成 bug。

**题 13 ★** AI 生成代码占比上升后，哪三类缺陷被系统性放大？哪两类评审习惯必须保留？

【要点】放大：① 单位与口径不一致（不同函数各自换算）；② 边界与空值路径（happy path 完整、异常路径静默）；③ 契约漂移（同名函数在不同生成批次里语义悄悄变了）。必须保留：① 读代码时对断言/不变式的追问；② 对"测试期望值从哪来"的溯源（见材料 C）。

**题 14** 怎么区分"它能跑"与"它是对的"？给你一个只能观察输出的黑盒，你能做到哪一步，做不到的是哪一步？

【要点】能做到的：不变式检查（同一输入两次结果一致、计数守恒、单调性）、差分测试（与参考实现/另一条路径对拍）、故障注入看降级是否合理。做不到的：语义正确性——"这个键该不该返回这条 value"必须由规格定义，黑盒永远测不出规格本身错了。这一句就是"自证正确"的边界。

**题 15 ★** 一份 review 意见怎么写才算有效？把"这里可能有并发问题"改写成合格的表述，并说明合格表述必须包含的四个成分。

【要点】四个成分：触发条件（什么负载/时序）、错误后果（哪个不变式被破坏、用户侧症状）、证据（race 报告/最小复现代码）、修法或建议的门禁位置。示范改写："`pending` 的读在锁外（L18），与 L26 的写在两 goroutine 重叠区间时并发，`-race` 可稳定报出，线上表现为进程 fatal 退出；建议把判重移到锁内，并在 CI 里对 `PrefetchRange` 加 `-race` 用例。"

## 用法

- 材料 A–E 每份做一次"限时 20 分钟当场判"，录音或写下你的判断，再对【要点】。
- 判完把漏掉的那条记进 `卡点` 清单——**漏掉哪一类缺陷比找齐更重要**，因为它就是你 review 的系统性盲区。
- 每两周重做一份，换一批材料：把 agent 生成的新变体当靶子，别复用同一份，重复做同一份只会记住答案。
- 材料可以从你自己的项目里挖：任何一次"AI 写的、我当时没看出问题"的提交，事后回捞成 review 靶子，是最真实的材料来源。
