# 场景取舍与方案匹配（分级版）

其余章节问「X 是什么、X 和 Y 差在哪」，这一章问「这个场景给你哪个方案、为什么不选另两个」。校招里淘汰人的场合常是面试官递了一个用错的方案，候选人顺着他的前提往下答。

这一章练的三步：① 先把场景归类（负载特征、数据规模、一致性要求、预算、运维半径）；② 在 2–4 个候选里选一个，说清它成立的**前提**；③ 说清不选另两个的**代价**，以及什么条件下会换回来。三步缺一步，答案就退回名词解释。

★ 在本章里表示优先练的题。

## 答题模板：四列卡（每题必须填满四列）

| 列 | 写什么 | 缺这一列的后果 |
|---|---|---|
| ① 候选 | 2–4 个方案，至少放一个「很流行但这里不该用」的 | 面试官判断你没见过别的做法 |
| ② 成立前提 | 该方案在什么条件下才是对的：访问模式、粒度、QPS 量级、可丢性、预算、谁来运维 | 变成背对照表 |
| ③ 塌了的现象 | 前提不成立时可观测的样子：哪个指标先动、曲线什么形态、日志里哪一字段变脏 | 他无法确认你真跑过 |
| ④ 换成谁 | 换成哪个候选、换的代价、什么条件下再换回来 | 只会说不会建 |

三条自检，答完当场过一遍：

1. 每一句取舍都带阈值或量级了吗？「延迟敏感」这种词一律重写成「P99 目标 200 ms 时，X 的排队代价已经超过 Y 的两次拷贝」。
2. 数字有没有落回 15 章的基准表？没有出处就明说「这个数我没实测过，量级按 15 章的 X 估」。
3. 有没有一句主动交代「这个选择在约束变成 Z 时会翻」？这句是本章的得分点。

自测方式：随机抽 5 题，每题限时 3 分钟，四列缺任列记 0 分。B 组（错配题）单独抽一轮，练的是顶住追问。

## A · 桥接：给场景和约束，在候选里选（1–14）

1. ★ 训练集 10 TB、4000 万张 30–300 KB 小图、每 epoch 顺序全读、200 卡同时拉数据。候选：对象存储直读 / 分布式文件系统挂载 / 本地 NVMe 缓存 / 合并大分片（WebDataset 类）。选哪个、怎么组合？
   【要点】组合：合并大分片 + 本地 NVMe 缓存，元数据自索引。前提：访问是顺序全量、样本不可单独寻址也不被随机改写。对象存储直读卡在第一字节（10–100 ms × 4000 万次）和请求费上，带宽问题排在它们后面（15 章延迟梯度）；FUSE 挂载每次 open 的元数据开销在小文件上会把吞吐压到设备上限的零头。塌了的现象：GPU 利用率均值不掉、方差变大，DataReader 队列深度长期为空。出处：05 章 18 题、05 章 31 题、04 章 13 题。

2. ★ 同一批数据，改成随机取单条样本（多模态采样、eval 抽一条、按标签过滤）。上一条的选择还成立吗？
   【要点】合并方案退化：大分片随机读要把整块读进来再切，放大倍数 = block/样本，300 KB 样本对 1 GB 分片就是 3400 倍。改成对象存储 + 分片级索引（清单文件）或 KV 型索引，牺牲吞吐换 O(1) 定位。这条翻转的判据：单次取样的字节数 ÷ 分片粒度 < 1/100 就别合并。出处：05 章 31 题、04 章 34 题。

3. ★ 推理网关做实例选择，候选打分依据：排队请求数 / GPU 利用率 / KV Cache 剩余块数 / 历史 P99。选哪个当主信号，其余各留下做什么？
   【要点】主信号 = KV 剩余块数（它直接决定这个实例还能不能接下一个请求，尤其是长 prompt），排队数做二级，P99 只做告警不做路由，利用率丢掉。理由：decode 阶段受显存带宽限制，利用率能同时出现在「快满」和「快闲」两种状态（06 章 1–2 题）。塌了的现象：路由后新请求 TTFT 抖动加剧、被选实例的 KV 在 1 秒内被打穿。出处：06 章 12 题、06 章 8 题。

4. 淘汰策略候选：LRU / LFU / FIFO / W-TinyLFU。分别放到「顺序 epoch 全量读」和「多租户共享前缀」两种负载上，哪个组合选哪个？
   【要点】顺序全量读下三者趋同（无复用可淘汰，准入才是决定项），W-TinyLFU 的准入优势要在有 lookahead、有热前缀时才出现；共享前缀场景选 W-TinyLFU + 前缀感知的准入。答完必须补一句「这个差异在小 lookahead 下测不出来」，否则就是背结论。出处：18 章 43 题、04 章 17 题。

5. 线性一致读候选：ReadIndex / LeaseRead / 直接读 Leader。什么场景选哪个，时钟前提各自是什么？
   【要点】ReadIndex 多一次心跳确认，QPS 高时把 Leader 打成瓶颈；LeaseRead 靠时钟稳定换性能，lease 依赖时钟漂移上界，跨机房或 NTP 抖动的集群上会读到旧值；纯读 Leader 最简单但失去分片。判据给法：读多写少 + 同机架（RTT 0.1–0.5 ms）选 LeaseRead，跨可用区（1–10 ms）选 ReadIndex，读占比 >90% 且要吞吐就加 follower 陈旧读并显式声明一致性等级。出处：04 章 9 题、04 章 2 题。

6. 元数据索引候选：B+ 树 / LSM-tree / 全内存哈希（bitcask 模型）。给两条判据把它们分开。
   【要点】判据一读写比：写读比 >1:10 偏 LSM，读远大于写且 key 可全放内存偏 bitcask。判据二「索引内存 ÷ 数据量」比值：key 短、数量 10⁷ 量级时全内存放不下，比值决定它什么时候出局。B+ 树在范围扫描上赢，LSM 在追加写下赢，代价是 compaction 抢 I/O，把前台 P99 拉出毛刺。出处：04 章 17 题、04 章 34 题。

7. ★ 冗余策略候选：三副本 / EC 8+3 / 热数据副本 + 冷数据 EC。checkpoint 与训练热集分别选哪个？
   【要点】checkpoint：三副本或对象存储 + 异步转 EC，别用同步 EC 写；理由是 checkpoint 是突发大块写 + 要立刻可恢复，EC 的重建读放大在恢复期会拖长停机。训练热集：判据是读放大，容量排在其后；缓存可重建时副本数可以降到 1–2。算式要写出来：EC 8+3 恢复一个 1 GB 块要读 8 块 ×125 MB，重建流量 = 数据的 8 倍，这条决定了它不适合放在恢复窗口紧的路径上。出处：04 章 12 题、04 章 13 题。

8. ★ 把数据从页缓存送到用户态/显存，候选：read+write / mmap / sendfile / splice / O_DIRECT / GDS。按「数据要不要被程序碰一次」分两路各选什么？
   【要点】不碰（纯转发、镜像分发）：sendfile/splice，省两次拷贝两次 syscall。要碰（解码、增广、算子）：O_DIRECT + 自己的缓冲，绕开双重缓存，代价是丢掉页缓存复用，重复读同一块时命中率归零。进显存且对齐要求满足才上 GDS。判据：单次读重复消费同一数据 ≥2 次就别 O_DIRECT。出处：01 章 3 题、01 章 7 题。

9. 高并发 I/O 模型候选：线程池阻塞读 / epoll + 工作线程 / io_uring / Reactor / Proactor。数据面是 GPU 喂数（大块顺序读）时选哪个，控制面是网关（大量小连接）时选哪个？
   【要点】数据面：io_uring 或 O_DIRECT + 固定线程池，重点是批量提交把 syscall 摊薄（一次 syscall ~1–3 μs，每秒几百万次的账在 15 章）；Reactor 的边缘触发对 epoll 有意义但对顺序大读没意义。控制面：epoll + 事件循环足够，io_uring 的收益来自 syscall 数，与连接数无关。答完要承认：瓶颈在 Python 侧时换 I/O 模型没用（05 章 34 题）。出处：01 章 8 题、01 章 30 题。

10. GPU 隔离候选：整卡 / time-slicing / MIG。推理服务在线 SLO 与离线批处理混部时怎么分？
    【要点】在线延迟敏感给整卡或 MIG 的固定切片（有独立显存与 SM 配额，故障域小）；time-slicing 便宜但延迟尾部分布会变胖，只给离线。取舍写具体：MIG 切 7 份后单份显存放不下模型就要退回整卡，这是硬约束。出处：03 章 10 题。

11. 服务发现与转发候选：iptables(Kube-proxy) / IPVS / 用户态网关直连。推理网关需要按 KV 状态选实例时，前两个为什么不够？
    【要点】iptables/IPVS 是连接级四元组负载均衡，拿不到请求长度和实例内部状态；要做 KV 感知必须把路由决策收到应用层网关，K8s 只提供端点信息与健康位。代价：自己维护 endpoint 同步与连接池，informer 缓存陈旧会带来错调度。出处：03 章 18 题、18 章 30 题。

12. ★ 跨机训练通信候选：RDMA（RoCE/IB）/ TCP。你没集群权限、机房异构、运维只有你一个人时怎么选？
    【要点】把「带宽」和「故障域」分开算：RDMA 省 CPU、延迟低，但 PFC/ECN/MTU 三前提任一不满足就性能崩且难定位；TCP 慢 2 倍却处处能跑、可观测性好。零起点约束下选 TCP 跑通端到端，再把 RDMA 做成旁路传输组件（独立进程 + 薄 C ABI），别在热路径上做第一次集成。出处：01 章 51 题、20 章 12 题。

13. ★ 多轮 agent 会话要做 KV 复用，候选：引擎内 prefix cache / 宿主内存 swap / 宿主 NVMe 文件层 / 远端 KV 池（Mooncake Store、LMCache）/ RDMA 传输（NIXL）。会话长度 5–50 轮、请求跨实例、进程要能重启，选哪个、怎么组合？
   【要点】跨实例复用必须出引擎，落到远端 KV 池加精确索引；宿主 NVMe 文件层只在同一台机器上进程重启后还有效（vLLM 的 `OffloadingConnector` 有 fs tier）；RDMA 传输要命中收益覆盖搬运时间才值，判据写成百分比：一次跨层取回的时间低于该请求剩余 decode 时间的某个阈值才放进关键路径。会话是否 sticky 是第一条前提，llm-d 1.0 起有 session-aware routing 与 `previous_response_id`，这决定命中率归属哪一层。塌了的现象两种：命中率涨但 TPOT 也涨，说明搬运进了路径；池容量涨但命中率不涨，说明准入策略失效（W-TinyLFU 那条线，04 章 17 题）。出处：06 章 29 题、30 题。

14. ★ 网关要拿实例的 KV 状态打分，候选：拉 `/metrics` 聚合指标 / 订阅引擎 KV 事件（ZMQ）/ 网关内本地近似前缀索引 / 外部元数据服务存索引。500 实例、block 事件高频、网关本身要无状态。
   【要点】四条路的陈旧度、扇出量与恢复语义各不相同。拉指标最便宜，但 `vllm:prefix_cache_queries`、`vllm:prefix_cache_hits` 只给聚合值，给不出哪个前缀在哪台机器；订阅事件精确，代价是扇出量（500 实例 × 每秒 block 生命周期事件）与断线重放（`--kv-events-config` 的 `replay_endpoint`、`buffer_steps`）；本地近似索引无外部依赖、跨引擎通用，会随淘汰偏离真实，用 `vllm:kv_block_idle_before_evict_seconds` 能量出偏离度；外部元数据服务换来网关重启后索引不丢，代价是新增一个强一致依赖，它的翻转条件见本章 C 组。先算事件量级再选，算不出就用近似方案并声明陈旧度上界。塌了的现象：打分抖动导致请求在两三个实例间来回，命中率反而下降。出处：06 章 28 题、19 章 26 题。

## B · 错配：面试官递一个用错的方案（15–26）

答法固定：① 先复述他方案要解决的问题（表明你听懂了）；② 指出它成立的哪一条前提在这个场景不成立；③ 给出可观测的失败现象；④ 给替代并说代价。不许一上来就说不行。

15. ★ 面试官：「训练样本缓存层我们打算用 Redis。」
    【要点】前提冲突：Redis 的价值在内存延迟 + 简单数据结构，训练样本是大 value、要顺序扫、可重建。账：主存 vs NVMe 的每 GB 成本差一个量级以上，缓存 10 TB 热集用内存等价于买几十块 NVMe。大 value 还会阻塞单线程事件循环（几百 MB 的 value 一次 GET 就卡住整个实例）。替代：本地 NVMe + 元数据放 etcd/自建索引，Redis 只留小对象（请求幂等键、配额计数）。追问「我们要低延迟」时补：样本读延迟只要低于 step 时间的 5% 就够，把延迟压到 μs 是浪费。

16. ★ 「模型 checkpoint 用 EC 8+3 存，省两倍空间。」
    【要点】省的是稳态容量，付的是恢复时间与重建放大。checkpoint 的负载是突发大块写 + 故障时要立刻全量读回；EC 写要做编码与分散落盘，恢复单块要读 8 份。故障常常发生在多任务同时跑的时候，重建流量会挤占训练读带宽，形成第二个故障源。替代：热副本 + 归档转 EC，或对象存储（本来就是 EC）+ 本地留最近 N 份。

17. ★ 「我们按 GPU 利用率做 HPA 弹性伸缩。」
    【要点】利用率在推理场景语义模糊：decode 阶段受带宽限制，利用率 30% 可能是带宽打满，也可能是队列积压；它还是滞后量，扩缩容正反馈的第一环（12 章 9 题）。替代信号：KV Cache 剩余块数、排队时长、TTFT 分位。代价要认：自定义指标接入 HPA/KEDA 需要自己保证指标可用性与延迟，指标挂了会退化成不扩。出处：06 章 12 题。

18. 「实例响应变慢，我们把 Liveness 探针超时调短一点，早点杀掉重启。」
    【要点】慢不等于死，杀进程丢的是在途请求与模型加载时间（权重重加载按 15 章算：70 GB 模型走存储到显存的分钟级开销）。可用实例越少，剩余越忙，越容易被继续摘，这就是健康检查误摘除那条最难发现的路径（表象像自愈）。改法：Readiness 摘流量、Liveness 只在真死时重启，超时对齐 P99。出处：12 章 9 题。

19. 「Prefix cache 打开就行，所有负载都受益。」
    【要点】收益等于前缀重复率，短随机 prompt 场景命中率接近 0，但索引、哈希、块元数据、锁竞争的成本一直在付。先测重复率再决定：同一会话/同一模板系统 prompt 才成立；判据要写成数值阈值。替代：按租户/模板维度开启，或只做系统 prompt 常驻。出处：06 章 8 题、19 章 26 题。

20. ★ 「显存放不下就 swap 到主机内存，vLLM 有这功能。」
    【要点】PCIe 4.0 x16 有效 ~25 GB/s，HBM 2–4.8 TB/s，两个量级以上的差距：swap 后的访问延迟直接进入每 token 路径，吞吐下降远大于你腾出显存的收益。它用来「不丢请求」，扩容不能靠它。替代顺序：量化权重 / chunked prefill / 准入控制限并发 / PD 分离，最后才谈 offload。出处：06 章 8 题、15 章带宽表。

21. 「全部走 O_DIRECT，绕开页缓存更可控。」
    【要点】可控的前提是每个字节只被消费一次。重复读小文件、多任务共享同一热集时，页缓存是免费的第一层缓存，绕开它等于把命中交给自己的缓存策略，而你的策略大概率不如内核的准入成熟。改法：大块流式读走 O_DIRECT，元数据/清单/小对象走 buffered I/O。出处：01 章 7 题、05 章 31 题。

22. 「换成 io_uring，QPS 应该就能上去。」
    【要点】io_uring 摊薄 syscall，前提是负载卡在系统调用上。CPU 卡在 Python 迭代、collate、锁或 GIL 时，换 I/O 模型收益为 0；先按 USE 定界（07 章 2 题）再决定。答法里给出「我怎么证明它现在卡在系统调用上」的证据：strace 计数、perf 的 syscall 占比、每请求 syscall 数 × 量级账（15 章一题）。出处：01 章 8 题、05 章 34 题。

23. 「Score 插件里同步调一次缓存服务的 RPC，拿最新就绪状态。」
    【要点】Score 每对 (节点, Pod) 都执行一次，几百节点下 RPC 数量 = 节点数 × 排队 Pod 数 × 调度周期，调度器吞吐直接崩，还会把缓存服务打成单点。本地 informer 缓存陈旧换调度吞吐是正确取舍，代价用 TTL 与降级路径写死。出处：18 章 30 题。

24. 「训练集挂 NFS，客户端越多越省存储侧带宽。」
    【要点】省的是数据面，不省元数据面。小文件场景每文件的 open/getattr 都打到服务端，NFS 属性缓存让客户端看到的是陈旧目录树，扩容时先炸的是元数据 QPS。客户端数增加还会让同机架带宽成为新瓶颈。判据：单目录条目数 × 打开频率。出处：04 章 13 题、11 章 1 题要点。

25. 「日志和指标全打进 Kafka，背压问题就没了。」
    【要点】背压只是搬到 broker 和客户端缓冲区。客户端内存攒批有上限，满了之后要么阻塞业务线程要么丢数据，必须事先决定丢哪一类；指标链路要能容忍丢，审计链路不能。改法：分级（采样 / 本地预聚合 / 直连），并把「满了怎么办」写成显式策略。出处：07 章 2 题。

26. 「为了安全，GPU 训练任务全跑在 gVisor 里。」
    【要点】用户态内核的系统调用要翻译，块 I/O 与 GPU 直通路径上的开销在小文件和高频 ioctl 上放大，冷启动也变慢。隔离强度、冷启动、密度三者不能同时拿满。替代：不可信代码进沙箱，自己的训练代码用普通容器 + 资源与网络策略；GPU 直通要先核实支持矩阵。出处：09 章 36 题。

## C · 边界翻转：找出让答案掉头的那个约束（27–32）

这类题没有固定答案，考的是你能不能把「前提」说成一个可观察的量。每题要求交付三件：翻转点、翻转前的可测征兆、翻转后要换的方案。

27. ★ 一个多租户缓存层，租户从 5 家涨到 500 家。容量、命中率、成本三个约束都没变，哪个决策先翻转？
    【要点】先翻的是公平性与记账方式：手工配额在 5 家时够用，500 家必须变成 per-tenant 令牌桶 + 自动账单；共享缓存让成本摊不回单租户，摊不回来定价就失真。容量与命中率是二阶的。出处：11 章 2 题要点。

28. ★ 预取副本 fanout 从 2 涨到 3。字节成本线性涨，命中收益边际递减，最优点出现在哪条曲线上？
    【要点】把两条曲线写进同一个式子：预取字节 = fanout × 数据量 × 预取比例；命中收益 = 命中率增量 × 省下的回源时间。最优点在边际收益（多一个副本换来的命中率增益 × 单位回源成本）低于边际成本（一份副本的字节费）处。判据要能算：连续两档 fanout 的每 GB 成本增幅超过 2 倍就停。出处：18 章 32 题。

29. ★ KV 前缀索引的 block 粒度 256 token。什么条件下该调小，什么条件下该调大？
    【要点】调小的收益是命中粒度细、前缀截断浪费少；代价是事件量与索引条目膨胀（block 数 ÷2，事件 ×2）。调大的收益是索引小、哈希少；代价是长尾请求截断浪费。分界看请求长度分布：短请求为主且重复率高 → 小；长请求为主、共享率低 → 大。出处：19 章 26 题。

30. 三副本与 EC 8+3 的交叉点。容量、写放大、重建时间三条线，哪一条先逼你换方案？
    【要点】通常先逼人的是重建时间：集群越大，单盘故障越接近日常事件，EC 重建读 8 份的流量在故障窗口里挤占业务带宽，SLA 先崩的是恢复。写放大第二，容量第三。答完给一句：小集群（<50 节点）容量压力根本排不到第一位。出处：04 章 12 题。

31. ★ 什么条件下你会推翻「元数据用 etcd、不自研 Raft」这个决定？
    【要点】三个反例条件：你要的语义超出强一致元数据（例如带缓存状态同步的复制语义），etcd 的数据模型装不下；etcd 的写放大与租约模型压不住你的 QPS；部署面受限（不允许依赖外部 KV）。条件要具体，「etcd 慢」不算理由，要给数值。出处：20 章 1 题。

32. 持续预取从异步改成同步，什么场景下同步反而更快？
    【要点】源站本身很快、缓存欠配、fanout=1 时，异步预取的排队、准入决策、去重与索引更新都是纯开销，同步读直接命中带宽上限。另一个是阶段切换后重预取：上一阶段的预取预算还没花完，异步会与新阶段抢带宽。判据来自阴性子区间比例，别只讲方向。出处：18 章 33 题。

## 本章的用法

1. 一轮只练一类。A 组练归类，B 组练顶住预设，C 组练找阈值，混着练会三类都浮在表面。
2. 每次答完挑一列补深。多数人的短板是第 ③ 列（说不出现象），因为这列需要真实跑过的数据，装不出来。
3. 答不出第 ② 列（成立前提）时不要背题，回去把对应机制章那道题重答一遍：本章只考迁移，机制本身在 01–10 章。
4. B 组加一条硬规矩：不许在没复述对方目标的情况下开口反驳。校招里最差的观感是「你这个不对」连着三条理由，而没说清对方想解决什么。
