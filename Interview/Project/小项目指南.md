### 5.2 S2 RDMA 传输

**背景**

P1 的 P2P 走 gRPC stream，RDMA 是网络数据面的核心考点。Mooncake、NIXL、UCX 已经把生产级传输做完了，这一项复用的是机制理解与接口实现能力，不造新轮子。

**前置**

需要一套能在上面跑 Verbs 代码的 RDMA 环境，以及一个可对照的普通 TCP 路径。硬件选择上有三条路，按成本和真实性权衡：

第一条，普通 CPU 通用计算型 ECS 两台，按需计费，不勾选任何特殊网卡。在本机或其中一台 ECS 上用 Linux 内核自带的 `rdma_rxe`（Soft-RoCE）做机制验证。成本最低，确定性最高，C 代码和 Go 适配器的接口逻辑完全可以在没有真实 RDMA 硬件的情况下调通。缺点是 Soft-RoCE 的数字只能用于功能验证，性能不可采信。

第二条，支持“启用 EFI”的 CPU 通用计算型 ECS 两台，购买时在网络配置的扩展网卡处勾选“启用 EFI”，开启华为云自研的 vRoCE。勾选本身不额外收费，成本主要来自 ECS 实例本身。比 Soft-RoCE 更接近真实 RDMA 路径，但仍不是 IB，性能数字同样只适合自己参考，不进简历。

第三条，超高性能计算型 H2 实例两台，自带 100Gb/s EDR InfiniBand 网卡（Mellanox ConnectX-4），是华为云上能在预算内摸到真实 IB 硬件的入口。代价是 H2 起步 16 vCPU、128GB 内存，按需费用需要登录控制台确认实时报价；关机仍然计费，停止扣费唯一方式是删除实例；删除后本地 SSD 数据清空；私有镜像需手动安装 Mellanox OFED 驱动（建议 4.2-1.0.0.0 版本）。这条路的定位是“浅尝辄止”：在真实 IB 网卡上跑通 `ibv_devinfo`、`rping` 和你的 verbs 链路，获得开/关 RDMA 的对比感受，但不对 IB 相比 RoCE 的性能优势下结论。**注意：H2 没有 GPU，它只适合纯 CPU 通信项目，补不了任何 GPU + NCCL + IB 的联合测试。**

我的选择顺序：先用第一条把机制跑通，再视预算决定是否升到第二条或第三条。三条路的 Verbs 代码是同一套，换硬件不需要改接口。

**具体执行步骤**

1. 按选定路径租用两台实例，放在同一 VPC、同一子网内，确保网络互通。按需计费，不用竞价实例。
2. 理清四个 verbs 对象的生命周期：PD 是保护域，MR 是注册过的内存，QP 是队列对，CQ 是完成队列。QP 要按 INIT → RTR → RTS 迁移，参数里目的 QPN、rkey、GID 一项都不能错。
3. 数据面用单边 Write 配预注册槽位。接收端启动时注册 8 个 1MB 槽位，把地址与 rkey 经控制面发给对端；发送端直接写，不要求对端提前 post receive。双边 Send/Recv 需要接收端预先挂缓冲区，延迟多一跳，适合控制消息。
4. 注意 `ibv_reg_mr` 会锁页并建立地址翻译，耗时随内存大小上升。4KB 小块按需注册会被注册开销吃掉，所以槽位预注册、按需只做一次地址交换。
5. CQ 用轮询。Soft-RoCE 上事件通知会丢，轮询是被迫选择，代价是一个核被占满。
6. 跨语言用独立 C 进程加 C ABI，四个函数：init、write、poll、shutdown。cgo 每次调用有 2 到 5 微秒切换开销，CQ 轮询放 C 进程更干净；Go 的切片地址会被 GC 移动，注册过的内存必须由 C 侧分配并通过句柄引用。
7. 数据面协议：控制面走 gRPC 交换槽位地址与 rkey，数据面走一条 Write，完成后由 CQ 通知 Go 侧。
8. 跑 `rping` 双向验证，再按块大小 4KB、256KB、4MB 三档各 1000 次采延迟数据，记录 P50 与 P99；同时采注册耗时曲线。如果走的是 H2 路径，额外存下 `ibv_devinfo` 输出和 IB 设备状态，作为“在真实 IB 网卡上走过基础链路”的凭证。
9. 测完立即删除实例（H2 关机仍计费，必须删除），先把数据拷走。

**验收**

`rping` 双向通过；块大小 4KB、256KB、4MB 三档各 1000 次，P50 与 P99 有数；注册耗时曲线有数；结论明确写“功能可验证、性能不可采信”，任何 Soft-RoCE 或 vRoCE 数字不进简历。若走了 H2 路径，边界报告里注明 IB 部分只做了设备层与基础链路验证，未做 GPU + NCCL 联合测试，未对 IB 与 RoCE 的性能差距下结论。

**弹药**

Write 与 Send/Recv 的取舍；GC 移动内存导致注册失效、跨子网丢包不重发两个坑；三档延迟曲线与注册耗时；三条硬件路径的成本与真实性权衡（Soft-RoCE 最便宜但数字不可采信，vRoCE 居中，H2 有真 IB 但无 GPU 且关机仍计费）。

**讲法**

先说为什么不在主路径上用 RDMA，再说这条臂验证了哪些机制，最后用一句“真实性能要 eRDMA 或 IB 才能采信”收口。被问到硬件时说清楚：机制验证在 Soft-RoCE 或 vRoCE 上完成，IB 只在预算允许时用 H2 做了设备层浅尝，没有把 IB 经历模糊成 GPU 分布式训练经验。


### 5.3 S3 SLO 校准与回放台

缺口：Pact 第 9 节给了预测的四步计算，第 10 节给了四类处置，两节都缺实测数据上的校准与策略对照。上游的 SLO 调度工作偏策略设计与仿真，公开的校准报告很少，这部分能力通常只在服务商内部。

交付物：一个纯 CPU 仓库，含 trace 加载、预测器、校准报告、漂移检测、回放器、一页结论。

范围：离线批处理。不接在线控制面，不做模型训练平台，不做 GPU 推理。

设计：

1. 输入 schema：每请求一行，字段有到达时刻、输入 token 数、输出 token 数、前缀命中深度、排队时长、每个 prefill 分段时长、每步 decode 时长、是否取消、副本 ID、SLO 阈值。公开 trace 缺字段时插值，并在报告里标“推断字段”。
2. 标签构造注意三件事。窗口内未完成的请求没有标签，做右截断；违约率通常很低，按时间分桶重采样并记录前后分布；特征只能用入队时刻可见的量，输出长度只能用同类历史分布。
3. 预测器两条基线先跑：历史同长度分位数、Little 定律估算（并发乘平均服务时间）。主力模型用分桶回归或 GBDT，输出概率，另给区间。
4. 校准四步：按概率分桶画可靠性图；算 Brier 与 ECE；用等距回归或 Platt 缩放做后处理并比较；按副本、负载类型、命中深度切片，找出失效的那一档。
5. 漂移检测用 PSI 或 KL 散度滑窗，输入分布与时延分布各一条。阈值取校准误差开始上升的位置。人为把到达率翻倍，验证告警在多长时间内触发，并给重校准触发条件。
6. 回放器事件驱动，时间轴按到达与完成推进。四类动作各一个决策点：准入拒绝、降级、扩容加副本并预热、按副本余量路由。每个动作带迟滞与冷却，代价表把拒绝损失、质量折损、扩容成本、跨域时延折到同一单位。
7. 结论部分回答两件事：哪类动作在哪种负载下有效；预测误差放大到 ±20% 时收益还剩多少。

验收：校准前后各有可靠性图与 Brier、ECE；漂移告警表；四类动作的违约率与成本对照；敏感度曲线；一个失败案例归到特征、标签或漂移。

弹药：概率校准与点预测的取舍；右截断标签、类别不平衡、时间泄漏三个坑；Brier、ECE、动作对照、敏感度四组数据。

讲法：先说为什么交付概率、布尔判定在哪些场景失效，再说校准没通过就不允许自动处置，最后用一张动作对照表说明收益来自哪里。


### 5.7 M4 外部口径校验

缺口：Pact 引擎侧在进程内埋点，有侵入也可能有偏差。外部探针不改代码，但只能看到函数边界。两套口径需要一次对齐。

交付物：偏差表、开销表、一条判定规则、一条不一致案例。

范围：两天量级，附录题。不改 vLLM 源码。

设计：

1. 挂点选 `Scheduler.schedule` 与 `execute_model`，再加每步输出处。CPU 后端与 GPU 后端分开登记，GPU 后端只挂宿主侧 Python 函数。
2. 用 bpftrace 的 uprobe 记录进入与退出时间，采样率可配。Python 符号解析不稳时固定解释器版本与符号表。
3. 对齐按 request id 或到达顺序，对到账本记录。偏差拆成两部分：时钟源差异（CUDA event 与单调时钟）与插桩位置偏差。
4. 开销：开与关探针对 TTFT、ITL、吞吐的影响，采样率变化对开销与丢事件的影响。
5. 污染声明：为了观测关掉 async scheduling 会改变被测行为，这一点必须写进结论。

验收：三个阶段的偏差 P50 与 P99；开销百分比；判定规则一句话；一条对不上的请求拆到阶段。

弹药：外部观测与进程内打点的取舍；观测污染、符号漂移两个坑；偏差分布。

讲法：先说两套口径各自看到什么，再说偏差来自哪里，最后给判定规则。


### 5.8 N1 DDP→ZeRO 显存账

**背景**

P1 是数据流与缓存主线，训练并行侧没有材料。面试问显存公式时只能背书，说不出实测差在哪、什么规模下分片才划算。

**前置**

需要一台能跑双卡、且显存可被 PyTorch 正确观测的 GPU 实例。硬件选择上的权衡：

第一条，2 卡 T4 直通实例，推荐 `pi2.4xlarge.4`（2×T4，每卡 16GB 显存），或两台单卡 Pi2 实例。T4 是直通整卡，显存可观测，官方定位包含轻量级训练场景，对你的 GPT-2 small 或 6 到 10 层 Transformer、BF16 加 AdamW、双卡不追求收敛的规模完全够用。按需计费，测完立即释放。这是本项目的首选路径。

第二条，V100 的 P2s/P2v 实例。性能更强，但对这个不追求收敛的小规模验证来说过剩，价格也更高。除非你同时要跑别的重负载，否则没必要。

第三条，任何 GPU 裸金属或 8 卡实例。本项目明确不做大规模，用不上，也不该为它花钱。

**不需要 RDMA。** 本项目的通信发生在同一台机器内部，走 PCIe，完全不经过网络。H2 的 IB 网卡在这里帮不上忙，不要为这个项目租 H2。**不需要整卡之外的任何网络特殊配置**，购买时也不用勾选 EFI。

**具体执行步骤**

1. 租一台 `pi2.4xlarge.4`（2×T4）或两台单卡 Pi2，按需计费，放在同一可用区。镜像选带 CUDA 和 PyTorch 的公共镜像或你自己的私有镜像。
2. 搭好 GPT-2 small 或 6 到 10 层 Transformer 的训练脚本，BF16 加 AdamW，双卡，不追求收敛，跑通即可。
3. 先写公式：每参数 16Ψ 字节——参数 2、梯度 2、Adam 一阶与二阶各 4、fp32 主权重 4。ZeRO-1 分片优化器状态后是 4Ψ + 12Ψ/N；ZeRO-2 再分片梯度，是 2Ψ + 14Ψ/N。公式预测值单列一列，准备和实测对照。
4. 分别跑 DDP、ZeRO-1、ZeRO-2 三种配置，每种配置用 PyTorch profiler 或 `torch.cuda.max_memory_allocated` 采峰值显存，同时记录稳定步耗时和通信占比，三者同表。
5. 对照公式与实测，解释实测降幅为什么小于理论值：激活显存与层数、batch、序列长度成正比，不参与分片。
6. 重点测“2 卡 ZeRO-1 变慢的条件”：DDP 每步一次 all-reduce，通信量约 2Ψ；ZeRO-1 每步多一次 all-gather，量级 Ψ，小卡数下这次通信摊不薄。把变慢的边界条件用一组数据支撑出来。
7. 保存原始数据表、profiler 记录和可复现脚本。测完立即释放实例。

**验收**

原始数据表与公式对照齐全；2 卡 ZeRO-1 变慢的条件能说清；边界条件有一组数据支撑。一页笔记里含公式、实测表、profiler 记录、可复现脚本。

**弹药**

实测降幅小于理论值的原因；小卡数下 DDP 更划算的边界；all-reduce 与 all-gather 的占比；硬件上为什么选 T4 直通而不是 V100 或裸金属（规模匹配、显存可观测、成本可控，本项目不走网络所以不需要 RDMA 和 IB）。

**讲法**

先写公式，再给实测差，最后说清什么规模下分片才划算。被问到硬件时说清楚：双卡 T4 直通就够，通信在机内走 PCIe，这个项目从头到尾不碰 RDMA，也不需要为 IB 花钱。

### 5.11 N4 NCCL 与恢复 runbook

**背景**

08 章 30、31 题有参数名与 checkpoint 的账，12 章 12 题有 NCCL 超时排查，都停在知识层。真上集群后第一步敲什么、看哪行输出、什么值算正常，没有一张表。这一项补的是上机流程，不是通信优化本身。

**前置**

这个项目拆成三层，每层对硬件的要求不同，需要分开租、分开测。

第一层，gloo 四进程恢复流程。**只需要一台普通 CPU 通用计算型 ECS**，不需要 GPU，不需要 RDMA，不需要 IB。按需计费，跑几小时就删。这是三个层次里成本最低、确定性最高的部分，建议最先做。镜像选你熟悉的 Linux 发行版，Python 和 PyTorch 环境装好即可。

第二层，单卡双 rank 读 NCCL 输出。需要**一台带 GPU 的实例**。硬件选择上：T4 直通实例（`pi2.2xlarge.4` 或 `pi2.4xlarge.4`）够用，T4 提供 GPU 硬件直通能力，显存 16GiB，单卡起两个进程用 NCCL backend 做拓扑输出解读完全足够。V100 的 P2s/P2v 性能更强但对这个“读输出、认路径”的目的来说过剩，没必要多花钱。**不需要 IB**：单卡双 rank 的 NCCL 通信走的是卡内 P2P/IPC 或 SHM，不经过网络，IB 在这里帮不上忙。如果你同时做 5.8 的显存账，复用同一台 T4 实例即可，不额外租机器。

第三层，nccl-tests 的 `all_reduce_perf` 扫描和 busbw 曲线。**这是唯一涉及多卡网络通信的部分，也是 IB 需求真正出现的地方，但需要 GPU + IB 同时存在。** 华为云上带真实 IB 的实例是 H2（100Gb/s EDR InfiniBand，Mellanox ConnectX-4），但 H2 是纯 CPU 实例，**没有 GPU**，跑不了 NCCL 的 GPU 通信测试。带 GPU 又带 IB 的按需入口主要是裸金属或 GPU 集群规格，成本远超你之前设定的预算。所以这一层有两种处理方式：要么接受“busbw 曲线在 vRoCE/以太网口径下采集，注明不是 IB 结论”；要么把 IB 部分标注为“因成本约束未实测”，用数字账外推，外推假设在讲法里报出来。**不要为了凑这条曲线去租带 IB 的裸金属。**

关于 vRoCE：如果你手头的 CPU ECS 规格支持“启用 EFI”，可以在网络配置的扩展网卡处勾选，免费开启 vRoCE。但 vRoCE 是华为云自研的虚拟化 RDMA，不是 IB，性能数字的口径需要自己标明。这个项目对 vRoCE 的需求是“可选”，不是“必须”。

**具体执行步骤**

1. **第一层，gloo 四进程。** 租一台普通 CPU ECS，按需计费。`torchrun --nproc_per_node=4` 配 gloo backend，跑 DDP 加 DCP checkpoint，量恢复四段时间：检测（进程死到判定死）、定位隔离、rendezvous、checkpoint 加载与预热。打点位置是进程启动、rendezvous 完成、load 完成、第一个 step 完成。四类注入各跑一遍：杀 rank、断连（停 store 端口或 iptables 丢包）、慢节点（一个进程里加 sleep 或限 CPU 配额）、写满盘（checkpoint 目录所在文件系统填满）。每类记四段时间与告警是否触发。gloo 数字标明口径，不当集群结论。
2. **检测段先调。** `init_process_group(timeout=...)` 默认 30 分钟，改成 5 分钟并打开 `TORCH_NCCL_ASYNC_ERROR_HANDLING`，量四段里第一段的变化。配 `--max-restarts`（默认 0，不开则自动重启不发生）。
3. **第二层，单卡双 rank 读 NCCL 输出。** 租一台 T4 实例（`pi2.2xlarge.4` 单卡即可，如果同时做 5.8 就选 `pi2.4xlarge.4` 双卡）。同一张卡起两个进程用 NCCL backend，开 `NCCL_DEBUG=INFO` 与 `NCCL_DEBUG_SUBSYS=INIT,GRAPH,ENV,TUNING`，逐段注解：INIT 段走 P2P/IPC 还是 SHM 还是 Socket，GRAPH 段的 ring 顺序与 channel 数，ENV 段实际读到的变量。改 `NCCL_ALGO`（Ring/Tree/NVLS）与 `NCCL_PROTO`（LL/LL128/Simple）看选路怎么变。
4. **第三层，size 扫描。** 在同一台 T4 实例上跑 nccl-tests 的 `all_reduce_perf`，扫 message size 8 B 到 1 GB，画 busbw 曲线，标硬件上限。小 size 段低是延迟主导，大 size 段仍低于上限才是通信有病。ring 的 busbw = algbw × 2(N−1)/N。**口径标注：这是单机双卡/多卡走 PCIe 和 vRoCE（如启用）的数字，不是 IB 结论，不进简历。**
5. **恢复侧的账写成公式。** 70B 混合精度 Adam 每参数 16 字节共 1.12 TB，分片到 1024 卡每卡 1.1 GB；一千客户端同读一份对象存储时元数据先撑不住，所以每 rank 写自己的分片。保存间隔按 √(2 × 保存成本 × 平均故障间隔) 定。
6. **读三份：** MegaScale（NSDI‘24，万卡故障分类与 per-rank 诊断）、Gemini（SOSP’23，邻居主机内存冗余 checkpoint）、PyTorch DCP 与 torchelastic 文档。
7. **填 runbook 空格。** gloo 四段时间用第一层实测填；NCCL 拓扑注解用第二层实测填；busbw 曲线用第三层实测填，并在表头注明硬件口径（T4 直通 + PCIe / vRoCE，非 IB）。**测完立即释放所有实例**，H2 关机仍计费所以如果租了 H2 必须删除，T4 实例按需释放即可停止计费。

**验收**

runbook 每条四栏齐全；gloo 四段时间有实测值且标明口径；NCCL 三段调试输出能逐段解释；云窗口后 busbw 曲线有实测值，并标注硬件口径（T4 直通 + PCIe/vRoCE，非 IB）；PCIe 与单卡双 rank 的带宽数字不进简历。IB 部分若未实测，边界报告里明确写“因成本约束未在 IB 上采集 NCCL busbw 曲线，GPU + IB 联合测试留待有预算的云窗口”。

**弹药**

三种病因分法（延迟主导、带宽主导、慢节点）；检测段默认 30 分钟这个误诊源；1.12 TB 分片账与保存间隔公式；慢节点常被误判成网络故障，治它在数据加载侧；硬件分层账（gloo 用 CPU ECS 零 GPU 成本，NCCL 拓扑解读用 T4 直通，busbw 在 T4 上走 PCIe/vRoCE 口径采集，IB 因无 GPU + IB 按需入口且 H2 无 GPU 而留作外推）。

**讲法**

先说没集群时练的是读输出、认路径、四段账，再说上机后第一步量什么，最后用一次云窗口的实测收口。被问到 IB 时说清楚：gloo 恢复流程和单卡双 rank NCCL 解读都不需要 IB，我在 T4 上完成了这两层；busbw 曲线是 T4 直通 + PCIe/vRoCE 口径，不是 IB 结论。被问规模就答 2 到 4 rank 加数字账外推，外推假设报出来。
