# RDMA 传输与 TrainCache 实战指南

## 这个项目要干什么

两件事，按顺序做：

1. **系统性学 RDMA Verbs 机制**：用 Soft-RoCE 在一台机器上把 PD、MR、QP、CQ 的创建销毁、QP 三段迁移、单边 Write、完成通知全部手敲一遍。目标是看到一段 Verbs 代码知道它在干什么，出错了知道看哪里。
2. **为 TrainCache 写一个可复用的传输模块**：学完之后产出的不是孤立 demo，而是一个包含 `init`、`register_buffer`、`write`、`poll_completion`、`shutdown` 五个函数的 C 模块，Go 通过 cgo 调用。这个模块的逻辑在 Soft-RoCE 上验证，功能和稳定性在真实 RoCE 实例上验证。

**不做的事：** 不碰 IB（没有设备，准入成本太高），不测 Soft-RoCE 的性能数字（软件模拟的数字没有采信价值），不做 GPU + NCCL + RDMA 三合一（TrainCache 是平台侧数据流，不走 NCCL）。

硬件路径：**Soft-RoCE 学机制 → 真实 RoCE 验模块**。华为云 vRoCE 或阿里云 eRDMA 都可以，两者都“无偿启用”，不额外收费，成本主要在 ECS 实例本身。


## 第一部分：Soft-RoCE 上学 Verbs 机制

### 要哪台机器

一台普通 CPU ECS。不需要 GPU，不需要 RDMA 网卡。按需计费，测完释放。

### 环境配置

加载 Soft-RoCE 内核模块，创建一个 rxe 设备绑定到物理网卡：

```bash
sudo rdma link add rxe0 type rxe netdev eth0
rdma link show
```

看到 `rxe0` 状态为 `ACTIVE` 即可。两个进程可以跑在同一台机器上，通过 `rxe0` 通信，loopback 也行。

### 必须手敲一遍的内容

**四个对象的生命周期。** 按顺序创建和销毁：PD（保护域）→ MR（注册内存）→ CQ（完成队列）→ QP（队列对）。销毁顺序反过来。每个对象的创建参数、销毁时机都要写对。

**MR 注册的关键点。** `ibv_reg_mr` 会锁页并建立地址翻译。注册的内存**不能被移动**。如果你用 Go 写上层，Go 的切片地址会被 GC 移动，所以注册内存必须由 C 侧分配并用句柄引用。这是新手最容易犯的错误之一。

**QP 的三段迁移。** INIT → RTR → RTS。每一段要填的字段：

- **INIT**：`qp_access_flags`（允许远程 Write/Read）、`pkey_index`、`port_num`
- **RTR**：`dest_qp_num`（对端 QPN）、`rkey`（对端 MR 的 rkey）、`ah_attr`（GID/地址信息）、`path_mtu`、`max_rd_atomic`
- **RTS**：`sq_psn`、`timeout`、`retry_cnt`、`rnr_retry`

**这几个字段错一个，QP 就迁不过去。** 报错信息往往不直接指向根因（比如 `ibv_modify_qp` 返回 `EINVAL`，但不说哪个字段错了）。迁移每一段之前打印当前参数，迁移后检查返回值，这是唯一高效的调试方式。

**单边 Write。** 接收端注册一块内存，把地址和 rkey 通过带外方式（同一进程内的全局变量、或两个进程间的 TCP/gRPC）告诉发送端。发送端直接 post send WR，`opcode = IBV_WR_RDMA_WRITE`，填 `remote_addr` 和 `rkey`。**接收端不需要 post recv。** Write 完成后，接收端内存内容应该和发送端一致。校验方式：接收端打印内存内容，或计算 checksum 对比。

**CQ 轮询。** 用 `ibv_poll_cq` 循环轮询。Soft-RoCE 上事件通知（`ibv_get_cq_event`）不可靠，轮询是唯一选择。代价是一个核被占满，但在学习阶段这不是问题。

### 必须跑一遍的验证

`rping` 双向通过。这是确认环境配对的最快方式：

```bash
# 服务端
rping -s -a 0.0.0.0 -v -C 10
# 客户端
rping -c -a <server_ip> -v -C 10
```

`rping` 通了，说明 CM 建链和基本 verbs 路径没问题，后面自己写代码出问题时可以排除环境因素。

### 这一层产出

一套能编译运行的 C 程序（或 C + Go 组合），证明：PD/MR/CQ/QP 创建销毁正确、QP 三段迁移成功、单边 Write 内容一致、CQ 收到完成事件、`rping` 双向通过。


## 第二部分：把代码整理成 TrainCache 可用的传输模块

### 接口设计

C 侧暴露五个函数，Go 通过 cgo 调用：

```c
void* tc_rdma_init(const char* dev_name);           // 初始化，返回上下文句柄
uint64_t tc_rdma_register(void* ctx, size_t size);  // 注册内存，返回句柄
int tc_rdma_write(void* ctx, uint64_t local_handle,
                  uint64_t remote_addr, uint32_t remote_rkey,
                  size_t offset, size_t len);        // 单边 Write
int tc_rdma_poll(void* ctx, int timeout_ms);        // 轮询完成事件
void tc_rdma_shutdown(void* ctx);                   // 销毁
```

**注册内存由 C 侧 `malloc` 分配**，Go 只持有句柄，不直接持有指针。这是为了避免 Go GC 移动内存导致 MR 失效。

### 控制面设计

接收端启动时注册一块或多块 buffer，把每块的 `(addr, rkey, size)` 通过带外方式发给发送端。在 TrainCache 的上下文中，这个“带外方式”可以是 gRPC 或简单的 TCP JSON 交换。发送端拿到 `(addr, rkey)` 后直接 Write，不需要接收端参与。

**预注册槽位模式**：接收端启动时注册 8 个 1MB 槽位（或根据 TrainCache 的实际缓存块大小调整），发送端写之前先确认目标槽位空闲。这个模式避免了按需注册的开销（`ibv_reg_mr` 锁页耗时随内存大小上升）。

### 这一层产出

一个独立的 C 模块 + Go 封装，在 Soft-RoCE 上验证：Write 到预注册槽位、内容校验通过、CQ 轮询收到完成、重复 Write 不泄漏资源、shutdown 后资源释放干净。


## 第三部分：在真实 RoCE 上验证模块

### 选哪个云

**华为云 vRoCE**：购买 ECS 时在网络配置的扩展网卡处勾选“启用 EFI”，不额外收费。vRoCE 支持 SOCKET 和 RDMA_CM 两种建链方式，QP 类型 RC/UD，SRQ 支持。需要安装 OFED 驱动（指定版本）和 vRoCE 驱动。

**阿里云 eRDMA**：购买支持 eRDMA 的实例规格，为主网卡开启弹性 RDMA 接口（ERI），不额外收费。需要安装 eRDMA 驱动。注意 GPU 实例和企业级实例的 eRDMA 工作模式不同，不能直接互通，但你的 TrainCache 传输模块跑在 CPU 实例上，不涉及 GPU。

**选择建议**：看你手头哪边的优惠券/资源可用。两者都是云上 RoCE 变体，对 Verbs 代码的接口是同一套。如果华为云券能覆盖 CPU 通用实例，走 vRoCE；如果阿里云有可用资源，走 eRDMA。**不要为了“更接近 IB”去租 H2**，TrainCache 不碰 IB，边界写清楚就行。

### 要两台实例

vRoCE 和 eRDMA 都需要两台实例才能测试节点间通信。华为云文档明确写了“当前版本不支持同一节点内的 vRoCE 通信”。所以真实 RoCE 验证必须租**两台**同 VPC 的实例。

### 验证什么

**功能验证（必做）：**

- `rping` 双向通过
- 你的 `tc_rdma_write` 在两台机器之间完成一次 Write，接收端内容校验一致
- QP 建链和断开正常，重复建链不报错
- 关闭一台机器的进程后，另一台能检测到连接断开（CQ 返回错误事件或 poll 超时）

**稳定性验证（必做）：**

- 连续 Write 1000 次（不测延迟，只看有没有失败、有没有完成事件丢失）
- 模拟链路异常：如果能在其中一台机器上临时禁用 RDMA 网卡或断开安全组规则，观察对端 CQ 收到什么错误事件

**不做的：** 不采 P50/P99 延迟，不画带宽曲线。vRoCE/eRDMA 的性能数字同样不适合进简历，因为它们不是物理 IB 或物理 RoCE 网卡。你的产出是“模块在真实云 RDMA 上功能正确、链路异常时行为可预期”。

### 这一层产出

- 两台真实 RoCE 实例上的 `rping` 日志
- 模块 Write 功能验证记录（成功次数、内容校验结果）
- 链路异常时的 CQ 错误事件类型记录
- 边界声明：“功能验证在华为云 vRoCE / 阿里云 eRDMA 上完成，未覆盖物理 IB，性能数字不采信”


## 第四部分：TrainCache 数据流加速的实战衔接

### 你的模块在 TrainCache 里干什么

TrainCache 是平台侧数据缓存层，类似 Fluid。它的 RDMA 路径是：**缓存节点把数据 Write 到计算节点的预注册内存里**，或者**计算节点从缓存节点 Read 数据**。不是 NCCL 梯度同步，是数据面搬运。

你的模块接口（`register_buffer` + `write` + `poll`）正好对应这个场景。缓存节点启动时注册数据 buffer，计算节点启动时注册接收 buffer，通过控制面交换 `(addr, rkey)`，然后缓存节点直接 Write。计算节点不需要 post recv，只需要在 CQ 上轮询完成事件。

### 实战时还需要补的（在真实项目里做，不在本实验范围）

- **多 QP 并发**：单个 QP 的吞吐有上限，TrainCache 可能需要多 QP 并行搬运不同数据块
- **完成事件批处理**：一次 poll 取多个 CQE，减少轮询开销
- **错误恢复**：QP 进入错误状态后如何销毁重建，已注册 MR 是否需要重新注册
- **与 TrainCache 控制面的集成**：gRPC 交换地址/rkey 的具体协议格式

这些在你的 RDMA 学习阶段不需要做，但知道它们存在，面试时能说“我的模块预留了扩展点，多 QP 和错误恢复是下一步”。


## 验收什么

1. **Soft-RoCE 阶段**：`rping` 双向通过；QP 三段迁移成功；单边 Write 内容校验一致；CQ 轮询收到完成。
2. **模块阶段**：五个函数的 C 模块 + Go 封装在 Soft-RoCE 上跑通；预注册槽位 Write 1000 次无失败。
3. **真实 RoCE 阶段**：两台 vRoCE 或 eRDMA 实例上 `rping` 通过；模块跨机 Write 功能正确；链路异常时 CQ 错误事件可观测。
4. **边界声明**：不碰 IB；不采信 Soft-RoCE/vRoCE/eRDMA 的性能数字；TrainCache 的 NCCL 无关性写清楚（平台侧数据流不走 NCCL）。
5. 测完释放实例，数据先拷走。


## 被问到怎么讲

“我 RDMA 这块分两步。第一步在 Soft-RoCE 上把 Verbs 机制手敲了一遍：PD/MR/QP/CQ 的创建销毁、QP 三段迁移、单边 Write、CQ 轮询，`rping` 和自写模块都通了。第二步产出一个 C 模块加 Go 封装，接口是 init/register/write/poll/shutdown，注册内存由 C 侧管理避免 GC 移动。这个模块在华为云 vRoCE 两台实例上验证了跨机 Write 和链路异常时的 CQ 错误事件。没碰 IB，因为 TrainCache 是平台侧数据缓存，不走 NCCL 也不走 IB 梯度网络，vRoCE 的功能验证已经覆盖了模块需要的 Verbs 路径。性能数字没有采信，Soft-RoCE 和 vRoCE 都不是物理网卡。”

被追问“为什么不做 GPU + NCCL + RDMA”：“TrainCache 是类似 Fluid 的平台侧项目，RDMA 用在缓存节点到计算节点的数据搬运，不走 NCCL。NCCL 是训练框架的梯度通信层，跟平台数据流是两个平面。我在推理侧单独做了 vLLM TP + NCCL 日志阅读，那部分是另一个叙事，不跟 TrainCache 混在一起。”层浅尝，没有把 IB 经历模糊成 GPU 分布式训练经验。
