## 5. 各项设计

### 5.2 S2 RDMA 传输臂

缺口：P1 的 P2P 走 gRPC stream，RDMA 是网络数据面的核心考点。Mooncake、NIXL、UCX 已经把生产级传输做完了，这一项复用的是机制理解与接口实现能力，不造新轮子。

交付物：C++ 传输组件加薄 C ABI，Go 侧一个 `rdmaTransport` 适配器，可注入 P1 的 P2P 模块；三档延迟吞吐数据；一份边界报告。

范围：Soft-RoCE 上的功能验证与接口实现。不做 GPUDirect RDMA，不做多路径与拥塞控制，不把 RDMA 放进 P1 主路径。

设计：

1. 四个 verbs 对象各有生命周期：PD 是保护域，MR 是注册过的内存，QP 是队列对，CQ 是完成队列。QP 要按 INIT → RTR → RTS 迁移，参数里目的 QPN、rkey、GID 一项都不能错。
2. 单边 Write 配预注册槽位。接收端启动时注册 8 个 1MB 槽位，把地址与 rkey 经控制面发给对端；发送端直接写，不要求对端提前 post receive。双边 Send/Recv 需要接收端预先挂缓冲区，延迟多一跳，适合控制消息。
3. `ibv_reg_mr` 会锁页并建立地址翻译，耗时随内存大小上升。4KB 小块按需注册会被注册开销吃掉，所以槽位预注册、按需只做一次地址交换。
4. CQ 用轮询。Soft-RoCE 上事件通知会丢，轮询是被迫选择，代价是一个核被占满。
5. 跨语言用独立 C 进程加 C ABI，四个函数：init、write、poll、shutdown。cgo 每次调用有 2 到 5 微秒切换开销，CQ 轮询放 C 进程更干净；Go 的切片地址会被 GC 移动，注册过的内存必须由 C 侧分配并通过句柄引用。
6. 数据面协议：控制面走 gRPC 交换槽位地址与 rkey，数据面走一条 Write，完成后由 CQ 通知 Go 侧。

验收：`rping` 双向通过；块大小 4KB、256KB、4MB 三档各 1000 次，P50 与 P99 有数；注册耗时曲线有数；结论明确写“功能可验证、性能不可采信”，任何 Soft-RoCE 数字不进简历。

弹药：Write 与 Send/Recv 的取舍；GC 移动内存导致注册失效、跨子网丢包不重发两个坑；三档延迟曲线与注册耗时。

讲法：先说为什么不在主路径上用 RDMA，再说这条臂验证了哪些机制，最后用一句“真实性能要 eRDMA 或 IB 才能采信”收口。

### 5.3 S3 SLO 校准与回放台

缺口：Pact 第 9 节给了预测的四步计算，第 10 节给了四类处置，两节都缺实测数据上的校准与策略对照。上游的 SLO 调度工作偏策略设计与仿真，公开的校准报告很少，这部分能力通常只在服务商内部。

交付物：一个纯 CPU 仓库，含 trace 加载、预测器、校准报告、漂移检测、回放器、一页结论。

范围：离线批处理。不接在线控制面，不做模型训练平台，不做 GPU 推理。

设计：

1. 输入 schema：每请求一行，字段有到达时刻、输入 token 数、输出 token 数、前缀命中深度、排队时长、每个 prefill 分段时长、每步 decode 时长、是否取消、副本 ID、SLO 阈值。公开 trace 缺字段时插值，并在报告里标“推断字段”。
2. 标签构造注意三件事。窗口内未完成的请求没有标签，做右截断；违约率通常很低，按时间分桶重采样并记录前后分布；特征只能用入队时刻可见的量，输出长度只能用同类历史分布。
3. 预测器两条基线先跑：历史同长度分位数、Little 定律估算（并发乘平均服务时间）。主力模型用分桶回归或 GBDT，输出概率，另给区间。
4. 校准四步：按概率分桶画可靠性图；算 Brier 与 ECE；用等距回归或 Platt 缩放做后处理并比较；按副本、负载类型、命中深度切片，找出失效的那一档。
5. 漂移检测用 PSI 或 KL 散度滑窗，输入分布与时延分布各一条。阈值取校准误差开始上升的位置。人为把到达率翻倍，验证告警在多长时间内触发，并给重校准触发条件。
6. 回放器事件驱动，时间轴按到达与完成推进。四类动作各一个决策点：准入拒绝、降级、扩容加副本并预热、按副本余量路由。每个动作带迟滞与冷却，代价表把拒绝损失、质量折损、扩容成本、跨域时延折到同一单位。
7. 结论部分回答两件事：哪类动作在哪种负载下有效；预测误差放大到 ±20% 时收益还剩多少。

验收：校准前后各有可靠性图与 Brier、ECE；漂移告警表；四类动作的违约率与成本对照；敏感度曲线；一个失败案例归到特征、标签或漂移。

弹药：概率校准与点预测的取舍；右截断标签、类别不平衡、时间泄漏三个坑；Brier、ECE、动作对照、敏感度四组数据。

讲法：先说为什么交付概率、布尔判定在哪些场景失效，再说校准没通过就不允许自动处置，最后用一张动作对照表说明收益来自哪里。


### 5.7 M4 外部口径校验

缺口：Pact 引擎侧在进程内埋点，有侵入也可能有偏差。外部探针不改代码，但只能看到函数边界。两套口径需要一次对齐。

交付物：偏差表、开销表、一条判定规则、一条不一致案例。

范围：两天量级，附录题。不改 vLLM 源码。

设计：

1. 挂点选 `Scheduler.schedule` 与 `execute_model`，再加每步输出处。CPU 后端与 GPU 后端分开登记，GPU 后端只挂宿主侧 Python 函数。
2. 用 bpftrace 的 uprobe 记录进入与退出时间，采样率可配。Python 符号解析不稳时固定解释器版本与符号表。
3. 对齐按 request id 或到达顺序，对到账本记录。偏差拆成两部分：时钟源差异（CUDA event 与单调时钟）与插桩位置偏差。
4. 开销：开与关探针对 TTFT、ITL、吞吐的影响，采样率变化对开销与丢事件的影响。
5. 污染声明：为了观测关掉 async scheduling 会改变被测行为，这一点必须写进结论。

验收：三个阶段的偏差 P50 与 P99；开销百分比；判定规则一句话；一条对不上的请求拆到阶段。

弹药：外部观测与进程内打点的取舍；观测污染、符号漂移两个坑；偏差分布。

讲法：先说两套口径各自看到什么，再说偏差来自哪里，最后给判定规则。

### 5.8 N1 DDP→ZeRO 显存账

缺口：P1 是数据流与缓存主线，训练并行侧没有材料。面试问显存公式时只能背书。

交付物：一页笔记，含公式、实测表、profiler 记录、可复现脚本。

范围：GPT-2 small 或 6 到 10 层 Transformer，BF16 加 AdamW，双卡。不追求收敛，不做大规模。

设计：

1. 每参数 16Ψ 字节：参数 2、梯度 2、Adam 一阶与二阶各 4、fp32 主权重 4。ZeRO-1 分片优化器状态后是 4Ψ + 12Ψ/N；ZeRO-2 再分片梯度，是 2Ψ + 14Ψ/N。
2. 激活显存与层数、batch、序列长度成正比，不参与分片，所以实测降幅小于理论值。
3. DDP 每步一次 all-reduce，通信量约 2Ψ；ZeRO-1 每步多一次 all-gather，量级 Ψ，小卡数下这次通信摊不薄。
4. 测量：峰值显存、稳定步耗时、通信占比，三者同表；公式预测值单列一列对照。

验收：原始数据表与公式对照；2 卡 ZeRO-1 变慢的条件能说清；边界条件有一组数据支撑。

弹药：实测降幅小于理论值的原因；小卡数下 DDP 更划算的边界；all-reduce 与 all-gather 的占比。

讲法：先写公式，再给实测差，最后说清什么规模下分片才划算。

### 5.11 N4 NCCL 与恢复 runbook

缺口：08 章 30、31 题有参数名与 checkpoint 的账，12 章 12 题有 NCCL 超时排查，都停在知识层。真上集群后第一步敲什么、看哪行输出、什么值算正常，没有一张表。这一项补的是上机流程，不是通信优化本身。

交付物：一份 runbook（每条四栏：命令、看哪行输出、正常值、异常时下一步查什么）、gloo 上的恢复四段实测表、单卡双 rank 的 NCCL 拓扑输出注解、一次云窗口的 busbw 曲线。

范围：机制验证与流程演练。不改 NCCL 源码，不做多机 IB 性能结论，不声称千卡规模。云窗口只租一次，2 到 4 卡带 IB，几小时量级。

设计：

1. gloo 四进程跑通机制。`torchrun --nproc_per_node=4` 配 gloo backend，跑 DDP 加 DCP checkpoint，量恢复四段时间：检测（进程死到判定死）、定位隔离、rendezvous、checkpoint 加载与预热。打点位置是进程启动、rendezvous 完成、load 完成、第一个 step 完成。四类注入各跑一遍：杀 rank、断连（停 store 端口或 iptables 丢包）、慢节点（一个进程里加 sleep 或限 CPU 配额）、写满盘（checkpoint 目录所在文件系统填满）。每类记四段时间与告警是否触发。gloo 数字标明口径，不当集群结论。
2. 检测段先调。`init_process_group(timeout=...)` 默认 30 分钟，改成 5 分钟并打开 `TORCH_NCCL_ASYNC_ERROR_HANDLING`，量四段里第一段的变化。配 `--max-restarts`（默认 0，不开则自动重启不发生）。
3. 单卡双 rank 读 NCCL 输出。同一张卡起两个进程用 NCCL backend，开 `NCCL_DEBUG=INFO` 与 `NCCL_DEBUG_SUBSYS=INIT,GRAPH,ENV,TUNING`，逐段注解：INIT 段走 P2P/IPC 还是 SHM 还是 Socket，GRAPH 段的 ring 顺序与 channel 数，ENV 段实际读到的变量。改 `NCCL_ALGO`（Ring/Tree/NVLS）与 `NCCL_PROTO`（LL/LL128/Simple）看选路怎么变。
4. nccl-tests 的 `all_reduce_perf` 扫 message size 8 B 到 1 GB，画 busbw 曲线，标硬件上限。小 size 段低是延迟主导，大 size 段仍低于上限才是通信有病。ring 的 busbw = algbw × 2(N−1)/N。
5. 恢复侧的账写成公式。70B 混合精度 Adam 每参数 16 字节共 1.12 TB，分片到 1024 卡每卡 1.1 GB；一千客户端同读一份对象存储时元数据先撑不住，所以每 rank 写自己的分片。保存间隔按 √(2 × 保存成本 × 平均故障间隔) 定。
6. 读三份：MegaScale（NSDI'24，万卡故障分类与 per-rank 诊断）、Gemini（SOSP'23，邻居主机内存冗余 checkpoint）、PyTorch DCP 与 torchelastic 文档。
7. 云窗口一次填完 runbook 里所有「待实测」空格：size 扫描、拓扑与参数对照、一次杀 rank 的四段计时。

验收：runbook 每条四栏齐全；gloo 四段时间有实测值且标明口径；NCCL 三段调试输出能逐段解释；云窗口后 busbw 曲线有实测值；PCIe 与单卡双 rank 的带宽数字不进简历。

弹药：三种病因分法（延迟主导、带宽主导、慢节点）；检测段默认 30 分钟这个误诊源；1.12 TB 分片账与保存间隔公式；慢节点常被误判成网络故障，治它在数据加载侧。

讲法：先说没集群时练的是读输出、认路径、四段账，再说上机后第一步量什么，最后用一次云窗口的实测收口。被问规模就答 2 到 4 rank 加数字账外推，外推假设报出来。
