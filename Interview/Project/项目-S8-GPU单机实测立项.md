## 二、前置条件（第 0 天，半天出结论）

1. 确认手上有什么：`lspci -nn | grep -i nvidia`、`nvidia-smi`、`nvidia-smi -q -d COMPUTE`。游戏本大概率带 dGPU，但笔记本 Optimus 切换、Secure Boot 下的内核模块签名、驱动与 CUDA 版本错配这三件事最容易卡人。装不上就当天切租卡，不要投第 2 天。
2. 显存档位决定能测什么（算法按 08 章 8 题：权重 ≈ 参数量 × 每参数字节；KV ≈ 2 × 层数 × hidden × 每 token 每层）：
   - 8 GB：1.5B～3B 的 fp16，或 7B 的 4bit 量化 + 短上下文。
   - 16 GB：7B fp16 + 小 KV，够做 batching 对照。
   - 24 GB：7B fp16 + 较大 KV，够把 KV 占用推到能看出驱逐行为的程度。
   低于 8 GB 或驱动做不出来，直接按第 3 条租卡，别做降级实验。
3. 卡时预算：累计 ≤ 20 卡·时。按小时租、采集窗口一关就释放实例；快照里不要留实例。本地有 dGPU 的话成本为 0，但笔记本功耗墙本身要当成一个观测项（见坑清单）。

## 三、做什么（时间盒 7 个工作日，第 7 天为止损日）

**档 1｜CUDA 三件热身（1.5 天）**
vector add、reduction（atomic 与两级归约各写一版）、matmul tiling（naive 与 shared memory 分块）。每件事只回答一个问题，各报一个自己测出的数字：合并访问差多少、atomic 竞争在哪一档开始咬、shared memory 复用把 HBM 读次数降到几分之一。不追峰值，不引别人的数。
产物：三个 `.cu` + 一段说明。这档可以随时被砍（见止损）。

**档 2｜单卡时间去向表（3 天，核心档）**
在一张卡上起 vLLM，跑 P2 的负载台，同负载三档并发（如 1 / 8 / 32，按显存档位定）各测一遍，出一张表：

| 采集项 | 手段 |
|---|---|
| TTFT、ITL、吞吐、前缀命中率 | vLLM `/metrics` 计数器 |
| 显存与 KV block 占用 | `nvidia-smi dmon` 或 DCGM 采样，同时读 `/metrics` 里的 KV 块占用指标（指标名以当日实际输出为准，别照抄旧版） |
| GPU 利用率与 SM/显存带宽忙闲 | `nsys` 或 `torch.profiler`，选一个即可，两个都上会互相干扰 |
| 每个 step 的 host 侧时间分解 | M4 的 uprobes 探针点，直接复用，不重新选函数 |
| data_wait 占比 | host 侧 `next(dataloader)` 等待 / step 总时长；这一列同时是 P1 负载改造要用的口径 |

表之外要有一段文字结论：decode 阶段这张卡的瓶颈在算力还是在显存带宽，依据是哪两列的比值。这句话是你后面所有 GPU 叙事的主语。

**档 3｜host 时间 vs GPU 时间对账（1.5 天）**
把 M4 在 CPU 后端得到的 token 级时间和 GPU 后端重跑一遍的结果并排。对不上就找差额落在哪一段（拷贝流、kernel launch、异步调度、还是探针本身的开销）。这个「对账」过程本身就是最好的坑素材。
产物：一张两列对照图 + 差异解释。

**档 4｜README 与回写（0.5 天）**
按 PDF 的 README 三节写：设计取舍、实验数据、复现命令。回写 P2 README 一句话（单卡 KV 占用曲线 → 网关侧扩容判据的依据），回写 08 章对应题一句（哪几个数字换成了自己测的）。

**止损**：第 4 个工作日检查一次，档 2 的表还没出来就砍掉档 1 和档 3，剩下 3 天全投给档 2 与 README。第 7 天收工，表只跑完两档也算收工，缺的那一档在 README 里写明缺，不许续期。

## 四、验收标准

弹药三件套，缺一件就按 PDF 口径降级成笔记：

- **一个取舍**：`--gpu-memory-utilization` 拉高让 KV 池更大、并发上限更高，代价是 OOM 风险与抢占频率上升；或者并发三档里哪一档的 ITL 已经不达标。要能报出你选的数值和理由。
- **一个亲自踩的坑**：必须是只有真 GPU 才会出现的，候选清单（按你实际遇到的写，不许事后编）：OOM 来自 KV 而不是权重；笔记本功耗墙导致同配置两次跑吞吐差 20% 以上；驱动/CUDA wheel 与 vLLM 版本不匹配；量化模型没有对应 kernel 导致退化到慢路径；显存碎片让 `num_gpu_blocks` 比理论值小；`torch.compile` 首步预热时间被误读成 prefix miss。
- **一张对照表**：档 2 的三档并发表，含 data_wait 列。

至少一条主项目能用的数字：单卡 decode 阶段的 GPU 利用率与 KV 占用随并发的变化曲线，用来支撑 P2 弹性伸缩那一节的「一个副本预热到什么程度才有意义」。这条进不了 P2 README，就说明 S8 白做。

可验证性按 16 章第四节四层给：过程痕迹（`git log`、原始采样文件、日志时间戳）、细节复述（哪个指标哪一档异常）、失败记忆（坑清单里那个）、现场动手（档 1 的三个 kernel 能当场改一行重跑）。

## 六、面试里的用法与边界

- 被问「你有 GPU 经验吗」：一句话 + 那张表 + 那个坑。说法是「单卡做过 vLLM 的 GPU 侧实测，写过三个 toy kernel」，不说「会 CUDA 优化」。
- 遇到阿里一面那类算子追问：能接的是 GEMM 的 tiling 与 FA 的 IO 账（08 章 17 题）、atomicAdd 与确定性（08 章 18 题）、合并访问与 bank conflict（08 章 9、10、19 题）；接不住的是生产算子调优。当场承认边界，把话题带回你能给数据的那层：单卡瓶颈判断与 KV 占用。
- 数字口径：记不准就按 15 章表先给量级，再声明会后核实，别把 GPU 实测的期望值当实测值报。

## 七、挡位/层级
第一层：概念层（必须，1–2周）
理解thread/block/warp作为调度单位的区别、SM的warp发射模型、shared memory与global memory的带宽差距、occupancy的限制因素（寄存器、shared memory、warp上限）。这一层用面试问答库的CUDA基础Q1–Q10就能覆盖，目标是被追问时能用正确的术语解释，而不是背定义。-27

第二层：阅读层（必须，2–3周）
能读懂一个简单的CUDA kernel（比如naive SGEMM或一个elementwise kernel），理解它如何把数据从global搬到shared、warp如何协作、__syncthreads在哪里使用。不需要会从零写，但需要能在给出代码时指出“瓶颈可能在访存还是计算”。

第三层：Triton实验层（可选但推荐，1–2周）
用Triton写一个融合算子（Softmax或LayerNorm），与PyTorch原生实现对比正确性和耗时。Triton的抽象层级更高，不需要你处理block/warp的细粒度调度，但能让你亲手体验“算子融合减少了多少HBM往返”。这一步的产出可以是一个简短的对比表格：PyTorch原生 vs Triton融合，在什么shape下差距明显，为什么。单卡RTX 3060 6GB就足够完成这一步。

不需要做的：CUDA C++手写高性能kernel、CUTLASS/CuTe、PTX。这些是算子专项岗的目标，与你的平台+推理交叉定位不匹配。
