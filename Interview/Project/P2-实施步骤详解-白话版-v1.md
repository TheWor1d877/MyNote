# Pact 实施步骤详解（白话版）

这份文档把《Pact 指南：推理服务契约层》里的 21 节展开成可以照着做的步骤。指南负责讲设计，本文负责讲顺序：每一步在做什么、为什么要先做它、做到什么程度算过关。指南的节号在每一步开头标出来，细节随时翻回去看。

## 先弄清楚：两种章节，一条主线

指南里有两类内容。第 2 到 13 节按零件组织，讲网关、打点、计量、预测、处置、归因、结算、可观测性各自长什么样；第 17 到 20 节按交付组织，讲怎么出数、交什么、哪些话不能说。

动手时以本文的步骤为主线，一步一个闸门。每一步都带过关标准，过不了就停下来修，不带着问题往下走。后面几步会用到前面几步的产物：打点的 trace 喂给预测，预测的概率喂给处置，处置的记录喂给结算，结算的数字再回到面板上。

## 名词小词典

| 名词 | 大白话解释 |
| --- | --- |
| TTFT | 请求发出到收到第一个内容 token 的时间。 |
| TPOT | 解码阶段相邻输出 token 的平均间隔。 |
| SLO | 服务等级目标，例如 P99 TTFT 低于 2 秒。 |
| 统计窗口 | 合同约定的达标率统计周期，例如一小时或一天。 |
| 违约 | 单个请求的指标超过合同阈值，计一次。 |
| 赔付口径 | 违约怎么判定、金额怎么折算的规则。 |
| 误拒率 | 被拒绝但本来能按时完成的请求占比。 |
| 契约服务 | 管合同登记、预测、处置、归因、结算的常驻服务。 |
| 流水表 | 每请求一行的记录表，存 token 数、四段耗时、批次组成。 |
| 批次快照 | 每个调度步里同批请求的组成与资源占用。 |
| 前缀命中 | 请求的开头与缓存里的内容相同，这部分不参与计算。 |
| chunked prefill | 把长 prefill 切成多段推进，和 decode 混在一批里跑。 |
| 抢占 | 显存不够时把某个请求踢出批次，V1 默认走重算。 |
| 重算 token | 被抢占后重新 prefill 时重复计算的 token 数。 |
| 校准 | 预测概率与实际发生频率对齐，可靠性图与 Brier 是两把尺子。 |
| Brier 分数 | 预测概率与真实结果之差的平方平均，越小越准。 |
| 漂移 | 输入分布或时延分布随时间移动，使校准失效。 |
| 证据包 | 一次违约的可复核材料，包含 trace、指标快照、批次组成、合同版本。 |
| 归因残差 | 四段耗时之和与总延迟的差。 |
| 回放 | 用同一份轨迹重跑，比较处置决策是否一致。 |
| CUDA event | 显卡侧的时间戳，用来对齐异步执行与主机时钟。 |
| CUDA Graph | 把一串 kernel 录成图重复播放，播放期间没有主机分支，打点进不去。 |
| 环形缓冲 | 固定大小的循环队列，写满覆盖最旧的数据，写入不加锁。 |
| 单卡副本组 | 一张卡上跑一主两从的 vLLM 实例，用来验证路由与扩容。 |

## 步骤 0：现勘与核实——先证明值得做（指南第 5 节）

这一步的目标：动工之前确认三件事。第一，打点位置拿得到，不改 kernel 也能测出四段耗时；第二，上游已经有预测器与归因模型，自己的增量站得住；第三，私有化合同里确实有延迟条款与赔付，需求不是编出来的。

具体做什么：

1. 单卡起一主两从的副本组，锁定镜像、模型、驱动、CUDA 版本，把启动参数读成一张映射表：显存比例、最大并发、block 大小、是否开前缀缓存、是否开 chunked prefill。
2. 精读 Scorpio、Cascade、LLMVisor 三篇，逐条列出它们覆盖的机制，写进现状矩阵。矩阵只回答一件事：哪些环节复用，哪些环节自研。
3. 核实云厂商推理服务的合同形态与赔付口径，只记录公开可查的部分，查不到就标未核实。
4. 在调度路径上找五个打点位置，确认每个位置在异步执行下能拿到时间戳。找不到就换后端或改方案，这一步是头号风险。
5. 产出现勘报告：现状矩阵、缺口排序、打点可行性结论。

过关标准：矩阵五行齐全，每行有版本号与出处；五个位置各有一个最小实验证明能取到时间；缺口排序写清先做哪一段。

红灯处理：打点位置拿不到，Pact 的归因段退化为模型估计，整个项目降级成网关侧的合同服务，先改范围再动工。

## 步骤 1：搭实验装置——你的实验室（指南第 6 节）

为什么第二步是它：后面每做完一段，都要立刻看到效果，看到效果全靠这套装置。装置不稳，所有数字都不可信。

具体做什么：

1. 网关：鉴权、配额、request id 注入、拒绝响应、路由五件事。SSE 转发与断连检测放在这里，断连要通知引擎取消，避免白算。
2. 负载台：按合同场景生成轨迹，参数有模型、SLO 分位、共享前缀比例、输入与输出长度分布、突发形状、租户数量、缓存冷热。同一份轨迹同时喂给本产品与对照组。
3. 存储：流水表按时间分区，契约与处置记录进关系库，指标走 Prometheus。流水表与指标库共用 request id，两边数字能互查。
4. 冷热态规程：冷态每轮重启副本并清空 KV，热态写清预热流程。两组数字分开报，不混在一张表里。
5. 一条命令拉起整套装置，轨迹文件版本化，换参数不改代码。

过关标准：一条命令起全套；同一份轨迹重跑两次，请求数、token 数、P50 TTFT 对得上；冷态与热态各有一组基线。

## 步骤 2：引擎侧打点——项目的灵魂（指南第 7 节）

这一步的目标：把请求级的时序从引擎里掏出来。上游只给聚合指标，Pact 的计量、预测、归因、结算全都要请求级记录。没有这一段，后面五段都是估计。

具体做什么：

1. 五个位置按时间顺序埋点：入队、出队、每个 prefill 块结束、首 token、结束或取消。每个位置记一条事件，带 request id。
2. 每个请求记八项：租户、入队与出队时刻、prefill 块数与每块 token 数、前缀命中 token 数、首 token 时刻、输出 token 数、被抢占次数与每次重算 token 数、KV 占用峰值。
3. 每个调度步记一条批次快照：同批请求 id、各自阶段、各自 token 数、当步 KV 占用、是否触发抢占。违约相关请求全量记，正常请求按 1/32 采样，采样率写进配置。
4. 写入走环形缓冲，调度路径上不申请内存、不加锁；落盘交给独立线程，按 step 或时间窗口批量导出。
5. 时间戳用单调时钟，GPU 侧用 CUDA event 记首 token 与块边界。CUDA Graph 捕获区内不埋点，Graph 重放期间只记 step 级时刻，请求级时刻按 step 归属推算。
6. 处理四类调度特性的语义：chunked prefill 把各段加总，段间让给 decode 的时间不算进该请求的 prefill；前缀命中按实际计算 token 归因，命中数单列；抢占记一次重算事件，重算 token 单列；取消记时刻与已生成 token 数。
7. 三组标定离线做，在线查表：TPOT 与 batch token 数的关系（扫 1、4、8、16、32）、prefill 每 token 时间（命中与未命中两档，输入 1k、4k、16k、32k）、排队时间直接测不用模型。
8. 三档开关：全量、采样、关闭。关闭时归因退化为模型估计，误差单列一节。缓冲区溢出丢最旧记录，丢弃条数进面板。

过关标准（三项，缺一不算过）：

1. 开销：开关前后同一轨迹跑两遍，P50 与 P99 TTFT、吞吐的差在 1% 以内；超了就降采样率。
2. 完整性：网关请求计数与 trace 条数对账，缺失率低于 0.1%。
3. 归因精度：同一批违约请求上，打点归因与模型估计对照，报误差。

常见坑：把打点写进 Graph 捕获区导致 replay 期间没有数据；用主机时钟量首 token，异步执行下比真实时刻晚；chunk 边界没按块对齐，段间被 decode 占用的时间被误算进 prefill。

## 步骤 3：流水表与计量口径（指南第 8 节前半）

这一步的目标：把所有数字钉在一套口径上，后面预测、结算、对账都用它。

具体做什么：

1. 流水表每请求一行，主键是 request id，按时间分区。字段与 7.2 的八项对齐，另加处置动作与最终结局。
2. 四条计量口径先定死：token 数取引擎返回的 usage，网关不估算；缓存命中是否计费写进合同，两种约定各给一组实验结果；被拒绝的请求计 0 token，计入误拒率；断连请求按已生成 token 计费。
3. 流水表与 Prometheus 共用 request id，任一面板数字都能回查到具体请求。

过关标准：随机抽十条请求，从网关日志、trace、流水表、指标四处读出的 token 数与耗时一致；命中计费两种口径各跑一组，数字能分开。

## 步骤 4：契约登记（指南第 8 节后半）

具体做什么：

1. 合同字段：模型、SLO 分位、统计窗口、最小样本量、赔付公式、允许的降级档位。
2. 版本管理：条款有版本号与生效失效时间，变更留审计记录；结算按请求发生时刻对应的版本计算。
3. 样本量门槛：不足时按合同约定处理，默认沿用上一窗口的达标率并标注。

过关标准：同一窗口内改一次条款，旧请求按旧版本结算，新请求按新版本结算，账能对上。

## 步骤 5：违约预测（指南第 9 节）

这一步的目标：给每个请求一个完成概率与区间，不给布尔判定。

具体做什么：

1. 三组特征：系统状态（队列长度、KV 占用、inflight、近期 TTFT 分位、副本余量）、请求形状（输入 token 数、是否命中前缀、合同分位）、输出长度估计（首 token 前用同类历史分布，首 token 后按已生成数与历史衰减更新）。
2. 四步计算，每步能单独核对：排队时间给区间；prefill 时间按实际计算 token 乘每 token 时间，命中与未命中分档；decode 时间按输出长度乘 TPOT，TPOT 查批次表；最后把输出长度分布积分成「总时间不超过期限」的概率。
3. 每一步留中间结果，出错时能定位到哪一步偏了。
4. 首 token 之前的预测误差最大，这一段单独报告。

过关标准：同一批请求，四步的中间结果与实测分段耗时逐段对照，误差落在可解释范围；预测概率的分布不塌缩到 0 或 1。

## 步骤 6：校准与漂移（指南第 9 节后半）

具体做什么：

1. 按预测概率分桶，比较桶内实际达标率与预测值，画可靠性曲线，报 Brier 分数与 ECE。
2. 未通过校准的概率不进入处置。校准按统计窗口重做，窗口与合同窗口对齐。
3. 漂移检测：特征分布与历史基线比较，超阈值告警并暂停自动处置，转人工确认。
4. 写清失效条件：突发到达时特征失真、缓存全冷时 prefill 分布偏移、模型或引擎版本切换后历史样本失效。

过关标准：可靠性曲线不穿过对角线太多；Brier 与 ECE 有数；人为把到达率翻倍能触发漂移告警。

## 步骤 7：处置（指南第 10 节）

具体做什么：

1. 四类动作：准入（概率低于阈值时拒绝，返回理由与建议重试时间）、降级（限输出长度、降优先级、切合同允许的小模型）、扩容（预测下一窗口集体违约时提前触发，触发点按预热耗时与预测窗口的交叉点定）、路由（按副本预测余量选，命中同一前缀优先送已缓存该前缀的副本）。
2. 代价表三项折算到同一单位：拒绝按合同请求单价折算业务损失；降级按合同系数折算质量折损；扩容按单位时间成本乘预热时长。
3. 迟滞与冷却按动作分别设，避免振荡。每次动作记录触发时的预测概率、动作类型与事后结果。
4. 误拒率单独统计，它是本方案的主要成本。

过关标准：四类动作都能演示一次；动作次数、收益、振荡次数进面板；同一场景下不出现同一动作反复开关。

## 步骤 8：归因与举证（指南第 11 节）

具体做什么：

1. 四段拆分：排队、prefill（含重算）、decode、客户端与网络。打点为主，模型估计为辅，两套结果在同一批请求上对照并报误差。
2. 交叉部分的归属规则写进报告：排队与 prefill 争抢同一份算力，重合区间按约定切分。
3. 证据包五件：违约事件编号、请求 trace、当时副本指标快照、批次组成、合同条款版本。
4. 证据包可回放：同一份轨迹重跑，比较处置决策是否一致。
5. 多租户归因：同时段批次快照加各租户请求占比，回答这次违约由谁的流量造成。

过关标准：任取一次违约，四段占比加起来与总延迟的残差有解释；证据包导出后能独立重跑；多租户归因能指出占比最高的租户。

## 步骤 9：结算与对账（指南第 12 节）

具体做什么：

1. 按合同窗口出四项数字：达标率、违约次数、赔付金额、归因占比。
2. 赔付公式可配置，设单窗口上限；样本不足按约定处理。
3. 账单与流水表对账，差异超阈值冻结出账并告警。
4. 争议期内证据包可导出，租户自行复核。
5. 差异的常见来源逐条排查：断连请求、重试请求、缓存命中计费口径、窗口边界。

过关标准：第三方拿同一份流水能复算四个数字；人为制造一次对账差异，系统能冻结出账。

## 步骤 10：可观测性（指南第 13 节）

具体做什么：

1. 五层指标：契约层（达标率、违约率、赔付额、误拒率）、预测层（校准误差、Brier、漂移告警数）、处置层（动作次数、收益、振荡次数）、归因层（四段占比、残差、重算占比）、引擎层（打点开销、trace 缺失率、采样率）。
2. 四块面板：契约总览、租户视图、副本视图、预测视图。
3. 四类告警：违约率、校准误差、误拒率、对账差异，各带 request id 样本，点开即到 trace。
4. 可回放是核心：任一违约事件能从面板跳进证据包，重跑一次并对比处置决策。

过关标准：从告警点到证据包再到回放，整条链路走通一次；每层指标都有负责人一栏写清。

## 步骤 11：端到端三组条件（指南第 17 节）

具体做什么：

1. 三组条件吃同一份轨迹：现状（反应式扩容加无准入）、仅预测不处置、完整方案。
2. 每组至少七次，取中位数，报区间；冷热态分开；模型、引擎、镜像、机器、负载配置随报告入库，一条命令复现。
3. 客户端饱和的轮次作废，负载台自身的 CPU 与连接数曲线作为附件。
4. 处置收益按同窗口内违约次数差计算，不用单次请求耗时差。
5. 校准单独一节，与性能指标分开报；打点开销单列一组。

过关标准：三组条件的违约率、误拒率、单位 token 成本能画在同一张图上；任一组能一键复现。

## 步骤 12：增量池（选做，指南第 14 节）

三项共用同一份 trace 与面板：多租户公平（按合同权重分配 KV 与算力，量干预前后的达标率差距）、缓存协同（违约预测与前缀预热联动，量预热对违约率的贡献）、结构化输出（合同加格式约束，看 token 预算与违约概率怎么变）。

过关标准：每项至少一组前后对照；没做就写“未做”，不留半成品。

## 步骤 13：调研层（只读，指南第 15 节）

P/D 分离、KV offload、跨副本迁移三项，只读文档与源码，各做一次集成实验，写调研笔记，不自建。覆盖边界在报告里单列一节。

过关标准：三份笔记各有一句“我们为什么不自建”；集成实验有截图或日志。

## 步骤 14：交付与诚实清单（指南第 19、20 节）

交付物：网关；契约服务五段；引擎打点与批次快照补丁；面板与告警规则；负载台；五份报告（打点开销与精度、预测校准、处置收益、归因精度、结算对账）；一份核实报告。

诚实清单逐条写进报告：合同模板自定义、赔付口径非行业标准；单卡双卡只做机制验证；首 token 前误差最大；四段归因有残差；突发下预测滞后；结算依赖业务口径；降级质量不评估；打点依赖引擎版本。

## 排期锚点与砍项顺序

顺序锚点：

1. 步骤 0 与 1 是闸门，任何一步红灯都先修，不带病写打点。
2. 步骤 2 是灵魂，验收三项不过就不做预测。
3. 步骤 3 到 5 打通后可以演示“请求进、概率出”。
4. 步骤 6 到 9 补齐后才是产品，四段归因与结算都要有数。
5. 步骤 10 到 11 出对外材料。
6. 步骤 12 到 13 有余力再做。

砍项顺序（从后往前砍，主线不动）：

1. 先砍增量池，三项都不做。
2. 再砍调研层的集成实验，只留笔记。
3. 再砍多租户归因，证据包只做单租户。
4. 再砍结算的自动对账，保留离线报表与人工复核。
5. 再砍扩容与降级两类动作，只留准入与路由。
6. 最后砍证据包回放，证据包保留导出。

不管砍到哪一步，打点、计量、预测、处置、归因这五段要留。它们是 Pact 与网关型产品的分界线。
