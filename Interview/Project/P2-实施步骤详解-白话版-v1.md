# Pact 实施步骤详解（白话版）

这份文档把《Pact 指南：推理服务契约层》里的 22 节展开成可以照着做的步骤。指南负责讲设计，本文负责讲顺序：每一步在做什么、为什么要先做它、做到什么程度算过关。指南的节号在每一步开头标出来，细节随时翻回去看。

## 先弄清楚：两种章节，一条主线

指南里有两类内容。第 2 到 14 节按零件组织，讲网关、打点、计量、预测、处置与副本容错、显存调度、归因、结算、可观测性各自长什么样；第 18 到 21 节按交付组织，讲怎么出数、交什么、哪些话不能说。

动手时以本文的步骤为主线，一步一个闸门。每一步都带过关标准，过不了就停下来修，不带着问题往下走。后面几步会用到前面几步的产物：打点的 trace 喂给预测，预测的概率喂给处置与显存调度，批次快照喂给慢副本判定，处置、调度与摘除的记录喂给归因和结算，结算的数字再回到面板上。

本文的顺序与指南的节号顺序不完全一致。显存调度在指南里排在结算后面，动手时排在归因前面：归因要拆换出等待与重算，策略先跑起来才有东西可拆。副本容错在指南里并进处置那一节，动手时单独成一步，排在显存调度后面、归因前面：归因要拆硬件子项，摘除与降频信号先采起来才有东西可拆。

## 名词小词典

| 名词 | 大白话解释 |
| --- | --- |
| TTFT | 请求发出到收到第一个内容 token 的时间。 |
| TPOT | 解码阶段相邻输出 token 的平均间隔。 |
| SLO | 服务等级目标，例如 P99 TTFT 低于 2 秒。 |
| 统计窗口 | 合同约定的达标率统计周期，例如一小时或一天。 |
| 违约 | 单个请求的指标超过合同阈值，计一次。 |
| 赔付口径 | 违约怎么判定、金额怎么折算的规则。 |
| 误拒率 | 被拒绝但本来能按时完成的请求占比。 |
| 契约服务 | 管合同登记、预测、处置与副本容错、显存调度、归因、结算的常驻服务。 |
| 流水表 | 每请求一行的记录表，存 token 数、四段耗时、批次组成。 |
| 批次快照 | 每个调度步里同批请求的组成与资源占用，全量记录。 |
| 显存事件 | 抢占、换出、换入、前缀驱逐四类动作各记一条，带 token 数与耗时。 |
| 前缀命中 | 请求的开头与缓存里的内容相同，这部分不参与计算。 |
| chunked prefill | 把长 prefill 切成多段推进，和 decode 混在一批里跑。 |
| 抢占 | 显存不够时把某个请求踢出批次，V1 默认走重算。 |
| 重算 token | 被抢占后重新 prefill 时重复计算的 token 数。 |
| 换出与换入 | 把请求的 KV 搬到主机内存腾显存，之后再搬回来，搬的期间请求不在批里。 |
| KV 池容量 | 引擎启动时配置的 KV 可用显存，产出率的分母取这个值。 |
| 达标 token 产出率 | 达标请求的输出 token 数，除以 KV 池容量与窗口秒数的乘积。 |
| 让位选择 | 池子超阈值时挑一个请求让出显存，比重算与换出哪个更便宜。 |
| 前缀保留 | 前缀缓存满时按「以后还能省多少计算」排序，驱逐排在末位的。 |
| 批组装 | 按批内 decode 请求的剩余期限挑 chunk 上限档位。 |
| 策略退回 | 参数过期、漂移超标或开销超标时改用上游默认策略，记一条事件。 |
| 校准 | 预测概率与实际发生频率一致，可靠性图与 Brier 是两把尺子。 |
| Brier 分数 | 预测概率与真实结果之差的平方平均，越小越准。 |
| 漂移 | 输入分布或时延分布随时间移动，使校准失效。 |
| 证据包 | 一次违约的可复核材料，包含 trace、指标快照、批次组成、显存事件、副本健康与硬件信号、合同版本。 |
| 归因残差 | 四段耗时之和与总延迟的差。 |
| 回放 | 用同一份轨迹重跑，比较处置决策、让位选择与摘除决策是否一致。 |
| CUDA event | 显卡侧的时间戳，用来对齐异步执行与主机时钟。 |
| CUDA Graph | 把一串 kernel 录成图重复播放，播放期间没有主机分支，打点进不去。 |
| 环形缓冲 | 固定大小的循环队列，写满覆盖最旧的数据，写入不加锁。 |
| 单卡副本组 | 一张卡上跑一主两从的 vLLM 实例，用来验证路由、扩容、摘除与回插。 |
| 副本级分布式 | 多个各自独立的引擎副本挂在同一个网关后面，副本之间不共享模型状态。 |
| 副本摘除 | 网关停止往某个副本发请求，它上面在飞的请求改路到别的副本重新算。 |
| 回插 | 修好的副本重新预热，先接一部分流量，达标率回到集群水平再恢复全量。 |
| 误杀 | 副本本来能按时完成请求，却被判定成坏的摘掉了。 |
| 慢副本 | 同样的批次组成下，step 时间持续比别的副本长的那个副本。 |
| 冷启动四段 | 进程拉起、权重加载、KV 池初始化与 CUDA Graph 捕获、前缀缓存重建。 |
| 热态稳态 | 前缀命中率与 step 时间都回到集群中位数的那个状态。 |
| XID | NVIDIA 驱动上报的硬件错误编号，79 是掉卡，63/64 是 ECC，74 是 NVLink。 |
| 降频 | 显卡因为温度或功耗把频率压下来，算力变小，探针照样通过。 |
| 硬件子项 | decode 段里能由降频或 ECC 解释的那部分耗时。 |
| 故障注入 | 人为制造副本故障，四类：杀进程、网络分区、慢副本、冷启动失败。 |

## 步骤 0：现勘与核实——先证明值得做（指南第 5 节）

这一步的目标：动工之前确认五件事。第一，打点位置拿得到，不改 kernel 也能测出四段耗时；第二，调度器的三处决策点能读外部参数；第三，上游已经有预测器与归因模型，自己的增量站得住；第四，私有化合同里确实有延迟条款与赔付，需求不是编出来的；第五，副本健康信号在这个部署形态下读得到，检测延迟能压到多少。

具体做什么：

1. 单卡起一主两从的副本组，锁定镜像、模型、驱动、CUDA 版本，把启动参数读成一张映射表：显存比例、最大并发、block 大小、KV 池容量、是否开前缀缓存、是否开 chunked prefill、chunk 上限默认值。
2. 精读 Scorpio、Cascade、LLMVisor 三篇，逐条列出它们覆盖的机制，写进现状矩阵。矩阵只回答一件事：哪些环节复用，哪些环节自研。
3. 核实云厂商推理服务的合同形态与赔付口径，只记录公开可查的部分，查不到就标未核实。
4. 在调度路径上找五个打点位置，确认每个位置在异步执行下能拿到时间戳。找不到就换后端或改方案，这一步是头号风险。
5. 在调度器里找三处决策点：抢占候选怎么排序、前缀按什么驱逐、chunk 上限从哪里读。确认三处能塞进外部参数，确认与打点位置是否共用同一段代码。三处都改不动时，显存调度整段砍掉，指南第 13 节标未做。
6. 实测设备到主机与主机到设备的带宽，扫 1 MB、16 MB、128 MB、1 GB 四个块大小，记固定开销。与重算成本比一遍，换出更贵就直接写明本机型只走重算分支。
7. 核实副本健康信号的三条路径：编排侧探针的判据与周期（K8s 默认 periodSeconds 10、failureThreshold 3，合计 30 秒）；容器里能不能读到降频原因与 ECC 计数，走 DCGM 还是 `nvidia-smi -q`；XID 从内核日志的哪条路径取，采集周期多长。三条各写一个最小实验证明读得到，读不到的那条标缺失。
8. 产出现勘报告：现状矩阵、缺口排序、打点可行性结论、三处决策点的可插入性结论、三条健康信号的可得性结论。

过关标准：矩阵七行齐全，每行有版本号与出处；五个打点位置各有一个最小实验证明能取到时间；三处决策点各有一处代码位置与一个改参数生效的最小实验；带宽表有四个块大小的实测值；三条健康信号各有一条「读得到 / 读不到」的结论与采集延迟；缺口排序写清先做哪一段。

红灯处理：打点位置拿不到，Pact 的归因段退化为模型估计，整个项目降级成网关侧的合同服务，先改范围再动工。决策点拿不到但打点拿得到，项目仍是契约层，显存调度改写成调研笔记。硬件信号读不到但 step 时间分布拿得到，容错按两条信号运行，归因的硬件子项标证据不足，故障责任只按一档折算。

## 步骤 1：搭实验装置——你的实验室（指南第 6 节）

为什么第二步是它：后面每做完一段，都要立刻看到效果，看到效果全靠这套装置。装置不稳，所有数字都不可信。

具体做什么：

1. 网关：鉴权、配额、request id 注入、拒绝响应、路由、摘除执行六件事。SSE 转发与断连检测放在这里，断连要通知引擎取消，避免白算。摘除执行只按处置器的判定摘 endpoint 并改路，网关不自己判副本好坏。
2. 负载台：按合同场景生成轨迹，参数有模型、SLO 分位、共享前缀比例、输入与输出长度分布、突发形状、租户数量、缓存冷热、KV 池容量、副本数、故障注入类型与时刻。同一份轨迹同时喂给本产品与对照组，两侧 KV 池容量与副本数取同一个值。
3. 负载形状分档：共享前缀比例取三档、输入长度分布取三档，每档单独出结论。分档参数写进轨迹文件名，换档不改代码。
4. 故障注入器四类：杀副本进程、网关到副本丢包或断连、cgroup 限 CPU 配额或 `nvidia-smi -lgc` 锁低频造慢副本、副本盘满或权重文件缺失造冷启动失败。爆炸半径限定一个副本，其余副本继续接流量。注入时刻、副本编号、手段写进轨迹元数据。
5. 存储：流水表按时间分区，批次快照与显存事件各一张表、按 step 序号与 request id 关联，副本健康事件一张表、按副本编号与时刻关联，契约与处置记录进关系库，指标走 Prometheus。流水表与指标库共用 request id，两边数字能互查。
6. 冷热态规程：冷态每轮重启副本并清空 KV，热态写清预热流程。两组数字分开报，不混在一张表里。
7. 一条命令拉起整套装置，轨迹文件版本化，换参数不改代码。

过关标准：一条命令起全套；同一份轨迹重跑两次，请求数、token 数、P50 TTFT 对得上；冷态与热态各有一组基线；九档负载形状各能生成一份轨迹；四类故障注入各能触发一次并留下注入记录。

## 步骤 2：引擎侧打点——项目的灵魂（指南第 7 节）

这一步的目标：把请求级的时序从引擎里掏出来。上游只给聚合指标，Pact 的计量、预测、归因、结算、显存调度、慢副本判定全都要请求级或步级记录。没有这一段，后面几段都是估计。

具体做什么：

1. 五个位置按时间顺序埋点：入队、出队、每个 prefill 块结束、首 token、结束或取消。每个位置记一条事件，带 request id。
2. 每个请求记九项：租户、入队与出队时刻、prefill 块数与每块 token 数、前缀命中 token 数、首 token 时刻、输出 token 数、被抢占次数与每次重算 token 数、换出与换入的次数与每次 token 数与耗时、KV 占用峰值。
3. 每个调度步记一条批次快照：同批请求 id、各自阶段、各自 token 数、当步 KV 占用、是否触发抢占。快照全量记录，不随请求采样率下降。请求级 trace 才是违约相关全量、正常请求按 1/32 采样，采样率写进配置。快照另按副本聚合出 step 时间分布，聚合时按 batch token 数分桶，同桶内的副本之间相比，这一步的产物喂给步骤 9 的慢副本判定。
4. 显存事件另记一张表，四类事件名：抢占、换出、换入、前缀驱逐。字段带时刻、request id 或前缀哈希、token 数、耗时、触发原因。策略退回上游默认时也记一条，带退回原因。
5. 写入走环形缓冲，调度路径上不申请内存、不加锁；落盘交给独立线程，按 step 或时间窗口批量导出。
6. 时间戳用单调时钟，GPU 侧用 CUDA event 记首 token 与块边界。CUDA Graph 捕获区内不埋点，Graph 重放期间只记 step 级时刻，请求级时刻按 step 归属推算。推算误差与 TPOT 条款阈值同量级时，decode 段归因改用模型估计，差值写进报告。
7. 处理五类调度特性的语义：chunked prefill 把各段加总，段间让给 decode 的时间不算进该请求的 prefill；前缀命中按实际计算 token 归因，命中数单列；抢占记一次重算事件，重算 token 单列；换出到换入之间的等待算排队段，换回后的重新 prefill 算 prefill 段的重算子项；取消记时刻与已生成 token 数。
8. 五组标定离线做，在线查表：TPOT 与 batch token 数的关系（扫 1、4、8、16、32，另加混批一档：decode 固定 8 个请求、chunk 取 512、1024、2048、4096）、prefill 每 token 时间（命中与未命中两档，输入 1k、4k、16k、32k）、排队时间直接测不用模型、换出与换入带宽（四个块大小加固定开销）、冷启动四段耗时（进程拉起、权重加载、KV 池初始化与 CUDA Graph 捕获、前缀缓存重建；权重加载扫对象存储与本地盘两个来源，前缀重建按共享前缀比例三档各记回到稳态所需的请求数与时间）。
9. 三档开关：全量、采样、关闭。关闭时归因退化为模型估计，误差单列一节。缓冲区溢出丢最旧记录，丢弃条数进面板。批次快照与显存事件不参与请求级采样，溢出时按同样规则丢弃并计数。

过关标准（三项，缺一不算过）：

1. 开销：开关前后同一轨迹跑两遍，P50 与 P99 TTFT、吞吐的差在 1% 以内；超了就降采样率。
2. 完整性：网关请求计数与 trace 条数对账，缺失率低于 0.1%；批次快照条数与调度步数对账；显存事件与引擎侧抢占计数对账。
3. 归因精度：同一批违约请求上，打点归因与模型估计对照，报误差。

常见坑：把打点写进 Graph 捕获区导致 replay 期间没有数据；用主机时钟量首 token，异步执行下比真实时刻晚；chunk 边界没按块对齐，段间被 decode 占用的时间被误算进 prefill；批次快照跟着请求一起按 1/32 采样，多租户归因的分母缺了三十倍；换出等待被并进 prefill，换出策略的代价看起来是零；step 时间分布不按 batch token 数分桶就直接比副本，接请求多的那个副本被判成慢副本。

## 步骤 3：流水表与计量口径（指南第 8 节前半）

这一步的目标：把所有数字钉在一套口径上，后面预测、结算、对账、产出率都用它。

具体做什么：

1. 流水表每请求一行，主键是 request id，按时间分区。字段与 7.2 的九项对齐，另加处置动作、最终结局、条款版本号、改路重算标记。
2. 四条计量口径先定死：token 数取引擎返回的 usage，网关不估算；缓存命中是否计费写进合同，两种约定各给一组实验结果；被拒绝的请求计 0 token，计入误拒率；断连请求按已生成 token 计费。
3. 流水表与 Prometheus 共用 request id，任一面板数字都能回查到具体请求。
4. 达标判定只写一处，结算、预测校准、产出率三处都调它，不允许各算各的。

过关标准：随机抽十条请求，从网关日志、trace、流水表、指标四处读出的 token 数与耗时一致；命中计费两种口径各跑一组，数字能分开；三处调同一个达标判定函数，改一次阈值三处同时变。

## 步骤 4：契约登记（指南第 8 节后半）

具体做什么：

1. 合同字段：模型、SLO 分位、统计窗口、最小样本量、赔付公式、允许的降级档位、可用性条款、故障责任分档的两档系数。
2. 版本管理：条款有版本号与生效失效时间，变更留审计记录；结算按请求发生时刻对应的版本计算。
3. 样本量门槛：不足时按合同约定处理，默认沿用上一窗口的达标率并标注。
4. 合同期限同时供三处读：结算判违约、预测器算完成概率、显存调度器算剩余期限。三处读同一个版本号，版本号写进流水表、预测记录与显存事件。可用性条款与分档系数的版本号另写进副本健康事件与归因记录，摘除决策与硬件子项判定按请求发生时刻的版本取系数。

过关标准：同一窗口内改一次条款，旧请求按旧版本结算，新请求按新版本结算，账能对上；任取一条显存事件能读出它当时用的条款版本；任取一条摘除记录能读出它当时用的分档系数版本。

## 步骤 5：违约预测（指南第 9 节）

这一步的目标：给每个请求一个完成概率与区间，不给布尔判定。概率与剩余期限同时供处置器和显存调度器用。

具体做什么：

1. 三组特征：系统状态（队列长度、KV 占用、inflight、近期 TTFT 分位、副本余量、副本健康状态：在役 / 疑似慢 / 已摘除 / 回插预热中）、请求形状（输入 token 数、是否命中前缀、合同分位）、输出长度估计（首 token 前用同类历史分布，首 token 后按已生成数与历史衰减更新）。
2. 四步计算，每步能单独核对：排队时间给区间；prefill 时间按实际计算 token 乘每 token 时间，命中与未命中分档；decode 时间按输出长度乘 TPOT，批内含 prefill chunk 时查混批表；最后把输出长度分布积分成「总时间不超过期限」的概率。
3. 每一步留中间结果，出错时能定位到哪一步偏了。
4. 首 token 之前的预测误差最大，这一段单独报告。显存调度在这一段不用预测值排序。
5. 副本被摘除时它上面在飞请求的概率归零，改路后按新副本的队列与前缀命中状态重算一次，原 request id 与重算标记一起带走。

过关标准：同一批请求，四步的中间结果与实测分段耗时逐段对照，误差落在可解释范围；预测概率的分布不塌缩到 0 或 1；混批与纯 decode 批各查各的表，查错表时误差能被中间结果暴露；摘除一个副本后，它上面在飞请求的概率全部归零且改路记录条数对得上。

## 步骤 6：校准与漂移（指南第 9 节后半）

具体做什么：

1. 按预测概率分桶，比较桶内实际达标率与预测值，画可靠性曲线，报 Brier 分数与 ECE。
2. 未通过校准的概率不进入处置，也不进入让位选择的排序。校准按统计窗口重做，窗口与合同窗口一致。
3. 漂移检测：特征分布与历史基线比较，超阈值告警并暂停自动处置，转人工确认。显存调度同步退回上游默认，记退回事件。暂停的是准入、降级、扩容三类按概率触发的动作；副本摘除按健康信号触发，不随漂移暂停，否则漂移期间的硬件故障没人管。
4. 写清失效条件：突发到达时特征失真、缓存全冷时 prefill 分布偏移、模型或引擎版本切换后历史样本失效、副本摘除与回插期间队列状态突变。

过关标准：可靠性曲线不穿过对角线太多；Brier 与 ECE 有数；人为把到达率翻倍能触发漂移告警，且显存调度的退回事件同时出现；漂移暂停期间杀一个副本，摘除动作照样触发。

## 步骤 7：处置（指南第 10 节前半）

具体做什么：

1. 五类动作：准入（概率低于阈值时拒绝，返回理由与建议重试时间）、降级（限输出长度、降优先级、切合同允许的小模型）、扩容（预测下一窗口集体违约时提前触发，触发点按预热耗时与预测窗口的交叉点定）、路由（按副本预测余量选，命中同一前缀优先送已缓存该前缀的副本）、摘除与替换（副本失联或判定为慢副本时摘 endpoint，在飞请求改路重算，备副本预热后接流量，修好的副本回插）。第五类的检测信号与恢复流程在步骤 9 落地，这一步先把动作接口、代价与记录格式定下来。
2. 代价表四项折算到同一单位：拒绝按合同请求单价折算业务损失；降级按合同系数折算质量折损；扩容按单位时间成本乘预热时长；摘除与替换按在飞请求重算的 prefill 算力成本加备副本冷启动机时，误杀时再加一次白付的冷启动。
3. 迟滞与冷却按动作分别设，避免振荡。每次动作记录触发时的预测概率或健康信号、动作类型与事后结果。
4. 误拒率单独统计，它是本方案的主要成本。误杀次数在步骤 9 单列，两者判定方式同构。
5. 划清与显存调度的分工：处置改变请求的命运（拒绝、降级、换副本、加副本、摘副本），显存调度改变请求在副本内的等待与计算顺序。扩容触发前先看池占用，长期低于阈值的副本不扩容。摘除与扩容共用预热耗时表，摘除造成的容量缺口由扩容补，两个动作之间带互锁。

过关标准：五类动作都能演示一次；动作次数、收益、振荡次数进面板；同一场景下不出现同一动作反复开关；网关的前缀路由与引擎的前缀保留各管各的，日志能分清是哪一层做的决定；摘除与扩容在同一窗口里同时触发时互锁生效，记录里能看出谁先谁后。

## 步骤 8：显存调度——固定算力下的产出（指南第 13 节）

为什么排在归因前面：归因要拆换出等待与重算，策略先跑起来，归因才有真实事件可拆。这一步依赖步骤 2 的标定表与显存事件、步骤 4 的合同期限、步骤 6 的校准结论，三者缺一就退回上游默认。

这一步的目标：在 KV 池容量不变的条件下提高达标 token 产出率。指标是达标请求的输出 token 数除以（KV 池容量 GB × 窗口秒数），分母取启动配置值，一组对照内固定。多副本时分母取参与对照的各副本配置容量之和，副本数在对照内固定。

具体做什么：

1. 让位选择。池占用超阈值时，对每个候选算两个耗时：重算耗时 = 已生成 token 数 × prefill 每 token 时间；换出耗时 = KV 字节数 / 实测带宽 + 换回的同量传输 + 两次固定开销。取小的那个动作。候选之间按「合同剩余期限 − 让位造成的延迟」排序，值最小的先让位。
2. 排序只在超阈值时触发，阈值写进配置。首 token 之前输出长度估计误差最大，这一段退回上游顺序并记退回事件。
3. 前缀保留。前缀缓存满时对每个前缀算保留收益 = 预计命中次数 × 每次命中省下的 prefill token 数 × 每 token 时间。预计命中次数由历史到达率与租户合同请求量给出。按收益升序驱逐末位，到达率漂移超阈值时退回 LRU。
4. 批组装。取批内 decode 请求的合同剩余期限最小值，按该值查混批表选 chunk 上限档位。期限紧的批取小 chunk，宽松的批取大 chunk。
5. 参数下发。三项策略各一组参数，契约服务按统计窗口算一次写进引擎可读的配置，引擎每步读取。参数缺失或过期时沿用上游默认，记退回事件。
6. 开销自测。策略计算在调度步内同步执行，记录每步的排序与查表耗时，与步长时间比。超 1% 就提高触发阈值或退回默认。
7. 四组对照跑同一份轨迹：上游默认、只开让位选择、只开前缀保留、三项全开。每组七次取中位数，冷热态分开，九档负载形状各跑一遍。

过关标准（三项门槛加一项开销，缺一不算过）：

1. 达标 token 产出率的提升幅度有数，报中位数与区间。
2. 误拒率与降级次数不高于对照组。误拒用配对轨迹判定：对照组按时完成的请求在实验组被拒绝，这些请求计入误拒分子，完成时间取对照组实测值。
3. 输入 ≥16K 请求的达标率不低于对照组。
4. 每步策略计算耗时不超过步长时间的 1%。

常见坑：分母用实测占用峰值而不是配置容量，把池子用满就显得产出率高；分子把违约请求的 token 也算进去，指标退化成普通吞吐；没有第三项门槛，策略把长请求全赶走，短请求产出率好看、长请求全违约；排序每步都跑，池子没满也付排序开销；换出比重算贵的机型上硬开换出分支，PCIe 成了瓶颈；多副本对照里把摘除掉的副本从分母里剔掉，摘除造成的损失被掩盖。

红灯处理：现勘发现三处决策点改不动，这一步整段标未做，项目回到五段契约层。带宽实测显示换出永远比重算贵，只留重算分支，让位选择的增量缩小到候选排序一项，报告里写明缩了多少。

## 步骤 9：副本容错——可用性条款的保障手段（指南第 10 节后半）

为什么排在归因前面：归因要拆硬件子项，摘除动作与降频信号先采起来，归因才有真实事件可拆。这一步依赖步骤 1 的故障注入器与副本健康事件表、步骤 2 的 step 时间分布与冷启动标定、步骤 7 的摘除动作接口。

这一步的目标：副本坏了或变慢时，故障窗口内的违约次数比无容错档少，同时误杀次数不增加。训练侧丢的是几小时的优化器进度，推理侧丢的是在飞的几十个请求和副本的热态，所以目标量是摘除到备副本能接流量的秒数，以及这段窗口里多出来的违约次数。

具体做什么：

1. 三条检测信号各采一路。网关探针判进程活着，周期与失败阈值决定检测延迟，K8s 默认 10 秒周期乘 3 次阈值合计 30 秒，要秒级就把周期降到 1–5 秒。step 时间分布判算得快，同 batch token 数桶内某副本的中位数连续 N 个窗口超过集群中位数一个百分比就标疑似慢。硬件信号判为什么慢，XID 从内核日志取（79 掉卡、63/64 ECC、74 NVLink），降频原因读 `nvidia-smi -q -d PERFORMANCE`，字段名旧驱动叫 Clocks Throttle Reasons、新驱动叫 Clocks Event Reasons，按实际输出记；ECC 与退役页读 `nvidia-smi -q -d ECC,PAGE_RETIREMENT`。
2. 三条信号各判一层，缺一路就降级运行。硬件信号读不到时慢副本判定只靠 step 分布，归因的硬件子项标证据不足，这一条在步骤 0 已经核实过，这里按核实结论配置。短诊断 `dcgmi diag -r 1` 秒级返回，只对已摘除的副本跑，在接流量的副本上跑会污染测量。
3. 摘除与改路。判定成立后处置器发摘除指令，网关摘 endpoint，在飞请求改路到其余副本重新 prefill。重算代价式子与步骤 8 共用一张表：已生成 token 数 × prefill 每 token 时间。跨副本 KV 迁移不在这里做，属于步骤 15 的调研层，迁移与重算的实测差值由那边给出。
4. 误杀门槛与回插。判定要连续 N 个窗口成立才摘除，摘除后带冷却期，冷却期内对同一副本不再重复动作。修好的副本重新预热再回插，回插时先给一部分流量，达标率回到集群中位数才恢复全量。机房温度导致降频时，摘掉旧副本拉起新副本一样降频，这一次冷启动是白付的，误杀判定就是抓这种情况。
5. 误杀用配对轨迹判定：对照组同一时刻该副本仍在役且请求按时完成，实验组把它摘了，这次计入误杀分子。两侧吃同一份轨迹与同一组注入时刻。
6. 冷启动四段分别计时，查步骤 2 的第 5 组标定表。权重 16 GB，对象存储 10 GB/s 是 1.6 秒，本地 NVMe 3 GB/s 是 5.3 秒；CUDA Graph 按捕获的 shape 数各付一次；前缀缓存重建靠流量重新命中，共享前缀比例高时要几十个请求才回到稳态。进程就绪与热态稳态是两个时刻，分开记分开报。
7. 三档对照跑同一份轨迹与同一组故障注入：无容错（探针失败也继续路由）、只探针摘除、探针加 step 分布加回插。四类注入各跑一遍，每组七次取中位数。

过关标准（三项门槛，缺一不算过）：

1. 故障窗口内的违约次数低于无容错档，报中位数与区间。
2. 第三档的误杀次数不高于第二档，慢副本判定新增的摘除动作里误杀占比单列。
3. 恢复四段耗时各有实测值，进程就绪与热态稳态分开报，秒级恢复的结论只挂在前者上。

常见坑：只靠探针，慢副本探针照样通过，违约一直发生却没人摘；step 时间分布不分桶就比副本，接请求多的那个被误杀；摘除后没有冷却期，同一副本反复摘了又插；回插时直接给全量流量，前缀缓存全冷，达标率掉下去又触发摘除，来回振荡；把进程就绪当成恢复完成，对外报秒级恢复，实际热态还要几十个请求才回来；锁频模拟的降频被写成温度故障的复现。

红灯处理：三条信号只剩探针一条（step 分布拿不到或硬件信号读不到），容错退化成编排侧已有的健康检查加摘除，本项目的增量只剩改路重算与冷启动分段计时，报告里写明缩了多少。误杀次数压不下来时退回只探针摘除档，慢副本判定标未做。

## 步骤 10：归因与举证（指南第 11 节）

具体做什么：

1. 四段拆分：排队、prefill（含重算）、decode、客户端与网络。打点为主，模型估计为辅，两套结果在同一批请求上对照并报误差。
2. 换出的归属按步骤 2 定的规则落代码：换出到换入之间的等待算排队段，换回后的重新 prefill 算 prefill 段的重算子项。两段分开报，合并会掩盖换出策略的真实代价。
3. decode 段拆硬件子项，判据两条同时成立：该副本 step 时间偏离同桶集群中位数超阈值，且降频原因或 ECC 计数非零。只满足前一条时子项标证据不足，偏离留在批次组成里解释。子项占比供步骤 11 的故障责任分档用。
4. 交叉部分的归属规则写进报告：排队与 prefill 争抢同一份算力，重合区间按约定切分。
5. 证据包七件：违约事件编号、请求 trace、当时副本指标快照、批次组成、显存事件序列、副本健康与硬件信号快照、合同条款版本。
6. 证据包可回放：同一份轨迹重跑，比较处置决策、让位选择与摘除决策是否一致。
7. 多租户归因：同时段批次快照加各租户请求占比，回答这次违约由谁的流量造成。批次快照全量记录，分母不缺。

过关标准：任取一次违约，四段占比加起来与总延迟的残差有解释；换出等待与重算两项能单独读出来；锁频注入造出的违约能落到硬件子项，证据不足的情况能标出来；证据包导出后能独立重跑；多租户归因能指出占比最高的租户。

## 步骤 11：结算与对账（指南第 12 节）

具体做什么：

1. 按合同窗口出四项数字：达标率、违约次数、赔付金额、归因占比。
2. 赔付公式可配置，设单窗口上限；样本不足按约定处理。
3. 故障责任分档：硬件子项成立时按平台侧硬件故障那一档系数折算，证据不足时按运行态违约那一档折算。两档系数与判定依据取步骤 4 登记的条款版本，申诉时以证据包里的硬件信号快照为准。
4. 账单与流水表对账，差异超阈值冻结出账并告警。
5. 争议期内证据包可导出，租户自行复核。
6. 差异的常见来源逐条排查：断连请求、重试请求、摘除后改路重算的请求、缓存命中计费口径、窗口边界。
7. 结算与显存调度共用步骤 3 的达标判定，两处读同一个条款版本。产出率不进结算单，它衡量平台侧效率，不构成对租户的赔付依据。

过关标准：第三方拿同一份流水能复算四个数字；人为制造一次对账差异，系统能冻结出账；结算单里查不到产出率这个字段；同一次锁频注入造出的违约，硬件子项成立与证据不足两种情况分别按两档系数出账，金额差能算出来。

## 步骤 12：可观测性（指南第 14 节）

具体做什么：

1. 六层指标：契约层（达标率、违约率、赔付额、误拒率）、预测层（校准误差、Brier、漂移告警数）、处置层（动作次数、收益、振荡次数、摘除与回插次数、误杀次数、故障窗口违约次数、冷启动四段耗时）、显存层（产出率、换出与重算比例、前缀命中率、长请求达标率、策略退回次数）、归因层（四段占比、残差、重算占比、硬件子项占比与证据不足条数）、引擎层（打点开销、策略计算开销、trace 缺失率、采样率）。
2. 四块面板：契约总览、租户视图、副本视图、预测视图。副本视图里加 KV 池占用、换出吞吐、产出率与长请求达标率，与对照组同图；再加健康状态、同桶 step 时间分布、摘除与回插记录、进程就绪与热态稳态两个时刻。
3. 七类告警：违约率、校准误差、误拒率、对账差异、长请求达标率低于对照组、副本失联、副本 step 时间偏离同桶集群中位数。前五类带 request id 样本，点开即到 trace 与当步批次快照；后两类带副本编号与健康信号快照，点开即到摘除决策与当时三条信号的取值。
4. 可回放是核心：任一违约事件能从面板跳进证据包，重跑一次并对比处置决策、让位选择与摘除决策。

过关标准：从告警点到证据包再到回放，整条链路走通一次；每层指标都有负责人一栏写清；人为把长请求达标率压到对照组以下，第五类告警能响；锁低频造一个慢副本，第七类告警能响且点进去能看到三条信号的取值。

## 步骤 13：端到端对照（指南第 18 节）

具体做什么：

1. 契约层三组条件吃同一份轨迹：现状（反应式扩容加无准入）、仅预测不处置、完整方案。
2. 显存调度另跑四组：上游默认、只开让位选择、只开前缀保留、三项全开。
3. 副本容错另跑三档：无容错、只探针摘除、探针加 step 分布加回插。四类故障注入各跑一遍，爆炸半径限定一个副本，注入期间与无注入轮次共用同一份负载轨迹。
4. 每组至少七次，取中位数，报区间；冷热态分开；模型、引擎、镜像、机器、负载配置、KV 池容量、副本数、故障注入类型与时刻随报告入库，一条命令复现。
5. 客户端饱和的轮次作废，负载台自身的 CPU 与连接数曲线作为附件。
6. 处置收益按同窗口内违约次数差计算，不用单次请求耗时差。
7. 校准单独一节，与性能指标分开报；打点开销与策略计算开销各单列一组。
8. 九档负载形状各出各的结论，不合并成一个总均值。收益接近零的档位照实报。
9. 恢复耗时按四段分别报，进程就绪与热态稳态是两个时刻，两者都进报告。

过关标准：三组契约条件的违约率、误拒率、单位 token 成本能画在同一张图上；四组显存条件的产出率与长请求达标率能画在同一张图上；三档容错条件的故障窗口违约次数与误杀次数能画在同一张图上；任一组能一键复现。

## 步骤 14：增量池（选做，指南第 15 节）

两项共用同一份 trace 与面板：多租户公平（按合同权重分配 KV 与算力，量干预前后的达标率差距）、结构化输出（合同加格式约束，看 token 预算与违约概率怎么变）。

过关标准：每项至少一组前后对照；没做就写「未做」，不留半成品。

## 步骤 15：调研层（只读，指南第 16 节）

P/D 分离与跨副本迁移两项，只读文档与源码，各做一次集成实验，写调研笔记，不自建。KV 到主机内存的换出已在步骤 8 实现，这里只调研跨节点与落 NVMe 的换出。跨副本 KV 迁移在步骤 9 里默认走重算，这一项的集成实验给出迁移与重算的收益账，实测差值写进步骤 9 的报告。覆盖边界在报告里单列一节。

过关标准：两份笔记各有一句「为什么不自建」；集成实验有截图或日志；笔记里写明与步骤 8、步骤 9 已实现部分的分界；迁移与重算的差值有一组实测数。

## 步骤 16：交付与诚实清单（指南第 20、21 节）

交付物：网关；契约服务六段；引擎打点、批次快照与调度策略补丁；面板与告警规则；负载台与四类故障注入器；七份报告（打点开销与精度、预测校准、处置收益、显存调度收益、副本容错收益、归因精度、结算对账）；一份核实报告。

诚实清单逐条写进报告：合同模板自定义、赔付口径非行业标准；单卡双卡只做机制验证；首 token 前误差最大且让位选择在该段退回默认；四段归因有残差；突发下预测滞后；结算依赖业务口径；降级质量不评估；打点与策略插入位置依赖引擎版本；换出收益依赖 PCIe 与主机内存带宽，换机型要重测；共享前缀比例低、输入短、池占用长期低于阈值时显存调度收益接近零；副本容错只在单机多卡上验证，跨机故障与真实网络分区未覆盖；锁频模拟的是降频的结果，温度与电源故障的成因未复现；硬件信号在容器里可能读不到，读不到时慢副本判定只剩一条信号；进程就绪是秒级、热态稳态靠流量重新命中，两者分开报；误杀门槛与回插流量比例没有普适值，换场景重标；故障责任分档是自定义模板，法律效力未经核实；跨机张量并行的通信占比是量级推算，本期不做模型并行，推算值不进收益结论。

## 排期锚点与砍项顺序

顺序锚点：

1. 步骤 0 与 1 是闸门，任何一步红灯都先修，不带病写打点。
2. 步骤 2 是灵魂，验收三项不过就不做预测。
3. 步骤 3 到 5 打通后可以演示「请求进、概率出」。
4. 步骤 6 到 8 补齐后能在固定算力下出收益数字，这是往算力方向走的那一段。
5. 步骤 9 补齐后可用性条款有保障手段，故障注入能出违约次数差与误杀次数。
6. 步骤 10 到 11 补齐后才是产品，四段归因与结算都要有数。
7. 步骤 12 到 13 出对外材料。
8. 步骤 14 到 15 有余力再做。

砍项顺序（从后往前砍，主线不动）：

1. 先砍增量池，两项都不做。
2. 再砍调研层的集成实验，只留笔记。
3. 再砍慢副本判定与回插，容错只留探针摘除与改路重算。
4. 再砍硬件子项归因，故障责任只按一档折算。
5. 再砍多租户归因，证据包只做单租户。
6. 再砍结算的自动对账，保留离线报表与人工复核。
7. 再砍扩容与降级两类动作，只留准入、路由与摘除。
8. 再砍前缀保留与批组装，显存调度只留让位选择一项。
9. 最后砍证据包回放，证据包保留导出。

不管砍到哪一步，打点、计量、预测、处置、显存调度、归因这六段要留。它们是 Pact 与网关型产品的分界线。
