# 生产故障与 on-call 排查（分级版）

## 七类骨架表（本章的答题模板）

| 类 | 定层顺序 | 能区分两层的关键指标 | 落到代码/配置的判据 | 第一动作 |
|---|---|---|---|---|
| 延迟 | 应用 → 内核/系统 → 网络 → 存储/设备 → 硬件 | 同一段路径上的分段耗时；P50 与 P99 是否同步移动 | 分段耗时定位到具体函数/调用点，能构造复现 | 先止血（摘流量/回滚），延迟类不影响正确性时留现场 |
| 吞吐 | 消费者 → 队列 → 生产者 → 设备上限 | 队列深度 + 拒绝数；设备 util 与单请求耗时的乘积 | 算出理论上限，实测达到上限的百分比，缺口归到某一环 | 判上限：是机制问题还是容量问题 |
| 资源 | 进程 → cgroup/容器 → 节点 → 集群 | 配额线 vs 实际用量的差；同类指标的时间曲线形状（阶跃 or 缓涨） | 缓涨指向泄漏或无上限增长，阶跃指向配置与流量 | 摘流量 + 限并发，别先加配额（会把问题推到下一个天花板） |
| 可用性 | 依赖 → 自身 → 流量 | 错误是集中在某依赖还是均摊；健康检查摘除数与恢复数 | 熔断/超时/重试三项配置逐条核 | 止血优先于定位，且必须先停重试风暴再看下游 |
| 正确性 | 写入 → 索引 → 缓存 → 读取 | 端到端逐位比对；计数守恒（写入数 = 读到数 + 丢弃数） | 能构造出必现的错误样本 | 隔离污染数据，禁止先重启（会销毁现场） |
| K8s 原生 | 事件 → 调度 → kubelet/运行时 → 网络插件 → 存储插件 | `kubectl describe` 的 Events 与 conditions；同类 Pod 是否同节点 | 是否属于装置问题（镜像/证书/配额） | 看事件再动手，Pending 与 CrashLoop 的处置完全不同 |
| GPU/训练集群 | 单卡 → 单机 → 网络 → 并行框架 | 同任务内 peer 对比（谁和均值不一样）；绝对阈值在混合硬件下误报率高 | 区分 straggler（慢节点）与 stall（全体等数据） | 先定位到"哪张卡/哪个 rank"，再决定换卡还是换机 |

## T1 · 必须脱口而出

1. ★ 通用骨架：任何一次线上故障，"定层 → 定界 → 取指标 → 落代码"四步各自的产出物是什么？为什么定界（全局还是局部）必须先于取指标？

【要点】四步的产出物分别是：候选层集合（能缩到 1–2 层）、影响范围（哪个节点／哪条路径／哪类请求）、一条能证伪某层的读数、一个能改的代码行或配置项。定界必须先于取指标，因为指标有几百条，只有先划定“全局还是局部”才知道看哪一组；不先定界就会退化成“每个面板都看一眼”。
2. ★ 排查约束变体：只给你 dashboard 权限（无 shell）、只给你日志（无 metrics）、只允许重启——三种约束下排查顺序分别怎么改？每种约束最容易永久失去哪一条信息？

【要点】只有 dashboard：失去进程内部状态与调用栈，只能靠分段指标 + 同类实例对比，最易失去的是“没发生的事件”（队列是不是空的看不出来）。只有日志：失去曲线与并发时序，只能靠时间戳和聚合计数，最易失去的是分位数。只能重启：现场全部销毁，唯一合法动作是先抓三样（见 T3 第 40 题），并把这次结案标成“未定位”。
3. ★ on-call 第一决策：什么信号必须立刻叫人并回滚，什么信号可以留到早上？用"影响面 × 可逆性 × 有没有真值可核对"给出你自己的判据表。

【要点】判据三轴：影响面（全量／单租户／单节点）× 可逆性（回滚是否无损）× 有没有真值可立刻核对。全量且回滚无损 → 立刻回滚并叫人；局部且动作不可逆 → 先隔离不先修；无真值可核对 → 禁止自动修，直接升级。一句话：止血的成本几乎总低于定位，但止血的不可逆性要单独评估。
4. 【延迟】★ 推理服务 P99 从 200ms 涨到 4s，QPS 没变，GPU 利用率从 90% 掉到 40%。列三个候选原因并按可能性排序，每个说清"哪一条指标能把它和另外两个分开"。

【要点】(a) 请求卡在网关排队或超时，根本没进引擎；(b) 显存不足触发抢占／KV 换出，大量时间耗在 PCIe；(c) 某个实例故障导致流量集中或重路由。区分：(a) 看网关队列深度与 429/503 计数；(b) 看引擎侧 preempt/swap 次数与 PCIe 吞吐；(c) 看分实例 P99 与连接分布。利用率从 90% 掉到 40% 已排除“算力打满”，方向必然是 GPU 在等东西，(a)(b) 优先于 (c)。
5. 【延迟】★ P50 一点没动、P99 涨了十倍，根因落在排队。为什么这条曲线几乎只能由排队造成？给出至少两个能造出它的机制。

【要点】P50 不动说明典型路径没变慢，只有少数请求撞上长队列、重试或慢实例，这条曲线由排队造成。两个能造成该曲线的机制：长上下文请求占住 batch 造成 head-of-line blocking；慢实例 + 客户端重试把尾部放大。若是计算本身变慢，整条曲线会一起平移。
6. 【吞吐】★ 训练吞吐掉了 30%，GPU 利用率均值不变、方差变大。这是慢节点还是数据管道 stall？两个假设分别用什么证据钉死？

【要点】均值不变、方差变大 = 一部分 GPU 在等，指向 straggler。钉死 straggler：逐 rank 的 step 时间分布 + peer 对比（谁和均值不一样）。钉死 stall：全体 step 时间同步抬高且数据管道队列见底。反证很关键：如果是全体等数据，利用率均值会整体下移，方差不变。
7. 【资源】★ 节点 available 还有几百 GB，进程仍被 OOM 杀掉。列三个候选原因（cgroup 配额、NUMA 单节点耗尽、slab/page table 内核态占用）并给出排查顺序。

【要点】顺序：先从 dmesg 的 OOM 报告读 constraint 字段，判断是 cgroup OOM 还是全局 OOM（前者最常见，容器里看不到节点 available）；再看 per-NUMA 空闲是否严重不均（绑定后单节点先耗尽）；最后看 slab／page table／conntrack 的内核态占用。三条各对应一行确认命令，答不出命令就别说自己会排。
8. 【可用性】★ 后端 P99 30s、客户端超时 10s、失败重试 2 次、峰值 1000 QPS：后端真卡住 60 秒时，你第一个掐断哪一环——客户端重试、网关并发上限还是队列拒绝？三条路各自的副作用是什么？为什么"先掐客户端重试"常常来不及？（放大倍数的算式见 15 章）

【要点】放大倍数与在途数量见 15 章第 13 题。处置：先掐网关侧的新请求准入（队列有界、满即 429/503）。客户端重试配置要发版才改得动，后端已经在过载里，只有网关能立刻把到达率压下来。副作用是把故障变成用户可见的拒绝——而这正是“显式降级”优于“隐性雪崩”的地方，必须主动说出来。
9. 【可用性】★ 级联故障的三条常见放大路径：重试风暴、健康检查误摘除、扩缩容正反馈。在你没设请求超时的前提下，哪一条最先发生、哪一条最难发现？

【要点】没设超时的前提下，重试风暴最先发生（客户端等不到就重试，白烧的算力还在后端排队）；健康检查误摘除最难发现，因为它的表象是“系统在自愈”，实际是可用实例越少、剩余越忙、越容易被继续摘。扩缩容正反馈排第二，它需要 HPA 指标本身是滞后量才成立。
10. 【K8s】★ Pod 处于 CrashLoopBackOff，每次能活约 8 分钟，日志为空。前三步动作分别能排除什么？为什么"能活 8 分钟"这一条就把镜像和启动崩溃排除了？

【要点】“能活 8 分钟”直接排除镜像拉不到、启动即崩、探针初始延迟配错。前三步：① describe 看 last state 是 OOMKilled、Error 还是被 liveness 杀掉——分内存、应用异常、探针三类；② 看节点事件有无 eviction 或内存压力污点；③ 确认日志是不是只写 stderr、或落文件后被运行时丢弃。每步都能排除一整类，不许跳步。
11. 【K8s】★ Pod 长期 Pending，事件只有 `0/12 nodes are available`。怎么把这条信息读成可执行的下一步？taint、资源、亲和、PVC 未绑定四类各看哪一行？

【要点】这条事件的全文其实逐行给了过滤原因：insufficient cpu/memory、有未容忍的 taint、node affinity 不匹配、PVC 未绑定或无可用卷。下一步是 describe pod 读 Events 全文 + 对照节点可分配量，四类各查一行。反模式是先看应用日志——Pod 还没起来，日志里没有答案。
12. 【GPU】★ 单机 nccl-tests 跑满带宽，多机训练 NCCL 间歇性超时。候选：(a) 网络侧 PFC 水线或路由；(b) 某张卡降频或 ECC；(c) 某个 rank 卡在数据加载反向传导。排序并给判据——为什么 (c) 最容易被误判成 (a)？

【要点】排序 (c)→(a)→(b)。理由：单机测速正常只能排除“本机 GPU 与本机网络栈”，不排除跨机路径；而 (c) 某 rank 卡在数据加载会让 collective 超时长得像网络问题。判据：超时发生时各 rank 是否停在同一个 collective 序号——一致说明是通信路径，不一致说明有 rank 迟到。(a) 看同时段 PFC pause/ECN 计数是否上涨；(b) 看 Xid、降频、ECC。
13. 【正确性】★ 缓存返回了另一个 key 的内容，或者读到了旧数据。怎么区分键冲突、失效竞态、并发写覆盖三类？各设计一个能定位到代码路径的构造实验。

【要点】键冲突：构造两个内容不同但算出同一 key 的对象，看是否互相覆盖；失效竞态：在写入与缓存失效之间注入延迟，写后立即读，看是否拿到旧值；并发写覆盖：同一 key 两个 writer 无版本号并发写，检查是否丢更新。每条都要能指到具体代码行和断言，说不出构造就只是背了三个名词。
14. 【延迟】★ 黑盒决策树：一个训练任务突然变慢，你只有一台机器上的 shell，给出完整排查顺序与每一步的判断依据。（迁自 07）

【要点】顺序：时间对齐（什么时候开始慢、同时有什么变更）→ 定界（同任务其他 rank？同节点其他任务？同集群？）→ USE 逐资源（CPU／内存／IO／网络各看 util、saturation、error）→ 尾延迟与排队 → 应用层分段。每步写清判断依据，例如“只有本任务慢而同节点其他任务正常 → 排除节点级故障，进任务内部分段”。

## T3 · 扩展与速查

29. 【正确性】重复消费与 exactly-once：工程上真正能做到的是哪一档？幂等键、去重窗口、补偿动作分别兜住哪种失败？
30. 【正确性】怎么自证"没丢数据"？写入侧计数与落盘侧计数对不上时，第三个能打破歧义的观测点是什么？
31. 【GPU】慢节点检测：为什么判据取同任务内 peer 对比？绝对阈值在什么规模与硬件混合度下失效？阈值该设多大、误报的代价是什么？
32. 【GPU】ECC 错误、Xid、GPU 降频、NVLink 降级四种告警的语义差别，哪些必须马上换卡、哪些可以先隔离？
33. 【延迟】跨机架 incast：为什么多台同时读一个节点时 P99 暴涨而单台正常？ECN/PFC、分片读、客户端限并发三条缓解各自的副作用。
34. 【K8s】HPA 扩了又缩的抖动：指标选错、冷却时间过短、扩容目标本身冷启动慢三种成因各自的修法。
35. 【on-call】runbook 的最小可用结构为什么是"症状 → 判据 → 动作"三段？操作步骤清单在哪些故障上失效？各举一个失败反例。
36. 【复盘】根因、触发条件、促成因素怎么切三层？为什么把事故写成"某人配置错了"必然是一次失败的复盘？
37. 【方法论】"先复现再修"在有真实用户的故障里为什么要反过来？不破坏现场的前提下，取证的最小动作集是什么？
38. 【方法论】怎么证明修好了？故障注入复跑、指标基线、观察窗口长度——这三项你各按什么规则定，能不能用"跑一次没报错"当结论？
39. 【存储】文件系统写满、inode 耗尽、只读 remount 三者在容器里的连锁表现：为什么应用层的报错总是晚于内核一层？
40. 【方法论】"重启就好"为什么是有害结论？给出重启前必须抓走的三类现场数据，以及抓不到时的替代方案。
41. 【吞吐】★ 如何系统化定位一个训练任务的瓶颈在 CPU、内存、I/O、网络还是 GPU？要求每一层给出"支持它的证据"和"排除它的证据"两栏。（迁自 07）
