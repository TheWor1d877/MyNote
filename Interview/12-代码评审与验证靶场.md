## 必会

1. 我描述一段 Go 预取器的实现：它用一个 map 记录哪些块正在预取，读这个 map 时没加锁、写的时候加了锁；预算字段叫 budgetMB，这个函数里按一百万换算，项目其他地方都按 1024×1024 换算；预取循环的条件写的是下标小于等于 cursor 加 window。你觉得这段实现有什么问题？哪个最致命，为什么？
2. 一个显存 block 池的 PR 我念给你听：原来的 Release 加了锁，而且设计成幂等的——引用计数为零才回收，调用方在错误路径上也会重复调它。新代码把锁删了，改成每次调用递减计数、减到零就归还空闲列表，没有下界保护；还新增了一个批量释放函数，在 for 循环里对每个块写 defer。这个 PR 合并前必须拦下哪几处？每处会在生产的什么症状里首次现身？
3. 一份预取窗口的测试用例集，六个场景全绿，覆盖率很高。但我告诉你：所有期望值都是按 window 加一写的，包括 window 等于零那条——而 window 等于零本来是「关闭预取」的对照配置。这份测试为什么永远抓不到边界缺陷？断言该怎么改，才能在缺陷引入的第一时间失败？
4. 一份实验结果：直读组每次都是冷缓存，预取组每次都是暖缓存，同一轮里直读先跑、预取后跑，每格跑一两次，报出八百倍加速、变异系数小于 0.5%。这个结论能不能成立？问题出在哪几处？只允许你加一个实验臂，你加哪个？
