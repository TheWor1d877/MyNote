## 计算机基础
- <span style="color:rgb(221, 85, 85)">从一次推理请求进入网关开始，到 GPU 返回 token，列出沿途可能涉及的操作系统、网络、存储、GPU 数据通路关键环节</span>
分为两个阶段讲： 冷启动与稳态

模型权重可能在远端存储或者本地盘上面，并且占用空间很大，将模型加载到显存走的是存储 -> 主机内存 -> GPU显存 走的是Pcle路线，这一阶段比较慢，可能会用上GDS，GPUDirect RDMA加速
模型加载完成之后，相关权重就常驻显存

到稳态阶段： 一次请求从进来到token出去
1.请求先进入网关： 
数据包到达网卡，网卡DMA写进Ring Buffer，触发中断，内核协议栈处理，最后用户态网关进程读走数据，中间经历系统调用与上下文切换
这一步的瓶颈点在于网卡多队列配置，中断与系统调用的开销，网关进程的并发模型 
如果是GO写的，还要考虑Goroutine在GMP模型中怎么调度，与GC优化
然后网关会将这个请求发给后端，这个过程同机走Unix  Socket，跨机再走一次网络

2.请求进入推理引擎排队
请求进入vLLM后，会先进入调度队列凑batch，咱够一批请求才开始算
并且还能通过continuous batching（调度的粒度从「一个 batch」变成「一次 token 生成」）动态插入新请求，让算力使用更加充分
batch终端的每个请求占显存存 KV Cache，所以KV Cache的管理是重点
比如：vLLM 用 PagedAttention，

3.GPU计算
输入的token从主机拷贝到显存，走PCle路线。然后分配相应的KV Cache空间
之后kernel launch，CUDA Stream调度，模型前向计算。
这里的显存带宽是瓶颈

4.token返回
返回是流式的，协议选择上可以分情况考虑：
SSE：格式简单，单向的，适合API
HTTP/2 streaming： 多路复用头部压缩，还能服务端推送，适合Web之类的
gRPC streaming：基于 HTTP/2，二进制、体积小、强类型、跨语言，适合内部服务间

5.可观测性
整条链路要能定位瓶颈：GPU 利用率、显存带宽、PCIe 吞吐、网络吞吐、CPU 占用、网关连接数。这些指标交叉看，才能知道当前卡在哪一环。

追问：
- "KV Cache 在显存和 CPU 内存之间换出，涉及哪些数据通路？"
物理通路就是 PCIe。 GPU 显存和 CPU 内存之间没有直连总线，所有数据都得走 PCIe。也就是说，KV Cache 换出和换回，全程受 PCIe 带宽约束。这里有个量级感受：一张卡几百 GB/s 的显存带宽，跟 PCIe 5.0 x16 单向几十 GB/s 比，差一个数量级。所以换出本身就不便宜，它是用带宽换显存空间。

逻辑通路上面有多种实现方式 :
最朴素的是 cudaMemcpy，同步拷贝，GPU 得等着，拷完才能干别的。这在推理里基本不能用，因为会阻塞计算。

稍微好点的是 cudaMemcpyAsync 配合 CUDA stream，让拷贝和计算在不同 stream 上重叠，走的是 GPU 的拷贝引擎（copy engine）。这样拷贝不占 SM，但依然走 PCIe。

再往上，如果是零拷贝或者 pinned memory，情况会好一些。所谓 pinned memory 是锁页内存，不会被操作系统换出到磁盘，GPU 能通过 DMA 直接访问，省掉一次中转。KV Cache 换出通常要用 pinned memory 做缓冲，否则性能很差。

还有一条路是 GPUDirect RDMA——如果换出的目标是远端存储或者另一台机器，可以让网卡直接读写显存，不经过 CPU 内存。

- 冷启动加载权重，和稳态 KV 换出，虽然都走 PCIe，但模式有什么不同？"
顺序大块读 vs 随机小页读写
先说冷启动加载权重。 模型权重存在存储上，加载时是从头到尾顺序读一遍，块很大，几百 MB 到 GB 级别连续读。这种模式对 PCIe 极其友好：数据大、连续、可预测，能轻松把 PCIe 带宽跑满，DMA 效率也高。
 冷启动追求峰值吞吐，怎么把大块数据最快搬进显存。
 
再说稳态 KV 换出。 这是完全相反的模式。KV Cache 是按页管理的，换出换入是小页、随机、高频。PCIe 带宽利用率上不去
。稳态换出追求低延迟和调度效率，重点是换出策略

- "网关用 Go 写，高并发长连接下 GC 和 goroutine 调度会带来什么影响？
Go 的调度是协作式的——goroutine 只在特定点（比如 channel 操作、syscall、函数调用栈检查）才会让出。如果一个 goroutine 在做纯 CPU 的密集计算，它会占着 P 不放，其他 goroutine 就得等。
o 网络模型是 netpoller，非阻塞 IO 加 epoll，正常情况下 goroutine 等 IO 时会被挂起，不占线程。但如果调了阻塞式 syscall，就会占住一个 M，M 不够时调度器得新建线程，上下文切换开销就上来了。
Go 的 GC 是并发三色标记加清除,堆大了 GC 就重
堆上面有长连接本身，每个连接的buffer，KVCache的引用，请求上下文等等
堆越大，标记阶段扫描的对象越多，GC 占用 CPU 越多，跟业务抢核。

大对象和频繁分配。 每个请求的临时对象、buffer 反复分配回收，会加剧 GC 压力
Go 里常见的优化是 sync.Pool 复用 buffer、减少逃逸、用 `[]byte `代替 string 拼接。


## Go语言
- <span style="color:rgb(221, 85, 85)">如果让你用 Go 写一个 vLLM 前面的高并发推理网关，你会如何设计 goroutine 模型、连接管理、限流、超时、背压与优雅关闭？</span> 
因为GPU是稀缺资源，要控制每个请求的用量，也不能让某个慢请求将连接和goroutine占死，所以设计的核心是围绕："资源可控"展开

Goroutine模型： 一个请求使用一个Goroutine，这个Goroutine请求不直接调用vLLM，因为请求数可能远远高于一次的并发数，将请求转交给一个有界队列，由固定数量的worker去调用，并发度首先得到了限制

连接管理： 
客户端到网关使用长连接+SSE流式返回，因为生命周期长，是goroutine泄漏的高发区，所以对context，channel，计时器等都要做出限制
网关到vLLM： 连接池复用请求，因为推理请求本身延迟就高，不允许建立连接还是高延迟的
客户端断连需要context 级联 cancel 到上游 vLLM 请求

限流：
接入层限流：按 API key 或租户做令牌桶，目的是保护网关自己，挡住洪峰和滥用。
调度层并发限制：就是 worker 的数量，目的是保护 vLLM。

超时：
排队超时： 队列中等待太久没有被调度
首个token超时： 进入vLLM太久没有输出token，说明vLLM卡了
空闲时长超时： 流式相应中间太久没有新token

背压：
队列必须有界，满了就明确拒绝。
满了之后，接入层的 goroutine 不能傻等，要返回 429 或 503，告诉客户端过载了
绝对不能用无界 channel 或无限起 goroutine 去“缓冲”

优雅关闭
停收新连接，让队列里的请求跑完或超时。
等在途的流式响应把剩下的 token 推完。真正退出。
外加一个足够长的 preStop 缓冲，因为 K8s 摘 Endpoint 和发信号是并行的，中间有时间差

如果vLLM是多实例，还需要用一致性哈希做负载均衡
并且要考虑实例的健康检查，故障节点排除，检查是否有慢实例拖慢请求
