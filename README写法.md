**就业项目 README 的「大项目感」写作指南**

这份指南只讲**写成什么样子**——语气、句式、密度、证据和视觉。不给填空模板。

---

### 一、气质的核心：陈述，不推销

大项目 README 的语气像**说明书**，学生作业的语气像**答辩稿**。区别在于有没有在说服读者。

- 说明书假设读者已经决定要用，只提供事实。
- 答辩稿假设读者要打分数，所以拼命证明价值。

招聘者看 README 的心态接近前者：他不打分，他只判断“这人是不是真的做过”。你越用力证明，越像没做过。

**检验方法**：把 README 里所有形容词删掉，如果剩下的内容还能让人看懂这是什么、怎么跑，那语气就对了。如果删完空了，说明整篇都是推销。

---

### 二、语气三条铁律

**1. 主语必须是具体事物，不能是人或“本项目”。**

> ❌ 本项目采用了 Redis 作为缓存层。 ✅ 缓存层用 Redis，TTL 默认 300s。

产品不会自我介绍。出现“笔者”“我们”“我”“团队”“在学习过程中”，立刻删。

**2. 动机必须是外部问题，不能是内部愿望。**

> ❌ 为了深入学习 K8s 调度机制，开发了…… ✅ Pod 启动耗时中，镜像拉取和数据预热占 70% 以上，且预热只在启动阶段触发，调度器不参与。

第一句摆一个冷事实，第二句指出缺口，第三句才说这个东西。**顺序不能倒**。一旦先说“我做了个 X”，后面所有话都会变成自我辩护。

**3. 结论必须由数字或命令收尾，不能由评价收尾。**

> ❌ 启动速度显著提升，用户体验更好。 ✅ 同批 50 个 Pod，P50 启动时间从 41s 降到 19s（见 `docs/bench.md`）。

“显著”“明显”“更好”这类词没有主语也没有量纲，是大项目和作业最容易被一眼分辨的地方。

---

### 三、证据规则：每句断言都要有落点

写下的每一句**实质性断言**，必须能落到以下四种之一：

|证据类型|形式|例子|
|---|---|---|
|命令|可复制的代码块|`just demo`|
|版本|具体版本号|Go 1.22、K8s 1.28+、Node 20|
|编号|截图编号 / 文档编号|图 2、`docs/3`|
|数值|带量纲的数字|38 KB gzip、LCP 1.4s、12 个配置项|

**没有落点的句子一律删除**，不要改写，直接删。这是控制篇幅最有效的手段，也是去掉 AI 味最快的方法。

有一条例外：**状态声明可以没有证据，但必须有**。写“alpha”“未实现”“pending”，本身就是可信度资产。

---

### 四、信息密度：首屏最密，往下递减

大项目 README 的信息分布是**倒三角**：标题行最密，越往下越松。学生作业通常是正三角——前面三段背景铺垫，最后才出现命令。

具体做法：

- **前 5 行内必须出现可执行的东西**（技术栈、Demo 链接或一条命令）。
- **前 10 行内必须出现一张真实截图**。
- **背景说明不超过 3 句**，且必须全是外部事实，不含你的动机。
- 从第 6 段开始才允许出现“为什么这么设计”这类解释性内容。

招聘者的阅读路径是：扫首屏 → 判断值不值得点 → 拉下来找命令 → 复制粘贴。任何挡在这条路上的段落都在赶人走。

---

### 五、各区块该有的样子（按语气要求讲）

**标题与一句话**：名字要像个产品名（短、可念、不带功能描述），定位句用“接收 X → 输出 Y → 跑在 Z”的结构。不要出现“基于”“一站式”“平台”。

**截图**：图下必须有一句**动作描述**，说明这张图里正在执行什么操作。只写“主界面展示”等于没写。有编号的图才是被认真对待过的图。

**与上游的关系**：这是求职项目独有的区块，语气要像**变更说明**而不是致敬词。三件事：参考了哪部分、改写了哪部分、上游链接与 license。用“设计参考 Fluid”，不用“对标”。

**能做什么**：每条是一个**用户能执行的动作**，不是能力名词。“支持全文搜索”是名词，“在命令面板输入关键词后按回车过滤”是动作。后者才有说服力。

**快速开始**：前置条件写清楚（OS、版本、端口、是否需要 Docker），命令≤4 条，**必须包含预期输出和清理命令**。有清理命令的项目立刻显得成熟，因为作者考虑到了读者的环境会被弄脏。

**技术决策**：只写**取舍**，不写选型清单。“用了 Redis 所以高性能”是废话；“先用 SQLite 后换 Postgres，因为并发写入锁冲突，报错原文是 database is locked”才是有价值的内容。**报错原文是最强的可信度信号**，它证明你真的踩过坑。

**数据**：有真实数字就写方法与结果；没有就整段删，或写“评测 pending”。绝不写模糊结论。

**已知限制 / 不做什么**：这是提档性价比最高的一块。限制要写得**具体到让人能复现**（“单节点，跨节点缓存组未实现”），不要写客套话（“仍有优化空间”）。边界声明（不做什么）比能力声明更难编，因此更可信。

---

### 六、视觉纪律

- 全篇**固定一种主题**（亮或暗），所有截图统一。混用是最明显的业余痕迹。
- **裁掉浏览器 chrome**（地址栏、标签页、开发者工具），固定画板宽度。
- 架构图能用 Mermaid 就用 Mermaid——代码生成的图比画图工具拖出来的专业，而且能随代码一起改。
- 方块少、箭头有方向、每层有名字、图上不出现口号词。
- WebP，单张 <300KB；每张有 alt；正文里至少引用一次。
- GIF 控制在 5–8 秒，超过就放视频链接。

---

### 七、README 之外的工程痕迹（决定 70% 的第一印象）

README 写得再好，周围文件一露馅就全毁。按 ROI 排序：

1. **语义化版本号**，且 README 里引用的镜像 tag 与 CHANGELOG 最新条目一致。不一致是最致命的一种穿帮。
2. **一条命令能起**（`docker compose up` 或 `just demo`）。
3. **CI 绿勾**——但只有真跑测试才放 badge，面试官会点进去。没有就一个字都别提 CI。
4. **`docs/` 分层**：design、dev、screenshots。README 只做索引。
5. **CHANGELOG.md**，哪怕只有三条记录。它证明这个项目被持续维护过。
6. **LICENSE** + `.gitignore` 干净 + git 历史里无密钥。
7. **目录里没有 `test1`、`final_v2`、`.DS_Store`、注释掉的旧代码块**。

第 7 条成本为零，但杀伤力极大。作业的特征就是“写完就不管了”，干净度是维护行为最直接的证据。

---

### 八、红线

- 不放假 badge、假 star、假下载量。
- 不编评测数据。
- 不让文档与代码对不上（文档写 `-p 3000`，代码监听 `8080`）。这一条比前两条加起来更伤人，因为它暗示你自己都没跑过。
- 不放设计稿冒充运行截图。如果是设计稿，就标注“设计稿”。

---

### 九、写完后的三种读法自检

**读法一：形容词剥离测试。** 删掉所有形容词和副词，剩下的东西还能不能成立。不能成立的部分重写或删除。

**读法二：陌生人复现测试。** 新开一个终端，`git clone` 到一个全新目录，只照 README 操作，能不能跑通并看到预期输出。卡住的地方就是你写得最像作业的地方。

**读法三：面试官追问测试。** 对每一句断言问自己“他要是让我现场演示这个，我能不能”。不能演示的，要么补证据，要么删掉。**面试官不会追问你写了的部分，只会追问你没写的部分**——所以“已知限制”里每一条都必须是你准备好被问的。

---

### 十、改稿流程（比从头写重要）

初稿允许写得烂，但改稿必须按这个顺序：

1. 先砍：删背景段、删亮点、删 Roadmap、删所有无落点的句子。
2. 再落地：给每句剩下的断言补命令/版本/编号/数值。
3. 再对齐：版本号、端口、镜像 tag、截图内容与正文描述全部核对一遍。
4. 再视觉：统一截图主题、裁边、压缩、加 alt 和编号。
5. 最后跑一遍复现测试。

顺序不能乱。很多人先调截图再砍内容，最后舍不得删，又塞回去。

---

最后一句：**大项目感不是“写得漂亮”，而是“经得起核查”。** 你能提供的最强信号，是让读者在任何一句上停下来，都能找到一个命令、一个数字、一个编号或一行报错原文去验证。验证点越多，越不像作业；验证点越少，文案再精致也像作业。
