三个问题一起回答：轮询可取吗？需要强一致吗？该换成数据源主动通知吗？

结论先行：**轮询可取；不需要强一致，需要的是一致快照的及时可见；不建议换成纯通知，真要优化就走「Controller 集中轮询 + 扇出」。**

## 背景：这个机制在做什么

TrainCache 的缓存节点（Agent）要跟上数据集的更新。更新走「快照」方式：新数据、新索引都写成**不可变对象**（内容确定后不再改的对象），最后一步把 `CURRENT` 指针从旧快照 S1 原子地切到 S2。`CURRENT` 是个几十字节的文本文件，内容就是 `"<快照id> <指纹前8位>"`。

Agent 侧的跟进动作：每 5 秒（`IndexRefreshInterval` 默认值）GET 一次 `CURRENT`，发现快照 id 变了，才去下载 manifest（快照清单，一份分片引用列表）和需要的索引分片，构建新映射后一次性原子切换。没变就什么都不做。

## Q1：轮询在时效性和源站压力上可取吗？

**可取。轮询的成本被设计对象刻意压小了。**

| 对比项 | CURRENT 轮询 | 数据块回源下载 |
|---|---|---|
| 单次大小 | 几十字节 | 64 MiB |
| 频率 | 每节点每数据集 5s 一次 | 预热/缺读时触发 |
| 稳态行为 | 内容没变就结束（可走条件 GET，返回 304） | 真下载、真落盘 |

- 压力：100 个节点 × 10 个数据集 ÷ 5s ≈ 200 QPS 的小请求。对象存储（MinIO、COS、OSS 这类 S3 服务）本来就是为海量小请求设计的，这点流量远在能力范围内，和数据面流量差了 6 个数量级。
- 时效：要放在系统的时间尺度里比。数据集提交新快照是分钟/小时级的事；一次预热的主要耗时是块下载 + 校验，也是分钟级。5 秒的感知延迟相对这些是噪声，不在关键路径上。
- 顺带一提：真正的轮询之外还有个更费的操作——读者登记心跳（Agent 定期写一个"我在用 S2"的小对象给 GC 看，间隔是刷新的一半）。它比 CURRENT 轮询写得多，但同样是小对象，量级可控。

小结：贵的流量在数据面，不在指针面；5s 延迟相对预热耗时不是瓶颈。

## Q2：这个项目需要缓存和数据源强一致吗？

**不需要。系统承诺的是「快照级原子可见」，不是「随时读到最新写入」。**

先看各层各自的一致性（细节见同目录《一致性模型笔记》）：

| 层面 | 保证 | 靠什么实现 |
|---|---|---|
| 写侧提交点 | 线性化 | `CURRENT` 条件写入：只有它还指向 S1 时才能改成 S2，并发提交不会互相覆盖 |
| 单节点读侧 | 完整快照，无中间态 | 新映射在旁路构建好，再用 `atomic.Pointer` 一次性切换；加载失败就保留旧映射 |
| 跨节点可见性 | 最终一致，≤5s 窗口 | 各 Agent 独立轮询，看到新快照的时间有先后 |
| 块内容 | 自校验 | 内容寻址（按数据自身的哈希指纹命名存放）+ 读回校验，指纹不对就删块重下 |

对训练来说，这个性质比强一致更对路：训练消费的是"某一个提交点的不可变视图"，宁可旧一点，但必须自洽——不能读到一半索引是 S1、一半是 S2。而"任意时刻都能读到数据源刚写入的内容"对一个预热缓存既做不到也没意义：没命中就回源读，慢一点但不错。

小结：正确性锚在原子切换和指纹校验上，时效只影响性能，所以弱一致 + 强自洽就够了。

## Q3：该让数据源主动通知吗？

**不建议用通知替换轮询；要优化就通知 + 轮询并存，轮询兜底。**

反对纯通知的理由：

1. S3 协议没有 watch/推送原语。想做通知就得额外引入消息队列、webhook 之类的通道，等于给"数据源只是一块对象存储"的系统加了一个新的依赖，还要操心它的投递保证。
2. 通知丢了，缓存会**永久**停在旧快照；轮询最多落后一个周期，自带自愈性。这是两种方案的本质差距。
3. 通知省的是延迟，但延迟在 Q1 里已经论证过不是瓶颈；请求压力本来就便宜，省不出什么。
4. 这个场景是"写侧低频、读侧海量"，正是轮询的适用形态；推送适合高频小变更。

如果规模真涨到轮询有压力（万级节点 × 多数据集，逼近对象存储单前缀 QPS 上限，约 3500/s），合理的演化不是让每个 Agent 去听通知，而是：

```text
Controller 每 5s 轮询一次 CURRENT            ← 源站小 GET 从 O(节点数) 降到 O(1)
    └─ 发现变了 → 沿已有的 Agent gRPC 连接下发  ← 走集群内部网络，不碰源站
```

Controller 和 Agent 之间本来就有控制面连接（预热指令就走这条路），加一个"快照变更通知"的 RPC 改动面很小，还能拿到亚秒级感知。现在做属于过度设计。

小结：纯通知是拿投递可靠性换不需要的延迟；分层扇出才是压力真出现时的解法。
