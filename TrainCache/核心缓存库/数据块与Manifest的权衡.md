## 核心结论

**用「manifest 略大」换「数据块更小」是划算的。推荐数据块 4–8MB，分片每片 10 万条，manifest 大小是自然结果（几十万块 → 几 KB）。**


## 一、代价不对称：这是权衡的起点

| 操作 | 大小 | 频率 | 代价 |
|---|---|---|---|
| 改 manifest | 几 KB | 每次提交 | 小、固定、可忽略 |
| 改分片 | 几 MB~10MB | 只传变更片 | 中，靠复用优化 |
| 改数据块 | 由块大小决定 | 只传变更块 | **大，真正的大头** |

manifest 重写是「每次几 KB」，数据块重传是「每块几 MB」。**差 3~4 个数量级。**
所以：**manifest 便宜、数据块贵 → 让数据块小一点，用 manifest 变大来换。**


## 二、两个量的关系

```
条目数（Entry 总数） = 数据集总块数 = 总数据量 / 块大小
分片数 = 条目数 / 每片条目数
manifest 大小 ∝ 1/数据块大小 ∝ 分片数 
```
关键链条：
- **块越大** → 条目越少 → 分片越少 → manifest 越小，但复用粒度粗
- **块越小** → 条目越多 → 分片越多 → manifest 越大，但复用粒度细
manifest 只存**分片引用**（每个约几十字节），不存条目。所以 manifest 随「分片数」增长，而分片数 = 条目数 / 10 万。


## 三、数据块不能无限小：三条下限
#### 约束 1：元数据占比不能显著
数据块元数据 = 块头 128 字节（+ 文件系统开销）。

| 块大小 | 块头占比 |
|---|---|
| 8 MB | 0.0015% |
| 1 MB | 0.013% |
| 64 KB | 0.2% |
| 4 KB | 3.1%（显著） |

**块 ≥ 64KB 就满足「远大于元数据」。**

### 约束 2：条目数不能爆炸

```
块 8MB  → 1TB = 13 万条
块 1MB  → 1TB = 105 万条
块 64KB → 1TB = 1677 万条  ← 索引爆炸
```

### 约束 3：单次读不能发太多请求

训练读一个 1MB 样本，块 64KB → 要读 16 块 → 16 次请求，延迟叠加。

## 四、设计原则

**让「典型提交的改动量」远小于「每片条目数」，这样一次提交只碰少数分片，其余全复用；同时数据块别小到元数据占比显著或条目爆炸。分片大小不跟着块缩小，避免 manifest 暴涨。**
