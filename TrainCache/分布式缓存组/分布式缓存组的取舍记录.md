## 我最初想干什么

Agent 以 DaemonSet 部署在每个训练节点上，每个节点各自从对象存储拉一遍自己那部分数据，训练开始前都要预热一遍，这一段的下载量是按"节点数 × 数据集体积"走的。对象存储放在公有云上，出口按量计费，这笔钱随节点数线性涨。

我想要的是让缓存节点之间互相供给：一份数据在集群里只从对象存储取一次，别的节点从邻居那里拿。

出发点是成本，不是延迟。

## 查下去发现的四件事

### 一、缓存只有磁盘一层，"预热在内存里"是个错觉

预热和持续预取都把块写成磁盘上的文件。下载完成时会读回来校验一遍，这遍读把数据带进了内核页缓存，所以"预热之后第一次读其实已经在内存里"看着成立。

页缓存不算一层缓存：它没有配额，Agent 侧没有"某个块在不在内存"的状态，内存紧张时内核直接回收，回收之后没有任何机制把它填回来。

结论：现状的收益是"数据已经在本地盘上，读的时候不联网"，跟"数据在内存里"是两回事。

### 二、块是散的，谁手里有谁没人知道

每个节点按自己的消费顺序预热，块集合天然不同，缓存还会被淘汰重填。要做节点间供给，得先回答"这个块该问谁"。我一开始的答案是"谁有块谁回答"，查下去发现这个答案本身就是难点。

### 三、块集合的重叠程度由训练形态决定，不是随机数

- 数据并行是主流形态：一份数据集，多个进程各取不同切片，遍历的是同一份数据。集合级重叠是 100%，跟采样怎么随机无关。
- 每个进程一份独立数据集：重叠为 0。
- 同一份数据集被多个任务消费：预热时段错开，先做完的那个节点本地躺着整份数据，后一个直接从它拿。

我的实验环境是 5 个 Pod 用完全不同的数据，重叠为 0。这条观察的价值在于基准环境必须能产生目标收益，否则测出来的是装置不产生交集，不是特性没有价值。

热块也由数据内容决定，与哪个节点无关：两个节点消费同一个数据集，反复被读的那几批块在两边是同一批。

### 四、源站字节的主要来源是"每个节点各自预热一份"，跟请求是否同时无关

这一条决定了后面所有取舍：省源站字节要动的是"有几份副本"这件事。

具体到训练集群：Agent 以 DaemonSet 部署，每个训练节点一份，训练集群有 N 个训练节点就有 N 份缓存。数据并行训练里 M 个 Pod 分布在 M 个节点上，每个 Pod 实际读到多少数据取决于采样方式：按 rank 分片时每个 Pod 只读 1/M，集群整体只需要一份数据；每个 rank 都读全量、只是取不同 batch 时，N 份重复是训练方式固有的。

现在的预热订单由数据集、随机种子、批大小和预取因子算出，不含 rank 与全局进程数的信息。所以按 rank 分片的训练里，每个节点会按全量顺序预热，实际读到的只有其中一份。浪费出现在预热范围和消费范围对不齐这一层，与缓存放在哪一层无关。

## 一致性哈希环：为什么在这里用不了

环解决的是这样一类问题：手上没有数据分布信息时，算出该问哪几个节点。节点增删只影响邻域，这是它相对取模哈希的全部价值。

我提了环，然后把它删掉了。三个原因：

- 环是静态映射，副本分布是动态的。谁预热了谁有，一个节点的缓存会被淘汰重填，环算出来的归属跟实际情况对不上。
- 分布的粒度是数据集级，而环的邻居按块键取，跟数据集无关。顺时针邻居完全可能持有的是另一个数据集的块。
- "谁可能有什么块"这个问题，调度侧本来就有答案：哪个节点消费哪个数据集、每个节点加载了哪些路径，这些信息一直在上报。

改成按数据集分组：候选从已知信息算出来，不做哈希。

这一步的收获不在实现。如果一个特性需要引入"静态映射"去调和"动态分布"，说明这个特性放错了位置。

## JuiceFS 的缓存组：它为什么能做

JuiceFS 的分布式缓存做法：挂载了同一个组名的客户端构成一个缓存组，缓存块按一致性哈希分布在组内成员节点并在组内共享。任一成员读文件时按哈希算出这个块该在哪个节点，向那个节点请求；对方没有就从对象存储下载、缓存下来，再返回给请求方。成员之间的通信只发生在组内。

它还提供"独立缓存集群"形态：常驻节点组成缓存组供给数据，应用侧客户端用只取不贡献的参数加入，避免短命的计算客户端频繁变动把缓存利用率拉低。

它的多级缓存层次是：内核页缓存、进程内存缓存、本地磁盘缓存、分布式缓存组。

## 我的架构差在哪

三点。

**读路径在客户端进程里，可编程。** JuiceFS 的应用通过 FUSE 读，客户端进程决定"这个块去问谁"，peer 请求插在读路径上。TrainCache 的读路径刻意不过 Agent：训练 Pod 用只读挂载直接读文件，Agent 不参与读 I/O。这是当初为了读路径零额外延迟做的取舍，代价是读路径不能被改写。

这一条对 Agent 之间互相供货不构成障碍，训练 Pod 的读路径不需要动，Agent 收下字节落盘即可。真正的障碍是下面两条。

**块的位置一个是确定的，一个是动态的。** JuiceFS 里块在哪由哈希算出来，任何客户端算出同一个结果。TrainCache 里副本位置取决于谁预热了什么。

**组管理缺一个中枢。** JuiceFS 有元数据引擎和挂载参数里的组名、节点列表，组成员发现有现成通路。TrainCache 的元数据在对象存储的快照索引和集群自定义资源里，没有"缓存组成员"这个概念，要新增。

还有一条供给侧的映射成本：TrainCache 的块按内容指纹命名，训练侧按"路径 + 块号"找文件，两边没有共同坐标系。peer 传输时供给方要把"路径 + 块号"翻译成指纹，接收方要把指纹落成训练侧能读到的文件。JuiceFS 缓存的是文件块，客户端天然带着路径语义。

JuiceFS 的"独立缓存集群"形态我这边已经有一半：常驻的缓存节点供给数据，短命的应用侧只取不贡献，这正是 Agent 与训练 Pod 的关系。缺的是组内成员互相取数那一段。

## 候选从哪来：不用摘要的近似值

绕开摘要设计的一个发现：节点手里已经有一份精确的块清单。每个节点加载了哪些路径、这些路径下有哪些块，都在索引里，索引条目带着块指纹。把这些条目汇总起来就是一份精确的持有清单，比近似摘要更准。

这份清单放不进集群自定义资源（那地方单对象上限 1.5 MB，块数上百万时清单是 MB 级），要放对象存储，集群自定义资源里只留指针和规模。这一点与现有的读者登记同一套落法。

于是"谁可能有这个块"从概率问题变成了枚举问题：调度侧知道哪些节点消费这个数据集，各节点的清单给出精确答案。

## 集中式缓存和分布式缓存的取舍

| 维度 | 集中式缓存 | 分布式缓存（节点间互供） |
|---|---|---|
| 同一份数据存几份 | 一份，所有节点共享 | 每节点一份，靠副本重合度复用 |
| 容量 | 一台机器的容量 | 所有节点容量之和 |
| 投入方式 | 集中投资一台大机器 | 用现成节点的闲置盘 |
| 命中率 | 高，与副本重合度无关 | 由训练形态决定 |
| 新增故障面 | 单点 | 节点间网络、节点身份、跨节点失效传播 |
| 容量上限 | 单机上限 | 集群总量 |

判断标准只有一条：集中式缓存装不下这个数据集，或者不愿意把容量集中投资在这上面，否则分布式缓存的复杂度换不回等量收益。

我这边的收益结构是"每节点一份"，集中式同样能把"每节点一份"变成"每集群一份"，代价小得多。

## 内存层：训练侧用不上，它带来的开销却是实的

### 内存和磁盘各自的定位

- 磁盘：容量大、单位成本低、持久、训练 Pod 能直读、能当供给源。
- 内存：延迟最低、给别的节点供货时发送成本近零；容量小，只装得下热块；易失；训练 Pod 读不到。
- 内核页缓存：已经在提供内存效果，由内核管理，不可分配、不可跨节点复用。

### 为什么大家不把训练缓存放在内存里

- 装不下整个数据集。块默认 64 MiB 量级，训练一个 epoch 就把数据集过一遍，内存只够放热块。
- 训练进程本身吃内存，缓存挤占训练。
- Pod 重启、OOM、节点驱逐都会清空，训练重启等于冷启动。
- 内存缓存不能跨进程、跨节点复用，放到集群里收益折半。
- 在 TrainCache 里它连"给训练读"这个位置都没有：训练 Pod 不经过 Agent，读的是磁盘文件。

### 内存层剩下的唯一用途是给别的节点供货

发送方从内存直接吐字节，不读磁盘，这一步确实划算。代价随之而来：

- 独立的容量和淘汰策略
- 同一块在内存和磁盘各有一份，两个淘汰顺序要协调
- 节点重启内存层清空，要重新填
- 节点间要表达"内存里有"，覆盖窄、假阳性多

为一个可能不做的特性先加一层缓存，这笔账不划算。

## 我提出的方案

结论是：在调度侧收敛副本，暂不引入节点间缓存。

**调度侧收敛副本。** 源站字节等于消费同一数据集的节点数乘以数据集体积。让消费同一数据集的 Pod 尽量落在已经持有该数据集副本的节点上，份数就从"节点数"降到"少数几份"。这条路改的是调度侧已有的节点筛选与分配逻辑，不动读路径，不新增网络通路，不加内存层。

代价写在明面上：同一节点上 Pod 密度上升，训练进程和缓存 Agent 抢同一块盘和同一条网卡的带宽；数据集亲和与资源均衡互相冲突，亲和要设权重或设上限。

**把内容寻址的复用用起来。** 块按内容指纹存储，同一份内容挂在不同路径下只存一份。已经消费过同一份数据的节点天然持有这些块，这部分复用不需要新机制，只是别把索引当成"路径到文件"来用，要当成"内容到文件"。

**让预热范围和实际消费范围对齐。** 这一条排在最前面，代价也最小。

Agent 以 DaemonSet 部署，每个节点一份，训练集群有 N 个训练节点就有 N 份缓存。数据并行训练里 M 个 Pod 分布在 M 个节点上，每个 Pod 实际读到的数据取决于采样方式：

- 按 rank 分片时，每个 Pod 只读自己那 1/M，集群整体只需要一份数据，源站字节是 1 份数据集体积。
- 每个 rank 都读全量、只是取不同 batch 时，源站字节是 N 份数据集体积，这份重复是训练方式固有的。

现在的预热订单由数据集、随机种子、批大小和预取因子算出，不含 rank 与全局进程数的信息。所以按 rank 分片的训练里，每个节点会按全量顺序预热，把整份数据集拉了一遍，实际读到的只有其中一份。这一部分浪费来自预热范围和消费范围对不齐，与缓存放在哪一层无关。

把 rank 分片信息接进消费顺序，每个节点只预热自己那一份，源站字节从 N 份降到 1 份。这条要改的是订单生成侧，代价远小于节点间互供。

**peer 供给的触发条件。** 以后要重启这件事，条件写在这里：训练任务每个 rank 都读全量数据（预热范围对齐之后源站字节仍然是主要成本）；同数据集的 Pod 分散在多个缓存节点上，且调度侧收敛之后仍然压不下来；单台集中式缓存装不下这个数据集；节点间网络与节点身份在集群里已有现成通路。四条同时成立才做。

## 价值区间：这套系统只在窄窗口里划算

取一个训练节点的可用缓存空间做分母，节点盘 8~16 TB，扣掉系统和模型占用后按 8~12 TB 算。

| 数据集总量 | 缓存命中率 | 省字节的收益 | 持续预取的状态 | 系统固定开销的占比 |
|---|---|---|---|---|
| 几十 GB，小训练 | 接近满 | 出口费省几十 GB，绝对值很小 | 预热阶段一次拉完，之后无事可做 | Controller、Gate、Agent、sidecar、钩子的固定开销压倒收益 |
| 几百 GB 到几 TB | 高 | 省一份数据集体积 | 既省字节也抗淘汰 | 划算 |
| 几十 TB 以上 | 低，等于盘与数据集之比 | 源站字节接近全量 | 本地装不下，全程在拉被淘汰的块，价值从省字节变成抗 stall | 命中率的收益被摊薄，磁盘写放大高 |

三个判断：

1. **容量不是约束。** 集群总缓存容量远大于数据集总量，"所有节点装得下所有数据"成立。约束是副本份数，源站字节等于份数乘以数据集体积。
2. **收益集中在窄窗口。** 数据集太小，绝对收益抵不过系统固定开销；数据集太大，命中率低，省字节的收益被摊薄。
3. **持续预取的边际价值随"预热阶段已经拉完的比例"下降。** 小数据集里它无事可做；超大数据集里它全程跟淘汰赛跑。

对产品的含义：这套系统应该按需启用。没有大预热需求的任务直连对象存储、用本机页缓存就够，不必进 CRD、Gate、Agent 这一整套流程。

## 结论

这个特性我没做。理由有三条，按重要性排：

- 源站字节里最大的一块来自预热范围和消费范围对不齐，这一条改订单生成就能压下来，不需要节点间互供。
- 收益依赖集群形态，而收益上限可以由训练形态直接推出来，不需要先写代码。同数据集多进程的形态普遍时收益大，每个进程一份独立数据时收益为零。产物要落在面向哪种集群上。
- 成本大头在节点间网络和节点身份，不在数据结构。这两样在当前集群里没有现成通路。
- 有一张更便宜的路：调度侧收敛副本，直接从"每节点一份"降到"每集群几份"，不改读路径。

被否掉的方案：一致性哈希环那一版，为 peer 供货专门加的内存层，以及用近似摘要判断块归属的做法——节点手里已有的索引条目就是精确清单，近似摘要没有存在的必要。

被保留下来的：按数据集分组找候选，用节点已有的索引条目汇总出精确持有清单，用内容寻址做跨路径复用。

## 面试常问的取舍题

**问：真实集群里缓存成本的主要来源是什么？**
答：Agent 每节点一份，训练集群有 N 个训练节点就有 N 份缓存。先看训练任务的采样方式：按 rank 分片时集群整体只需要一份数据，浪费来自预热订单没有 rank 信息、每个节点按全量预热，这一条改订单生成就能压下来；每个 rank 都读全量时重复是训练方式固有的，才轮到节点间复用。

**问：为什么不直接做分布式缓存组？**
答：收益上限由集群形态决定，同数据集多进程时才有收益；成本大头在节点间网络和节点身份。有一条更便宜的路（先让预热范围对齐消费范围，再在调度侧收敛副本）能拿到大部分收益，所以先做那些。

**问：一致性哈希环为什么没上？**
答：环是静态映射，这里副本位置是动态的，分布粒度是数据集级而环按块键取，邻居可能持有另一个数据集的块。候选可以直接从已知信息算出来，不需要哈希。

**问：缓存为什么放磁盘不放内存？**
答：内存装不下数据集，训练一个 epoch 就过一遍；训练进程要抢内存；Pod 重启、OOM、驱逐都会清空；内存不能跨节点复用。而且 TrainCache 的训练 Pod 直读只读挂载目录，不经过 Agent，内存层在训练读路径上没有位置，它只能给别的节点供货。

**问：JuiceFS 有缓存组你没有，差在哪？**
答：三点。它的读路径在客户端进程里可编程，能插 peer 请求；它的块位置由哈希确定性算出；它有元数据引擎和组名做成员发现。我的架构里读路径刻意不过 Agent、副本位置动态、也没有组成员这个概念。

**问：怎么判断哪个节点有某个块？**
答：每个节点加载了哪些路径、这些路径下有哪些块，都在索引条目里，汇总起来就是精确清单，不需要近似摘要。清单体积到 MB 级，放对象存储，集群自定义资源里只留指针和规模。

**问：如果让你做，你怎么做？**
答：先在调度侧收敛副本，收益拿大头且不加复杂度；再按数据集分组找候选，用节点已有的索引信息判断谁可能持有某个块；确认源站字节仍然是瓶颈之后，再补节点间供给，节点间网络和身份单独做。

**问：你的实验能验证这个特性吗？**
答：不能。我的实验环境里 5 个 Pod 用完全不同的数据，块集合重叠为 0，测出来的是装置不产生交集，不是特性没用。要验证得先把装置改成同数据集多进程。
