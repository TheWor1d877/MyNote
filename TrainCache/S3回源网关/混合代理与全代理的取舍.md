# 混合代理与全代理：网关该接几个 S3 方法

## 结论

选全代理。GET、PUT、LIST 三个方法都进网关，PUT 与 LIST 只转发、不进合并窗口。

混合代理（GET 进网关、PUT/LIST 直连源站）在性能上拿不到可测的收益，省下的网关代码换走了 Agent 侧路由、降级判据、指标和排障四处的复杂度。

## 集群内实际打出去的方法

| 方法 | 调用点 | 单个载荷 | 频率 |
|---|---|---|---|
| GET 数据块 | `core/fetch/fetcher.go:223` | 64 MiB（`bench/config.py:80`） | 热路径，训练与预热都在打 |
| GET `CURRENT` / manifest | `agent/svc/server.go:219,232`、`agent/svc/wire.go:289` | 数百字节到数十 KB | 状态查询与归属解析路径 |
| PUT 读者 claim | `core/index/readers.go:160`，装配点 `agent/svc/assemble.go:139` | 百字节级 JSON | 每 dataset 每节点一个对象，随快照跟随刷新重写，默认 5s（`agent/svc/follow.go:106`、`agent/svc/config.go:48`） |
| LIST 枚举 | `agent/svc/wire.go:382`、`agent/rescan/rescan.go:12` | 全桶键列表 | 触发式低频（淘汰前的 Sweep、重扫描） |

三个方法不出现在集群内：`GetETag`、`PutIfMatch`、`Delete` 只被 `core/index/writer.go:122,241,303`（经 trainpublish）和 `core/cmd/traincacheds` 调用，两个都在集群外用 `--endpoint host:NodePort` 直连桶（`bench/compare/traincache/up.sh:158`）。

也没有 HEAD。minio-go v7.3.0 的 `GetObject` 只发一次 `http.MethodGet`（`api-get-object.go:782`），`core/objectstore/s3.go:44` 里那次 `obj.Stat()` 复用同一份响应头取大小（`api-get-object.go:537`），不落成第二次请求。

## 三个维度

| 维度 | 混合代理 | 全代理 |
|---|---|---|
| 性能 | 元数据少一跳 | 元数据多一跳，亚毫秒 |
| 网关实现 | 1 个方法（GET + 重签） | 3 个方法（GET 合并 + PUT/LIST 转发重签） |
| Agent 路由表键 | dataset × 操作类型 | dataset |
| 降级状态 | 每 dataset 两份 | 每 dataset 一份 |
| 指标 `source_mode` | 需按操作面拆标签 | 一个值 |

### 性能：平手

块下载走哪条路两个方案完全相同，差别只在 PUT 与 LIST 落在哪个地址上。算一下量级：claim PUT 每节点每 dataset 每 5s 一次、百字节级，4 个 worker（`bench/k8s/kind-config.yaml:8`）约 160 B/s；同一时刻 100mbit 档的块流量是 12.5 MB/s（`bench/config.py:91`）。这两个数差五个数量级。LIST 也不算什么：L 档数据集 32 GiB ÷ 64 MiB = 512 块，键长六十字节量级，一次全桶枚举的响应约 30 KB，触发点是磁盘水位到线的淘汰和重扫描。

延迟那一跳落在 claim 重写和枚举上，两者都在后台协程里，不在训练 Pod 的读路径（训练 Pod 用 hostPath 只读直读本地盘）。

### 实现难度：混合省网关两个方法，多花 Agent 一个维度

两个方案都要先解决同一件事。Agent 现在一个进程只有一个地址、一个 Store 实例（`agent/svc/assemble.go:107`），fetch 键 `<dataset>/blocks/<path>#<chunk>` 里 dataset 只是字符串前缀（`core/objectstore/blockkey.go:11`），全链路没有按它选后端的动作。落点是同一个：在 objectstore 层加一个实现 `Store` 接口的后端选择器，内部持健康标记与下次探测时间，`core/fetch`、`core/index`、`agent/rescan` 全不动。

选择键的维度不同。全代理是一张表：dataset 到后端。混合代理是两个维度：dataset 和操作类型，四个调用点要分别判定归哪条线，而 `core/fetch` 在 core 里，不能感知 Agent 侧的路由规则，规则得由选择器按方法名分派。

网关侧多出来的两个方法，量都不大。PUT 这边 claim 是普通对象上传，没有条件写，需要的是重算载荷哈希再签一次。LIST 这边要透传 `list-type=2` 的分页参数和 XML 响应体。

### 维护难度：全代理占优

降级判据要写的份数不同。10.0 line 51-53 那一套（连不上、TLS 握手失败、5xx、超时算失效，403 与 429 不算）在混合代理下写两遍：块下载路径判一次，元数据路径判一次，恢复探测也两套退避计时器。全代理只有一套。

故障归因路径不同。全代理下集群内到源站的流量只有一条路径，抓包看一处。混合代理下同一节点同时挂着两个后端，`agent/svc/wire.go:383` 那句「枚举对象存储失败」的告警要先分辨是直连断了还是配置串了。

以后接真云 S3（COS/OSS）时，minio-go 的签名与分片行为差异只需在网关验一次；混合代理要在两条路径上各验一次。

混合代理有一条实质好处：网关挂掉时元数据面（`CURRENT` 跟随、claim 重写、枚举）照常工作，全代理下这些一起进降级窗口。这条被 per-dataset 的一对地址抵消了：块下载和四个元数据调用点一起切直连，代价是探测窗口内那一次失败超时，之后与混合代理等价。

## 全代理带出三条契约

**1. 合并只认块前缀。** key 以 `<dataset>/blocks/` 开头的 GET 才进 singleflight。`CURRENT` 每 5s 换内容，一旦进了合并窗口，迟到者会收到旧快照指针，跟随停摆。现在这两个对象由 `agent/svc/server.go:219` 直连 store 读，不经 Fetcher，本来就在合并域外，网关要按 key 前缀复现这条边界。

**2. PUT 与 LIST 由网关重签。** Agent 发来的 `Authorization` 用不了，SigV4 把 Host 签进了规范请求，客户端签的是网关这个 host；网关要用自己那份 accessKey 与 secretKey 重新签一遍再转源站。载荷哈希的口径待实测：minio-go 对小对象 PUT 是走普通签名还是带 `aws-chunked` 流式签名，决定网关要不要解框，在装置上抓一次包定这条。

**3. 两侧 5xx 要分得开。** 网关自己的失败带一个自有响应头（例如 `x-traincache-gateway: unavailable`），降级判据只认到网关这一跳的失败。源站透传上来的 5xx 不触发降级：直连同样会失败，切过去只是把配置问题盖住。

## 已知限制

- 混合代理的对比基数建立在 v1 单桶单源站和 bench 的 4 节点拓扑上。节点数上去以后，claim PUT 按节点数线性增长，仍然比块流量低四个数量级以上，结论不变。
- 「多一跳」在 Agent 到网关走明文 HTTP 开关（10.0 line 39）下是亚毫秒；开关打到加密那一侧时这一跳含 TLS 握手，claim 重写与枚举都是后台协程，仍然不进训练读路径。
